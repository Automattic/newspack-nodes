# Dashboards Are Node Graphs, Not God Objects

A dashboard's data flow is a **real node graph with message traffic at every edge** — composable, introspectable, reusable — like any worker pipeline. One *view node* that takes a finished model from one server command and hands it to React is not a Nodes dashboard; it is a React app with a dead node stapled on.

**God nodes and god commands are one anti-pattern.** A client node holding the whole model is a god node; one server verb answering `{ sources, top, accumulated }` at once is a god command. Both kill composition, introspection and reuse. Decompose BOTH sides.

## The pattern — compose the data flow

```
Timer ─> Tee ─> Fetcher( receiver=countsIn, command=counts ) ──┐
             └> Fetcher( receiver=topIn,    command=top )    ──┤ (target = _shell/_http/<ci>)
       ┌───────────────────────────────────────────────────────┘
       ▼
       _shell (Tap — watch every send) ─> _http (HttpOut) ──────────┐
                                          │ ▲ responses batch back  │
                                          │ │                       │
                           POST one batch ▼ │                       │
                                ═══ server graph ═══                │
                              (small verbs / nodes, NO god command) │
                                                                    │
       ┌────────────────────────────────────────────────────────────┘
       ▼
       countsIn (Tee) ─> counts-view-node ─> <CountsWidget/>
                      └> the counts Fetcher, LAST, settling its ask
       topIn    (Tee) ─> transform ─> top-view-node ─> <TopTableWidget/>
                      └> the top Fetcher, LAST, settling its ask
```

- **`Timer`** ticks the poll and **hitchhikes** the router tick, so every command emitted on a tick — and every response — **batches into ONE HTTP round-trip**. The **Router** owns that bracket, not the dashboard: `RouterNode.fireCb()` calls `_http.lock()`, notifies every TIMER registrant, and flushes in a `finally`, so the whole tick leaves as one `postBatch`. **Fan-out is free: ten fetchers, one request.** A mount that opened a bracket of its own would cost that tick a second POST.
- **`FetcherNode`**, registered for `makeNode` as `Fetcher`: args = `<receiver> <command> [<command_args>…]`. Apart from a reply, its `fill()` ignores the payload — any other message is only the **trigger** to emit *its configured* command with `FROM` = its receiver. A trigger mints ONE ask and mints nothing more while any ask stands: the ask goes on the Fetcher's `outbox` when sent and leaves when the reply settles it, so a fast refresh on a slow verb asks once and waits rather than stacking identical commands. `retry_after_s` (15 seconds) re-asks an answer that never came; `0` disables that re-ask, which is what a WRITE wants, because an unanswered write may already have applied. An ask standing for 120 seconds is retired whatever its retry setting, so a reply that never arrives cannot leave a spinner turning and a button disabled for the life of the page. A POST that never reached the server comes back as a client-minted TM_ERROR carrying `undelivered`, and the two settings part company there: a read re-arms the ask in place — nothing settles, `isAsking()` stays true, and the next trigger re-sends at once — where a write splices it out and settles with the refusal, because the caller waiting on it needs to see it. A caller with an answer to wait on parks its own ask with `send( args, subject )` — the subject rides on FROM — and reads `isAsking( subject )` to know it still stands. Configure the command on the node, **never read it from the triggering message**: a node that sends whatever command its message carries IS a `Shell`, and a named, always-firing Shell wired into the graph is verboten (see Security Risks). Target **`_shell/_http/<ci>`**, not `_http/<ci>` directly — `_shell` is an observe-only **`Tap`** on the command-send path, so `connect _shell` watches every outgoing command without touching the graph, and skipping it is silent. Compose the path with `egressPath( ci )` rather than by hand.
- **Receiver = a `Tee`** with exactly two targets: the reply routes back `TO` = the fetcher's receiver, and the `Tee` fans it to the slice's transform — or straight to the per-widget view node when the slice declares none — and then back to the Fetcher, which settles the ask. A `Tee` fans out in connect order and that order is contractual, so the Fetcher going LAST leaves the ask standing while the reply renders; otherwise a consumer reading `isAsking()` from the widget sees an ask already settled.
- **Transforms** are small nodes on the receiver→view edge (rank, count, filter, join) — each consumes and emits, so the work sits *on the graph*, inspectable and composable rather than buried in a view. `WorkerStatusTransformNode` is the shipped example, joining a `dump_graph` snapshot on the `workerstatus:in → workerstatus:view` edge. Sitting on that edge means seeing EVERY message the poll produces, a TM_ERROR included, so a transform must re-address a failure to its own `target` and forward it untouched, or the view's error path never fires and the poll fails invisibly. A transform may also hold scalars sticky across polls — this one keeps the segment size, the server clock, the heartbeat interval and the on-disk log-partition count at last-known-good, updating each only when the current reply carries it, so a field one poll omits does not render as zero.
- **View nodes** are thin: each holds one widget's slice and publishes it with `setState( 'view', … )` for a small React component (`useNodeState`).
- **Server side decomposes too** — small verbs or a server-side graph, one Fetcher per slice; never one verb that returns everything. A consumer's CI mounts on the `newspack_nodes/request_graph_ready` action, beside the substrate's own, and `Service_CI_Node::slice_verb()` is the builder for a CI that genuinely splits. A verb whose sections must come from one atomic snapshot (`dump_graph`) legitimately stays one verb and is fanned to one transform on the client.

## Why (what a god object forfeits)

Traffic at every edge is the point: **`connect <node>` or drop a `Tee`** to inspect any stage, the **debug overlay** shows the counters move, and the nodes (`Fetcher`, `Tee`, a transform) are **reused across dashboards** rather than re-implemented per page. A god view-node plus a god command forfeits all of it: one edge carries one payload, so there is nothing to tap between the server and the render.

Go and look before you claim a graph works. `?nodes-debug=1` opens the overlay gate and sticks it in `localStorage`; **Ctrl+`** then toggles the panel, which draws the page's own live `Core.nodes` — every Fetcher, Tee and view at its real counter, climbing on each tick.

## Reusable primitives

Don't hand-wire the spine — the substrate ships it. `mountExospine()` (`src/runtime/exospine.js`) clips your graph onto the backbone where `_command_interpreter` sinks into `_router`, and hands back the five backbone nodes — `interpreter`, `router`, `shell` (`_shell`), `http` (`_http`), `heartbeat` (`_heartbeat`) — plus a `reinit()` and the `teardown()` your effect must call. Everything below sits on top of it.

Three aliases carry the substrate into a dashboard, all three resolved by the one `src/build-kit/alias-map.cjs` that esbuild and jest share. `@newspack-nodes/runtime` is the node-graph barrel: `Core`, `Node`, the `Message` constants, `mountExospine`, the React bridge, the `commandTransport` egress seam, the command-auth functions (`ensureSession`, `markLocal`, `signCommand`), `nodesData()` for the REST base and `wp_rest` nonce PHP localizes onto the page, and the node classes a consumer subclasses or constructs itself — `TeeNode`, `TimerNode`, `HookNode`, `CallbackNode`, `HttpOutNode`, `RemoteLinkNode`, `SseInNode` and `DumperNode` among them. The barrel is a deliberate SUBSET of `src/runtime/`, because a name added there is promised to every consumer pinned to a substrate tag; the five it withholds — `Dmesg`, `Fetcher`, `Metadata`, `Poller` and `Tap` — are reached as `interpreter.makeNode( '<name>', … )` instead. `@newspack-nodes/debug-overlay` is the overlay component a dashboard mounts dormant. `@newspack-nodes/shared/<subpath>` is everything in the tables below; `shared` has no barrel file, so every import names its subpath.

A consumer's own classes join the graph through `CommandInterpreterNode.registerNodeClasses( map )`, which merges them into `includeNodes` and hands the map back — the NAME is what TSL and the console palette spell, and the CLASS is what a programmatic builder gives `makeNode` ([ADR-16](../../../docs/architecture-decisions.md#adr-16-js-node-class-resolution--names-are-the-tsl-surface-classes-are-the-api)).

`includeNodes` starts at eighteen names: `Node`, `CommandInterpreter`, `Completion`, `Dmesg`, `Dumper`, `Echo`, `Fetcher`, `Heartbeat`, `HttpOut`, `Metadata`, `Poller`, `RemoteIpc`, `RemoteLink`, `SseIn`, `Tap`, `Tee`, `Timer` and `Uptime`. Two shared hooks add to it at import time — `useCommandOnce` registers `CommandResult` and `useStreamGraph` registers `CatalogListView` — so a bundle importing either one can spell that name in TSL as well. `RouterNode` is on the barrel and in no roster: `mountExospine` constructs the page's one `_router` on the first mount and carries it across every rebuild.

**A dashboard holds no signing key.** `mountExospine` opens the `newspack-nodes/v1/auth` command session; the Fetcher calls `markLocal()` on the envelope it mints, which signs it there, because the node that MINTS a command signs it and the transport signs nothing ([ADR-15](../../../docs/architecture-decisions.md#adr-15-command-authorization-local-taint--the-minter-signs)). A tick firing before the session exists mints nothing and `useBatchedPoll` re-offers it on the next tick, so neither the key nor that retry is ever the dashboard's to hold.

**The poll spine** — a dashboard that asks on a cadence.

| Primitive | Subpath | What it owns |
|---|---|---|
| `useBatchedPoll` | `hooks/useBatchedPoll` | The exospine mount, the fan-out `Tee`, the router-hitchhike `Timer`, the page-visibility gate, the first-load and unsigned-tick retries. You supply `build( { interpreter, tee } )`, the two node names and the cadence — the slices, and nothing else. `paused` suspends an open surface, `enabled: false` costs a never-opened one nothing at all, and `passenger: true` clips onto a backbone another mount owns. |
| `addSliceFetcher` | `helpers/addSliceFetcher` | ONE slice in one call: a Fetcher aimed at `target`, a receiver `Tee` fanning to the view — through a transform where one is declared — and the edge back to the Fetcher that settles the ask. Call it once per slice inside `build`. Its `argsFn` is a fire-time getter assigned to the Fetcher's `command_args`, so a filter, a sort or a page value reaches the wire without re-wiring the graph; a `null` return sends nothing that tick. |
| `egressPath` | `helpers/egressPath` | `_shell/_http/<ci>`, or a bare `_shell/_http` for a command-interpreter builtin such as `taillog`. |
| `useCatalogSlice` | `hooks/useBatchedPoll` | One CI's `list` verb as a slice, plus `loading`, `error` and `refresh()`. Default cadence 30 seconds — the tick IS the retry, so a refusal recovers with no latch and no memoised promise. |
| `useCommandOnce` | `hooks/useCommandOnce` | One verb sent once per `run( args )`, parked in the Fetcher's outbox and riding the same batch. `onDone` registers on the result node, so it runs once per reply rather than once per render, and `subjectOf` names what each send is ABOUT so the answer comes back carrying it. `retry: true` marks an idempotent READ, which re-asks a request that went missing and supersedes the one before it; a WRITE takes the default, because an unanswered write may already have applied and two deletions in one second are two commands that both have to go. `isPending( subject )` reads the Fetcher's outbox, so a table shows which row still waits. The hook's three nodes are named `<scope>:fetch`, `<scope>:in` and `<scope>:result`, and `scope` defaults to `<ci>:<command>`: two hooks on one page sending the same verb SHARE one Fetcher and one result node, crossing their outboxes and their replies with no error at all, unless each passes its own. The console's three readers of `topologies get` pass `editor`, `canonical` and `seed` for exactly that reason. A retried read arms its Timer at the 1000 ms tick and sets `retry_after_s` to 5; a write arms at 60 seconds and rides the `pollNow()` that `run()` calls, having no cadence of its own to keep. |
| `useRouterTick` | `hooks/useRouterTick` | "Call me on the router heartbeat" for any React poller, as a passenger on a backbone somebody else owns. `intervalMs` defaults to 0, which fires on every Router tick; a sub-second value takes a `setInterval` slot of its own but stays a graph node `list_timers` can see. |

`useBatchedPoll` returns `{ interpreterRef, pollNow }`. `pollNow()` marks this poll due and runs the Router's tick, which is how a filter change refreshes off-cadence; rebuilding a lock/flush bracket around hand-sent copies of the same verbs re-implements that one line.

`intervalMs` is **required and at least 1000 ms**; a lower value throws a `TypeError` naming the timer. That floor is `TimerNode`'s own hitchhike threshold — a sub-second timer takes its own `setInterval` slot outside the Router's bracket, which is one POST per slice per tick and no batch at all. Exactly 1000 rides every tick; above it the Timer throttles against the shared wall-clock grid ([ADR-17](../../../docs/architecture-decisions.md#adr-17-timers-fire-on-a-shared-wall-clock-grid)), so two surfaces on one cadence meet on the same tick and share the POST.

A control that WRITES and then reads its own answer back off the poll has a tick to bridge. Both of the console's — the Profiler's start/stop and the Inspector's trace toggle — flip local state at the click, let each reply reconcile it, and surrender to the server's answer after ONE disagreeing reply, so a refused write corrects itself on the next poll rather than latching on the optimistic guess. Neither shares the other's code, so copy that one-stale-reply tolerance rather than inventing a second rule for it.

A readout that needs no React hook at all takes a **`Poller`** instead: it rides the tick, mints its configured verb, and publishes the reply on `reply` for `useNodeState`. A subclass overrides `publish()` to say what the reply MEANS and publishes under its own key — `Uptime` trims the elapsed run, `Dmesg` tallies a stderr tail by level. One class serves every verb, because `verb`, `pollArgs`, `pollIntervalMs` and `target` are all set by the mounting view. Its default cadence is 10 seconds, deliberately slow, because a poll reply carries a whole row list rather than a delta. The barrel withholds `Poller` and `Dmesg` alike, so build each through the interpreter — `interpreter.makeNode( 'Poller', nodeName )` — rather than by import.

`Dmesg` reads the reply's TYPE before tallying: an object payload keeps `PollerNode`'s verbatim `reply` publication, so a view that retargets the node's verb at a structured one such as `list_timers` still gets its rows, while the `dmesg` state key silently stops updating. All three of the console's process-stats pollers — `_metadata`, `_uptime` and `_dmesg` — aim at `_cwd`, a bare `Node` whose `target` is whatever scope the operator has `cd`'d into; addressing it re-stamps TO for free, and that is the whole mechanism flipping those cards from the browser's own interpreter to a worker's and back with no rewiring.

What `_metadata` publishes reaches a canvas through `useGraphSource` (`src/topology-console/hooks/useGraphSource.js`), the ONE graph source both the debug overlay and the topology console read, so an in-process graph and a worker's go through one precedence rule. A published graph carrying at least one node always wins; a published graph of zero nodes means "nothing has answered yet" rather than "the graph is empty", so a poll that comes back with nothing cannot blank the graph already on screen. Under it sits `coreToGraph()` (`src/topology-console/utils/coreToGraph.js`), which composes `dumpMetadataPayload()` with `parseMetadata()` to read the browser's own live registry with no command and no round trip, giving a local read the same fields, defaults and hidden backbone a remote reply carries. `coreFallback` defaults true and belongs on only where the consumer's Core IS the whole graph being shown, as the overlay's is: the console passes `false`, because its canvas is scoped to a worker and a local read would paint the browser's own exospine scaffolding — `_shell`, `_http` and `_heartbeat` — beside every node the console page itself mounted, none of which a worker graph holds. Those three and the worker's `_repl` are what the returned `hasNodes` discounts, because scaffolding alone is not content: laid out by itself it fixes the layout, and every real node arriving on the next poll then stacks below it in one column instead of joining a full layout pass.

**The stream spine** — a dashboard that follows a log over SSE.

| Primitive | Subpath | What it owns |
|---|---|---|
| `useStreamGraph` | `hooks/useStreamGraph` | The three nodes every SSE dashboard is made of — `<prefix>:link` (`RemoteLink`), `<prefix>:stream` (a `Tee` whose one target is the view, and where a `connect` taps the live stream), `<prefix>:view` (`viewClass`, trusting controls from its own name) — plus when the stream is open and where it reopens. Pause takes the same close path as the visibility gate, so pausing frees the bounded server slot. Every control that re-points the stream goes through `resubscribe( subs, positions )`, which RECORDS the intended target and touches the live link only while active, so a pick made while paused cannot revive a closed `EventSource`; Play and refocus re-apply what was recorded. `seek()` is that plus the matching view control, `control()` mints a `controlMsg` into the view, and `setFilter()` and `clear()` are named controls. An explicit seek is SINGLE-USE — delivering it reverts the recorded target to `positions: null` — so a later pause and play resume from wherever the tail actually reached instead of jumping back to the replay start. |
| `LogStreamViewNode` | `nodes/log-stream-view-node` | The base of every log-stream view: the O(1) newest-first ring (default cap 100 000 rows), the paused belt and step budget, the decaying `lps` readout, seek tracking, and the `pause` / `step` / `connection` / `browse` / `follow` / `clear` / `filter` / `select` controls. Subclasses implement `shapeRow( message )` and extend `_control()` / `viewModel()`. |
| `useLogCatalog` | `hooks/useStreamGraph` | The catalog a subscription is chosen from, polled as a `passenger` slice every 10 seconds. Its `keep` filter is a memo dependency, so declare it with `useCallback`: a fresh arrow each render hands the caller a fresh array each render. |
| `useSteppedRead` | `hooks/useStreamGraph` | The paused single step: one record over the command channel, admitted through the view's paused belt. |
| `useSegmentBrowse`, `useLogPositions`, `useLogStatusSegments` | `hooks/useLogPositions` | The browse rail and the SSE `positions` seed each control selects. A seek needs no transport of its own. |
| `SeekTracker`, `browseControl` | `nodes/seekTracker` | The segment breadcrumbs and the replay-caught-up-to-live flip, both derived from each record's `segment:offset:length` ID. `LogStreamViewNode` owns one; a subclass never re-derives them. |
| `RateSmoother` | `rateSmoother` | The windowed average plus EMA behind `LogStreamViewNode`'s `lps` readout and the debug overlay's four Overview cards, so an idle rate decays to zero instead of freezing at its last burst. It is not universal: the topology console's per-node message and byte rates divide their own delta by elapsed time instead. |
| `LogStreamViewer`, `LogRowList`, `LogBrowser`, `LogListHeader` | `components/…` | The chrome, the ring-aware DOM virtualization, the segment rail and the column header. |
| `useDeepLinkedSelection` | `hooks/useDeepLinkedSelection` | The `?param=` contract for a picker: seed the selection from the URL once, on the first non-empty catalog, then reflect every pick back. |

Four optional knobs finish a `useStreamGraph` declaration. `endpoint` overrides the SSE route, which is how the Log Viewer opens `/log/stream` rather than `/messages/stream`; `maxEntries` sets the view's ring cap; `openAt` seeds the first open's position, and null tails; `clearOnOpen` empties the view before every open, for a model whose rows go stale across a connection gap. A dashboard whose subscription is CHOSEN rather than declared passes no `subscribe` at all — the link is built bare and opens nothing until a catalog names one through `resubscribe`.

That choice is the fork a new stream dashboard starts from, and the substrate's own stream dashboards reach `useStreamGraph` through one of two wrappers under `src/event-dashboards/hooks/` rather than calling it directly. A DECLARED subscription — a fixed log dir known at author time, as the topic-probe and jobstats tails and the Config Audit timeline are — goes through `useLogTailStream`, which adds the `mode` contract: `history` opens at `SEEK_START` so the server replays the whole retention and the tab shows real history instead of a thin client-side ring, `follow` tail-seeks to current, and any other value throws rather than quietly dropping the replay the view is drawn from. A CATALOG-PICKED one — the Partition Viewer and the Log Viewer, where the reader names the log at runtime — goes through `useLogReaderGraph`, which folds `useStreamGraph`, `useSteppedRead` and `useLogCatalog` into a single call and leaves its two callers differing only in the catalog verb and in who owns the default pick.

**View nodes** — where a reply becomes a render model.

- **`sliceView( { empty, parse, json, description } )`** (`nodes/slice-view-node`) is the default: a view whose whole content is an empty-model literal and a guard-then-map parse is a DECLARATION, not a class. `registerSliceViews( views )` declares a bundle's views, registers the names, and returns the classes — hand `addSliceFetcher` the CLASS when a hub tab builds through another bundle's interpreter, because `includeNodes` is a per-bundle static ([ADR-16](../../../docs/architecture-decisions.md#adr-16-js-node-class-resolution--names-are-the-tsl-surface-classes-are-the-api)).
- **`SliceViewNode`** is the base to subclass only when a view owns more than its slice — its own `fill()`, a timer, a teardown. Neither failure mode blanks the MODEL: a TM_ERROR keeps the slice already on the node and adds `error`, clearing `loading`, and an unparseable payload leaves the prior slice untouched. What the widget then draws is the widget's own call, and every shipped one renders the error notice INSTEAD of its data, because a stale number beside a failure reads as current.
- **`CommandResultNode`** (`nodes/command-result-node`) is its deliberate opposite, and where a one-shot's reply lands: EVERY reply publishes on `result`, refusals included, because a caller is waiting on the answer.
- **`CatalogListViewNode`** (`nodes/catalog-list-view-node`) is a `sliceView()` declaration holding a picker's rows under `items`, and `useLogCatalog` is its only builder.
- **`controlMsg` / `isControl`** (`helpers/controlMsg`) are the one control minter and its recognizer. A control is recognised by WHO SENT IT — the view's `controlFrom`, which `addSliceFetcher` assigns for a slice that declares one — never by what its payload looks like. Most slices declare none, because their view class owns no control path; stamping every view plants an inert field on most of them, and the wrong name on any view whose controls come from its transform. A view declaring no `controlFrom` takes no controls, and `controlMsg()` throws rather than stamp an origin nothing trusts.
- **`HookNode` (a predicate gate) and `CallbackNode` (an inline closure)** ship on `@newspack-nodes/runtime`, but each takes its closure as a REQUIRED constructor argument and neither appears in `includeNodes`. `makeNode` instantiates with a bare `new NodeClass()`, so no TSL line, no palette entry and no `addSliceFetcher` `transform` slot can build one — import the class and construct it yourself. `HookNode` also breaks the forwarding contract its siblings keep: an unwired sink DROPS the message where `Tee`, `Tap` and the base `Node` throw, which is what lets a gate be spliced in ahead of the sink it will forward to, and what makes a gate whose sink is never wired discard everything in silence.

**The React bridge** (`@newspack-nodes/runtime`) is how a component reads what a node publishes. Every hook addresses a node by NAME and re-resolves it, because the graph is rebuilt underneath the React tree.

- **`useNodeState( name, event )`** returns the LATEST cached payload. A burst of notifications inside one React batch costs one re-render, so this is the rendering half; a widget reads its own slice here and owns its own empty state.
- **`useNodeEvent( name, event, onNotify )`** runs once per NOTIFY. Anything that ACTS on each publication — rather than rendering the last one — registers here, or two replies in one batch collapse into one.
- **`useNodeFill( name )`** returns a stable callback that fills a message into the named node, resolving the name at call time so it survives a rebuild and drops the message while nothing holds it. The console sends a typed REPL line into `_command_interpreter` through it. A `controlMsg()` goes to the view instance instead, which is what `useStreamGraph`'s `control()` does.
- **`useGraphGeneration()`** re-renders on Core's full-rebuild signal, and re-runs a graph-building effect when it sits in that effect's deps.

| `storage`, `queryParams`, `fnv1a`, `parseOffsetJump` | `utils/…` | `localStorage` without a try/catch per call site, `?param=` reads and writes that preserve every other param, the hash, and the offset-jump parser — which takes a pasted `segment:offset:length` message ID or a bare offset against a caller-supplied segment, and refuses the bare form outright when there is no segment to resolve it against rather than seeking segment 0. |

Appearance is declared once too, in the SCSS partials under `src/shared/styles/`. The `src/ui/newspack-nodes-ui.scss` entry compiles seven of them — controls, buttons, focus, components, toolbar, modal and distinctive-roles — under the `.newspack-nodes-ui` scope, and `_tokens`, `_focus-mixins`, `_button-roles` and `_field-scope` are what those seven are built from. `_mixins` is the one a dashboard's own stylesheet forwards for itself, and `src/shared/styles/__tests__/styleOwnership.test.js` holds a surface to the set. A JS module must never `import` a `.scss` through the `@newspack-nodes/shared/*` alias — a shared component imports its own styles by RELATIVE path (`./Modal.scss`). Jest's shared-subpath mapper precedes its style mock and first match wins, so an aliased style import resolves to the real file and babel parses SCSS as JS. SCSS `@use`ing SCSS through the alias is fine; sass resolves that, not jest.

**Testing the graph.** The seam is the WIRE, not the client, so a hook's test drives the real thing. `installFakeCommandWire( replyFor )` (`test-utils/fakeCommandWire`) doubles the `/command` server: pack and unpack, `HttpOut`, the Router and the interpreter all run, replies come back `TO = FROM`, and `/auth` is stubbed so the graph signs for real. `makeFakeCommandWire` builds the same double and leaves the session alone, for a test packing its own signed messages. Either one records every POST body under `batches`, so a suite asserts WHAT was posted without replacing the transport, and a suite that does replace it answers through `commandReply( sent, payload )` — a reply built any other way misses `TO = FROM` and the test reads as silence rather than as a failure. `runClockFast()` (`test-utils/fastClock`) runs `Core.now()` sixty times wall speed from `beforeEach`, so a test watching a 30-second catalog recover reaches that boundary inside the first Router tick instead of sitting through half a minute. It moves only what is decided against `Core.now()` — `TimerNode`'s grid gate and the Fetcher's `retry_after_s` window; `SseInNode`'s reconnect watchdog and the command signer's expiry read the wall clock and stay at real speed, so a test fast-forwarding either one waits out the whole interval. A suite exercising the PRE-auth hold calls `forgetSession()` itself and points `__setAuthFetch` at a stub answering null, because `readyToMint()` re-runs `ensureSession()` and would otherwise re-mint off the installed stub a microtask later; `{ requireSignature: false }` then lets the double answer the unsigned commands that path posts.

**Where it mounts.** A substrate dashboard ships as a DevTools tab: `registerDevtoolsTab( descriptor )` (`devtools/tabRegistry`), rendered by `DevtoolsTabHost` on the hub page, the debug overlay, or both. The descriptor requires `id`, `label` and `component`, and a `host` of `overlay`, `hub` or `both`; `order` (ties broken alphabetically by label), `slug` (the `?tab=` deep link, defaulting to the id), `param` (a query param the tab owns, which the host clears while another tab is active), `gate` (a predicate excluding the tab), `icon` and `fullBleed` are optional. Registering an id again SHADOWS whatever held it, which is what lets a lazy tab register a placeholder carrying the same descriptor object — label, slug and order resolve before the bundle loads, and the arriving bundle swaps in the live component rather than adding a second tab beside it.

Tabs are React components, so the registry is JS and a bundle registers at import time. PHP only says which bundles to enqueue, through the `newspack_nodes/devtools_tab_bundles` filter, which the substrate's own five bundles and any contributed one go through alike. A contribution is `{ handle, dir, url[, localize][, lazy] }`; a plain bundle is enqueued so its tabs register as the hub shell boots, and a `lazy` one is not enqueued at all — its load recipe rides the hub handle and the shell fetches it when its tab is first activated. A malformed entry is dropped whole rather than coerced, so one contribution cannot break the others. `Admin::lazy_tab_script()` also returns null for a bundle with no built `index.js`, so that handle never enters the lazy map and `loadTabBundle()` returns silently instead of fetching a 404 — the tab's placeholder then reads "Loading…" for as long as anyone waits. That reads as a hung request and is a missing build; check the build output, not the network tab. The registry itself hangs off one window key, because every tab-bearing bundle inlines its own copy of the module and a module-local map would give the host page one empty registry per bundle.

A CONSUMER plugin's dashboard belongs on its own top-level menu, not in the substrate's. Contribute a `host: 'hub'` tab only when the surface genuinely is a Nodes-internal tool; [`writing-a-dashboard.md`](../../../docs/writing-a-dashboard.md) draws that line.

Consumer dashboards live in their own `src/` trees. The substrate's own are `src/event-dashboards/`, `src/topology-console/`, `src/event-aggregator/`, `src/vault/`, `src/sessions/`, `src/devtools-hub/` and `src/debug-overlay/`; the shared spine stays in `newspack-nodes/src/shared/`, and there is never a per-plugin `src/shared/`. The debug overlay is the one surface reaching into another's tree: it takes `THEMES`, `getStoredTheme` and the palette and inspector collapse keys from `src/topology-console/themes.js`, because it mounts the same `ConsoleShell` and must persist its skin and its chrome under the console's own keys rather than a parallel set.

## Red flags — STOP, you're building a god object

- A view node that receives the whole model and `setState`s it. Split it into a Fetcher, a receiver Tee, transforms on the edge, and one view per widget.
- A server command that returns `{everythingTheDashboardNeeds}`. Split it into small verbs, one Fetcher per slice.
- A dashboard node whose console counter never moves: nothing flows through it, so it is dead, not composed.
- "I'll just mount one view node and fire one `poll` command" — that IS the god pattern, the convenience that produced every god-object dashboard.
- Nothing on the canvas you could drop a `Tee` into, or that the overlay would show moving: there is no graph.
- **An op-id, a Promise registry, or `KEY` used to match a reply to its request.** The reply is ALREADY addressed: a node mints its command with `FROM = <its own name>` and the server replies `TO = FROM`, so it lands on that node and `fill()` handles it. An id minted into `message[ID]`, a `{ resolve, reject }` map keyed by it, or a Promise-returning `send()` all re-implement routing that already happened. A subject the answer must name rides on FROM as `<receiver>/<subject>` and comes back as the reply's remaining TO.
- **"I batch N verbs in one tick, so I need to tell the replies apart."** No — you have ONE node doing N jobs. Make it N nodes, one per concern — one `addSliceFetcher` call per slice, or the two `Poller` nodes `RuntimeView` mounts for `list_timers` and `list_handles`. Batching is orthogonal: the Router's lock/flush puts the whole tick in one POST however many nodes minted into it. Demux is a problem you invented.

`scripts/lint-contract.mjs`, part of `npm run lint:js`, refuses those last two mechanically: five of its eight rules catch a reply filed under its own argument, a parked `{ resolve, reject }`, a registry of pending resolvers, an id minted into `message[ID]`, and `KEY` used as a discriminator. The other three guard the two ADRs this skill leans on — a grid boundary computed outside `TimerNode`, and a bundle-registered class named as a string in a `makeNode` call or a `viewClass` option where the class belongs. Every one of the eight describes code that WORKS, which is why a correctness review passes it and a linter has to catch it.

## Security Risks

A node that sends whatever command its incoming message carries is a `Shell` (Shells *send* commands; interpreters interpret them), and a named shell is dangerous: a maliciously routed message could execute arbitrary commands. Configure the command on the node (the `Fetcher` pattern) and treat the message as a trigger only. Route through `_shell` (a `Tap`) so every send is watchable.

## Required background

`nodes-review` gate #8d holds the rule this skill rests on: everything sinks into the interpreter, and flow is steered by `target` and TO, never by a bespoke `sink` chain. The Tachikoma batching principle is the other half — the tick hitchhike means more fetchers cost the same one POST.
