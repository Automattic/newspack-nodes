The status line is decided at the first byte, so read the body too

One POST carries a JSONL batch. Each stage either turns the whole request away, writes a packed Message into the body, or writes nothing. The status rides out with the first write and is spent from then on, which is why a refusal latch is raised ahead of the verifier and lowered only on success, and why a capability refusal cannot change a 200.

The status. The first reply to reach _output's fill() sends it and opens the body; if nothing was written, dispatch() sends it alone. Then the controller exit()s so the REST server cannot append its own JSON envelope.

What the browser transport mints on its own

postBatch() unpacks the body whatever the status, because a 401 batch still carries every real reply, and returns those verbatim.

Only a body that unpacks to nothing is a bare WordPress REST error object (rest_forbidden, rest_no_route, the 429). There the transport mints one TM_COMMAND|TM_ERROR per command it posted, addressed back to that command's own FROM, with payload Command refused (HTTP <status> <code>) and undelivered: true beside it. That flag separates a batch that never arrived, where asking again is the recovery, from a verb that really refused; CommandResultNode passes it to a view node unchanged.

A transport failure is neither: fetch rejecting rejects the promise.

Three refusals a status code cannot tell apart

A 200 or 202 can carry a capability refusal (stage 5) or hide a struct drop (stage 5); a 401 from the door (stage 1) is a WordPress error object where the verification 401 (stage 7) is JSONL. Read the reply payload as well as the status, and treat an empty-bodied 202 for a command that expected an answer as a possible drop: the only evidence is the audit line in stderr and dmesg.

The substrate, event-logger-nodes and intelligence suites all assert the literal permission denied string, which makes it a de facto contract.
