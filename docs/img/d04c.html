Two ways a slot goes deliberately empty

On Atomic hosting a CPU is a PHP worker slot, and a worker holding one is a worker a visitor cannot have. An on-demand topology gives its slot back while its log is quiet. A deploy hold empties every slot at once.

When an on-demand worker leaves

Every consumer in its graph has to sit at the end of its log for the whole idle window. Then the worker exits without respawning, and it holds no lock.

Neither the peer scan nor the cron pass treats that absence as due. A stale lock still spawns, because a stale lock is a crash rather than an exit.

Three things wake it

1
A producer writes to a partition it tails.
2
An operator attaches a console.
3
The minute cron pass measures backlog on disk. It is the only tier that notices a process appending to a partition file from outside the substrate.

Deploying new code

A
New code already on disk: wp nodes restart writes the restart flag, each holder exits and self-respawns, and the old class dies with the process.
B
New files to swap in: take the fleet down first. A live worker's autoloader fails mid-swap, and a restarted successor boots into the same half-swapped directory.
wp nodes stop && wp plugin install release/<plugin>.zip --force && wp nodes start

The stop verb flags every lock directory and blocks until every lock is gone, ninety seconds by default. It exits non-zero and names the stragglers when that wait expires.
