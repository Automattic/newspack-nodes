What each verb does when root runs it

Workers run as the web user and own every lock, IPC and segment file. Root is refused by two verbs, warned by one, and skipped past by the rest, so a root run reports success while writing nothing. The exception is ingest, which writes as root and leaves the damage for later.

Is the effective uid 0?CLI::uid() answers; each verb asks for itself, cli and run at entry, the rest before each write

Refuse outright

clirun
Error: wp nodes cli must run as the same user as the workers, not root.

Both would seed {base}/ipc/ and locks/ root-owned, and the workers could never append to their own IPC again. Recovery after a run that got through: chown -R <webuser> of the base dir, which doctor's ownership row names.

Warn, then wait anyway

stop
Warning: could not write the stop flag for: job-worker.p0, …

Every stop flag is refused, so no worker exits. The command spins its whole timeout (90 s by default) and then exits non-zero, listing those same workers as stragglers. It is the one write-shaped verb that says so.

Skip the write, report success

restartmemcache flusha settings save
WARNING: running as root; skipping restart flag - a root-owned file would be unwritable by the workers
Success: Requested restart for 0 worker(s).

The restart flags, the fleet restart memcache flush runs after rotating the salt, and the reload watermark a settings save writes are all passed over. The warning is rate-limited on its shared prefix: the first refusal in the process prints, every later one is silent. Exit status is 0.

Work as usual

statustypesdoctor

Read-only verbs need no write, so denial costs them nothing. That is why denial is non-fatal by design.

ingest neither refuses nor skips

It writes through Topic_Node, which materializes partition directories and {seg}.log segments under logs_dir on first use. A root replay leaves root-owned dirs and segments the workers can no longer append to, rotate or prune. Nothing says so at the time; the damage surfaces later as doctor's ownership row.

Reading a quiet result

A 0 worker(s) restart on a fleet that is plainly live is a root run, not an empty fleet. A multisite subsite prints the same line for a different reason: the fleet is network-global and runs on the main site alone, so a subsite's restart flags nobody and still exits 0.
