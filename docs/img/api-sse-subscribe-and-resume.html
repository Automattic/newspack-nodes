What a subscription names, where it starts, and how a client resumes

A name resolves either to a worker's IPC output or to a glob over partition directories. Each reader is stamped, and the stamp keys three things: the starting cursor in the connected handshake, the FROM on every delivered record, and the positions a client sends back. positions is the ONLY resume input: no Last-Event-ID, no SSE id: field.

Resolving one name from subscribe (a CSV; blank entries dropped)

1. Split the groupA name is [<group>/]<rest>. No slash means logs. The group must be offsets or deadletter (Log_Discovery::GROUPS minus the default); an explicit logs/ prefix is refused, as is anything outside the list. That is what keeps a caller-supplied prefix from reaching a path.
2. Check the restIt must match /^[a-z0-9_-][a-z0-9_.*-]*$/D and contain no .., which leaves * as the only wildcard and confines a glob to one level under a browsable root. Anything else throws InvalidArgumentException.
3a. Worker IPCA bare exact name, no group and no *, whose worker holds a live channel at {base}/ipc/{name}/output, tails that channel tail-seeked: the attached console. It never reports idle, and one writer means it never takes the multi-writer grace.
3b. Partition dirsEverything else globs {base}/{group}/{rest} for directories and opens one Consumer per match: itself for an exact name, every partition dir for firehose.*. The stamp is the dir basename for a logs subscription and {group}/{basename} for a grouped one. A valid pattern matching nothing opens nothing. With multi_writer set, each log Consumer takes the seal grace (SEAL_GRACE_SECONDS = 2), because a peer can keep appending to segment N for up to DRIFT_RESCAN_INTERVAL_SECONDS (1) after N+1 appears; the client asserts it, since nothing on disk records which logs are shared, and a single-writer log would only pay the latency.
The connected envelope: a TM_INFO frame from _stream, VALUE a flat KEY VALUE string, never JSON
PID <pid>a browser stamps it into the FROM of attached commands, _sse:{pid}/{node}, so the server's filter demuxes async replies to this tab; must be a positive canonical decimal SLOT <slot>may be 0 OWNER <owner>an opaque positive decimal fencing token; clients keep it as TEXT, never a precision-limited number. Out of the CONNECTED state payload and every stderr line SUBSCRIPTIONS <csv>as requested INTERVAL <ms>the heartbeat cadence, 2000 CURSORS <csv>omitted when empty; else stamp=segment:offset pairs, the STARTING point of each live subscription. A stamp holding a space or comma is skipped rather than desync the pairing

SSE_In_Node validates rather than tolerates: a non-string VALUE, an odd token count, or a missing or non-canonical SLOT, OWNER or PID retires the lease, sets ERROR carrying connected envelope missing or invalid <FIELD>, and returns 0 from the write callback so the stream returns only after the backoff. Unknown extra pairs are ignored, so ADDING a field is safe; renaming one of those three, or spelling OWNER as anything but a positive decimal, kills every machine pull. The matching keepalive is workers heartbeat [ slot, owner ], and the server owns the lease TTL.

Advancing: every msg carries its own breadcrumb

ID "{segment}:{offset}:{length}" → next read boundary is offset + length within segment

FROM is stamped with the subscription's stamp, so the client knows which cursor to move. It starts from the CURSORS in the handshake, advances out of each delivered record, and sends the result back as positions on the next connect, so it is never handed a cursor it did not compute. CURSORS exists because an idle close makes zero-message streams the normal case: a reopen with no position tail-seeks and drops whatever arrived in the gap. SSE_In_Node, pulling over cURL, keeps its cursor the same way.

Omitting positions tail-seeks every subscription, which is what a browser dashboard does on a first connect.

positions: a JSON object keyed by stamp

A value is an exact {segment, offset} object, or one of Tachikoma's three seek sentinels, mirrored as Consumer_Node::SEEK_*, with the words accepted as aliases:

0 · startbyte 0 of the first segment
-1 · endthe newest segment's current size: a live tail
-2 · recentbyte 0 of the SECOND-newest segment, or of the only one, so it can replay up to a whole segment

Stating the seek as a number is what lets {segment: 0, offset: 0} mean the START of the log rather than an absent value: SSE_In_Node always sends a position, -1 when it has none, so a source resuming a 0:0 checkpoint replays its backlog instead of being tail-seeked past it.

Malformed JSON, or a value decoding to anything but an array, is treated as omitted. A per-key value goes the other way: position_arg() keeps a number as a number and a word as a string, and seek_sentinel() resolves any word it does not recognise to SEEK_START, so ONE typo'd position word replays that subscription's whole log rather than tail-seeking it.
