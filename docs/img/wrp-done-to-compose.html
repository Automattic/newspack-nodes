DONE rides behind the items, and the third one composes the draft

One Collect is a RESET and a TICK per source. Each source's DONE follows its items through both durable logs, gathering a consumer's name onto FROM at each hop, and the digest composes once it has counted three distinct senders.

Collect

The dashboard's button, or four lines typed into wp nodes cli. Nothing schedules it.

Sources

github, linear, feed: each TICK is a fetch, a dedup, an emit per item, then DONE.

ingest log + consumer

ingest:partition on disk; ingest:consumer tails it in line mode.

Enrich + scored log

summarizer, scorer, then scored:partition; scored:consumer tails it.

Digest

Digest_Builder, snapshotted into the scored consumer's offsetlog.

1Empties items, seen and reported, then appends one throwaway TM_INFO 'RESET' to scored:partition, the node its first make_node argument names; TO is set explicitly, since the target is the draft sink, and an empty argument disables the nudge. That advances scored:consumer, so its next checkpoint co-commits the emptied snapshot; without it the offsetlog would keep the stale item list and a restart would reload it.
2Each source appends its new items to ingest:partition and a DONE after them, FROM = github. An unconfigured source appends DONE alone: linear returns [] before it builds a request, github fetches without an Authorization header, feed never wanted a credential.
3set_line_mode true: the drain forwards at most one record per event cycle and skips its buffer top-up on any cycle that forwarded one, so a slow LLM call holds up the next item rather than a whole 64 KB block. The consumer prepends its name: ingest:consumer/github.
4Summarizer_Node::fill() and Scorer_Node::fill() each branch on TM_INFO before their TM_STRUCT work and forward it untouched, so DONE stays behind the items it followed. A transform that dropped what it did not recognize would strand the compose. Every scored item lands in scored:partition.
5The second consumer prepends its name too. What the digest reads is scored:consumer/ingest:consumer/github: still one distinct key per source, but not a name you can compare against.
6A TM_STRUCT is accumulated, deduped on id. A "DONE\n" sets reported[ FROM ] = true; when count( reported ) >= total, with total the literal 3 on the make_node Digest_Builder digest scored:partition 3 line, compose_draft() writes the draft through digest:tee to digest:log. Counting distinct FROM paths rather than raw signals keeps the tally idempotent across re-ticks and replays, so a stale DONE cannot overshoot.

Driving it by hand

> request_node digest RESET > request_node github TICK > request_node linear TICK > request_node feed TICK # the third DONE composes and writes digest:log

Collecting on a cadence would take a Timer_Node subclass whose fire() mints the same four requests.

Nothing computes the 3

The .tsl literal has to match the sources the topology TICKs, which Insights_CI_Node keeps in one private SOURCE_NODES list, github, linear, feed, that its Collect verb both counts and iterates. Add a fourth connector and both the list and the literal move.

Two more verbs, and an empty cycle

REGENERATE recomposes a draft from the items already collected, with no re-fetch; it is the only manual compose. A source that fetches nothing still reports DONE, so a cycle where every source comes back empty composes an empty draft rather than hanging: the finally in the base guarantees it.
