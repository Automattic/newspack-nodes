A Table fronts a durable record, and the walk that finds it stays in the app

A miss falls through a closure the application installed, which asks Partition for the newest record per key and hands back an entry with the life it has LEFT. Partition owns the index walk, its memo and the syscalls; the app owns only what a line means.

Caller

A dashboard request: lookup( $key ) or lookup_multi( $keys ).

Table_Node

The keyed store over the shared cache tier, one TTL fixed at construction.

The backing closure

Installed by backed_by( \Closure ). The application's: it knows the line format.

Partition_Node

Treats index lines and keys as opaque strings. Owns the walk.

1A hit is served from the cache. A miss, an expiry and a backend read error all take the same branch: through the backing when one is installed, and back as null when none is. A miss is never remembered as a miss.
2lookup_multi() asks once for all of its misses. The closure receives the key list and returns key => { value, ttl? }.
3The app passes its line parser and the keys to resolve, and gets key → position for those keys only. The key set bounds the table, the walk and the memo: a whole-index table grows with the PARTITION, and at ~300 bytes a locator an order-1M-key partition exhausts a 512 MB request to answer a handful of rows. The result's order follows $wanted, so read it by key, never by position.
4Inside Partition. One newest-first pass over the .idx sidecars: the first line a key appears on is its last write, within a segment and across them. A segment whose .idx is missing or unreadable is skipped and the extent is built from the .log id and size, so a transient read failure (EMFILE, a rotation in flight, a permissions blip) is recorded as absence, and the memo keeps it recorded until the log grows.
5Inside Partition. The memo, a class-level static keyed by the resolved partition DIRECTORY, records what was found AND what was searched for, so an absent key stays answered instead of costing a walk per batch. It is discarded the moment an append changes the segment extent or searched passes MAX_LOCATOR_MEMO_KEYS (100,000). It caches "this index did not answer for this key", never "this record does not exist".
6Reads the located positions one file handle per SEGMENT and returns the lines; the app decodes each into a value and the remaining ttl.
7A spent remainder (ttl <= 0) is SERVED and not warmed: a stated ttl bounds the cache and decays from the write, which says nothing about how long the record is still read. Entries with life left are warmed grouped by lifetime, one round trip per TTL, best-effort: a dead backend must not turn a read into a miss.
8The caller cannot tell a backed miss from "absent everywhere"; one that needs the distinction asks the record directly.

The one way to get a WRONG answer out of locate_by()

The memo assumes one index format per directory, which with_index already implies. Two readers of the same directory passing different $extract parsers share whichever walked first, and the second reader's keys land in searched as answered-and-absent, so each of its lookups comes back a silent miss.

Rejected

Leaving it in the application: two consumers in one plugin need it (Rule_Set::hooks_for() over an option, the stats mirror over a Partition), and each copy would carry its own key translation, TTL decay and scope guard. Pushing the line format down so Partition parses index entries: every consumer's fixed-width layout would land in the substrate. Letting the backing write through store(): it applies the table's TTL, which is exactly what a restore must not do.

Why the remaining-TTL rule and the newest-record rule are one rule

The lifetime is read off whichever record the key lands on, so resolving to an older write makes a live entry read as expired and vanish silently rather than loudly. A PartitionTest case pins it. Revisit if a consumer needs a miss to stay a miss, or a backing so slow that the fill belongs on a queue rather than in lookup().
