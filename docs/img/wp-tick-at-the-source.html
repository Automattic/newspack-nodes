One TICK moves the source's counter by two: the items, not the answer

A request arrives at fill(), which hands it to answer_request(). That reads the verb and runs the handler the schema declares for it. Each item leaves through parent::fill(); the reply leaves through the sink, already addressed and never counted.

1

The request arrives

TYPETM_REQUEST FROM_output/_cli:<pid>/_output, the breadcrumb the REPL stamped TOreleases, peeled by the router on delivery VALUE"TICK", the tail of the typed line joined with spaces

fill() calls answer_request() and nothing else. It takes VALUE's first word, upper-cased, and runs the handler of the requests entry of that name: tick(). request_node releases typo runs nothing and is refused with a TM_ERROR, unknown request verb: TYPO.

2

One message per item, minted fresh counter +1 each

TYPETM_STRUCT FROMreleases, this node's own name TOempty at the mint, then summarizer: Node::fill() stamps the target when TO is empty ID, KEYempty, and TIMESTAMP is the cached clock VALUE[ 'source' => 'releases' ] + $item

tick() never sees the request: answer_request() holds it and addresses the reply. Two items leave as two forwards, nothing acknowledges either, and tick() returns [ 'emitted' => 2 ].

3

One reply, addressed with the request's own FROM counter +0

TYPETM_STRUCT | TM_RESPONSE FROMreleases TO$message[FROM], set by answer_request() ID, KEYcopied off the request VALUE[ 'verb' => 'TICK', 'data' => [ 'emitted' => 2 ] ]

It leaves through require_sink()->fill(), which stamps no TO and counts nothing. The router walks it back to _output, whose Dumper prints it; with nothing wired the two items reach _router with an empty TO and are dropped with one message not addressed warning on stderr.

2

What the console card, ls -c and stats read after one TICK: Node::fill() increments the protected base counter on every forward, and only the items take that path.

A reply is addressed, never stamped

A request minted with no FROM gets a reply with an empty TO. Through the sink the router drops it with a warning; through parent::fill() it would have had summarizer stamped onto it and flowed downstream as though a source had emitted it. That is why answer_request() sends through the sink.

Never $this->fill() to send

That re-enters this node's own fill() and recurses. parent::fill() is the emit; Tail_Node::forward_line() is the same pattern in the substrate.

A second verb is a second entry

Declare another requests entry with its own handler. answer_request() does the parsing, and refuses an unknown verb on the error plane, a TM_ERROR to the same address, as the interpreter refuses an unknown command. Job_Worker_Node's GET_HEALTH is the same shape in the substrate.

Table_Node::handle_request() is the deliberate exception, a bare shape: one message per value and a TM_INFO count, no TM_RESPONSE bit and no { verb, data } envelope. Its verbs are case-sensitive, and an unknown one is refused with a TM_ERROR.

Narrow TYPE before the bitwise test

$message[ Message::TYPE ] is typed mixed. answer_request() reads it through Core::as_int(), and the shipped digest narrows it, is_numeric( … ) ? (int) … : 0, so a non-numeric TYPE matches no flag; Core::num_int() is that test behind a name. The shipped transforms take a /** @var int */ annotation instead, which satisfies PHPStan and does nothing at runtime: a TYPE arriving as a non-numeric string raises TypeError: Unsupported operand types: string & int there. Narrow wherever a message can reach you off the wire.
