One TICK moves the source's counter by three, not two

A request arrives at fill(). Each item leaves through parent::fill(), and so does the reply, so the count you watch climb in the console is the items plus the answer. Nothing on this path reads the verb.

1

The request arrives

TYPETM_REQUEST FROM_output/<pid>, the breadcrumb the REPL stamped TOreleases, peeled by the router on delivery VALUE"TICK", the tail of the typed line joined with spaces

fill() tests TYPE & TM_REQUEST and nothing else. request_node releases TICK, request_node releases typo and a bare request_node releases all emit the same batch: with one entry under requests, the flag is the whole dispatch.

2

One message per item, minted fresh counter +1 each

TYPETM_STRUCT FROMreleases, this node's own name TOempty at the mint, then summarizer: Node::fill() stamps the target when TO is empty ID, KEYempty, and TIMESTAMP is the cached clock VALUE[ 'source' => 'releases' ] + $item

Built in $response, never by reassigning $message, because step 3 still reads the untouched request. Two items leave as two forwards, and nothing acknowledges either.

3

One reply, addressed with the request's own FROM counter +1

TYPETM_STRUCT | TM_RESPONSE FROMreleases TO$message[FROM], so TO is already set and Node::fill() stamps nothing ID, KEYcopied off the request VALUE[ 'emitted' => 2 ]

The router walks it back to _output, whose Dumper prints { "emitted": 2 }. The reply is the only thing the REPL shows; with nothing wired the two items reach _router with an empty TO and are dropped with one message not addressed warning on stderr.

3

What the console card, ls -c and stats read after one TICK: Node::fill() increments the protected base counter on every forward, items and reply alike.

A request minted with no FROM delivers its reply as an item

An empty FROM leaves the reply's TO empty, parent::fill() stamps summarizer onto it, and { emitted } flows downstream as though a source had emitted it. Job_Worker_Node and Table_Node send replies through $this->require_sink()->fill( $reply ), which stamps no TO and counts nothing. The walkthrough keeps parent::fill() for symmetry with the emit; a source of your own should take the require_sink() form.

Never $this->fill() to send

That re-enters this node's own fill() and recurses. parent::fill() is the emit; Tail_Node::forward_line() is the same pattern in the substrate.

A second verb means parsing VALUE

The requests array documents verbs for the Inspector and help; it dispatches nothing. Job_Worker_Node::handle_request() is the shape to copy: uppercase the first token of VALUE, test it, and answer an unknown verb with an error payload rather than a throw, because no interpreter sits on this path to turn a throw into a TM_ERROR reply.

Table_Node::handle_request() and its GET <key> is the other exemplar, deliberately different: case-sensitive, a reply with no TM_RESPONSE bit and no { verb, data } envelope, and an unknown verb dropped with no reply at all.

Narrow TYPE before the bitwise test

$message[ Message::TYPE ] is typed mixed. The shipped sources and the digest narrow it, is_numeric( … ) ? (int) … : 0, so a non-numeric TYPE matches no flag; Core::num_int() is that test behind a name, and the substrate's own nodes call it rather than repeat the ternary. The shipped transforms take a /** @var int */ annotation instead, which satisfies PHPStan and does nothing at runtime: a TYPE arriving as a non-numeric string raises TypeError: Unsupported operand types: string & int there. Narrow wherever a message can reach you off the wire.
