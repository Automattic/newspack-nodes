From fill() to the segment

Three nodes stand between a producer and the bytes on disk. The Topic chooses the partition, the Partition batches and flushes, and no writer ever takes a lock on the segment it appends to.

1fill(message)

Any node fills it, in any process. A page request builds a Partition or a Topic as readily as a worker does, because the constructor touches nothing on disk. The file handle opens on the first fill().

The producer never learns how many partitions there are.

2Pick one partition

TO already names p{N}: that partition. A replay keeps its pin.
KEY set: crc32(key) & 0x7FFFFFFF, modulo N. One function for every producer, so one key always lands in one partition.
No KEY: round-robin.

3Pack and batch

The seven fields become one line, a record, appended to the batch. The Topic batches nothing; the record follows the chosen Partition's flush rules.

A record over the cap is dropped with a rate-limited warning and never truncated, because half a record desyncs every reader after it.

Fit the line at the producer

Line_Fitter trims named fields until the line fits under the cap. The cap stays; the record shrinks.

The hash is the concurrency control

One partition has one reader. Every message with one KEY lands in one partition, so one process reads that key's messages serially, in append order, and no per-key lock ever needs to exist.

4Flush before 4096 bytes

The batch is written whole before its next record would carry it past PIPE_BUF, 4096 bytes on our hosts. POSIX lands an append of that size intact, so many processes append to one segment and none takes a lock.

Two opt-ins lift the cap to 32 MiB

Both claim exclusivity. A lock in the partition directory enforces one writer. void_warranty() takes no lock and trusts the caller: safe for a log inside one process, silent corruption anywhere else.

One host's local filesystem only

The PIPE_BUF promise is the kernel's, for its own filesystem. A network mount voids it, and the lockless append with it.
