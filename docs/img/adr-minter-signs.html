The minter signs, the ingress only verifies, and which key signs is the destination

In-process, a command carries a taint no wire can forge. Across a boundary it carries an HMAC envelope inside VALUE. Both are checked by one authorize closure at every Command_Interpreter_Node, and a refusal replies unauthorized: <verb>.

The canonical signing string: JSON.stringify([ ts, name, arguments, nonce ]), semantics only

[
tsTIMESTAMP, aligned to the verifier's clock by the now in the auth reply
namethe verb
argumentsthe flat token list, verbatim
nonce16 random bytes, claimed once
]
TYPEenvelope; left out so a mint can sign at build time before flags are OR'd in
TO, FROMRouter peels TO and nodes stamp FROM in transit; a signature over them breaks in flight

PHP encodes with JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE to match JSON.stringify byte for byte; tests/fixtures/signatures.json pins that parity from both languages. Tachikoma's Command.pm::sign covers id:timestamp:name:arguments:payload for the same reason. HMAC-SHA256 at every tier; no asymmetric signing anywhere.

Client tier: Message::LOCAL, index 7

Two sites stamp it: a Shell_Node on the command it mints from a console line, and cmd_reply_to() on the sub-command it re-addresses — safe because the outer reply_to already cleared the same gate, and a nested reply_to is refused outright, since FROM is set raw there and the recursion would be unbounded. The default policy is isset( $message[ Message::LOCAL ] ).

Both ports slice packed() / pack() to LAST_VALUE_INDEX + 1, and PHP's unpacked() rejects any line that is not exactly seven fields, so LOCAL cannot cross a boundary. That is what makes its presence mean something, and why nothing else may be appended on that basis.

Server tier: Command_Auth::verifier()

Installed by verifier processes: a worker reading IPC, the /command request-scope CI, a dashboard's event stream. Accepts LOCAL, or a valid envelope at VALUE['auth'], which rides inside VALUE and so survives IPC.

age at most MAX_PAST_S 20 s old, MAX_FUTURE_S 10 s ahead sig matches the HMAC recomputed under the resolved key nonce claimed by an atomic add() at NONCE_TTL_S 60, via local_first(): unique to the verifying process, so APCu is the faster answer handle rides outside the signed string; Command_Auth::check() installs the session's scope as Capabilities::$session_scope, the ceiling for this one command, which verify() slams to NONE on refusal and interpret() restores

Most refusals name themselves through the handling interpreter's drop_message: wrong type, bad envelope, stale or skewed timestamp, unencodable arguments (logged as invalid signature), signature mismatch; an unknown or expired handle and a replayed nonce log nothing; a missing cache backend logs through print_less_often(), an environment fault rather than a verdict. HTTP_In latches any refusal, so a batch with one answers 401.

Key 1: the per-site secret, no handle

Command_Auth::sign() under hash_hmac( 'sha256', 'nodes-command-v1', wp_salt('nonce') ). The attached cli's Shell, same host, over a filesystem-gated IPC partition. Carries no ceiling: it is the site's own authority. The secret survives only where the signer is already inside the trust boundary.

Key 2: a session key, established first

POST /newspack-nodes/v1/auth returns { handle, key, scope, expires_in, now }: a random 16-byte handle and 32-byte key, stored under a site-namespaced address with add() never set(), so a colliding handle fails instead of displacing a live session; the response is the only place the key is ever disclosed. TTL SESSION_TTL_S 3600 by default; a request may ask for its own, clamped to 60..86400, and it is never slid on use. Stored through shared_first(), because a session minted in a web request must resolve in a worker. The route sits behind fleet_gate() and READ: issue() clamps the scope to the highest role the minting user holds.

sign_for( $destination ) IS the destination binding

A signature under one remote's session verifies only there, which pins a command to its destination without signing TO. No session means no signature: the minter waits rather than emit something refused. Waiting alone deadlocks, because every minter refuses to queue unsigned and nothing else asks for the handshake, so the skip branch kicks it: resolve the target's head through Core::node(), type-test for HTTP_Out_Node, call ensure_session(). Settings_Sync_Node::send_set() is the worked example; on the JS side Node.command() returns null when readyToMint() finds no session, and the caller re-arms for a later tick.

Sign at the ingress

Makes the boundary an ORACLE: anything reaching it acquires authority however it got there, so a wire-arrived frame routed into the egress would go back out signed.

LOCAL alone, everywhere

Cannot cross a process boundary, which is what makes it trustworthy in-process and useless for a worker that legitimately reads commands off IPC.

One shared site secret for every client

Anything shipped to wp-admin is readable by whoever sits there. A session key is a capability scoped to one session with a bounded life.

Asymmetric signing (Ed25519)

Rejected even for hub → spoke authority through sign_for(): both ends of a session are one trust domain, since the site that minted the key verifies it. Public-key signing buys non-repudiation and third-party verification; no consumer needs either, and it costs a key-distribution problem.

crypto.subtle in the browser

Returns promises; awaiting one makes the Shell's dispatch async and moves every graph mutation a microtask later. Synchronous @noble/hashes instead.

Filesystem permissions alone for IPC

They gate the directory, not the message. Still the first gate; the signature is what makes a command believable however it reached the partition.
