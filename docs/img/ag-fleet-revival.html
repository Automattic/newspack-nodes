There is no supervisor: three tiers revive the fleet, and every spawn crosses one gate

A worker respawns itself; every live worker's _fleet scan catches a peer whose lock is missing or stale; WP-Cron catches a fleet with nothing left running. Supervision survives the loss of any single process, and only total fleet death falls through to cron cadence.

Tier 2 · the peer scan, _fleet

every 15 s (SCAN_INTERVAL_MS): Fleet_Node, a Timer_Node hitchhiking the Router in every worker
1
Reload watermark in THIS worker's lock dir? Topology_Registry::invalidate_config_cache() — the options cache, Config::reset(), the on-demand memo, the probe cadence — then notify RELOAD. Gated on the watermark because Config::reset() drops the parsed-TSL caches: run every pass, it would re-glob both topology directories and re-parse every .tsl to reach the value already held.
2
Re-read the active fleet from Bootstrap::expand_workers(); defer a newly-appeared type by NEW_TYPE_SPAWN_DELAY_SCANS 1 so a still-exiting predecessor can flush; a cold start skips the deferral. Drain every worker if the last topology was deactivated.
3
For each worker, at most MAX_SPAWNS_PER_TICK 4 per pass: due when worker_needs_spawn() — a stale heartbeat, or a missing lock dir on a topology that is not on-demand — and not deferred, and not spawned in the last 15 s (recorded in memory only here).
4
Spawn_Coordinator::spawn_each() reads the active set for a write conflict (two fleets on one partition) and suppresses the whole pass on one; then one fire-and-forget POST per due worker. FIRE is notified before every guard, so it ticks even when the scan does nothing.

The gate every path crosses: POST /newspack-nodes/v1/workers/spawn
Authhash_hmac( 'sha256', "newspack_nodes_{$purpose}:{$window}", $salt ) with $window = floor( now / Internal_Request_Token::WINDOW_S ), 10 s; the current AND previous window are accepted. The purpose spawn is inside the hash, so a health-cache token never validates here. Or: a MANAGE user, a WP nonce, and RATE_LIMIT_S 2 per user. A bad token answers 403.
400 · partitionvalidate_partition() first: a type or partition outside the active fleet is refused before anything else is read.
409 · deploy holdSpawn_Coordinator::hold() is the non-autoloaded newspack_nodes_hold option, not a file: a reinstall may wipe the base directory, and a hold that evaporates mid-deploy is worse than none. wp nodes stop sets it FIRST, flags every worker and polls up to STOP_TIMEOUT_S 90; wp nodes start clears it and spawns.
429 · throttleMIN_SPAWN_INTERVAL_S 15 per {type}|{partition}, persisted through Cache_Backend::shared_first() (transient fallback) at twice the interval. Checked and recorded HERE, which is what makes N scanners as safe as one and stops a thundering herd when locks flap.
Then the worker runsinline in this request for its whole life: ignore_user_abort( true ), set_time_limit( 0 ), Worker_Base::execute().

What wp nodes status reads off a slot

livestaledownidleheldinactive

A held lock reads live or stale from its heartbeat age against the type's stale_timeout (60 s default; job-worker declares 600). No lock reads held under a deploy hold, idle when the topology declares an on_demand_idle window, down otherwise. A catalog topology outside the active set reads inactive. A stale or down slot is due for a spawn, and so is a held one on a topology that is not on-demand: no spawner checks the hold, so the endpoint refuses it with 409.

On-demand: scale to zero, wake at the write boundary

var on_demand_idle = <seconds> rides the stale_timeout path into each worker descriptor. A cleanly MISSING lock dir then spawns nothing, Alerts::evaluate() raises nothing, and status renders idle; a STALE dir still spawns, because a stale lock is a crash. Every producer's Partition_Node::fill() marks its directory and the Router-tick flush wakes whoever tails it, through Bootstrap::on_demand_wake_map(), cached in APCu for 60 s. A partition nothing tails is absent from the map.

Faster is not better

A faster scan would only reach a MISSING lock dir sooner; the stale case is dominated by stale_timeout either way, and a crashed worker's queue is durable, so the lag costs nothing. The scan is revival and nothing else: housekeeping lives in the cron pass so it runs with the fleet down. On multisite only the main site runs the fleet.
