The spoke's stream, pulled: six states and a 45-second watchdog

SSE_In_Node owns one cURL easy handle, one {segment, offset} cursor and one connection's parser state; its patron drives maybe_connect() and check_stale(), and every data: payload reaches that patron raw through the on_message seam. The browser mirror opens the same endpoint with numbers of its own.

One connection's states, PHP side

Every received event resets the backoff to the floor and refreshes liveness, so a talking stream never ages into check_stale(); a stale close doubles the backoff like any failure. A refused open, a non-HTTPS url under require_ssl or a failed curl_init(), goes to DISCONNECTED without ever holding a handle. A clean 200 close on a stream that advertised a reopen delay, the retry event or a plain server's retry: field, holds that delay from THIS moment, clamped into the same 1 … 30 s range, and sets scheduled_reconnect_at; it leaves the failure state untouched: no error, no doubling, nothing a dashboard reads as a dead link.

connection(): the patron's whole status contract

connected is the LEASE, true only past the handshake and never merely because the socket opened; connecting is that open-but-unhandshaked window, neither up nor a failure; scheduled_reconnect_at is the explicit "closed on purpose, back at T" reading, because a null last_error also means "never attempted". Remote_Source_Node republishes these into the remote:<node>:<partition> memcache snapshot, so a dashboard counting connected / total under-reports a healthy fleet and files a mid-handshake stream as down.

Five states through setState, read back with register() / useNodeState on the link's :sse-in child: CONNECTING on open, CONNECTED once the handshake parses, DISCONNECTED on a close by either side, RECONNECTING while backing off or waiting out the server's advertised retry, ERROR for a malformed handshake or frame and for a msg carrying TM_ERROR.

It exports SEEK_START (0) and SEEK_END (-1) only; the wire accepts -2 but no browser caller asks for it, so a feature wanting recent adds the constant and threads it through seekMap(). There, a position actually reached outranks the seed: a subscription that read one record resumes past it whatever started it, one that read nothing keeps its seed, a named one holding neither tails from SEEK_END, and a GLOB is the one seek a client cannot state, since the server keys positions by the dirs it expands to.
