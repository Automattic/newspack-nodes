The life of a session key

A session is a random handle and a random key, minted server-side because caller entropy is unverifiable. The key is disclosed once, in the mint response, and the cache holds it recoverable so verification can recompute an HMAC from it. That is the argument for a short lifetime.

1. Mint

POST /newspack-nodes/v1/auth, or the sessions create verb.

The response carries handle, secret, the clamped scope, expires_in and now, the server clock the client aligns its signed TIMESTAMP to.

2. Sign, then verify

The minter signs [ TIMESTAMP, name, arguments, nonce ] under the key and sends the handle beside the signature, outside the signed string.

The verifier resolves the key from the cache by that handle and recomputes the hash. Repointing an envelope at another handle only stops the signature matching.

3. Revoke

The cache entry goes first, the directory entry second, so the key stops verifying at once rather than after the listing catches up.

A revoked handle fails the next command it signs.

4. Expire

The lifetime never slides on use, so a leaked handle expires on schedule no matter how busy it is.

The cache drops the key at that moment, and the session stops verifying with it.

Lifetime, requested as ttl and clamped to this range

60 sFloor. A shorter request clamps up to it.
3600 sThe default when the caller names no ttl.
86400 sCeiling. A longer request clamps down to it.

Where a session lives, in two places

A WordPress option holds the directory of issued sessions: the label, the scope, the minting user and the expiry. A label is sanitized and cut to 64 characters, because a listing is a listing and not storage.

The cache holds the key, and so decides whether a handle still resolves. Mint throws when it cannot store the key, rather than handing back a session nothing can verify.

The session records its minting user, so a credential presented outside a browser acts as that user under the scope as its ceiling.

The same verbs, over JSON-RPC to an agent
POST /newspack-event-logger-nodes/v1/mcp
Each tool names a service interpreter, a verb and the role that verb declares.
The bearer credential is handle.secret. It names a live session, and the request runs as that session's minting user under its scope.
The server filters the tool list to that scope, so an agent is offered only what it can run.
Named arguments become the verb's token list, and replies come back JSON-encoded inside a <site-data> fence.
One handle gets 20 calls per 10 seconds.
