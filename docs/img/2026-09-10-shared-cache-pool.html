One memcached pool, many sites, and the one ingredient a neighbour cannot compute

On WP Cloud every site on a pool writes into one keyspace. A scope string in each key is what keeps them apart.

How this site builds its scope

substr( md5( DB_NAME : base_prefix : salt ), 0, 12 )

DB_NAME — a neighbour on the pool can work it out
base_prefix — likewise, and usually wp_
salt — random, minted once per install, stored in an option. The only secret in the recipe.

Every key then reads newspack_nodes:v3:<scope>:<name>.

Question 2a

Is a random per-install salt the right protection, or should the scope derive from the site secret, as command sessions already do through wp_salt('nonce')? Two costs stand against copying that: folding the site secret into the scope risks splitting the keyspace on an install that predates it, and the salt is read straight from the database because the lightest boot path has no option API.
