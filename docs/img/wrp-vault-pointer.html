The topology carries a pointer; the secret never leaves the server

An operator enters a token once, in the Vault tab. The .tsl names the entry's id, the node opens it at config() time, and the dashboard that manages the store never sees the password. Nothing goes on a Settings page.

1

The operator adds an entry Vault tab, Vault_CI_Node

idgithub, 1 to 64 of [a-zA-Z0-9_-] urlhttps://api.github.com, the API root the token belongs to: HTTPS is required even for an entry that exists only to carry a token auth_usernamethrough sanitize_text_field(), then capped at 256 bytes auth_passwordthe token, control characters stripped, capped at 256 bytes, sealed as $enc$… under a key derived from wp_salt( 'auth' )

The cap is silent: add() and update() still return true and seal the truncated value, and the only symptom of a longer token is a 401 from the far side. MAX_SERVERS is 100. Rotating AUTH_KEY or AUTH_SALT leaves every stored password unopenable.

2

It lands in one option newspack_nodes_vault, not autoloaded

The one source: the Vault tab and the vault CI verbs write it, the config file declares no entry, nothing pins one. A stored value without the $enc$ prefix was planted by database write and reads as no password.

3

The topology names the id newspack-intelligence-ingest.tsl

make_node Github_Source github cmd github:config set_vault_id github cmd github:config add_repo Automattic/newspack-plugin

The verb stashes the id on the node, last write wins, and dump_config() writes it back out, so the console can serialize a live graph to a .tsl that re-applies it. Its schema arg is typed vault_id, which the console renders as a dropdown of existing entries, or a text input while there are none.

4

The node opens it at fetch time config(), the Vault_Secret trait

'token' => $this->resolve_vault_secret( $this->vault_id ) // '' when the id is blank, unknown, or the Vault class is not loaded Vault::get_instance()->get( $vault_id )['auth_password']
5

It rides one header, or none

GitHub: Authorization: Bearer <token>, added only when the token is non-empty, beside the User-Agent GitHub requires. Linear: the raw token, verbatim, never Bearer. Feed: no credential at all.

What a reader ever gets back

The list and get verbs return Vault_CI_Node::public_shape() alone: { id, url, auth_username, has_credentials }. The password is computed away into that flag. The username does leave, because it is half an address rather than a secret and the Edit form cannot offer to change what it cannot show. That holds only while every Vault verb gates at manage; declaring one read would put the username in front of a role that cannot otherwise open the store.

The soft failure is what makes an unconfigured source harmless

An empty token throws nowhere. Linear_Source_Node::fetch() returns [] before it builds a request, so its TICK is a silent no-op; Github_Source_Node::request_args() omits the header and fetches unauthenticated. Activation is safe before an operator has visited the Vault.

One read per process, and two ways to drop it

get_all() memoizes the decrypted registry for the life of the process, so a resident worker reads the option once. Config::RESET_ACTION, the config-reload signal Vault::reset() is wired to at boot, is how a rotated credential reaches a worker that would otherwise serve the old one until it recycles. Vault::fresh() is the same singleton with its memo dropped, for a request-scope reader that writes an entry and reads it back inside one request; code that does both in one pass must call it or it reads its own stale answer.

Everything non-secret is a verb too

add_repo (multiple: true), add_url, set_api_url, set_model, set_feature, add_profile: ordered, round-trippable, no options table. There is no github_repos or linear_token option anywhere. The one Settings submenu the plugin registers, Clients_Settings, takes a CSV upload of the publisher master: application data an administrator uploads, not runtime configuration.
