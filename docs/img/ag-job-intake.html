Job_Intake is three logs and a set of refusals, and the delayed ones circulate

Every producer of async work — an importer, a cron pass, a web request — writes through one class. Which log an entry lands in decides its size cap, its lock and its scheduling. Four refusals return false rather than throw, so the caller has to look; misuse throws.

jobintake.p<N>queue() / write_job() — LOCKED: the intake holds the partition's write lock from its first write to close(), admits an entry up to MAX_JOB_SIZE 32 MiB, and a Consumer drains it into jobs (job-intake.tsl on a substrate-only install, ELN's job-router.tsl otherwise). All options live here: not_before / delay, retries, batch, unique + unique_ttl.
jobfeed.p<N>feed() / write_feed() — unlocked, PIPE_BUF-bounded, rotating at FEED_SEGMENT_SIZE 1 MiB, so a job router tails jobs alone instead of the whole firehose. No options at all.
jobdelay.p0the parking lot — an entry whose not_before is still ahead lands here instead of the intake, single partition, hardwired; Job_Delay circulates it on the minute pass. No .tsl declares any of the three dirs: Bootstrap::register_log_producers() states each layout on newspack_nodes/registered_log_producers, so Log_Cleaner leaves queued jobs alone.

Job_Delay: a circulating buffer on the minute pass

sweep_action() rides newspack_nodes/periodic and reports a failure rather than propagating it, so a throw costs no other periodic subscriber its turn. Each pass drains jobdelay.p0 with a durable-cursor Consumer, delivers the due entries into the live intake with their delay fields stripped and their key re-hashed, re-appends the rest to the tail, THEN checkpoints — an abort replays the sweep and duplicates rather than drops. Late is correct: not_before means not before.

Two failures, neither the dead-letter path: a write_job() returning false is one stderr line and the cursor moves on, the job gone; a RuntimeException (the intake write lock timing out) is held and recirculates once a minute with no attempt count. ts is restamped on every hop, so QUEUE_MS measures from delivery.

Four things make a write return false, never throw

A handler name failing HANDLER_NAME_PATTERN — a letter, then letters, digits, _ and -, 64 at most, and this one writes no log line; an id over MAX_JOB_ID_LEN 128 bytes; a payload that will not wp_json_encode or exceeds MAX_JOB_SIZE; a feed() record over Partition_Node::MAX_LINE_SIZE. A caller that fires and forgets loses those jobs silently.

An intake INSTANCE holds the locked partition's write lock from its first write until close(); the static queue() and feed() close in a finally, queue_many() does not, and every other writer to that partition waits 15 s and gets a RuntimeException meanwhile.

Dedup and batches live in the cache, fail closed

unique + unique_ttl claim job-uniq:{handler}:{token} with an atomic add() on Cache_Backend::shared_first(), EARLY, before the size check — a refused entry holds the slot for the whole window — and a false add() drops the enqueue whether it was a duplicate or a sick backend. unique without a positive ttl throws InvalidArgumentException, and with no backend LogicException.

queue_many( $jobs, $key, $batch ) opens a batch by seeding job-batch:{id} (the outstanding count) and job-batch-err:{id} at BATCH_TTL_S seven days; settle_batch() deletes both at zero. A batch that never settles holds both keys, and its id, for the full seven days, and reusing that id throws RuntimeException. Compare the return against your job count.
