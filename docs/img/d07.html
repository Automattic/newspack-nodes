One spoke and the hub: the life of one connection

The hub is the HTTPS client in both directions. Its Remote_Source for the spoke bend is a broker, spokes:bend: one connection carries both streams its pairs name, the spoke's firehose.p0 and sources/php, and a hidden reader per stream keeps that stream's cursor. :sse-in holds the long stream open, and :http-out posts one signed batch per tick. The hops are numbered in order.

Connect · the brokers start one every half second, so no spoke answers a burst with refusals
First tick: builds and owns :sse-in, :http-out and :null, named after itself, and a reader for each exact pair, each with its own offsetlog and dead-letter partition under <topology>.bend/<kind>.
1reads the entry keyed bend, the short id the broker names as its first argument: an HTTPS URL, a username and a password. The password is sealed with libsodium under the site's auth salt and opened only here, on the way out.
2GET /messages/stream, with HTTP Basic auth: the hub user's WordPress application password, on this and every request. One subscribe names both streams, and positions carries each reader's own cursor.
3the handshake event names the slot leased to this stream, one of a limited set, and where each stream starts, which goes to the reader that owns it.
Stream · one long HTTP response, one server-sent event per record, both streams interleaved
and on to the broker, which hands it to the reader its FROM stamp names. Each record's ID is its place in the spoke's own log.
4one record per event.
Each reader keeps the record's FROM as the spoke sent it and sends it to its pair's target, firehose.p0 to remote-job-rewrite and sources/php to php-errors:partition. It checkpoints the record's ID to its own offsetlog and resumes from it on every reconnect; a record that will not parse is quarantined at that position, in its own dead-letter partition.
5POST /auth, once, before the first batch of commands.
6a command session: a handle and a key. The hub holds both under the spoke's Vault id, and the node that mints a command signs it under the key of the spoke it is bound for.
7POST /command, one per tick. A heartbeat signed under this key every 15 s keeps the slot lease; a paused reader's read_message step, set and get ride the same batch. Commands queued before the session exists are held.
8the reply, in the same response. The spoke writes every field of it, TO included. A 401 makes the hub forget the session.
Reply gate, allow_replies_to. The router delivers whatever TO names, so every outbound node carries an allowlist. A TO on the list, matched as a whole path, is delivered: the broker lists its own name and each reader's, so heartbeat replies reach the broker and a step's answer reaches its reader. Any other TO is dropped. An empty TO goes to :null.
Pressure and loss
More than 512 KB buffered across the readers: :sse-in stops reading the socket, and the spoke blocks on write. Reading resumes under 256 KB. One connection, one valve.
945 s of silence is a dead stream. :sse-in reconnects after a delay that doubles from 1 s to 30 s, and hop 2 asks again from each reader's own offsetlog.
