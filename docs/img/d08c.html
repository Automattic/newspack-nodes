Every dashboard bundle comes off one build kit

A consumer's scripts/build.mjs declares what to bundle and injects its tools. The substrate owns everything else: alias resolution, the WordPress externals and the manifest.

// newspack-event-logger-nodes/scripts/build.mjs const substrateSrc = process.env.NEWSPACK_NODES_SRC1 || path.resolve( ROOT, '../newspack-nodes/src' ); const { buildDashboards } = await import( kit( substrateSrc ) );2 const { esbuildAlias, assertNoRetiredOverrides } = aliasMap;3 assertNoRetiredOverrides( process.env );4 const alias = esbuildAlias( substrateSrc );5 const ENTRIES = [6 { entry: 'src/overview/index.js', outDir: 'build/overview' }, { entry: 'src/error-log/index.js', outDir: 'build/error-log' }, // gyroscope, settings, requests, current-request ]; buildDashboards( { esbuild, sass, rtlcss, root, ENTRIES, alias } );7
1One base directory names the substrate's src: a sibling checkout, or this variable wherever the substrate sits elsewhere.
2The kit, src/build-kit/index.mjs, is reached by joining a path onto that same base, so it carries no alias of its own.
3src/build-kit/alias-map.cjs is the one resolver esbuild and jest share. The .cjs is load-bearing: jest requires it while the build imports it.
4The four retired per-alias overrides are refused, never ignored. One left beside a correct base would build green against the wrong checkout.
5Three aliases fall out of the base: runtime, shared and debug-overlay, each under @newspack-nodes/.
6The consumer names its entries, one per screen, and injects esbuild, Sass and rtlcss from its own tree.
7The kit takes no bare dependency on those three, so it builds against a substrate checkout carrying no node_modules.

What one entry emits, and who reads it

<name>.js

The minified bundle. A banner stamps the substrate version into it, so a deployed bundle names what it was built against.

<name>.css

The extracted stylesheet, emitted whenever the entry imports styles.

<name>-rtl.css

The rtlcss companion of that stylesheet.

<name>.asset.php

The manifest PHP reads: the script handles the bundle reached for, and the version to enqueue at.

Shared code is inlined, so every consumer rebuilds

Each bundle above carries its own copy of the shared hooks, the view-node base and the debug overlay. Editing one changes nothing on a page until that consumer rebuilds. The release workflow checks the substrate out at a pinned tag, so a stale pin builds green with older shared code inside.

Every @wordpress/* import reads a global WordPress already serves

The kit rewrites each one to its window.wp.* global and records the handle in the manifest, because a second React breaks hooks. Icons is the exception: WordPress registers no handle for it, so a consumer bundles the icons it imports.

The pin moves only when WordPress does

Every runtime @wordpress/* package is declared exactly at its wp-7.0 dist-tag version, no caret, and scripts/lint-wp-pin.mjs fails the push on a range or a drifted lock. A bump ships no new code, because the build externalizes the package: it moves the API the build compiles against ahead of the one the browser runs, and a component changed between majors then breaks at runtime with every gate green.
