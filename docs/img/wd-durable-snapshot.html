The worker writes a snapshot the web request reads

Four topology lines make an in-memory accumulator readable from another process: a Partition writes the log, a Consumer tails it back, and each checkpoint co-commits the digest's save_state() beside the read cursor. What a dashboard shows is the last frame, not the worker's memory.

On respawn: cursor and state in lockstep

1
init_position() reads the last frame, seeds the cursor, and calls restore_state() on every node add_snapshot_node named. The items and the cursor come from one record, so they cannot disagree.
!
A name that cannot restore degrades, never loses. A node absent by the first poll, declaring no restore_state(), or with no blob in the frame logs a rate-limited WARNING: snapshot node '<name>' missing, stateless, or absent from the frame; skipping its restore. The blob is carried into every frame this reader writes from then on, until a live save_state() replaces it or a boot where the node exists restores it. A typo in the name reads as never restored, never lost, and that warning is its only symptom.

Keep the snapshot bounded

1
Every frame carries the whole save_state() payload — no diff, no cap. The demo stays cheap because FLUSH empties $items; an accumulator that never drains makes every frame larger than the last. Drain it, cap it, or snapshot a summary.
2
add_snapshot_node lifts the offsetlog's own 4,096-byte cap — the worker holding the topology lock is its sole writer — so an oversized frame is written rather than dropped. The cost is size, not loss.
3
Both void_warranty lines lift the cap on a data log: a scored batch on the partition, a composed draft on digest:log. Without them an oversize record is dropped whole, never truncated, and a flush reports { flushed: N } while digest.md.0 stays empty (ADR-4).
