A message, the path it takes, and how its reply finds the way back

Seven fields. Two of them are addresses. Nothing keeps a table of requests awaiting answers.

The request leaves probe

FROM = probe

TO   = vault/spoke-01

A node that mints a message writes its own name into FROM.

The router

Takes the first segment of TO, looks that name up in the process's table of nodes, and hands the rest of the path to that node.

vault / spoke-01  →  vault.fill( TO = spoke-01 )

The reply leaves vault

TO = probe  (the request's FROM)

The answer is addressed by copying the request's FROM into its TO. That copy is the whole correlation.

Each hop prepends a name

A node a message passes through puts its own name in front of FROM, so a reply can walk the whole path back: probe becomes http-out/probe, then _output/http-out/probe on the wire.

Why this is the security boundary

Whatever TO names, the router will reach. A reply written by a remote site names its own TO (Part 1). A message that loops grows FROM without bound, so a path past 1,024 bytes is refused, and the door it came in by is what refuses it (Part 2b).
