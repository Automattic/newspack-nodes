The hub as client: one batch per tick, one session per spoke, no retry

HTTP_Out_Node is the push side of HTTP_In. Minters fill it; the next drain tick POSTs everything buffered as one JSONL body to the spoke's /command on the Event_Framework's shared cURL multi, so nothing blocks. What happens to a batch is decided in this order.

Every minter refuses to fill() unsigned, so a minter with no session calls ensure_session() rather than skip: skipping alone deadlocks both sides, since HTTP_Out handshakes only inside fire() and only fill() arms that tick. The blocking path: probe_command()

Behind vault test and aggregator probe, where an operator is waiting on the verdict, so it bounds itself tighter and reads its reply off the response body instead of routing it: FROM is stamped as the _http boundary rather than a live node, signed at the mint site with sign_for().

It returns the reply envelope's payload array and nothing else, throwing RuntimeException on every other outcome: a plaintext url under vault_require_ssl, a spoke that will not issue a session, a WP_Error, a non-200, a body carrying no struct-VALUE envelope, a TM_ERROR reply, and a missing or non-array payload. The payload is a remote's JSON, so the caller allowlists the keys it renders, as Vault_CI_Node::probe_remote() does.

What an operator reads off a flapping spoke

Each loss leaves exactly one rate-limited line and nothing else: transport error <n>, HTTP <code>, or the drop reason with the message count. A hub that keeps re-authenticating is one whose batches keep answering 401; look for the one envelope whose signature fails, since it takes the session down for the rest of the POST.

The session is established at the spoke's /auth (AUTH_PATH, /wp-json/newspack-nodes/v1/auth) under the Vault credential Vault::credential_header() resolves, Basic over Bearer, the one place that rule lives for all three transports that reach a spoke.
