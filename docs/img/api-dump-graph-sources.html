One snapshot, two readers: where each dump_graph key comes from

Workers_CI_Node::collect_dump_metadata() reads the lock dirs, the topicprobe log, the log catalog, the dead-letter dirs and config into one envelope. Read a row left to right to see what a key is measured from, what each of its rows carries, and where it can mislead.

The topicprobe logThe last 128 KiB of topicprobe.p0's newest segment, one Probe_Record per reader, through CLI::consumer_rows().
→
consumers[]one row per reader that reported inside the window
readersourcepartitioncursor_segmentcursor_offsetend_segmentend_sizedistancemsgs
A report, not an inventory: not one row per offsetlog dir on disk. A reader absent from the window drops out rather than reading stale. A record older than Topic_Probe_Node::stale_after_s(), two sweeps of the declared cadence (15 s by default), is re-measured off its offsetlog through Consumer_Node::lag_from_disk(). Rows come in the order the window first names each reader, so wp nodes status sorts them itself.

workers dump_graph: the dashboard's one round trip

The six sources above, plus graph and a logs[] entry for each active topology's Log file sink, in ONE reply: the browser joins a worker list against a graph and a segment list, and separately timed verbs would capture those at different instants. A real segmented-log entry outranks a synthesized one of the same name.

Alerts::evaluate(): the same snapshot

It calls collect_dump_metadata() itself and reads workers[], consumers[] and deadletter_by_reader for its worker-liveness, consumer-lag and dead-letters families, so an alert can never name a fleet the dashboard does not show. A second reader of the lock dirs and the probe log would drift from the first.
