A plugin on disk: what the scaffold writes, and who reads each file

A Nodes plugin is an ordinary WordPress plugin plus two additions: a Composer classmap, so make_node can find its classes, and one registration call. The scaffold writes both, one working node, a topology wiring it into a stock Log, and a README, and never overwrites a file.

Four commands, run from wp-content/plugins

1wp nodes scaffold plugin my-pipeline
Writes the plugin. A bootstrap, a classmap composer.json, one working node, a topology and a README. The fleet can run it before you write a line.
2cd my-pipeline && composer dump-autoload -o
Builds the classmap make_node resolves through. Run it again after every new or renamed node.
3wp plugin activate my-pipeline
Lets the bootstrap run. register_plugin() enters the namespace prefix and every .tsl in the directory into the catalog.
4wp nodes activate my-pipeline
Adds the topology to the active set and spawns its workers. Nothing spawns until you say so.

Six files, and the part of the substrate that reads each

my-pipeline/
read by

my-pipeline.php plugin file

Waits for plugins_loaded, checks the substrate is present, requires the classmap, then calls Topology_Registry::register_plugin() with a namespace prefix and a directory.

WordPress loads plugins alphabetically. A slug sorting before newspack-nodes would otherwise load before the substrate's classes exist.

The command interpreter's namespace table

make_node Foo becomes My_Pipeline\Foo_Node.

composer.json classmap

A classmap over the plugin's classes, compiled by composer dump-autoload -o.

Composer's autoloader

make_node loads the class through it once the namespace table has named it.

includes/<Type>_Node.php three of them

A class named <Type>_Node under the prefix, extending Node: one entry point, fill(), and a node_schema() naming category, description, positional arguments, requests and commands.

The console palette, the Inspector, the REPL's help

All three render node_schema(). The graph itself calls fill() and nothing else.

topologies/my-pipeline.tsl

var frontmatter, make_node, connect_node, a closing secure: the lines the REPL accepts.

The one topology catalog

Fed by every registered directory. The active set is what spawns, and wp nodes activate adds a name to it.

includes/Service_CI_Node.php service interpreter

Answers the dashboard's verbs. Its verb table is its own node_schema(): each entry brings dispatch, authorization and help, and names which of Part 5's three roles (read, tune or manage) may call it. Naming none requires manage.

Every request graph

Mounted on newspack_nodes/request_graph_ready through the base interpreter's make_node(), which constructs, names and sinks it in one step. The sink is the reply's way out:

reply→TO = sender→_router→_outputwrites the HTTP response

src/dashboard/ React page

Built against @newspack-nodes/shared, on its own top-level admin menu.

Admin::enqueue_react_page()

Enqueues the bundle and localizes the REST URL and the nonce the page sends with every command.

The ladder make_node Releases_Source releases climbs

1Bootstrap ran

plugins_loaded has fired and the substrate's classes exist.

2Plugin active?

Inactive, and register_plugin() never ran: the answer is unknown class.

3Namespace table

Releases_Source becomes My_Pipeline\Releases_Source_Node.

4Classmap knows it?

A stale classmap gives the same unknown class. Check activation first, then composer dump-autoload -o.

5Node stands

Constructed and named releases; connect_node can now give it a sink.
