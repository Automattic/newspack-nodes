A Topic picks one partition per message by three precedences, then gets out of the way

Topic_Node::fill() is the only ingress and does no batching of its own: it chooses an index and hands the message to that Partition, whose own batch and flush rules take over. Widening a log is a topology argument, num_partitions.

hash_to_partition is canonical

[ $stripped ] = explode( '?', $key, 2 );
return ( crc32( $stripped )
    & 0x7FFFFFFF ) % $num_partitions;

The query string is stripped, then a 31-bit mask. Every partition router MUST call this one function: a diverging hash family routes the same key to different partitions and breaks ordering (ADR-6).

Modes propagate to partitions built later

allow_large_writes(), void_warranty() and with_index_named( $formatter ) record the mode on the Topic, apply it to every materialized Partition, and partition() applies it again to each one it creates. Each is a {name}:config verb and dump_config() re-emits it, so the round trip keeps the mode.

The two allow_large_writes() disagree about their first parameter: Partition's is $max_wait_ms, Topic's is $debounce_ms, so $t->allow_large_writes( 0 ) is hold mode, not a try-lock.

Two counters aggregate; two double-count

bytes_written() sums and largest_msg_sent() maxes over every materialized partition, which is what gives the Topic a meaningful canvas row: dump_metadata skips the patron-linked p{N} children.

stats and ls -a walk the whole registry and list the Topic beside its children, so WRITTEN double-counts there, and so does COUNT: fill() increments the Topic's counter before the partition increments its own.
