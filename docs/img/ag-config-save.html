A setting reaches running workers through a save door, a cache reset and a reload watermark

Settings_Schema declares every key once — its default, bounds and restart class — and Config and Admin both derive from it. A running worker froze its config at boot, so a save has to tell it, and only two doors know how.

Four layers resolve one key, weakest first; the option wins by PRESENCE

Config::load_config_defaults() folds the first three and memoizes them; Options_Overlay::apply() lays the option over the result. A file's keys layer ONE level deep, [ ...$config, ...$parsed ]: naming an array key replaces the whole array, so a local file naming one memcache server drops every server the shipped file declared. That bites memcache_servers, topologies, log_sources and allowed_users.

Door 1 · the settings page

Field::sanitize_callback() CLAMPS a bounded int silently: 900 typed into Num Partitions stores 16 with no notice. Every rendered numeric setting declares an inclusive min and max, and the bounds bind at the two doors alone, never on read.

Door 2 · the settings verb

Settings_CI_Node::cmd_set() REFUSES with invalid value for setting: <key>, because a programmatic caller must be told rather than handed another number. A set to the value already stored is a no-op, so Settings_Sync's sweep never recycles the fleet.

No door · a file or a direct option write

Taken as written, and nothing clamps it: Partition_Node throws only below a segment_size of 1, so a config file naming 5 gives five-byte segments. SSE_Slot_Pool is the one family that re-clamps on read.

A write outside wp-admin signals nobody

newspack-nodes.php constructs Admin only inside is_admin(), so a newspack_nodes_* option written from WP-CLI, from a worker or by a consumer plugin resets no cache and signals no worker: the change lands when the next generation boots. That is why cmd_set() repeats the recipe by hand.

Purge before reset

Config::invalidate_options_cache() purges alloptions, notoptions and each schema key's own options entry, since WordPress caches an option under its own key too. Where a Config::reset() follows, the purge runs FIRST: reset only re-arms the next load_config(), whose option layer reads through get_option(), and a purge afterwards leaves any read in between memoized on the stale snapshot.
