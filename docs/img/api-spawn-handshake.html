One POST spawns a worker, and answers only when the worker dies

Every spawner crosses this one gate: a worker's own self-respawn, each worker's _fleet peer scan, the WP-Cron cold-start pass, and an external caller holding manage who presents a WordPress nonce for newspack_nodes_spawn_worker. The refusals come in a fixed order, and the accepted request holds the PHP process for the worker's whole life.

Spawner

Fire-and-forget POST with a sub-second timeout; it is long gone before the answer is written.

Worker

Built by whatever answers newspack_nodes/spawn_worker.

1Form-encoded (application/x-www-form-urlencoded) or JSON (application/json). All three fields are required, so a missing one answers 400 rest_missing_callback_param before any callback; a type no ACTIVE topology declares fails the route's validate_callback the same early way.
2Fleet gate first: a multisite subsite gets 403 newspack_nodes_not_fleet_site. An EMPTY nonce answers 403 invalid_token with Missing spawn token.
3Validator A, internal. Spawn_Coordinator::validate_spawn_token() against the current or previous 10 s window. No capability check and no rate limit: the peer scan, the cron pass and self-respawn take this door.
4Validator B, a person. Capabilities::can( MANAGE ), then wp_verify_nonce( $nonce, 'newspack_nodes_spawn_worker' ), then a 2 s per-user limit backed by a transient. Capability comes before the limit so an unauthenticated burst cannot fill the transient table. Neither validator: 403 invalid_token; inside 2 s: 429 rate_limited.
5In order: 400 invalid_partition (negative, at or above MAX_PARTITIONS = 16, or past the type's active count); 409 fleet_held while a deploy hold stands in Spawn_Coordinator::HOLD_OPTION; 429 spawn_throttled while {type}|{partition} sits inside the shared 15 s window.
6Accepted. Record the spawn against the 15 s throttle, in memory and in the shared cache at twice the window; ignore_user_abort( true ) and set_time_limit( 0 ); write $_SERVER['NEWSPACK_NODES_WORKER_TYPE'] and …_PARTITION; fire newspack_nodes/spawn_worker( $type, $partition ).
7Topology_Registry::spawn_worker builds the worker and calls execute(). It runs INLINE, 595 s by default.
8The body is written once the worker exits. Nobody is listening for it.

The internal token, one purpose per endpoint

# window changes every 10 s; the previous one validates too, # so a token that crosses a boundary in flight is not refused $window = floor( time() / 10 ) # spawn: a purpose-bound key, never the raw salt $key = hash_hmac( 'sha256', 'newspack_nodes_spawn_key', wp_salt( 'nonce' ) ) $token = hash_hmac( 'sha256', "newspack_nodes_spawn:{$window}", $key ) # health-cache: the same shape under wp_salt( 'nonce' ) itself $token = hash_hmac( 'sha256', "newspack_nodes_health-cache:{$window}", wp_salt( 'nonce' ) )

The purpose sits INSIDE the hashed message, so a spawn token never validates at /health/cache and a health-cache token never spawns. The derived spawn key is what makes it safe to hand to a process outside PHP: the raw nonce salt forges every nonce on the site. A token names neither type nor partition; until its window passes it authorizes any spawn the endpoint would otherwise accept.

A cross-language wire contract

Nuclear-gyrobase exports the spawn key to the Perl engine, and Gyrobase::Log::_spawn_token() re-implements the construction with its own $SPAWN_WINDOW_S = 10 mirroring Internal_Request_Token::WINDOW_S and the message string newspack_nodes_spawn:{window} copied by hand, pinned on the Perl side by t/spawn-token.t in a separate repository.

Change either constant here and the break fails CLOSED and silently: the doorbell POST is refused 403, the worker is never woken, and the only symptom is job latency indistinguishable from the WP-Cron backlog sweep working normally.
