A session key signs the semantics of a command and nothing else

The door authenticates the request and signs nothing. POST /auth hands out the key once; the node that mints a command signs four things under it; the verifier recomputes the same string and claims the nonce once. Everything that changes in transit stays outside the signature.

POST /auth, three optional fields

scope — read, tune or manage; default manage, CLAMPED to the highest role the minting user holds. Unknown: 400 invalid_scope; a caller holding no role never reaches issue(): the permission callback returns false, and WordPress answers 401 rest_forbidden anonymously, 403 logged in. issue() repeats that refusal as 403 invalid_scope, so the clamp and the gate stay one decision.

label — the Sessions-tab name, through sanitize_text_field() then cut to 64 characters; empty keeps the session out of the listing. sessions create echoes the label as SENT, so the next list can disagree.

ttl — seconds, clamped into 60 … 86400, default 3600. Never slid on use.

No error code for a failed mint. mint_session() throws RuntimeException when store_session() cannot persist the key (no cache backend, or a handle already taken) and nothing catches it on this route, so the POST fails as an uncaught exception; the sessions create verb reaches the same throw and reports it as a command error.

The response, disclosed once
{ handle32 hex chars, server-chosen: a caller's handle could collide with or fixate a live session key64 hex chars, never shown again; the cache holds it recoverable, not hashed, so the HMAC can be recomputed: the argument for a short ttl over a long-lived token scopewhat was GRANTED, not asked expires_inseconds; a leaked handle expires on schedule nowserver clock; the client aligns its TIMESTAMP to it }

The session records the minting user too, so a credential presented outside a browser, an MCP client or a script, acts as that user under the scope as its ceiling.

What the minter signs: JSON.stringify([ TIMESTAMP, name, arguments, nonce ]), HMAC-SHA256 under the key

The result rides under VALUE.auth:

{ nonce32 hex sig64 hex HMAC handlethe session; absent means the per-site secret }

Command_Auth::sign() omits the handle and signs under the per-site secret: the same-process path the attached wp nodes cli takes over a filesystem-gated IPC partition, never a browser.

sign_for( $destination, … ) signs under the session held with that remote, and choosing the key IS the destination binding: a signature under one spoke's key verifies only there. No session: it refuses to sign. A VALUE that cannot be JSON-encoded is left unsigned on purpose, so the verifier refuses it rather than fall back to HMAC('').

The bytes are exactly what JSON.stringify produces, because src/runtime/command-auth.js signs the same string; tests/fixtures/signatures.json pins the parity from both languages.

The ceiling installed in Capabilities::$session_scope for this one command, restored by Command_Interpreter_Node::interpret() afterwards:

A verified session installs its scope, which can only subtract from what the user's capability grants.
The per-site secret installs null: the site's own authority carries no ceiling.
Every refusal installs Capabilities::NONE, so a command whose authority never resolved leaves no wider ceiling standing behind it. The reply is TM_COMMAND|TM_ERROR carrying unauthorized: <verb>, names no cause, and the whole batch answers 401.
