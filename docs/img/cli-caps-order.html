The capability swap, the hub user, and what uninstalling takes down

Three roles resolve to manage_options until caps install moves them onto real capabilities. Only then can hub-user mint a credential narrower than everything, and caps uninstall later revokes every such credential at once.

1. wp nodes caps install

rolegatesmanage_options →
readdashboards, SSE streams, read-only introspectionnewspack_nodes_read
tunesettings and application datanewspack_nodes_tune
managefleet control, the credential vault, command sessionsnewspack_nodes_manage

Grants all three to every role holding manage_options at that moment, and creates the newspack_nodes_hub role carrying read and tune alone. Every action ends by printing the map under two lines a host can answer differently:

granular: yesThe capability grants stand on every host.
hub role: absentA managed host reverts a role it did not sanction. install warns and names the direct grants step 2 makes instead. A supported deployment, not a broken install.

It reads the roles table once, when it runs: re-run it after adding a role that holds manage_options, or that role holds none of the three and every gated surface refuses it. A re-run is idempotent, adding the missing grants and changing nothing else. The one thing a re-run cannot repair is a hand-edited hub role: off VIP add_role() returns null on an existing slug, so only uninstall then install rebuilds it.

2. wp nodes hub-user <login>

wp nodes hub-user newspack-nodes-hub
Warning: Shown once. Store it in the hub Vault entry for this spoke.

Refused until step 1 has run: before the swap the hub role still resolves to manage_options and the credential would hold everything.

It creates, or converts, the least-privilege user an aggregator authenticates as, and grants newspack_nodes_read and newspack_nodes_tune to the USER directly, and that grant is the credential's authority: a user capability lives in the user's own meta and never consults WP_Roles, which is what Capabilities::can() reads. The role goes on top only where the host carries it, removing the account's every other role, since set_role() replaces the whole map and the grants follow it.

The role carries no WordPress read, so the account is REST-only: no wp-admin, no profile screen, and its credential can be issued only here. Every run mints a new password, shown once and kept nowhere readable: it never looks for one under the same label and never revokes one, so a second run against a lost password leaves two live credentials on a user whose credential is permanent by design. Retire the old one with wp user application-password delete, or pass --no-password, which creates or re-roles the user without minting one. --email sets a new user's address (default <login>@<site host>); --name labels the password (default newspack-nodes hub).

wp nodes caps uninstall reaches every hub credential in the fleet

It deletes the switch option FIRST, so the map is back on manage_options before the capabilities it named disappear; then it strips newspack_nodes_{read,tune,manage} from every role in the table, hand-made grants included, and removes the newspack_nodes_hub role outright.

Each aggregator user keeps its two direct capabilities and the role name in its meta, and both resolve to nothing on the manage_options map: every hub application password stops authorizing and each spoke starts answering 403. Nothing warns and nothing enumerates those users first. uninstall.php makes the same call, so deleting the plugin takes the hub credentials with it.

Recovery, and the safe order

wp nodes caps install swings the map back and revives the hub users off the capabilities they still hold. Short of that, give each hub user a real role before uninstalling. Where the hub role does not exist, an account bound to it alone would hold nothing: WP_User::get_role_caps() filters the role straight back out, and the credential is refused at can( READ ) — a 401 that reads as a bad credential. The direct grants are what keep it working.
