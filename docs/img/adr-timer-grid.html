Timers fire on one wall-clock grid, so harmonic cadences meet and share a POST

Every browser poll rides the _router tick, and HTTP_Out batches whatever was minted in one tick into a single POST. A timer pacing itself from its own last fire keeps the second it was armed in forever; a timer snapping to a grid computed from the clock converges with nothing shared.

Rejected: pacing from the timer's own last fire

When a surface opens decides which second it polls in: a 5 s catalog opened at :02 and another at :04 never share a tick again, and each pays its own POST forever. A page with four cadences pays four requests where one would do, and no test sees it, because every poll works. Also rejected: a per-interval phase (slides each cadence a few hundred milliseconds off the others and destroys the alignment), a shared scheduler node (state where arithmetic suffices; the Router already is the heartbeat), and snapping to the first tick after arming (makes the phase depend on when the surface opened).

nextBoundary( after, intervalMs ) lives in TimerNode and nowhere else

( floor( ( after − phase ) / interval ) + 1 ) × interval + phase, with ONE phase for every cadence, GRID_PHASE_MS = 360. The offset only keeps the grid off :00, where every other periodic job on the box already is. A subclass picks a harmonic interval and never computes a boundary; scripts/lint-contract.mjs's grid-math rule keeps it so, which is why MetadataNode extends PollerNode rather than pacing itself.

The throttle applies to a node registered on the _router tick with an interval above 1000 ms. A node holding its own setInterval slot — a sub-second cadence, an unnamed node, the Router itself — already fires at interval_ms and skips the boundary test.

Two methods refresh outside the cadence without leaving the grid: markDue() clears lastFireTime so the very next tick fires, as a dashboard answering a filter change or a cd needs; markFired() counts from the NEXT boundary, so the following fire owes a full interval — deliberately not lastFireTime = now, which lands anywhere inside the period and can fire again one tick later.

The one cost, paid once

The first period after arming is the short remainder of the period the timer opened in, so a poll can fire twice in quick succession at mount. A test asserting "no second fire within N seconds" pins the clock FORWARD to just past a boundary; moving it back reads to every watchdog as a stream gone silent. The PHP side has a second grid on purpose: LRU_Cache::next_boundary() carries no phase, because no cadence inside the cache aligns with another, and snaps to an epoch grid rather than localtime components so no boundary lands in a DST discontinuity. Revisit if the runtime gains sub-second cadences, where a 360 ms phase is a large fraction of a period.
