One hash decides where a key lands, and the hash is the concurrency control

One partition has one consumer, so a key's messages are processed serially, by one process, in append order. Per-key mutexes, CAS loops and read-modify-write guards never need to exist, as long as every producer computes the same partition for the same key.

How Topic_Node::fill() picks a partition, in order

Rejected: per-producer hashing

Divergent hash families silently split a key across partitions and break all of it: no error, only wrong colocation. Every routing site calls Partition_Node::hash_to_partition(); a site needing different behaviour is an explicit, named alternative, never a divergent re-implementation.

Why the 31-bit mask

crc32() returns a value that is negative on 32-bit PHP for half its range; masking with 0x7FFFFFFF keeps the modulo non-negative on every build. The query string is stripped so /page?cb=1 and /page?cb=2 land together.

Revisit if

The partition count outgrows CRC32's distribution, or a genuinely different key family is required: then a NEW, named routing function, not a quiet second hash.
