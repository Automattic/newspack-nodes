The orphan sweep deletes only what no active topology declares, spares the last hour, and refuses to run on a set it could not build

Log_Cleaner runs in the minute reconcile pass and on wp nodes gc. A directory is an orphan only when nothing ACTIVE declares it, so deactivating a topology orphans its log and offsetlog directories and stopping its workers does not.

1Build the declared set. Every active topology's resolved directories, each counted to at most Spawn_Coordinator::MAX_PARTITIONS, 16; log directories also come from the newspack_nodes/registered_log_producers templates. A set that will not build comes back null, and then neither bucket is swept: the red card opposite.
↓

Swept only on a NON-empty set: an empty log set can mean the producer filter has not run yet, and sweeping then would delete a live firehose. offsets/
Swept even on an empty set: only topologies declare offsetlogs, so empty means none is active and no consumer holds a cursor.

Three degraded inputs skip BOTH sweeps

A name in the topologies config that Bootstrap::get_topologies() neither found nor could synthesize, since it drops such names silently; a .tsl that Topology_Analyzer::resolved_resource_dirs() cannot read; and a producer template landing under no directory beneath the logs root.

The only signal is one rate-limited Log_Cleaner: skipping sweep: … line on stderr. wp nodes gc still prints Success: No orphan dirs past the 3600s grace, the workers CI's dump_cleanup returns an EMPTY expected_basenames with every directory listed as an orphan, and dump_graph's logs[] comes back empty, so the Log Viewer shows nothing at all: both read the declared set, which fails closed to []. Read that as the GC refusing to run, never as a list to act on. A stale topology name is the likely cause, on any deployment whose shipped config still lists a topology a plugin has since removed.

Victim: --force and the delayed-jobs cursor

offsets/jobdelay-sweep.p0 is created by PHP and declared by no .tsl; the producer filter protects logs/jobdelay.p0/ alone. Each sweep's checkpoint keeps it inside the hour, but --force removes it, and the next sweep starts at the head of jobdelay.p0 and re-delivers every entry the log retains: delayed jobs and in-flight retry backoffs run again. Renaming the reader id by hand does the same.

Victim: a Topic wider than 16 partitions

Topic_Node clamps num_partitions to at least 1 and no maximum, so a literal 32 writes 32 directories, while Topology_Analyzer::declared_partition_count() stops the declared count at 16. Log_Cleaner::declared_log_dirs() never hears of foo.p16 and up, which are deleted once their hour of grace passes, and resolved_node_dirs() carries the same cap, so Bootstrap::node_dirs() hands a reader the first 16 alone. The dir_template cannot expand to num_partitions error fires only when a template produces FEWER directories. The num_partitions setting is bounded 1..16 for this reason; hold a hand-written .tsl literal to it.
