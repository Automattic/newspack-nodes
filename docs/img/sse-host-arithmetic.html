A stream spends a php-fpm child, and the child count is the budget

Ten workers per site by default. Each open stream holds one for its whole life, each node worker holds one for its ~595 seconds, and pages, cron and the loopback share whatever is left. Past ten, the host queues each request and refuses it with 429 when no worker frees in time.

Cache reads per second, by open streams

reads/s = streams × 10 ticks/s × 3 reads per check()

A tick with no timer armed waits Event_Framework::IDLE_TIMEOUT_US, 100 ms, and SSE_Slot_Pool::check() runs on every one: the pointer, the liveness key, then the pointer again, because a rival can reclaim the slot between the first two. That is the floor before any data moves; raising sse_max_streams buys children and cache round trips in proportion.

One reader's share: three of the six

sse_max_slots reserves nothing. Slots are pooled host-wide; the share only stops one reader with many tabs from taking the site down alone. An identity is {user id}:{8-hex md5 of REMOTE_ADDR}, so every tab one person opens draws on the same three.

Three, because an idle stream closes after sse_idle_timeout (15 s) and reopens sse_retry_ms later (5 s), and a stream whose process dies before the release leaves its lease standing for the whole TTL while the client is already asking for another.

The share is approximate; the host cap is exact

Two connections from one identity can both read the count before either claims, and a lease read that fails counts as not-held, so either path lets one reader exceed its share. That direction is deliberate: an exact share would need a second compare-and-swapped counter, and a wrong value there leaks capacity permanently rather than for one TTL. The host cap needs no counter: a claim is a compare-and-swap on a fixed number of pointers.

Six is a budget, not a target

It is the ceiling that still leaves the site serving pages while fully subscribed. A deployment that reaches it regularly wants a larger allocation or fewer dashboards, because the headroom left over is what absorbs a traffic spike. Burst capacity above the allocation is not guaranteed and cannot be spent on something sustained, and a stream holding a child for minutes is exactly that shape. Read the live worker count from wp nodes status before raising a stream bound.
