The offsetlog frame carries the evidence a crash cannot leave

A caught throw is quarantined on sight. A death with no throw only shows as an attempt count that climbs, so the count is what the reader boots from, and a graceful stop is what keeps an innocent cursor from climbing. Shared by Consumer_Node and Remote_Source_Node through Dead_Letter_Queue and Durable_Reader.

One checkpoint frame, committed every CHECKPOINT_INTERVAL_S (30 s), at a clean stop, and after every message in crawl

segmentthe cursor's segment
offsetbyte offset in it; together the next UNREAD position
attemptsevery boot resumes at +1; a graceful stop stamps 0; a fatal skips the stamp
reasonthe last poison reason, or '' on a graceful stop
first_crash_tswhen the streak began; null on a graceful stop, so the window never accrues across clean recycles
cacheConsumer only: its snapshot nodes' state, co-committed beside the cursor

The cursor names the next unread position identically in both readers, and a disposed record is committed past. Without the graceful attempts=0 a clean ~10-minute recycle is indistinguishable from a crash, and an idle cursor would cross the crash threshold and quarantine an innocent message. The handoff is skipped on a fatal (is_fatal_shutdown()) on purpose: a climbing count is how a deterministic fatal reaches crawl. Each record's crumb stamps segment:offset:length; the length is what a pull source advances by, and a two-part crumb moves the cursor by nothing.

Caught throw: quarantined on sight
1The sink's fill() raises inside Durable_Reader::forward_line, the shared emit seam (Remote_Source overrides it for its crumb-derived cursor).
2dead_letter() writes the message to the :deadletter sibling, replayable with wp nodes ingest. An unparseable line goes the same way with its raw bytes kept.
3The cursor advances past it and the disposal commits gracefully, so it is never re-delivered and never re-quarantined. No retry, no head block: a throw is deterministic per message, and the transient failures a retry would target are upstream.
Tail_Node and File_Tail_Node are the third override of that seam and wrap nothing: a throw from a Tail's sink escapes the drain loop, the cursor never advances, and a Tail reaches its :deadletter only through the crawl-entry sacrifice.
Cooperative stop: the fair shot
1cooperative_stop() strikes the in-flight message only when the worker stopped ON the message it booted on: cursor never advanced, Worker_Should_Stop escaped its fill().
2At COOP_MAX_ATTEMPTS = 2 strikes it is quarantined, and the shutdown frame lands PAST the head, at the virgin baseline, so the successor boots straight onto the next record.
A memory stop whose fresh baseline was already near the watermark is a leak, and an alert, rather than poison.
A plain Worker_Should_Stop leaves the cursor for a replay; Worker_Should_Stop_Clean commits past, because the downstream already finished the message (ADR-14).
Uncatchable death: crawl
1OOM, fatal, SIGKILL: no catch point. The next boot sees attempts climb with no reason. Below CRASH_MAX_ATTEMPTS = 5, the first successful forward clears the streak.
2At the threshold, crawl: the boot-pinned suspect is sacrificed to the DLQ with reason 'crash' and committed past, which closes the sacrifice-to-checkpoint crash window — Consumer takes the first buffered line at the boot cursor, Remote_Source matches the crumb start against the boot pin (a suspect the stream resumed past disarms without sacrificing).
3Checkpoint after EVERY message so a re-crash pins the culprit, attempts pinned at the threshold. Crawl will not exit while the sacrifice is still armed.
CHECKPOINT_INTERVAL_S = 30 crash-free seconds exit to the healthy baseline. One accepted false positive: the entry-transition head, when the crash was deeper in the window.

State that survives a quarter-hour of crashing is the suspect

When the boot frame's first_crash_ts is older than Consumer_Node::STATE_WIPE_AFTER_S (900 s), the co-committed cache is discarded rather than restored: the snapshot nodes come up empty and the cursor resumes alone. The only symptom is a rate-limited WARNING: naming the discard. Read it before taking a Request_Builder or Digest_Builder that came back empty for lost data.

Triage lives on the reader's own interpreter

Dead_Letter_Queue merges dl_list, dl_show, dl_requeue and dl_purge into the using node's node_schema()['commands'], so both readers expose them on {name}:config with no CI edit. All four are hidden, because dl_show and dl_requeue need a sidecar locator only the listing supplies. Every give-up emits a rate-limited alert and, when configured, a replayable entry.

A third user with no cursor at all

Partition_Node uses the same trait for a short write or a failed segment open: it quarantines the messages that never landed and refuses dl_requeue there, because redelivering a record that was never written is a different operation from retrying the write. The rejected shapes: drop on first failure (loses data), unbounded retry (wedges the stream), one shared read loop (the buffer/line and SSE-push models differ; only the accounting is shared), automatic retry for caught throws.
