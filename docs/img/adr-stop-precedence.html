A broad catch re-throws the stop before it handles anything else

Worker_Should_Stop extends \RuntimeException, so every catch (\Throwable) on the drain path catches it. Treated as an error, the stop is swallowed and the worker runs past its deadline until the next drain tick re-checks. A loop that attempts every step raises everything it caught after the last, and one site carves itself out.

Inside a broad catch on the message or drain pathEvent_Framework::stop_check() raises it from a long in-process job (timeout, memory, shutdown); pump() is its throttled form, which firehose writers reach per write. Without the rule a mid-job stop is guaranteed only on the direct firehose path, from Log_Manager through Topic to Partition, because an intervening Tee or Command_Interpreter eats it.

Yes: catch (Worker_Should_Stop $e) { throw $e; } — it is control flow, not an error.
No: propagate it, or translate it into a result the caller sees — a TM_ERROR reply, a refusal. Printing it and moving on swallows it. Broad catches stay legal.
The failure the rule prevents: the stop logged as an error, the worker draining on past max_runtime or the memory watermark.

Attempt-all loops: fan-out (Tee, Tap and send_signed() via Fanout_Targets), Settings_Sync, Vault_Group_Node::forward(), LRU_Cache eviction, HTTP_Out replies

A step throwing says nothing about its siblings, so the loop attempts EVERY step through Worker_Should_Stop::attempt_each(), which returns everything caught, and raise() throws it after the last, combined. A skipped healthy target is a permanent loss once the poison path dead-letters the message and advances the cursor; duplicates on replay are the accepted cost.

Tap performs its passthrough before raising — the passthrough IS the pipeline — and the passthrough's own failure joins the list, so a clean tap stop beside a failed pipeline write replays. Vault_Group_Node::forward() re-raises each child's refusal naming that child, in the same list as any stop.

Not a carve-out: after_job

Job_Worker_Node's newspack_nodes/job_worker/after_job fires whether the handler returned or threw, and a listener's throw joins the job's own through raise(): neither masks the other, and a stop beside it is a plain stop carrying it, so the reader replays.

A before_job listener that throws fails the job the way a handler does, after after_job has fired.

Not a carve-out: Log_Manager::finish() (event-logger-nodes)

Every line it writes before the terminal is a write — the orphan drain, the memory line, the resources line, complete() itself — so a stop or a failed write can land on any of them. Skipping the terminal strands the request in flight until eviction, because finished latches on entry and nothing retries it. So it writes the terminal whatever the drain threw — aborted, when that was a stop — then raises both through raise().

Terminal-last is a wire contract: Reqgrep_Core finalizes and evicts the rid on it, so anything written after arrives at a request that no longer exists.

Why no marker interface yet

The control-flow family is Worker_Should_Stop plus its subclass, so one explicit-first catch on the parent already covers both. A second, unrelated control-flow exception is the revisit condition: introduce a shared base and catch that.
