A broad catch re-throws the stop before it handles anything else

Worker_Should_Stop extends \RuntimeException, so every catch (\Throwable) on the drain path catches it. Treated as an error, the stop is swallowed and the worker runs past its deadline until the next drain tick re-checks. Three sites carve themselves out.

Inside a broad catch on the message or drain pathEvent_Framework::stop_check() raises it from a long in-process job (timeout, memory, shutdown); pump() is its throttled form, which firehose writers reach per write. Without the rule a mid-job stop is guaranteed only on the direct firehose path, from Log_Manager through Topic to Partition, because an intervening Tee or Command_Interpreter eats it.

Yes: catch (Worker_Should_Stop $e) { throw $e; } — it is control flow, not an error.
No: handle it as a real error: log it, wrap it TM_ERROR, defer it. Broad catches stay legal.
The failure the rule prevents: the stop logged as an error, the worker draining on past max_runtime or the memory watermark.

Carve-out 1: fan-out (Tee and Tap via Fanout_Targets, and LRU_Cache::evict_bucket() over its callbacks)

A target throwing says nothing about its siblings, so a fan-out attempts EVERY target and defers the throwable: a skipped healthy target is a permanent loss once the poison path dead-letters the message and advances the cursor. Completing the fan-out preserves at-least-once; duplicates on replay are its accepted cost, and they arise with any fan-out regardless of when it throws.

Tap always performs its passthrough before re-throwing — the passthrough IS the pipeline, and a Worker_Should_Stop_Clean commits PAST the message, so aborting early would drop it from the main path. Tap claims no exemption as observability: a snapshot node raising the clean stop from a tap participates in cursor semantics, so Tap defers an ordinary target error exactly as Tee does rather than swallowing it.

Carve-out 2: post-job finally

Job_Worker_Node's newspack_nodes/job_worker/after_job swallows everything, WSS included. It fires whether the handler returned or threw, so propagating out of it would either false-poison a completed job — the drain would quarantine an already-processed message (ADR-12) — or mask the failure it fired after.

Its before_job counterpart is NOT a carve-out: it re-throws WSS first and swallows only a listener's own error, which skips that one job instead of killing the batch.

Carve-out 3: Log_Manager::finish() (event-logger-nodes)

Every line it writes before the terminal is a write — the orphan drain, the memory line, the resources line, complete() itself — so a stop can land on any of them. Skipping the terminal strands the request in flight until eviction, because finished latches on entry and nothing retries it. So it marks the request aborted, writes the terminal, then re-raises.

Terminal-last is a wire contract: Reqgrep_Core finalizes and evicts the rid on it, so anything written after arrives at a request that no longer exists.

The winner moves the consumer cursor, so the slot holds whichever throwable is safest to act on. Advancing past a message that needed a replay loses it; replaying a clean one is a duplicate the contract already tolerates. tests/unit/TeeStopPrecedenceTest.php pins the inversion.

Why no marker interface yet

The control-flow family is Worker_Should_Stop plus its subclass, so one explicit-first catch on the parent already covers both. A second, unrelated control-flow exception is the revisit condition: introduce a shared base and catch that.
