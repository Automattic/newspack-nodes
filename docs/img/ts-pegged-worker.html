stuckA row that PERSISTS across runs with a COUNT that never advances. A cURL-multi handle that never completes, on an SSE or HTTP egress node.

routineCOUNT is per-registration, not cumulative: unregister_curl_easy() drops the tally when no registration points at the node, register_curl_easy() re-seeds it at zero, and a node holding no handle has no row. A zero or an absent row reads as "recently re-registered" or "valve closed".

valveSSE_In_Node::disarm() is Remote_Source's backpressure valve, edge-triggered at a 512 KB high and 256 KB low water mark; it unregisters the live handle, so a hub under sustained backpressure flaps in and out of the table, as does any node reconnecting.

list_handles reads the Event_Framework's registered cURL handles and list_timers the node registry, which is why a hitchhiker gets a row at all; both measure live state rather than a cached snapshot.

Slow rather than pegged: profile

1. profile on turns on _router's per-node self-time accounting.

2. list_profiles prints the table slowest average first. Times are parent-subtracted, so a node's row is its own work, not its subtree's.

3. profile off.

The Inspector's Profiler modal, in the topology console and the debug overlay's Console tab alike, runs the same sequence in one window: its toolbar button sets profiling in whatever scope the console is cd'd into, and its grid renders that scope's list_profiles rows live.

Uptime resets every ~595 s. That is DEFAULT_MAX_RUNTIME, by design: a worker is an HTTP request that outlives its response and releases its lock before self-respawning.

Across a recycle, the exception subtype alone decides the in-flight message

The cooperative stop lands on whatever message is in flight. Worker_Base::execute() prints the same stopped mid-job (pump) line for both outcomes, so the log settles neither.

Arrives twice: plain Worker_Should_Stop

The cursor stands where it was and the successor replays. A duplicate means the node that finished the message never raised the clean subtype — it carries no Deferred_Clean_Stop bracket, or the chain writes durably with no snapshot node to speak for it and wants cmd <reader>:config assume_clean_shutdown 1.

Vanishes: Worker_Should_Stop_Clean

Commits the cursor past the message. A loss is the opposite error: the clean subtype was raised for a record nothing had forced to disk.

A long job runs twice and its worker's uptime resets underneath it

A peer stole the lock. A handler heartbeats only where it reaches should_continue() — Event_Framework::pump() at a fetch point, or the drain loop between messages — and one that reaches neither for a whole stale_timeout looks dead.

topologies/job-worker.tsl carries var stale_timeout = 600 for exactly that, against the Lock_Node::STALE_TIMEOUT default of 60. A topology whose handlers block longer than its own stale_timeout needs a larger one, or a pump() call inside the handler.
