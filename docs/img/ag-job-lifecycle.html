A job enters through one of three logs, runs once behind a filter, and leaves as stats, a retry or a dead letter

Ten hops from Job_Intake to the jobstats sweep. The before_job filter and the after_job action are the only place a job's context is managed, and the argument order ( $id, $parameters ) is a contract the handlers ship with.

Job_Intake

Import, cron and web processes write here; three logs, one class.

jobs.p<N>

The pool's Topic; a Consumer per partition feeds the worker.

Job_Worker_Node

fill() dispatches by the entry's k.

Handler

A callable from newspack_nodes/job_handlers or …/remote_job_handlers.

Job_Delay · DLQ · stats

Where a job goes when it does not simply finish.

1queue() writes the LOCKED jobintake.p<N>, feed() the unlocked jobfeed.p<N>, and an entry whose not_before (or now + delay) is still ahead parks in jobdelay.p0 instead; the Job_Intake diagram draws the three.
2KEY hashes the entry to one partition, so a keyed handler runs serially behind one Consumer. The entry is k, handler, an optional id (write_job() omits the key when it is null or empty), parameters, ts, plus retries, attempt, batch and key when set — the four DISPATCH_FIELDS a normalizer must overlay rather than rebuild.
3k = 'job' selects local_handlers, which every host's worker runs; k = 'remote_job' selects remote_handlers, which only a hub's worker runs. Both maps load eagerly in the constructor from their filters, since plugins_loaded has fired by topology-evaluation time. An entry whose handler no map owns is dropped.
4apply_filters( 'newspack_nodes/job_worker/before_job', true, $handler, $id, $message ): a filter, so a listener that will not set a context up for a job, one addressed to another host, can decline it. Only an explicit false DECLINES: the handler is skipped, nothing is counted, no batch settles. A listener that THROWS is not a decline — the handler is still skipped, but the batch's error counter, jobs_executed and the cache-flush counter all advance, because the job failed HERE and no other host will run it.
5$id FIRST, because the request context is named for it, and it may be ''. The return value is the outcome: classify_outcome() reads stats.success_count (sentinel -1 when absent) and stats.error_count and nothing else. Errors beside an EXPLICIT 0 successes read error; every other case, a bare return included, reads success. There is no partial, so throwing is the only way to signal failure.
6do_action( '…/after_job', $handler, $id, $outcome ) fires in a finally, for a thrown, a declined and a completed job alike. A completed job's per-identity counters (handler:id, or the bare handler when the id is empty) advance here; a thrown one's advance inside the catch, hop 7. Then every job neither declined nor poisoned counts toward jobs_executed and runs gc_collect_cycles(), and every cache_flush_interval jobs — the node's one positional argument, CACHE_FLUSH_INTERVAL 50 by default, clamped to ≥ 1 — wp_cache_flush(). A declined job counts nothing, and a poisoned one propagates past all three. An entry carrying batch settles its fan-in counter unless it was retried, declined or poisoned; the decrement reaching zero fires newspack_nodes/job_worker/batch_complete and one alerts.p0 row.
7The handler threw. Stats are recorded first, inside the catch, so the run counts in both RUNS_DELTA and ERRORS_DELTA. Worker_Should_Stop is re-thrown at both the listener catch and the handler catch instead, recording no stats, scheduling no retry and settling no batch, so the successor replays the message.
8schedule_retry() re-parks a FRESH entry in jobdelay.p0 at RETRY_BASE_S 30 × 2^attempt seconds, capped at RETRY_MAX_S 3600, carrying handler, id, parameters, key, retries, attempt + 1 and batch. It goes through write_job(), which hardcodes 'k' => 'job': a remote_job comes back local. A failed requeue write falls through to hop 9, because a job must never vanish into a swallowed error.
9Poison. The Consumer dead-letters the entry to its :deadletter sidecar and advances (ADR-12). A poisoned batch member deliberately does NOT settle — the crash lineage re-runs it, and double-settling would miscount.
10The counters are swept into jobstats.p0 as one Jobstats_Record per identity: fields 2..7 are deltas over the record's own ELAPSED_MS, fields 8..11 last-run detail that survives the drain. At N partitions one identity yields N records per sweep, and a quiet identity keeps emitting zero rows for the worker's life.
