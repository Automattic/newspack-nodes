# Newspack Nodes Architecture

A WordPress-internal, message-passing node graph built on WordPress primitives — the options table, WP-Cron, the REST API, nonces and memcache all do real work — rather than a standalone PHP bus. This document describes the substrate; application-level shape lives in the consuming plugin's own architecture guide.

## Overview

Three core ideas:

1. **Nodes** — processing units. Every node has `fill( array $message )` as its only entry point.
2. **Messages** — 7-field arrays carrying a type bitmask, a mint timestamp, a routable path (FROM/TO), an ID, a KEY, and a VALUE.
3. **Drain loop** — Event_Framework picks the soonest pending timer's deadline as its wait timeout, then sleeps on `curl_multi_select` (when cURL handles are registered) or `usleep` (otherwise), and fires expired timers.

```
┌───────────────────────────────────────────────────────────┐
│                      Event_Framework                      │
│  drain():                                                 │
│   - compute timeout = next-timer deadline                 │
│   - if cURL handles: curl_multi_select(timeout) ->        │
│       drain transfers                                     │
│   - else:           usleep(timeout)                       │
│   - handle signals                                        │
│   - refresh Core::$now                                    │
│   - fire expired timers                                   │
│   - loop check (should_continue) at the top of the next   │
│       iteration                                           │
└─────────────────────────┬─────────────────────────────────┘
                          │ on each tick
                          ▼
┌───────────────────────────────────────────────────────────┐
│                         Router                            │
│  fill($message):                                          │
│   - if TO == '': drop_message (unaddressed) + return      │
│   - if FROM > MAX_FROM_SIZE: drop_message + return        │
│   - [head, rest] = explode('/', TO, 2)                    │
│   - target = Core::$nodes_by_name[head]                   │
│   - if !target: send_error NOT_AVAILABLE (TM_ERROR) to    │
│        FROM (set_state NOT_AVAILABLE first)               │
│   - else: TO = rest; target->fill($message)               │
│   - fire_cb tick: notify_timer(), flush_pending_wakes(),  │
│        Core::prune_logs(), trim_profiles()                │
└─────────────────────────┬─────────────────────────────────┘
                          │ fill($message)
                          ▼
┌───────────────────────────────────────────────────────────┐
│                       Node graph                          │
│   ┌────┐    ┌────┐    ┌────┐                              │
│   │ A  │ ──>│ B  │ ──>│ C  │ ──> [terminal]               │
│   └────┘    └────┘    └────┘                              │
│              fan─out via Tee:                             │
│             ┌────┐    ┌────┐                              │
│             │Tee │ ──>│ X  │                              │
│             └────┘    └────┘                              │
│                 │     ┌────┐                              │
│                 └────>│ Y  │                              │
│                       └────┘                              │
└───────────────────────────────────────────────────────────┘
```

## Message Format

```php
namespace Newspack_Nodes;

class Message {
    public const TYPE      = 0;   // bitmask of message types
    public const TIMESTAMP = 1;   // unix SECONDS as a float, microsecond resolution
    public const FROM      = 2;   // path message came from (trace/reply)
    public const TO        = 3;   // path message is going to
    public const ID        = 4;   // unique identifier (ack/correlation)
    public const KEY       = 5;   // routing/partition/grouping key
    public const VALUE     = 6;   // the data
    public const LAST_VALUE_INDEX = self::VALUE;
    public const LOCAL     = 7;   // in-process provenance taint; packed() never emits it
}
```

**Why arrays not hashes**: indexed access is faster than hash lookup in hot paths. Messages flow through every Node in the graph; this is one of the busiest data structures in the runtime.

**Field layout rationale**: TIMESTAMP sits at index 1 so [WHAT + WHEN] groups at the front of the array. KEY/VALUE naming matches Kafka's `ProducerRecord<K,V>`, SQS message attributes, Redis Streams' `XADD key value`. Its UNIT is a cross-port contract rather than a detail — `src/runtime/message.js` mints `Date.now() / 1000` precisely so a message crossing between the browser and PHP compares — and reading it as a microsecond count is off by a factor of a million. PHP stamps the cached per-tick clock `Core::$now`, falling back to `Core::right_now()`, so every message minted inside one drain tick carries the SAME timestamp and a delta between two of them measures nothing.

**Type-flag bitmask** (11 flags):

```
TM_BYTESTREAM = 1;
TM_EOF        = 2;
TM_PING       = 4;
TM_COMMAND    = 8;
TM_STRUCT     = 16;
TM_ERROR      = 32;
TM_INFO       = 64;
TM_REQUEST    = 128;
TM_RESPONSE   = 256;
TM_NOREPLY    = 512;
TM_UNTYPED    = 1024;
```

`TM_UNTYPED` is the mint default `new_message()` stamps: a free high bit matching NO type gate, so a message reaching a sink still carrying it is an untyped-message bug the drop audit names — not a message that is every type at once (what a `-1` sentinel would be).

`TM_NOREPLY` is the fire-and-forget command flag: a `Shell` run with `want_reply( false )` (script / topology-load mode) ORs it onto each command and `Command_Interpreter_Node` then suppresses the routed reply (surfacing only an error to stderr). Without it, a worker's boot-topology command reply routes to `_output/<pid>` — which has no node in a worker — and bounces a dropped `NOT_AVAILABLE` on every startup.

**Convention — `TM_COMMAND` vs. `TM_REQUEST` (which plane is this?).** Two control planes, two types, two destinations. **`TM_COMMAND` is startup & administration**: graph construction (`make_node`/`connect_node`), config verbs, topology load — dispatched by a `Command_Interpreter_Node` (the node's `node_schema()['commands']` verb table; `command_node` / `cmd` in the REPL). **`TM_REQUEST` is runtime triggers & live queries** — things that drive or interrogate an *already-running* graph. The substrate ships three: `GET_LAG` (Consumer/Tail: bytes and segments behind the source tail), `GET_HEALTH` (Job_Worker: memory, handler counts, cache-flush progress) and Table's `GET <key>`, which answers the value or a `NOT_FOUND` TM_ERROR. Table is the one that declares no `requests` in its `node_schema()`, so its verb exists on the wire while `help Table` and the console Inspector show none. A request is handled in the addressed node's **own `fill()`** (branch on `$type & TM_REQUEST`, do the work, reply `TM_STRUCT | TM_RESPONSE` to `TO = $message[FROM]`), declared under `node_schema()['requests']`, and fired from the REPL with `request_node <node> <VERB>`. `Consumer_Node::handle_request` is the canonical substrate example. The rule of thumb: if it runs once at build time, it's a command; if it fires against a live graph, it's a request — so a *runtime trigger is never a `cmd_*` verb*.

Flags compose via bitwise OR: `TM_COMMAND | TM_RESPONSE` = a response to a command. Receivers check via `&`: `if ( $type & TM_COMMAND ) { ... }`. **Never use strict `===`** on combined flags — it misses every combination.

**ONE shape, everywhere**: the positional indexed array IS the message — in PHP, in JS (`src/runtime/message.js` exports the same indices/flags), in memory, and on the wire. There is **no** `{ type, ts, from, to, id, key, value }` object form anywhere; if you see one it's a bug. `LOCAL` at index 7 is the single exception and proves the rule: it is appended *after* the canonical seven, and `packed()` / `pack()` slice it off, so it cannot cross a process boundary (see [Command authorization](#command-authorization-two-tier)).

**Wire format**: `Message::packed( array $message ): string` JSON-encodes the canonical seven under `JSON_UNESCAPED_SLASHES | JSON_INVALID_UTF8_SUBSTITUTE`, falling back to `wp_json_encode`; `Message::unpacked( string $data ): array` is `json_decode`. The in-memory indexed array is the wire representation, so there's no key-to-index translation per side. `packed()` never returns an empty string — a residual encode failure logs the reason to stderr and substitutes a self-describing TM_ERROR frame, because an empty frame surfaces as a shape error three steps from its cause. Substituting a bad UTF-8 byte rather than failing the encode is what keeps a latin1 column in a logged SQL string from voiding the whole record. The two ports differ on malformed input — a documented divergence:

- **PHP** `unpacked()` accepts ONLY `count() === 7 && array_is_list()`. Anything else **throws** `InvalidArgumentException`. Callers that read off-disk lines catch it: `Durable_Reader::forward_line` quarantines the bad line to the `:deadletter` sibling and advances, and `Partition_Node::last_frame_of` — the offsetlog resume behind `read_last_offsetlog_frame()` — logs it and hands back null, so the reader starts with no durable cursor.
- **JS** `unpack()` accepts `Array.isArray && length >= 7`, truncating to the canonical seven; anything else (including a JSON parse error) yields a fresh `newMessage()` — never a throw.

**Message constructors**:

```php
$m = Message::new_message();
$m[ Message::TYPE ]  = Message::TM_BYTESTREAM;
$m[ Message::KEY ]   = '/some-url';
$m[ Message::VALUE ] = $line;
$node->fill( $m );
```

There is no parallel `write()` / `produce()` / `query()` API on any node — `fill()` is the only way a message enters a node.

Three more statics round out the class. `packed_size()` measures a packed frame against `MAX_LINE_SIZE` (the JSON alone, so a caller sizing a written record adds one for Partition's newline). `type_labels( int $type ): list<string>` names every flag set, in the one order both ports render; an empty result is the caller's to name, and the drop audit calls it `TYPE_UNKNOWN`. Rendering a mask as one line is not the caller's, though: `Dumper_Node::format_type_flags( int $type )` is the public static that joins the labels with ` | ` and names a mask no label matches `TM_UNKNOWN(0x<hex>)`. It is shared surface rather than display-local — `Dead_Letter_Queue`'s `dl_show` builds its `type_flags` field through it — so a new surface that has to show a TYPE calls it instead of re-joining the labels itself. `split_first( string $path ): [ head, remainder ]` takes a leading path segment, and is what everything reading a node path off a message goes through — `Router::send_error`'s naming of the missing node, the `Fanout_Targets` liveness prune, `Settings_Sync`'s target head, the `HTTP_Filter` pid gate. It splits on `/` alone, which is what makes the `_sse:<pid>` reply address work: the colon keeps the pid inside ONE head segment for the gate to compare whole, where an `_sse/<pid>/<node>` spelling would leave the head a bare `_sse` and drop every attached-worker reply with no diagnostic. The browser composes that same string independently in `src/runtime/remote-ipc-node.js`, and no shared constant spans the two ports, so the separator is convention rather than something a compiler holds. A second definition of what a path is belongs nowhere else. (`Router::fill` inlines the same `explode( '/', $to, 2 )` on the hot dispatch path.)

## Node Base Contract

A node connects two ways: **`sink`** is the physical next node `fill()` forwards to; **`target`** is a logical path string stamped into `message[TO]` when TO is empty (the message's logical `owner`). **There is NO `edge`** — the second physical output some node graphs carry is intentionally absent here; don't look for one.

```php
class Node {
    public const MAX_FROM_SIZE = 1024;
    public const REDACTED      = '<redacted>';

    protected string $name = '';
    protected ?Node  $sink = null;
    protected $target = '';      // string for single target; array for Tee fan-out
    protected int $counter = 0;
    protected int $bytes_read = 0;
    protected int $bytes_written = 0;
    protected int $largest_msg_sent = 0;
    protected int $debug_state = 0;        // 0/1/2 trace level
    protected array $registrations = [];   // events declared in node_schema()
    protected array $set_state = [];       // cached set_state payloads
    protected array $arguments = [];       // constructor tokens, list<string>
    protected ?Node $patron = null;        // set = plumbing; hidden from the canvas
    protected ?Command_Interpreter_Node $interpreter = null;

    public function fill( array $message ): void;
    public function arguments( ?array $args = null ): array;
    public function sink( ?Node $node = null ): ?Node;
    public function target( $value = null );
    public function display_targets(): array;    // routed targets plus declared-only ones (ADR-19)
    public function connect_node( string $target ): void;     // sets target (Tee appends)
    public function disconnect_node( string $target = '' ): void;
    public function name( ?string $name = null ): string;
    public function patron( ?Node $node = null ): ?Node;      // set BEFORE name(), or it refuses
    public function remove_node(): void;
    public function counter(): int;
    public function bytes_read(): int;
    public function bytes_written(): int;
    public function largest_msg_sent(): int;
    public function debug_state( ?int $level = null ): int;

    public function stamp_message( array &$message, string $name ): bool;
    public function drop_message( array $message, string $error ): void;
    public function stderr( string $text ): void;
    public function print_less_often( string $text, string ...$extra ): void;
    public function log_midfix( ?string $text = null ): string;

    public function dump_node(): array;       // state snapshot for the `dump_node` verb
    public function dump_config(): string;    // round-trippable make_node line
    public function dump_metadata(): array;   // console/canvas manifest
    public static function node_schema(): array;
    public static function serialize_args( array $tokens ): string;
    public static function serialize_arg( string $token ): string;
    public static function command_line( string ...$tokens ): string;
    public static function target_list( $value ): array;

    public function register( string $event, string $listener, ?callable $cb = null ): void;
    public function unregister( string $event, string $listener ): void;
    public function notify( string $event, mixed $payload = '' ): void;
    public function get_state( string $event ): ?string;
    public function registered_listeners(): array;
    protected function set_state( string $event, string $payload = '' ): void;
}
```

**Default `fill()`** stamps TO from `target` (only when TO is empty), counts, then forwards:

```php
public function fill( array $message ): void {
    $sink = $this->require_sink();   // throws 'fill requires a wired sink'
    if ( '' === $message[ Message::TO ] && \is_string( $this->target ) && '' !== $this->target ) {
        $message[ Message::TO ] = $this->target;
    }
    ++$this->counter;
    $sink->fill( $message );
}
```

Subclasses override with their actual behavior, and every one that forwards through `parent::fill` inherits the stamp — Hook, Grep, Echo, Log, Table, Age_Sieve, Value_Timeout, the JSON pair, Dumper's `emit()`, Tail's `forward_line()` and Consumer's own `fill()`. Two families never reach it, for opposite reasons. Three primitives emit without it: `Shell` addresses each message it mints itself, from the cwd `prefix()` builds; `Callback` hands the message to a closure instead of a sink; and `Durable_Reader::forward_line()` — the read path Consumer and `Remote_Source` share — stamps TO from `target` itself and fills the sink directly. The terminals emit nothing at all: `Null`, `Stdout` and `Stderr` count the message and stop there, so they never call `require_sink()` and are legal at the end of a graph with nothing wired downstream.

**`stamp_message`** prepends `$name` to the message's FROM with a `/` separator:

```php
$message[ Message::FROM ] = $from === '' ? $name : ( $name . '/' . $from );
```

It returns false — and the caller must drop the message — two ways: when the new FROM would exceed `MAX_FROM_SIZE = 1024`, which is what stops a cycle from growing the trail, and when `$name` is empty (mid-construction or post-rename), which would compose a `/from` path Router cannot resolve. Both log through `print_less_often`.

**Name registration**: `$node->name('foo')` registers the node in `Core::$nodes_by_name`. Renaming throws on collision (catches duplicate-node bugs at construction time), and a node that owns siblings cascades the new name to them (`Consumer` renames its `:source`, `:offsetlog`, `:deadletter` and `:config` nodes). Two more guards shape what a caller may ask. An empty name throws `name() requires a non-empty name; use remove_node() to unregister`, because a node left registered under no name is unreachable and leaving the registry is `remove_node()`'s job alone. Re-setting the name the node already answers to returns early instead of colliding with itself, which is what makes a topology reload and a `move_node` that re-spells a node to its current name idempotent. `check_name_availability()` pre-checks every slot the rename will touch — each owned sibling first, the auto-wired `:config` interpreter last, then the node's own — so a collision throws before anything is unregistered or moved. Pre-checking rather than unwinding is sound only because `Core::$nodes_by_name` is a per-process array mutated synchronously; an out-of-process registry would make it TOCTOU and bring the unwind back.

**Owned siblings** are a private slot map only `publish_sibling( $kind, $sibling )` and `retract_sibling( $kind )` write, and only four cascades read — the collision pre-check, the rename, the sink cascade and the teardown. Publishing IS declaring: a sibling built in a constructor is enrolled the moment it exists and takes the name `{patron}:{suffix}` when the patron takes one. `Partition` publishes `lock` and `heartbeat`, `Topic` publishes one `p{N}` per partition, `Consumer` publishes `source`, `Durable_Reader` publishes `offsetlog`, `Dead_Letter_Queue` publishes `deadletter`, `Remote_Link` publishes `sse-in` / `http-out` / `null`, and `Schema_Reflection` publishes the auto-wired `config` interpreter. `patron()` must be set BEFORE `name()` and refuses otherwise — it is both the interpreter's drop and the canvas-visibility flag.

Publishing into an OCCUPIED slot is refused rather than silently overwritten: `publish_sibling()` throws `sibling slot occupied: {$kind}; retract_sibling() to replace it`, because the displaced sibling would stay registered and keep whatever handle it opened while no cascade could still reach it. A builder that means to REPLACE calls `retract_sibling( $kind )` first, and the naive idempotency guard is therefore wrong — re-publishing on a second `arguments()` replay throws instead of swapping. Publishing is atomic on failure too: when `set_sibling_names()` refuses the composed `{patron}:{suffix}` name, the slot is emptied again before the exception propagates, so a caller's own guard rebuilds rather than serving a half-published sibling.

The two sidecar Partitions are built once, by the `Sidecar` trait: `make_sidecar( $dir, $geometry )` constructs a patron-linked `Partition_Node`, copies the patron's sink, and opts it out of write-stall quarantine. `Durable_Reader` reaches it for the offsetlog and `Dead_Letter_Queue` for the quarantine — an empty `$dir` disables either. Spell out every position of the geometry: an omitted `segment_size` or retention axis does not fall back to something sidecar-appropriate, it resolves to the operator's general `<config:*>` default and hands the sidecar whatever retention was picked for the data partitions. Both current callers name all six for that reason.

**Drops leave one audit line.** `drop_message( $message, $error )` names the type flags (or `TYPE_UNKNOWN`), FROM, TO and — for TM_INFO, TM_REQUEST, TM_ERROR and TM_COMMAND — the payload, with credential-named keys and `--auth_password=…` tokens replaced by `Node::REDACTED`. `NOT_AVAILABLE` prints unprefixed; every other reason gains `WARNING:`. The line goes through `print_less_often`, keyed on the reason and the type flags so a recurring drop cannot flood; the FROM/TO/payload tail rides unkeyed.

**One redaction vocabulary, pinned across both ports.** `Core::SECRET_NAME_PATTERNS` holds the eight substrings that name a credential — `password`, `passwd`, `secret`, `token`, `credential`, `api_key`, `apikey`, `private_key` — and `Core::is_secret_property()` matches them anywhere in a lowercased name. Bare `auth` is deliberately absent, so `auth_username` and `authorize` stay readable. That predicate is the one rule every redactor asks. `dump_node()` masks a non-empty secret-NAMED property whole and leaves an empty one visible, because its absence is state; `Node::redact_secrets()` catches the two shapes a secret takes elsewhere — an array key at any depth, and an `--auth_password=…` argument token, which is how the Vault admin UI sends one — keeping the name and replacing only the value with `Node::REDACTED`. `src/runtime/core.js` keeps a byte-identical list behind `Core.isSecretProperty()`, which the browser's `dump_node` mirror and the console's localStorage writer both ask; the console matcher additionally ends a value at its QUOTING rather than at the first space, since `Node::serialize_args()` quotes a passphrase whole. Adding a ninth pattern to one port leaves both internally consistent and one of them storing cleartext, so `src/topology-console/core/__tests__/secretPatternsParity.test.js` parses the PHP list out of `includes/class-core.php` and fails unless the two match exactly, in order — pinning the `REDACTED` marker to `Node::REDACTED` the same way. It is the same two-halves-of-one-contract arrangement as [`Node_Names` and `reserved-node-names.json`](#topologies-tsl).

**Pre-declared events**: a subclass lists every event it emits under `node_schema()['registrations']`, and the base constructor's `seed_registrations()` turns that list into the runtime allow-list. `register()` throws on an undeclared event — the declared list is the publishing node's contract surface.

`seed_registrations()` reads `static::node_schema()['registrations']`, and a subclass's `node_schema()` REPLACES its parent's rather than merging into it. So an override that omits `\array_merge( parent::node_schema(), … )` starts life with an empty allow-list, and any later `register( 'FIRE', … )` on it throws. Dropping the merge is sometimes the point: `Connect_Queue_Timer_Node` sheds both halves of what `Timer_Node` declares — the `interval_ms` positional, because its cadence is the `INTERVAL_MS` constant, and the `FIRE` registration, because its `fire()` notifies nothing.

## Router

`Router` extends `Timer`. Both ports override `fire_cb` to run `notify_timer()` — a **DIRECT `fire_cb` dispatch** to every TIMER-registered node (`Router::fire_cb → notify_timer`). This is the **Router-hitchhike pattern** for cheap periodic work without per-node Event_Framework slots. The override is necessary because the Router has no sink, so it can't fall through `Timer_Node::fire_cb`'s no-sink guard. (`Worker_Base::build_scaffolding()` arms it via `$router->set_timer( Router_Node::DEFAULT_TICK_MS )` = 1000ms; without that the TIMER channel never fires, which is why a request-scope or REPL graph builds a Router and never ticks one.) `notify_timer()` walks a snapshot of the names in `registrations['TIMER']`, resolves each to a live node, and calls its `fire_cb()` directly — no message, no `fill()`; a name with no live node is warned and dropped (forgot to unregister), and a registrant that isn't a `Timer_Node` is skipped rather than fataled, because one misregistration must not take down every other hitchhiker.

Three chores ride the same tick, which is the one fixed cadence a worker already pays for: `Partition_Node::flush_pending_wakes()` wakes on-demand readers once per process instead of once per partition write, `Core::prune_logs()` re-windows the rate limiter so a recurring warning eventually prints again, and `trim_profiles()` drops idle profile entries while profiling is on. The PHP tick also warns while `Core::$secure_level` is 0 — a command surface exists and nobody has declared a policy for it — through that same rate limiter, so the line repeats about once a minute rather than on every tick (see [Secure levels](#secure-levels)).

Nothing guards any of it in PHP. `fire_cb()` runs `notify_timer()` first and wraps it in no `try`, so a hitchhiker whose `fire()` throws takes the whole tick with it: every registrant later in the walk goes unfired, all three chores are skipped, and the throw unwinds out of `Event_Framework::drain()` into `Worker_Base`, which catches only `Worker_Should_Stop`, so the worker exits and respawns. The JS Router differs, wrapping `notifyTimer()` in a `finally` that still runs `http.flush()` and `trimProfiles()`. The rule for anyone writing a hitchhiking `Timer_Node` subclass is therefore that `fire()` must let nothing but `Worker_Should_Stop` escape; `Fleet_Node::fire()` is the worked example.

`Router::fill()` (PHP) drops an unaddressed message first, then peels the head segment and dispatches:

```php
public function fill( array $message ): void {
    ++$this->counter;
    if ( '' === $message[ Message::TO ] ) {
        $this->drop_message( $message, 'message not addressed' );
        return;
    }
    // FROM is MEASURED here, not trusted: a message off the wire was
    // stamped in another process, where stamp_message()'s guard never ran.
    $from = Core::as_string( $message[ Message::FROM ] ?? '' );
    if ( \strlen( $from ) > self::MAX_FROM_SIZE ) {
        $this->drop_message( $message, 'path exceeded ' . self::MAX_FROM_SIZE . ' bytes' );
        return;
    }
    $parts     = \explode( '/', Core::as_string( $message[ Message::TO ] ), 2 );
    $node_name = $parts[0];
    $remaining = $parts[1] ?? '';                        // '' when TO is a bare name
    $target    = Core::$nodes_by_name[ $node_name ] ?? null;
    if ( null === $target ) {
        $this->send_error( $message, 'NOT_AVAILABLE' );  // set_state NOT_AVAILABLE + bounce TM_ERROR to FROM
        return;
    }
    $message[ Message::TO ] = $remaining;
    // With `profile on`, a stack frame brackets the dispatch below.
    $target->fill( $message );
}
```

`send_error()` fires `set_state( 'NOT_AVAILABLE', … )` (so observers see the miss even when there is no FROM to reply to), with the flat `KEY VALUE` payload a TM_INFO listener expects: `NODE`, `TYPE`, `FROM`, `TO`, `ID`, `KEY`. Then — unless the message already carries `TM_ERROR`, and only when FROM is non-empty — it builds a TM_ERROR (VALUE `"NOT_AVAILABLE\n"`, TO=FROM, FROM=the failed TO, ID copied) and re-fills it through this same Router so the error walks the FROM trail back. A `handling_error` guard breaks recursion (an error about an error is dropped via `drop_message`).

**Empty-TO drop, both ports.** Both PHP and JS drop an empty-TO message up front via `drop_message( $message, 'message not addressed' )` — there is no PHP-bounce-vs-JS-forward divergence here. The JS Router (`src/runtime/router-node.js`) does the identical thing; it also has no sink (the `set sink` setter throws on any non-null value, the getter always returns null). PHP is the stricter of the two: `Router_Node::sink()` gates on `func_num_args()`, so ANY argument throws `InvalidArgumentException` — `$router->sink( null )` throws where JS accepts null. That is why `_router` can only be placed by `new Router_Node()`, as `Worker_Base::build_scaffolding()` and `Bootstrap::mount_request_graph()` both do. `Command_Interpreter_Node::make_node()` ends its construction sequence with `$node->sink( $this )`, so a `make_node Router <name>` line in a `.tsl` throws and the catch removes the half-built node, and `set_sink _router <target>` at the REPL throws the same way.

**The bounce itself does diverge.** PHP reads the original TO before peeling it, so the TM_ERROR it sends back carries FROM = the path that failed to resolve, and the miss is published as the flat `NODE TYPE FROM TO ID KEY` string a TM_INFO listener expects. JS peels TO into the remainder first, stamps the bounce's FROM with the Router's own name, and publishes NOT_AVAILABLE as a two-field `{ node, from }` object. A browser-side recipient of the TM_ERROR therefore learns only that `_router` refused; which destination went missing survives in the state payload's `node` field and nowhere else.

Routing is path-based (`a/b/c` → "find node `a`, pass remaining path `b/c`"), not socket-based. Replies use the `TO=$message[FROM]` convention to walk back along the breadcrumb trail. Both ports increment `counter` on the recursive NOT_AVAILABLE re-fill, so one inbound miss bumps the counter by 2 (intentional, matched across ports).

**Dispatch profiling** is off by default and costs nothing while off: `Router_Node::profiles()` is null, and `fill()` takes the plain dispatch branch. The `profile [ on | off ]` verb flips it; while on, each dispatch is bracketed by a stack frame whose elapsed time is subtracted from its parent, so the table reports **self** time per node. Read it with `list_profiles [-s] [ <regex glob> ]` (slowest average first, plus a `--total--` row); `-s` returns those same rows as a struct for a view that wants to sort them. Entries idle longer than `PROFILE_TTL_S = 900` are trimmed on each tick.

The two reads that bracket a dispatch are bare `\microtime( true )`, deliberately never `Core::right_now()`: `right_now()` assigns `Core::$now`, and un-freezing the cached per-tick clock mid-dispatch would move the timestamp on every message minted downstream of the profiled node — the same mechanism `Event_Framework::pump()` uses on purpose. `trim_profiles()` takes the opposite side and measures idleness against `Core::$now`. The seam over those two dispatch reads alone is `Router_Node::$clock`, a `public static ?\Closure` of signature `function (): float` that tests assign to script an exact elapsed sequence; it never stands in for the trim sweep, and `src/runtime/router-node.js` mirrors the split with `RouterNode.clock` over `Core.now()`. Normalising the bare `microtime` onto the codebase's standard clock accessor would silently shift message timestamps whenever profiling is on.

`Router_Node::$profiles` and `$profile_stack` are static, mirroring `Router.pm`'s package-global `$PROFILES` / `@STACK`, so the table belongs to the PHP PROCESS rather than to any Router instance: it survives a Router being removed and rebuilt, and every Router in the process shares one table. That decides where profiling is useful. Enabled inside a worker — `wp nodes cli <type>.p<N>`, or a console whose cwd is that worker — it accumulates for the worker's whole life. Enabled against the request-scope graph `Bootstrap::mount_request_graph()` builds for `POST /newspack-nodes/v1/command`, it covers one request's process and is gone before the next, so the toggle appears not to stick and `list_profiles` comes back with nothing but `--total--`. The console's toggle reads its truth from `dump_metadata`'s `_header.profiling` key, which is `null !== Router_Node::profiles()` in whichever process answered.

**NOT_AVAILABLE drops log via `Node::drop_message`, not Router.** `Router::send_error` builds the NOT_AVAILABLE error inline and logs nothing itself; the audit line appears wherever `drop_message` IS called, in the shape [Node Base Contract](#node-base-contract) describes.

**TIMER hitchhike, both ports.** PHP's Router fires its tick on the Event_Framework-driven `set_timer`. The JS Router (`src/runtime/router-node.js`) has no drain loop, so it **self-starts** its own slot in the constructor via `setTimer( ROUTER_TICK_MS )` (1000ms — the Router IS timer-driven) and its `fireCb` brackets `notifyTimer()` with `http.lock()` and `http.flush()` — locking `HttpOut` before and flushing after — so every emission a tick produces (each subscriber's poll) batches into ONE `/command` POST. The Router looks `_http` up itself, so batching is a property of having a graph rather than of which hook happened to mount; `_http` is only ever mounted by `mountExospine` as an `HttpOut`, and flushing an empty buffer costs no request. Tests that don't want the slot running call `stopTimer()`.

**TIMER subscribers batch.** Both `_metadata` and `_uptime` register against the Router's TIMER channel rather than running their own intervals. `_metadata` polls `dump_metadata` on a cadence it scales to the graph it last parsed — `computePollIntervalMs()` rounds `nodes × 10ms` to the nearest five seconds and floors it at five — and `_uptime` polls `uptime` every 5 seconds. Every metadata cadence is therefore a multiple of the uptime one, and both ride the shared wall-clock grid, so a metadata tick always coincides with an uptime tick and the two leave in ONE POST. The bracket lives in the Router itself, so a dashboard that never heard of it still batches.

## Storage: Topic + Partition

### Partition

One file-segmented append-only log, with an optional `.idx` companion. Storage primitive AND Node: `Log` extends it, `Topic` fans into N of them, and a worker's IPC is one, so every producer in the runtime reaches disk through this class.

```php
$p = new Partition_Node();                              // no-arg ctor; config is positional via arguments()
// Token order matches node_schema()['arguments']; max_segments precedes the two lifetimes.
$p->arguments( [ $partition_dir, $segment_size, $min_segments, $num_segments, $max_segments, $min_lifetime, $lifetime ] );
$p->fill( $message );                                   // ONLY ingress — no write()/produce()
$p->flush();                                            // land the in-memory batch now
$p->read_at( $segment_id, $offset, $length );           // read bytes
$p->read_message_at( $segment_id, $offset, $length );   // …unpacked to a Message; null if torn
$p->read_many( $positions );                            // batch of {segment, offset, length}
$p->locate_by( $extract, $wanted );                     // index walk behind a Table's backed_by (ADR-18)
$p->scan_index( fn ( $line, $seg ) => ..., $newest_first );
$p->index_mtimes();                                     // segment id => last .idx append time
$p->get_segments( $force_refresh );                     // [{id,size}, ...] sorted by id
$p->get_segment_path( $segment_id );                    // absolute {dir}/{seg}.log
$p->truncate_after( $segment_id );                      // drop everything past a rewind point
$p->requeue_deadletter( $locator );                     // REFUSED: replay with wp nodes ingest
$p->allow_large_writes();                               // 4KB -> 32MB; acquires a Lock
$p->void_warranty();                                    // 4KB -> 32MB; NO lock (caller asserts single-writer)
$p->without_write_deadletter();                         // sidecars opt out of write-stall quarantine
$p->with_index( $formatter );                           // opt in: JSONL .idx line formatter
$p->with_index_named( $formatter_name );                // …the round-trippable form
```

**Indexing is opt-in via `with_index( $formatter )`.** Without a formatter no `.idx` file is created or written at all — the `.log` segments stand alone. `with_index()` installs a per-line formatter `fn(array $message, array $position) => string|null` — it receives the unpacked 7-field Message and `{segment, offset, length}`, never the serialized line; each write whose formatter returns a non-empty string appends that string as one JSONL line to the segment's `.idx` (return `null`/`''` to skip the entry). `with_index_named( $name )` is the round-trippable form: it resolves a registered `Formatters` name, which is what `dump_config()` emits and what a Topic propagates to every partition it materializes. `scan_index( fn ( $line, $seg ) => ..., $newest_first )` walks those JSONL entries (a no-op when no formatter is set), and `read_at( $seg, $off, $len )` seeks into the `.log` using positions the formatter recorded. `index_mtimes()` returns segment id => the `.idx` file's last-append time, which is the one clock a reader owns: an index line carries a producer's timestamp, and on a hub the producers are many. It stats fresh rather than caching, because a warm list would report a filling segment as closed, and it omits any segment whose index cannot be stat'd — the same segments `scan_index()` skips. There is no default binary index format — indexing always goes through `with_index`/JSONL.

**`Formatters` is the name registry `with_index_named()` resolves through.** TSL has no closure syntax, so a plugin calls `Formatters::register( $name, $cb )` and a topology line addresses the callable by name. Registrations are per-process static state, so they belong at plugin load: every process that parses a topology or dispatches a verb — worker, REST, CLI — makes them for itself. `resolve( $name )` answers the callable or null, and each caller words its own refusal — the `with_index` verbs raise `unknown formatter: <name>`, `with_index_named()` returns false. `list_names()` is what `Classes_CI` publishes as the topology console's picker for a `formatter_name` argument — a worker-facing picker only, since the browser runtime keeps no registry to mirror and `useJsCatalog` answers `formatters: []`, so the same argument on a node built in the browser-local graph or the debug overlay offers nothing to select. `reset()` empties the registry for tests sharing a process. The registry checks no signature: a companion-index formatter must satisfy `fn(array $message, array $position): ?string`, and that contract belongs to whoever resolves the name. Registration is last-wins in one flat namespace no plugin scopes — `register()` overwrites whatever held the name, with no warning and no return value — so two plugins choosing one name resolve to whichever registered last and the loser's partitions silently write the winner's index rows. Prefix the name the way event-logger-nodes does (`request-index`, `flame-index`, `stats-index`). The same rule cuts the other way and is why registering at plugin load is safe: re-registering an identical name costs nothing.

**There is NO `Partition::write()` method** — the only way bytes enter a Partition is `fill()`, which packs the whole message via `Message::packed()` (+ `"\n"`) and appends to the current segment. All TYPE flags pass through — Partition is a generic transport including control messages (TM_REQUEST, TM_ERROR, TM_EOF). The attached-cli IPC pattern relies on this: cli ↔ worker round-trips drain markers (TM_EOF), error responses (TM_COMMAND|TM_ERROR), and introspection requests (TM_REQUEST) through Partition-as-bus. Data partitions like firehose only ever see TM_BYTESTREAM / TM_STRUCT in practice, so the broader contract is a no-op for production paths.

**Three statics read a directory with no live node**, for a dashboard or a CLI verb holding a path and nothing else. `read_latest_value_at( $offsetlog_dir )` returns the newest committed checkpoint — the last non-empty line of the newest segment, unpacked to its VALUE — or null when the dir is empty or unreadable; `last_frame_of()` is that read against an already-built Partition, falling back one segment when the newest was rotated but never written. `read_latest_snapshot_cache( $offsets_dir, $glob, $node )` fans it across every dir the glob matches and concatenates their co-committed snapshot items into one list, skipping a dir whose cache is missing or misshapen. `read_tail_frames_by( $dir, $key_field, $max_bytes )` indexes the newest segment's last 128 KiB by a VALUE field and returns each key's latest record beside the Message TIMESTAMP it was written at, which is what tells a reader whether the producer is still reporting. It reads that segment alone, so it answers "currently active", never a historical sweep.

**Class-API contract**:

`new Partition_Node()` and `new Topic_Node()` MUST be safe to call from request-scope code without an Event_Framework running. Specifically:

- No `set_timer` from constructor (silent leak: registers in Event_Framework, never fires).
- No `Core::node()` lookup during construct.
- No `scandir` in constructor (eager scandir × N partitions × every request burns syscalls).
- No `$this->name()` from constructor (`Command_Interpreter_Node::make_node` owns naming).
- File handles open lazily on first `fill()` / `read_at()`.

The one thing the constructor DOES build is the sibling `{name}:config` interpreter, via `Schema_Reflection::auto_wire_interpreter()` — pure object construction from `node_schema()['commands']`, no registry lookup and no I/O. It stays unnamed until the node itself is named, and `name()` then cascades.

**`hash_to_partition`** is the canonical partition-routing function:

```php
public static function hash_to_partition( string $key, int $num_partitions ): int {
    [ $stripped ] = explode( '?', $key, 2 );             // strip query string
    return ( crc32( $stripped ) & 0x7FFFFFFF ) % $num_partitions;  // 31-bit mask
}
```

Topic and any other partition router MUST call this same function. Diverging hash families across producers means the same key routes to different partitions and breaks ordering.

**Three-rule retention**: `cleanup_segments` prunes oldest-first above a hard floor of 2 segments when ANY rule fires — the **age rule** (older than `lifetime`, keeping at least `min_segments`), the **count rule** (more than `num_segments`, keeping anything younger than `min_lifetime`), or the **hard cap** (more than `max_segments` — UNCONDITIONAL; `min_lifetime` does not protect, only the floor of 2 does, so a hot partition full of young segments can't grow past it; `0` derives to `2 × num_segments`). Low-traffic partitions may still retain segments for days under the age/count floors — documented behavior, not a bug.

**The declared geometry is not always the enforced one.** Before any rule runs, `arguments()` normalizes the three counts UPWARD in order: `min_segments` rises to `MIN_SEGMENTS_FLOOR = 2`, `num_segments` then rises to that `min_segments`, and `derive_max_segments()` raises an explicit `max_segments` to `num_segments` (or, at the `0` sentinel, derives `2 × num_segments`). So `num_segments 1` runs as 2, and a line declaring `min_segments 5 num_segments 3 max_segments 4` runs as 5 / 5 / 5. An operator sizing disk off a TSL line therefore gets a smaller answer than the code applies; `derive_max_segments()` is public precisely so the admin and CI ceiling displays agree with `cleanup_segments()`, and it is the one authority on what the hard cap actually is.

**`SEGMENT_CACHE_TTL = 0.25` seconds**: segment-list cache so back-to-back reads don't `scandir` per call. Readers may see stale segment lists for up to 250ms after rotation. Consumer's checkpoint logic must tolerate this. A partition that lifted the write cap serves its cache warm without the TTL — no peer can change the directory behind a single writer. Cutting the other way, `maybe_rescan_segments()` re-reads the directory at most once per `DRIFT_RESCAN_INTERVAL_SECONDS = 1.0` and follows a peer's rotation, so a multi-writer log recovers from the TOCTOU window instead of appending to a superseded segment.

**`MAX_LINE_SIZE = 4096`** (PIPE_BUF) caps default writes; the size check is on the FINAL packed bytes (envelope + `"\n"`), not VALUE alone. `allow_large_writes( int $max_wait_ms = DEFAULT_LOCK_WAIT_MS, int $debounce_ms = 0 )` lifts to `MAX_LARGE_LINE_SIZE = 33554432` (32MB) AND takes a `Lock` at `{partition_dir}/write.lock.d/`, blocking up to `max_wait_ms` — `DEFAULT_LOCK_WAIT_MS = 15000` (15s), sized for an EXTERNAL writer with no worker lease and no loop to retry from: long enough to ride out a live writer's burst, short enough that a web request never hangs on one. It deliberately does NOT outwait a crashed predecessor's lock, which only becomes stealable once its heartbeat ages past `LOCK_STALE_TIMEOUT_SECONDS = 60`; a topology worker passes 0 (try-lock) or a debounce window and retries on its next tick. The optional second arg picks the locking mode: **hold mode** (`$debounce_ms = 0`, the default) acquires the Lock up front and holds it for the partition's lifetime; **debounced mode** (`$debounce_ms > 0`) does NOT acquire up front — `fill()` grabs the lock at the start of a write burst and `fire()` frees it after `$debounce_ms` of quiet, so a partition that writes large lines only intermittently doesn't monopolize the lock between bursts. **There is NO `with_lock()` wrapper.** A held Lock is kept fresh two ways instead: inside a running event loop a heartbeat `Timer` (`{name}:heartbeat`, KEY=`heartbeat`) sinks into the Lock and refreshes it; in request scope (no drain) `fill()` drives the heartbeat inline (at most once per `stale_timeout/3` s) and throws if `Lock::heartbeat()` reports the lock was stolen. `void_warranty()` lifts the same cap with NO lock on the caller's assertion that it is the sole writer — see [ADR-4](architecture-decisions.md#adr-4-pipe_buf-atomic-writes) for which form to pick. Single-writer partitions writing >4KB payloads lose data silently (oversize drop) without one of the two opt-ins.

**A short write is quarantined, never swallowed.** The `File_Writer` trait's `write_all()` returns the bytes that actually landed rather than a success flag, retrying a refused write until `MAX_WRITE_ATTEMPTS = 5` is spent so a full disk cannot spin the single-threaded drain loop. `recover_write_stall()` truncates the partial record off the segment — a torn record would desync every reader after it — then dead-letters every message that didn't land in full to `{base}/deadletter/{dir-under-base,dotted}`, replayable via `wp nodes ingest`. A failed segment open takes the same path. Sidecars (offsetlogs, the quarantine partitions themselves) opt out via `without_write_deadletter()`: a quarantine that quarantines into a quarantine chains forever on a full disk. Partition overrides `requeue_deadletter()` to refuse — the trait's version redelivers to the node's SINK, and a Partition's sink is `_command_interpreter`, so a replay would hand an unwritten data record to the interpreter and lose it, so `dl_requeue` is never the replay path here.

**Per-partition batching.** `fill()` packs the message and appends it to an in-memory `$batch` string. If adding the new packed bytes would push the batch over `MAX_LINE_SIZE` (4KB), the existing batch flushes FIRST and the new message starts a fresh batch — preserving PIPE_BUF atomicity per syswrite. Each batched `fill()` also arms a 0-delay one-shot timer via `set_timer(0, true)`; when the event-loop iteration finishes, `fire()` calls `flush()` to land whatever's still accumulated. `__destruct()` also flushes, so request-scope writes land before GC.

Messages larger than 4KB (only reachable on `allow_large_writes` partitions) bypass the batch entirely — they're already over PIPE_BUF so batching can't shrink them. The held write Lock serializes them with batched small-message flushes.

`Topic::flush()` walks every materialized Partition and calls `Partition::flush()` on each. Callers handing off to a subprocess that writes to the same partition path use this to land pending writes before forking, so the parent's accumulated messages land on disk in source-order with the child's appends.

### Topic

Multi-Partition wrapper. Hashes KEY to partition, falls back to round-robin when KEY is empty.

```php
$t = new Topic_Node();                                 // no-arg ctor; config is positional via arguments()
// dir_template carries a {partition} token, substituted with each index 0..N-1.
$t->arguments( [ $dir_template, $num_partitions, $segment_size, $min_segments, $num_segments, $max_segments, $min_lifetime, $lifetime ] );
$t->fill( $message );    // ONLY ingress — KEY -> partition routing; no write()
$t->flush();             // flush every materialized partition's batch
$t->allow_large_writes( $debounce_ms );  // 4KB -> 32MB on every partition, each behind a Lock
$t->void_warranty();                     // …with NO lock (caller asserts single-writer)
```

**There is NO `Topic::write()` method** — `fill()` is the only ingress. Three precedences in `fill()`:

1. **TO field already set** — caller pre-pinned. Topic parses a leading `p\d+` out of TO and, if in range, routes there directly. Used by replay tools and any producer that needs a specific partition.
2. **KEY present** — `Partition::hash_to_partition($key, $num_partitions)`.
3. **No KEY** — round-robin via a static counter (`self::$rr_counter++ % $num_partitions`).

That counter is `protected static`, so a keyless write to one Topic advances the cursor for every other Topic alive in the process, and `remove_node()` does not reset it. It is deliberate — request-scope Topics are short-lived, and a per-instance counter would start each one back at partition 0 and pile keyless traffic there — but it means keyless spread is even in aggregate across the process rather than per topic, and two Topics of the same width in one request advance in lockstep.

**`READY` event** is declared in `node_schema()` and fired (`set_state`) from `sink()` — wiring the sink is what materializes every partition, so that is the moment the Topic is usable. Late registrants get the cached payload immediately. `Partition::sink()` fires its own `READY` the same way.

**No `RESET` event** — our partitions are local directories that don't move at runtime, so there's no partition-map mutation to signal. Pre-declaring an event you'll never fire is a foot-gun for downstream registrants.

**Per-partition settings propagate, including to partitions built later.** `allow_large_writes()`, `void_warranty()`, and `with_index( $formatter_name )` record the mode on the Topic and apply it to every materialized Partition; `partition()` applies it again to each one it creates. Each is exposed as a `{name}:config` verb, and `dump_config()` re-emits it, so the round-trip preserves the mode.

**The two `allow_large_writes()` share a name and disagree about their first parameter.** On a Partition it is `( int $max_wait_ms = DEFAULT_LOCK_WAIT_MS, int $debounce_ms = 0 )`; on a Topic it is `( int $debounce_ms = 0 )`. So `$t->allow_large_writes( 0 )` reads as a try-lock and is in fact hold mode. A Topic exposes no per-call timeout at all — `apply_large_write_mode()` always passes `Partition_Node::DEFAULT_LOCK_WAIT_MS` down to each child — and the `allow_large_writes` verb on `{name}:config` takes the same single optional `debounce_ms`.

**A Topic in `allow_large_writes` mode can therefore block and throw from `fill()`.** The verb takes no lock when it runs: it records the mode, and `partition()` applies it to each child as that child is materialized. So the first message routed to a given index can wait out those 15 seconds and then raise the `RuntimeException` a live writer's held lock produces, and that exception travels straight out of `fill()`, the only ingress. The refused partition is retracted from its `p{N}` sibling slot and never cached, so the next message routed there rebuilds from the start rather than being served a cap-lifted partition with no lock behind it. A request-scope producer under `allow_large_writes` has to be ready for both the stall and the throw; `void_warranty()` takes no lock and can do neither.

**Two counters aggregate rather than count this node.** `bytes_written()` sums and `largest_msg_sent()` maxes over every partition the Topic has materialized, where `Node` declares both per-node. That is what makes a Topic's row meaningful on the canvas at all, since `dump_metadata` skips patron-linked nodes and the `p{N}` children never appear there. `stats` and `ls -a` walk the whole registry instead, listing the Topic beside its children, so WRITTEN double-counts there — and so does COUNT, because `fill()` increments the Topic's own counter before handing the message to a partition that increments its own.

**No Topic-level batching.** Per-partition batching happens INSIDE `Partition::fill()` itself — see the Partition section above. Topic is a pure router on top, so a single message routed to a partition lands in that partition's `$batch` and follows the partition's flush rules (size threshold + 0-delay one-shot timer).

### Offsetlog

Just another Partition, at the directory the reader's `offsetlog_dir` argument names (the stock topologies point it at `<config:offsets_dir>/<topology>.<log>.p<partition>`). Each checkpoint is a `TM_STRUCT` Message whose VALUE is `{segment, offset, attempts, reason, first_crash_ts, name, target, targets, worker_type, source_log}` — plus `cache`, the snapshot nodes' co-committed state keyed by node name, where a reader declared one — routed through `Partition::fill` (so it lands as the canonical packed wire format, not raw JSONL) and `flush`ed immediately. On restart `load_offsetlog()` reads the newest segment's last line, `Message::unpacked`s it, and decodes VALUE to seed the cursor. There is no "already dead-lettered" flag: `resume_attempts_from_frame()` resumes at `attempts + 1`, and a frame carrying no `reason` — an uncatchable death rather than a caught throw — at the crash threshold enters crawl and arms a one-shot skip of the resumed head, which is the message that was in flight when the process died ([ADR-12](architecture-decisions.md#adr-12-dead-letter-poison--crash-lifecycle)). An empty `$offsetlog_dir` disables the offsetlog entirely (ephemeral readers like the cli's `reply-in`). No special class.

Its retention geometry is deliberate: `OFFSETLOG_SEGMENT_SIZE = 1` makes one checkpoint one segment one **keyframe**, which is what the time-travel debugger seeks by; the rest keep 10 keyframes minimum, target 30, hold anything younger than 5 minutes, prune past 15, and hard-cap at 60. A 1-byte threshold spams no empty segments, because `do_rotate()` adopts the still-empty newest segment on the first commit and only rotates once it has content.

## Consumer + Tail

**Consumer** tails a source Partition and commits its cursor `{segment, offset, attempts, reason, first_crash_ts, ...}` to its offsetlog (itself a single-partition Partition). On restart, it reads the newest offsetlog entry to seed the cursor. It is a `Timer_Node` that `use`s `Durable_Reader` — the offsetlog cursor, the timer-driven buffered pump, and the time-travel debugger — which brings `Dead_Letter_Queue` (quarantine and attempt accounting) and `Sidecar` (the two sidecar Partitions) in with it.

```php
$c = new Consumer_Node();                              // no-arg ctor; config is positional via arguments()
$c->arguments( [ $source_dir, $offsetlog_dir, $deadletter_dir ] );  // token array
$c->next_offset( 'start' | 'recent' | 'end' | ['segment'=>, 'offset'=>] );  // seek
$c->poll();                        // read new bytes, re-emit each line's Message, advance cursor
$c->drain();                       // poll to exhaustion, then emit a terminal TM_EOF
$c->checkpoint( $graceful );       // append a {segment, offset, attempts, reason, first_crash_ts, ...} TM_STRUCT
$c->cursor_position();             // "{segment}:{offset}"
$c->has_checkpoint();              // a frame has been committed — false until the first poll
$c->set_multi_writer( true );      // shared-log seal grace
$c->set_assume_clean_shutdown( true );  // commit PAST the in-flight message on a cooperative stop
$c->set_stamp_as( '_repl' );       // override the FROM stamp at this I/O boundary
$c->probe_stats();                 // the Probe_Record fields Topic_Probe sweeps
$c->idle_since();                  // Idle_Reporter: when this reader last had work

Consumer_Node::lag_from_disk( $source_dir, $offsetlog_dir );  // static: lag without a live node
```

`lag_from_disk()` returns the live reader's eight lag fields plus a ninth, `cursor_known`, and a caller must branch on it. It is false when the offsetlog holds no committed frame — the ordinary state between boot and the first checkpoint — and when `$offsetlog_dir` is empty, and the `bytes_behind` reported alongside it then defaults to the WHOLE partition; it is true for an empty partition, where there is nothing to be behind. Anything acting on the number skips a false row rather than reading it as "all of it is behind", which is what `Spawn_Coordinator::wake_readers_with_backlog()` and `CLI::relag_from_disk()` do: treating it as backlog would respawn an on-demand reader on every minute pass forever, and would overwrite a live status row with a phantom lag.

`idle_since()` answers with the newest segment's mtime, and its two sentinels decide a worker's residency. Null means BUSY — the reader still holds unread bytes, or the newest segment's mtime is unreadable — and one null vetoes the whole worker's on-demand exit. A source with NO segments is deliberately not that case: it reports idle from the moment it was first seen empty, so a reader tailing a partition nobody has ever written cannot hold a peer's exit open forever.

`poll()` reads at most one `READ_BLOCK_BYTES = 65536` block per tick, splits the buffer on `\n`, leaves the trailing partial, and for each complete line `Message::unpacked`s it (Partition wrote a packed Message per line), stamps its own name — or its `stamp_override` — onto FROM, stamps TO from `target`, and fills its sink directly. The position breadcrumb goes in **ID** as `"{segment}:{offset}:{length}"` — **NOT KEY**. Overwriting KEY would destroy the producer's partition-routing key (rid / handler) and silently break multi-partition queues and RequestBuilder's rid grouping. (The cursor names the next unread position: each record advances it past itself by its own length, so a resume never re-delivers the last record read. A two-part crumb, carrying no length, moves it by nothing.) `fire()` then re-arms its own recurring timer at one of two cadences: `POLL_INTERVAL_BUSY_MS = 0` — the next event-loop iteration — whenever the last refill may have left more behind, and `POLL_INTERVAL_EOF_MS = 100` once the reader is genuinely at EOF, so a fully caught-up Consumer or `Remote_Source` still ticks ten times a second. Both sit below the Router's cadence, so `list_timers` shows `event_framework` in the MODE column rather than a hitchhike. Corrupt/unparseable lines are quarantined to the `:deadletter` sibling (raw bytes preserved; the cursor still advances) rather than aborting the poll — see [ADR-12](architecture-decisions.md#adr-12-dead-letter-poison--crash-lifecycle) for the full poison lifecycle.

**Multi-writer seal-grace.** A log many processes append to (the firehose) needs `set_multi_writer( true )` — the `set_multi_writer` config verb, or `command_node <consumer>:config set_multi_writer true` in a topology. A peer can keep appending to segment N for up to `Partition::DRIFT_RESCAN_INTERVAL_SECONDS` after N+1 appears, so the reader refuses to advance until the segment's size has held steady for `SEAL_GRACE_SECONDS = 2.0`; without the opt-in a straggler's final line is orphaned. The grace is charged at the head alone — it applies while the cursor sits on the newest segment or the one before it — so a reader replaying a long backlog crosses every boundary at full speed and only the reader catching up pays the two seconds. A single-writer log leaves the flag false and advances the instant the next segment exists, so it pays no latency.

`Remote_Source` declares the same verb, and it means the same thing one hop away: the read happens on the spoke, inside the Consumer its `/messages/stream` endpoint opens, so `set_multi_writer` rides out as a `multi_writer=1` query parameter on the SSE connect and the far-side reader takes the grace. The client asserts it because nothing on the spoke's disk records which of its logs are shared — that lives in a topology line, and the endpoint opens Consumers with no topology in the picture. A wrong assertion costs a grace window, never correctness. Being connect-time, changing the flag drops the current stream so the next one carries it, and what becomes of the undrained buffer depends on where the cursor sits. Normally it goes with the stream, because `SSE_In`'s resume position only advances on a successful forward, so whatever is still buffered sits ahead of it and the spoke re-sends it on reconnect. A resume position still at {0,0} is the exception: nothing has been forwarded, so the reconnect can resolve to the spoke's tail and replay nothing, which makes the buffer the only copy of those records. `Remote_Source_Node::set_multi_writer()` therefore KEEPS the buffer in that one case and clears it otherwise, preferring a possible duplicate to a certain loss — so flipping the verb on a hub that has just started costs duplicates rather than a gap. The browser dashboards never set the flag at all, which is what keeps the grace off the interactive path.

**Clean-shutdown assumption.** `assume_clean_shutdown` decides what a cooperative stop does with the message in flight, and it is off by default: a plain `Worker_Should_Stop` leaves the cursor where it is and the successor replays that message, which is the at-least-once guarantee. Turn it on — the `assume_clean_shutdown` config verb, or `command_node <consumer>:config assume_clean_shutdown true` in a topology — and the Consumer's `forward_line()` converts that plain stop into a `Worker_Should_Stop_Clean`, which `drain_buffer()` reads as permission to commit PAST the message ([ADR-14](architecture-decisions.md#adr-14-cooperative-stop-propagates-through-broad-catches)). Set it only on a chain that writes the message durably before the stop and has no snapshot node to raise the clean stop for it: an aggregator, a bare Consumer→Partition, a job router. Never set it on a Consumer whose sink RUNS work that can stop mid-flight with nothing durable written — a Job_Worker handler pumping mid-job — because committing past drops a half-run job. Crawl mode ignores the flag, since a crawl's pin isolates a crash suspect. `Remote_Source` declares the same verb from the same trait and honors it only on a record its breadcrumb can place, since one it cannot place has to replay. `Tail` and `File_Tail` inherit the verb and ignore it: their `forward_line()` mints the raw bytes and catches no stop at all, so a plain stop replays the line whatever the toggle says. `dump_config()` re-emits whichever toggles are on, so a console replay rebuilds the reader with them.

**Time travel.** `Durable_Reader` turns the offsetlog's keyframes into a debugger: `PAUSE` stops the poll timer and holds the cursor, `STEP` emits exactly one message (forcing line granularity, restoring the production `line_mode` on resume), `SEEK_FRAME <segment>` jumps to a keyframe by its offsetlog segment id — restoring that frame's co-committed snapshot state and repositioning the read cursor — and `PLAY` truncates the offsetlog after a rewind point (so the re-written timeline stays monotonic) and re-arms. The verbs are hidden `{name}:config` commands driven by the Inspector's transport bar; `time_travel_metadata()` feeds it the frame list, live cursor, and polling state. The Inspector shows that bar by SHAPE rather than by class: a node whose polled metadata carries an array `frames` beside a `cursor` gets it. So any node using the trait reports its own way into the debugger with no dashboard-side wiring, and one that stops publishing either key loses the panel just as quietly.

**Tail** is a subclass of **Consumer** (`Tail extends Consumer`) that emits each complete line's raw bytes as a `TM_BYTESTREAM` (newline restored, FROM-stamped at this I/O boundary) instead of unpacking a packed Message. Two source shapes, two classes:

- **`Tail`** reads a **Log**'s `{file}.{seg}` segments through a `Log_Node` source, so the whole inherited Consumer read model applies. It parts from Consumer at four seams and nowhere else: `make_source()` builds a `Log_Node`, `resolve_args()` reads the first argument as a file base rather than a directory, `default_offset()` starts a fresh reader at END, and `forward_line()` emits the raw line. The buffer/cursor scan that hands it each line stays in `drain_buffer()`, so it gets line_mode for free.
- **`File_Tail`** (`File_Tail extends Tail`) follows a SINGLE filename with `tail -F` logrotate semantics: it holds the open handle, drains a rotated-away generation to EOF before reopening the path at offset 0, resets on in-place truncation, and tolerates a missing path. The inode occupies the same cursor slot a segment id does, so `<inode>:<offset>:<length>` rides the existing offsetlog frame and DLQ machinery with no new field. A resume validates the persisted cursor against the current file and reads it whole from 0 whenever the stored generation is absent, zero or foreign, or the file shrank below the cursor; a cursor in the RIGHT generation that is not just past a newline is mid-line, so the read resumes there and syncs forward onto the next newline — at-least-once, never cross-generation hunting. Opening at `end` arms that same one-shot sync whenever the byte before the cursor is not a newline, so the bytes up to the next newline are dropped instead of shipped as though they were a line: the first record a fresh `File_Tail` delivers is always a COMPLETE line, never the tail of one whose start the reader never saw.

Both **inherit** the durable offsetlog cursor, the checkpoint cadence and time travel, and both part from Consumer on the other two. `Tail_Node::forward_line()` replaces `Durable_Reader::forward_line()` whole, taking its two quarantine paths and its `stopped_in_fill` flag with it, so a throwing sink propagates out of `drain_buffer()` instead of being dead-lettered and `cooperative_stop()` has no poison to strike; the `deadletter_dir` argument, the `:deadletter` sidecar and the `dl_list` / `dl_show` / `dl_requeue` / `dl_purge` verbs all still work. `File_Tail` loses the read half of snapshot co-commit as well: `init_position()` reads the newest frame through `read_last_offsetlog_frame()` rather than `load_offsetlog()`, deliberately, to keep the live inode in the cursor slot a stored one would overwrite. It therefore saves a co-committed `cache` on every checkpoint and restores none of it on respawn — a `SEEK_FRAME` still restores, reading the frame's cache itself — and because `arm_skip_head_from_frame()` never runs, `attempts`, `first_crash_ts` and the crash streak all come back virgin, so it never enters crawl and never sacrifices a boot head.

Lag is one more `File_Tail` substitution, and exactly one seam serves it: `GET_LAG`, `probe_stats()` and `idle_since()` all read `compute_lag()`, so the request reply, the probe record and the idle check cannot answer the same question three ways. A fresh reader with no durable cursor defaults to **end-of-file** (`default_offset` → `'end'`) — only bytes appended after start — and resumes from its offsetlog checkpoint on restart. `make_node Tail <name> <source_file> [offsetlog_dir] [deadletter_dir]`, `make_node File_Tail <name> <source_file> [offsetlog_dir] [deadletter_dir]`.

Idleness INVERTS across that same seam. A `File_Tail` over a path that does not exist reports null — not idle — for as long as the path is missing, where a Consumer over an empty source reports idle: a rotation gap is a moment between generations rather than a stream nobody writes, and hanging up on one would drop the reader before the new file appears. Two things pay for it. That one null vetoes the whole worker's on-demand exit, and `SSE_Out_Node::opened_at_eof_since()` falls back to the present, so a `/log/stream` subscription to a registry source whose file was never created waits out a full `sse_idle_timeout` window on every reconnect instead of closing on the first tick.

## Other Node Primitives

**Tee** is the fan-out node. Its target LIST and the pruning live in the `Fanout_Targets` trait, which any node that fans out uses — `Core::class_fans_out()` asks about the trait, not descent from `Tee_Node`, because the command minters that sign one message per spoke are `Timer_Node` subclasses. Each `fill()` reads the live-target list, copies the message per target with `TO=target` (if TO was empty) or `TO=target/originalTO` (path-prepend if TO carried subpath), and forwards through `sink` (typically `_router`). Every target is attempted: a throw is caught, the one that `outranks()` is deferred, and it re-throws after the loop — completing the fan-out is what preserves at-least-once ([ADR-14](architecture-decisions.md#adr-14-cooperative-stop-propagates-through-broad-catches)). Pruning is a liveness check on every read of the list, not "after a failed dispatch": it tests the FIRST path segment of each target, so a bare-name target is dropped when its node has disappeared, and a **path-shaped** target (has a `/`, e.g. `_repl/_output/12345`) is kept while its head node exists and dropped when the head is absent. Connect order is preserved through the prune and is contractual: a consumer may depend on an earlier target being fully delivered before a later one is. Tee declares no registrations, commands, or requests of its own.

The counter is incremented once per inbound message, ahead of the fan-out loop, so a Tee with five live targets forwarding 100 messages reports 100 in `ls -c`, `stats` and `dump_metadata` while 500 copies left through its sink; fan-out volume is measured on the downstream nodes' counters. Both ports agree on that and part company four ways: on failure, on the sink, on the registry the prune reads, and on a bare `disconnect_node`. Only PHP defers the throwable `outranks()` selects and re-raises it after the loop — the browser `TeeNode` catches each target's throw, reports it through `printLessOften` and raises nothing, because there is no consumer cursor in the browser for a cooperative stop to protect, so ADR-14's fan-out carve-out has no browser half. PHP also calls `require_sink()` up front, so an unwired Tee throws on any message, where the browser tests `this.sink` inside the loop and stays silent while no target is live. The browser prune resolves each head in the node's OWN registry rather than in one global table, which is what lets a topology-console draft hold its own `firehose` without every edge in the draft reading as dead. The two `disconnect_node` methods disagree on the bare call as well: PHP's clears the whole list, while `TeeNode.disconnectNode()` with no argument filters for the empty string and leaves every target connected. Both CLI verbs behave alike, each substituting the issuing command's FROM before calling down, so the divergence bites only a JS caller invoking the method directly and expecting the trait's clear-everything behavior.

**Hook** is the WordPress-extensibility bridge: `make_node Hook <name> <hook_name> [ <filter> ]`. Action mode is the default and fires `do_action( $hook_name, $value )`, forwarding with VALUE and TYPE untouched — the forward still runs through `parent::fill()`, so an empty TO takes the node's `target` stamp. The second positional is the schema `bool` that selects filter mode, read through `Schema_Reflection::truthy()`, so `1`, `true`, `yes` or `on` in any case turns it on and every other token leaves action mode standing. Filter mode forwards `apply_filters( $hook_name, $value )` as the new VALUE and **assigns** TYPE rather than swapping the content bit: a LIST return becomes TM_STRUCT and every other return TM_BYTESTREAM, and either way every flag the message arrived carrying — TM_COMMAND, TM_REQUEST, TM_RESPONSE, TM_NOREPLY — is gone, so keep filter-mode Hooks off control edges. An associative-array return is one of those "every other" cases: it leaves as an array VALUE under TM_BYTESTREAM, which every array-VALUE consumer denies, since the substrate's rule is to gate on TM_STRUCT and never on `is_array()`. Plugins observe completed requests, transform job payloads before routing, etc., without touching topology files. The hook name is refused at two different times: a bare `make_node Hook` throws `Missing required argument: hook_name` at construction, while a blank token and a `Hook_Node` built in PHP that never calls `arguments()` both satisfy the schema and are refused at the first message with `Hook::fill requires a hook_name`. That check and the sink check both run before the hook fires, so a misconfigured node leaves no side effect behind a message that never reaches a sink. The JS `HookNode` (`src/runtime/hook-node.js`) shares only the name and is no mirror of this one: the browser has no WordPress hooks, so it is a predicate gate taking a closure as a required constructor argument, forwarding a message only when the predicate accepts it, never stamping TO from `target`, and dropping rather than throwing on an unwired sink.

**Callback** is the closure-as-Node adapter: a `fill()` that hands the message to a stored closure and stops there. Its constructor takes a required callable, so `make_node`'s bare `new $fqcn()` ([ADR-11](architecture-decisions.md#adr-11-make_node-construction-sequence)) cannot build it and no topology line names it — a `Hidden` category keeps it out of the palette too. Callers construct it directly in PHP: a test asserting on what reached the end of a chain, `Job_Delay` sorting due entries from held ones, `Log_Sources::read_at()` capturing the one record a Consumer stepped to. It is a terminal, and the closure receives the whole 7-field message array rather than the VALUE. PHP hands that array by value, so a closure declaring `array &$message` mutates `fill()`'s local copy and nothing downstream; transform-and-forward means filling the next node yourself. The JS mirror, `CallbackNode` in `src/runtime/callback-node.js`, hands the array over by REFERENCE, so the same closure ported between the two runtimes edits the caller's message there and nothing here.

In the browser it is also how a component receives an out-of-band reply, outside the one-shot `CommandResultNode` / `useCommandOnce` path. `TriageView` (`src/topology-console/components/TriageView.js`) builds one per dead-letter verb, gives it the stable name `_triage:<verb>` so `command_node`'s `replyTo` can address it, and has the closure read the current handler off a ref at delivery rather than close over one — build it, name it, let the closure read live state. The obligation that comes with the name is teardown: `removeNode()` on unmount, or the next mount collides on it.

**Echo** is a routing helper that re-addresses messages on the way through. With both `target` and `TO` set it prepends the path, `TO = target/TO`; with both empty it bounces, `TO = FROM`, return-to-sender along the trail. Neither branch matches the two remaining cases, so both fall through to `parent::fill()`: a TO with no target passes unchanged, while a target with an empty TO takes the base stamp and routes to the target rather than staying unaddressed. TM_ERROR with empty TO is dropped rather than bounced (the producer isn't expecting the error trail). That drop is the FIRST thing `fill()` does and it ignores `target` entirely, so an Echo wired `target errors:topic` discards such an error instead of stamping the target on it — the obvious error-collection wiring swallows exactly the errors it was spliced in to catch. Route pathless errors with something other than an Echo, or give the producer a TO.

**Log** is the file-writer counterpart to Tail and a subclass of **Partition** (`Log extends Partition`). It differs from Partition three ways: it writes each fill()'d message's **VALUE** (the producer's payload, not the packed envelope), it lays its segments out as `{file}.{seg}` (`out.log.0`, `out.log.1`, …) rather than `{dir}/{seg}.log` — with no bare `{file}`, no logrotate `.0` shift, no `mode` / `max_size` / `max_rotations` — and its `fill()` DROPS control messages instead of packing them. Args: `make_node Log <name> <file> [segment_size] [min_segments] [num_segments] [max_segments] [min_lifetime] [lifetime]`. Rotation is monotonic and automatic when a segment passes `segment_size`; retention is Partition's three-rule scheme (`num_segments` count target / `lifetime` age / `max_segments` hard cap). It inherits the rotate lock, `allow_large_writes()`/`void_warranty()`, and the 4KB PIPE_BUF cap — an oversize VALUE is dropped unless the cap is lifted. TM_ERROR/TM_EOF/TM_REQUEST are dropped (append-only; EOF never closes it; segmentation is size-driven, so there is no rotate request), and a dropped message still advances `counter`, which keeps the base convention that `counter()` reports what a node RECEIVED rather than what it wrote — so a Log can sit at a counter well above its record count with nothing wrong, the way one inbound Router miss bumps that counter by 2.

Writing VALUEs rather than envelopes has two more consequences. The record TERMINATOR belongs to the producer: `Log_Node::serialize_record()` appends nothing, which is what lets a Log hold something other than lines, so a bytestream producer that omits its newline puts two records on one line and a `Tail` reading them back re-splits on the wrong boundaries. That is the second reason to splice a `Struct_To_JSON` in front of a Log for a struct source — it `rtrim`s and re-appends exactly one newline — the first being that `Core::as_string()` renders an array as `''`. And the inherited `read_message_at()` is inert here: a Log's bytes are the producer's payload rather than a packed 7-field envelope, so `Message::unpacked()` throws and the method answers null on every well-formed record, indistinguishable from the torn record it exists to report. Read a Log with `read_at()` or through a `Tail`, and keep `read_message_at()` / `read_many()` for a Partition.

**Timer** (and its subclass **Router**) is the time-driven base, with two scheduling modes. A NAMED node asking `set_timer( $ms, $oneshot )` for no interval, or for one at least as long as the Router's live cadence, takes the **Router hitchhike**: it registers itself on `_router`'s TIMER channel by name, and `fire_cb()` throttles down to `interval_ms`. Everything else — an unnamed node, the Router itself, or an interval shorter than that cadence — takes its **own Event_Framework slot**, which requires a concrete interval. The threshold is `Router_Node::interval_ms` rather than a hardcoded 1000, so a Router ticking slower than `DEFAULT_TICK_MS` doesn't hand a 1500ms timer a hitchhike that fires every 2000ms; `Router_Node::DEFAULT_TICK_MS` stands in where no Router is mounted. The two modes disagree about the FIRST fire, and anything reasoning about a boot-time burst has to account for it: `set_timer()` seeds a hitchhiker's `last_fire_time` at 0.0, so the throttle passes on the very first Router tick after arming and a 300-second collector or a 15-second probe fires about a second after boot and only then paces, while `Event_Framework::set_timer()` seeds an own slot's `next_fire` a full interval ahead, putting its first fire one whole period away. Either way `fire_cb` is the framework-side hook and `fire()` is the override point for subclasses; `timer_mode()` reports which mode is live, `timer_is_active()` whether it is armed at all, and `list_timers` shows the mode in its MODE column. Default `fire()` emits a TM_BYTESTREAM carrying the current timestamp at `target`, tagged with the `key()` stamp when one is set — unless the node has no target and sinks straight into a Command_Interpreter, which would be pure spam. It notifies `FIRE` listeners either way, so a subscriber works whichever branch the emit took. `cadence_ms()` is the one seconds-to-milliseconds conversion every self-pacing subclass shares, flooring at `MIN_INTERVAL_S = 1` so a sub-second declaration cannot become a free-spinning 0ms own slot.

`fire_cb()` returns before it ever reaches `fire()` while `sink` is null, and that is a rule for every subclass rather than a Router quirk: a Timer subclass whose `fire()` does pure side-effect work and emits nothing must STILL be wired a sink or it never fires — silently, with no error and no log line. `Connect_Queue_Timer_Node` is the live example. It emits nothing, so `Remote_Link_Node::queue_connect()` sinks it into `_command_interpreter` for no reason but to clear that guard, which is why a mount with no emit path still names a sink. A oneshot fares worse, because `fire_cb()` calls `stop_timer()` BEFORE the sink check: a sinkless oneshot is disarmed without ever dispatching. `make_node` sinks every node it builds, so the trap is a Timer subclass constructed in PHP and never handed a sink.

**Grep** (`Grep_Node`) is the payload filter: it forwards a message whose VALUE matches its PCRE and drops every other one. The argument is the pattern BODY, which Grep wraps in `{}` the way `Grep.pm` wraps `qr{}`; it compiles at `arguments()` rather than at first `fill()`, because `preg_match` answers a bad pattern with `false` and a `false` return would discard the whole stream silently. A Perl-style delimited pattern is therefore taken literally: `make_node Grep g /ERROR/i` compiles clean, matches those eight characters, and forwards nothing, with no refusal and no diagnostic — and there is no slot for a trailing modifier, so ask for case-insensitivity inline with `(?i)ERROR`. The default `.` needs one non-newline character, so it matches everything except an empty VALUE and a VALUE of newlines alone. A non-string VALUE is JSON-encoded before the match, so a struct producer greps without a transform in front — the pattern then reads JSON syntax, which walks straight into the delimiter. Braces delimit the pattern and PHP's delimiter scan is not regex-aware, so every literal brace needs escaping wherever it sits: `\{"k"` and `"job"\}` compile, `job}` is refused at load with `Unknown modifier '}'`, and even `\{[^}]*\}` fails on the unescaped closer inside its character class. A balanced quantifier such as `\d{2,4}` needs nothing. There is no type gate: a TM_COMMAND or TM_EOF that misses the pattern drops with the data, so keep control traffic off a grepped edge.

**Age_Sieve** and **Value_Timeout** are the two flow-control sieves ported from Tachikoma. `Age_Sieve_Node` (`AgeSieve.pm`) drops a message whose TIMESTAMP is older than `max_age` seconds, and setting `should_warn` sends each drop through `print_less_often`, so a shedding edge warns without flooding: `make_node Age_Sieve <name> [ <max_age> [ should_warn ] ]`. A `max_age` token of zero or below takes the 900s default rather than its literal reading, which would drop everything older than the current tick. Read `should_warn` as the schema's `bool` vocabulary rather than as PHP truthiness: `Schema_Reflection::truthy()` answers true for `1`, `true`, `yes` and `on` in any case, and false for everything else — the string `false` included, where PHP would read that same string as true. `AgeSieve.pm` assigns the raw token instead, so the argument pair `900 false` turns the warning ON upstream and OFF here. Neither the threshold nor the warning is retunable on a live graph: `Age_Sieve_Node::node_schema()` declares empty `commands` and `requests`, so the node has no `{name}:config` verb at all and moving the threshold means editing the `make_node` line, reloading the topology and restarting the fleet. `max_age()` is introspection only, where `AgeSieve.pm`'s accessor also sets.

`Value_Timeout_Node` (`PayloadTimeout.pm`) is value-keyed dedup: `make_node Value_Timeout <name> [ <timeout> <expires> <interval> ]`, with `DEFAULT_TIMEOUT` 900 seconds and `DEFAULT_EXPIRES` 3300. It suppresses a repeat of a VALUE inside the `timeout` window, drops anything older than `expires`, re-emits the trailing value when the window closes, and sweeps on an `interval` that defaults to `timeout / 60` floored at one second. Three drops precede the dedup, all of them silent and none of them counted, because unlike its sibling this node carries no `should_warn`: `fill()` returns early on any TYPE without the `TM_BYTESTREAM` bit, so a TM_STRUCT producer gets nothing through and TM_EOF, TM_ERROR, TM_INFO and TM_COMMAND are swallowed rather than passed; then on a TIMESTAMP that is absent, zero or non-numeric; then on an age past `expires`. An edge that stops delivering therefore gives no signal — Grep's missing type gate again, this time as a gate that admits one type only. It is as unretunable as its sibling, declaring empty `commands` and `requests`, and because that schema is a bare literal rather than a merge of its parent's it sheds `Timer_Node`'s `FIRE` registration too, so `register <value-timeout> <listener> FIRE` throws where it works on every other Timer subclass. That matches a `fire()` emitting values instead of a heartbeat and notifying nobody, though nothing in the schema says so.

Two things about the trailing re-emit decide whether it is usable. Both window maps are process memory, and `DEFAULT_TIMEOUT` (900s) outlives `Cooperative_Stop::DEFAULT_MAX_RUNTIME` (595s), so at the shipped defaults a worker recycles before `fire()` can ever find a window expired: the trailing send never lands, and the successor forwards the next duplicate of every value as new. Wire the reader's `add_snapshot_node <value-timeout-name>` so both maps co-commit with the cursor, or set a `timeout` comfortably under the worker's `max_runtime`. And the re-emit is a freshly minted message rather than the suppressed one — the node stores values, not messages — so KEY and ID are empty where the first, forwarded arrival kept them. On a `Value_Timeout → Topic` edge the first send is CRC32-routed by KEY and the trailing one round-robins to an arbitrary partition, splitting exactly the pair the dedup was meant to keep together. `fill()` also `rtrim`s the trailing newline off the value before keying, so a line-oriented and a bare producer share one window, and `fire()` appends one unconditionally.

**Null** (`Null_Node`) counts and discards, and it earns its place as a DESTINATION rather than as a placeholder. `HTTP_Out_Node::accept_inbound()` refuses a remote-addressed non-reply only while a target is SET, so the `<name>:null` sibling `Remote_Link_Node` publishes is what buys that refusal: with no target neither arm engages and a remote may name any node in the local graph and have the message delivered there. The other arm stamps the target onto the remote's unaddressed output, so the target has to be a node that swallows what lands on it — aiming it at the `Remote_Link_Node` owning the egress feeds the spoke's own output back out the wire. Counting rather than merely dropping is deliberate too: a silent black hole is indistinguishable from a broken route, so `ls -c` reports what a Null absorbed.

**Table** (`Table_Node`) is the keyed store, carrying Tachikoma's Table vocabulary over a memcache backing instead of in-memory buckets. `Table_Node::table( $ns, $ttl )` hands any process the same namespace, and `lookup()` / `store()` / `forget()` / `lookup_multi()` / `store_multi()` read and write it across processes; TTL replaces the bucket window. `fill()` is write-through, so a Table composes mid-graph. `table()` is deliberately NOT memoized, so hold the instance you configure — an accumulator rebuilt per call is empty every time. `accumulator( $bucket_size, $num_buckets )` puts an `LRU_Cache` in front for values a caller is still folding into: Tachikoma's buckets back as a TIER rather than as the store, rotating on capacity AND on an absolute wall-clock grid so a recycled process keeps its predecessor's phase, and promoting a hit to the newest bucket so only idle keys age out. `backed_by( \Closure $backing )` fronts a durable record — the walk that FINDS that record (`Partition_Node::locate_by()` / `read_many()`) stays in the application ([ADR-18](architecture-decisions.md#adr-18-a-table-can-front-a-durable-record-the-walk-that-finds-it-stays-in-the-app)).

Write-through comes with one qualification: a message carrying a KEY stores only while its VALUE is non-empty. `null`, `[]` and any string that `rtrim`s to nothing on `\r\n` call `forget( $key )` and DELETE the entry instead (Tachikoma's `collect` rule), so a bare line terminator counts as empty and splicing a Table onto a line-oriented edge — a Tail, or a Consumer forwarding raw lines — deletes a key on every blank line rather than storing one. A keyless message passes untouched, and the message forwards either way. Deleting a whole table is the namespace's job: every entry is addressed by the derived `Table_Node::entry_key( $ns, $key )` rather than by the bare key, so naming a new namespace — or re-calling `arguments()` on a live table — orphans every key at both tiers at once. That is the only whole-table invalidation there is and the supported way to carry a generation, since `wp nodes memcache flush` rotates the whole install's salt and takes every other Newspack plugin's keys with it: name the table `pyrobase:g47` and let a schema bump move it to `pyrobase:g48`.

The two read paths consult different tiers, and only one of them sees the accumulator. `accumulated( $key )` checks the buffer first and falls back to `lookup()`, which is what makes a cold or evicted key resumable; `lookup()` and `lookup_multi()` never consult the buffer at all, going to the cache and then to the backing. So a caller that has opted into an accumulator and reads a page of keys through `lookup_multi()` sees only what has been PERSISTED, missing every value still being folded in — and there is no batch `accumulated()`, so reading a still-folding set means looping `accumulated()` or draining through `accumulating()` first. `accumulating()` yields the held values under the caller's own keys, the namespace prefix stripped back off, and deliberately does NOT clear: a caller persisting whole values stays idempotent across drains, and clearing would discard whatever accumulated between them. `reset()` is the explicit clear, and it drops ONLY what the accumulator holds — nothing on `Table_Node` empties the cache tier or the durable backing.

Building a Table on a host with nothing to back it THROWS, and where the throw lands depends on who built it. `arguments()` raises `\InvalidArgumentException` on an empty namespace and `\LogicException` when `Cache_Backend::shared_first()` is null, and both travel out of `table()`, so a non-graph caller guards on `Cache_Backend::shared_first()` first rather than expecting the substrate to degrade. From a `.tsl` the same throw takes the ordinary construction path: `Command_Interpreter_Node::make_node()` removes the orphaned node and rethrows, `interpret()` catches it, and because `Topology_Loader` sends every line `TM_NOREPLY` it surfaces on stderr as `error from TM_NOREPLY command: …` — so the worker comes up with the Table ABSENT and the rest of the graph built, never as a `load_failed`.

`request_node <table> "GET <key>"` replies with the stored value under `TO = FROM` and KEY set to the requested key, and the reply TYPE follows the value's SHAPE: `TM_STRUCT` for an array, `TM_BYTESTREAM` for a scalar, `TM_ERROR` carrying `NOT_FOUND` when the key is absent. It diverges from `GET_LAG` and `GET_HEALTH` in four ways a caller has to know. The reply carries no `TM_RESPONSE` bit and no `{verb, data}` envelope; the request's ID is not echoed back; the verb match is case-SENSITIVE, where the two siblings `strtoupper`; and any other verb is logged through `print_less_often` and dropped with NO reply at all, so an asker waits out its own deadline. That missing response bit has a concrete remote consequence, because `HTTP_Out_Node::accept_inbound()` admits an inbound message as a reply only when TO is non-empty AND the type carries `TM_RESPONSE | TM_ERROR`: across `HTTP_Out` or `Remote_Link` a GET MISS gets home while a GET HIT is judged against `target` instead, and dropped wherever one is set. `KEYS` and `STATS` are deliberately absent — both enumerate buckets a cache backing cannot enumerate.

**Tap** is `Tee` with *hard* addressing plus passthrough — a `Tee_Node` subclass for observability fan-out: it copies the message to each tap with `TO=target` exactly (no remainder to route on) AND forwards the original down `sink`. Failure handling is Tee's: attempt every tap, defer the throwable that `outranks()`, perform the passthrough, and only then re-throw. The re-throw waits for the passthrough because the passthrough IS the pipeline — a `Worker_Should_Stop_Clean` commits PAST the message, so raising at the failing tap would drop it from the main path entirely (see [ADR-14](architecture-decisions.md#adr-14-cooperative-stop-propagates-through-broad-catches)). TO is saved before the tap loop and restored for the passthrough, so a Tap spliced mid-pipeline does not re-address the message it forwards.

Hard addressing is what makes the observe path work. `connect <tap>` with no target argument defaults to the issuing FROM — `_output/<pid>` for a REPL session — and `Dumper_Node`'s session filter matches TO against an anchored `^(?:_output/)?<pid>$`, so only an exactly-addressed copy renders. A Tap's copy passes that filter even when the tapped message carried an address of its own, where a Tee in the same position would emit `<target>/<remaining TO>` and be filtered out with no diagnostic; that is why the `connect _shell` workflow is a Tap and cannot be a Tee. The cost sits on the other side: a tapped copy no longer carries the address the message arrived with, so nothing downstream of a Tap target can read the original TO.

The two surfaces that DESCRIBE this node get it wrong, so trust this paragraph over either. Tap overrides `fill()` and declares no `node_schema()` of its own, so the palette lists it under Routing with Tee's description — "Fan-out: copies each message to multiple targets via Router." — and `help Tap` renders that same text. A Tap does neither thing: it hard-addresses instead of letting Router carry each copy down the remaining path, and it forwards the original besides. `src/runtime/tap-node.js` declares no `nodeSchema()` either, so the browser palette repeats it.

**Stderr** (`Stderr_Node`) is a bare diagnostic sink: it routes a TM_BYTESTREAM VALUE through the node's stderr chain and writes nothing else. That chain is `Node::stderr`, which tags the line with the node's own name, into `Core::stderr`, which stamps the process-identity midfix (site host, worker type or SAPI, pid, uptime), appends to the 100-line `dmesg` ring, fires the `newspack_nodes/stderr` action, and then runs the handler: the line goes into `_repl`, `_sse` or `_output` when one of them is mounted, and to `error_log()` either way. Splice one on the end of a debug tap (`Tee → Dumper → Grep → Stderr`) so rendered/filtered lines land in the diagnostic log without polluting the STDOUT data path. Only TM_BYTESTREAM is written — put a Dumper in front to render structured types first.

That chain carries no rate limiting: `Node::stderr()` is the unthrottled path, where `print_less_often()` is the throttled one. Every message a Stderr accepts therefore costs one `error_log()` write plus one fill into whichever of `_repl`, `_sse` or `_output` is mounted, and inside a worker `_repl` is the on-disk IPC output Partition — so a Stderr spliced straight onto a Tee of a hot edge appends a disk record per message and floods every attached `wp nodes cli`. The Grep leg of that recommended chain is what bounds the volume rather than decoration. The counter bumps ahead of the type test, so `ls -c` and `dump_metadata` report what ARRIVED rather than what was written: deliberate, since a tap swallowing struct traffic would otherwise sit at zero and read as a dead route, but it means a climbing counter beside an empty diagnostic log is the expected symptom of a missing Dumper rather than of a broken write path.

**Struct_To_JSON / JSON_To_Struct** are the round-trippable serialization pair. `Struct_To_JSON_Node` serializes a TM_STRUCT message's array VALUE into a TM_BYTESTREAM JSON line terminated with exactly one newline (splice in front of a Log or terminal so a struct producer's payload can be written as a line); `JSON_To_Struct_Node` is the inverse on the read side — decode a JSON line back into a TM_STRUCT array (a line that isn't a JSON array/object passes through as a plain bytestream). Neither assigns TYPE: each computes a masked bit swap, `( $type & ~Message::TM_STRUCT ) | Message::TM_BYTESTREAM` one way and the inverse the other, so a `TM_STRUCT | TM_RESPONSE` reply — the shape `Consumer_Node` and `Job_Worker_Node` mint — keeps TM_RESPONSE across the pair and a reply path still works with one spliced in. That is the substrate's reference for any transform that re-types a message; `Hook_Node`'s filter mode assigns the whole TYPE instead and loses exactly those flags. Splice a JSON_To_Struct behind a `Tail_Node` only: `Tail_Node::forward_line()` mints a fresh TM_BYTESTREAM carrying the raw line, so the struct has to be decoded back, while a `Consumer_Node` needs none — `Durable_Reader::forward_line()` calls `Message::unpacked()`, which restores the producer's whole 7-field envelope, array VALUE and TYPE included. That is the Log-versus-Partition split showing up on the read side.

The pair is round-trippable for an ARRAY VALUE alone, and both ways it can fail silently. `Struct_To_JSON_Node` gates on the TM_STRUCT bit and never on the VALUE's shape, so a VALUE that is already a string is adopted verbatim rather than JSON-quoted — quoting it would hand the read side a JSON string where TM_STRUCT promises an array — and the bare unquoted line it writes decodes back to null, which `JSON_To_Struct_Node` forwards untouched as a bytestream. The encode itself can also fail: `wp_json_encode` is called with `JSON_UNESCAPED_SLASHES` alone, without the `JSON_INVALID_UTF8_SUBSTITUTE` that `Grep_Node` passes, so invalid UTF-8 in the VALUE or a structure past the depth limit returns false, VALUE and TYPE are left alone, and the still-TM_STRUCT message forwards with no warning, no `drop_message()` and no counter. Downstream that reads as a blank record, because `Log_Node::serialize_record()` runs an array through `Core::as_string()`, which yields `''` — so a topology that HAS the splice and still writes empty records is a failed encode, not a missing one. A producer emitting TM_STRUCT with a non-array VALUE is the violation to fix upstream.

**Remote reader family (SSE-pull aggregation).** `Remote_Source_Node` is a self-sufficient, topology-visible SSE-pull node: it extends `Remote_Link_Node` (the channel layer — `SSE_In_Node` + `HTTP_Out_Node` patrons, heartbeat, reconnect, status) and `use`s the same `Durable_Reader` trait Consumer does, so each raw SSE `msg` payload appends to the pump buffer and the tick drains it exactly like a Consumer — with the same durable offsetlog cursor, time travel, and dead-letter/crash lifecycle ([ADR-12](architecture-decisions.md#adr-12-dead-letter-poison--crash-lifecycle)). Only two seams differ on the message path: the refill arms an async cURL valve rather than reading a block, and the cursor comes from each message's own breadcrumb rather than the local buffer chop. Time travel diverges further, because a pull is not a read — STEP is inert (`advance_one_message()` emits nothing and always answers `at_eof`), PAUSE disconnects the SSE stream outright, and a seek forwards a bare sentinel to the spoke instead of resolving it here. Credentials and URL come from the `Vault` entry the node's `<vault-id>` argument names; a missing entry leaves it disconnected rather than building mis-configured patrons. These are the cURL-driven nodes that register handles with the drain loop (see [Event_Framework](#event_framework)).

`make_node Remote_Source <name> <vault-id> <remote_partition> [offsetlog_dir] [deadletter_dir]`, where `<remote_partition>` is the SPOKE's own `<topic>.p<N>` (`firehose.p0`). Both directories are optional in the schema and both should be passed: omitting them means no durable cursor and no quarantine, the same contract Consumer has. The offsetlog dir must carry `<topology>`, because an offsetlog is a FLEET's cursor and two hubs pulling one spoke partition must not share one. `sibling_suffix()` names those two sidecars `<name>:<remote_partition>:offsetlog` and `:deadletter` while the transports keep the plain `<name>:sse-in` and `<name>:http-out`.

The JS `RemoteLinkNode` mirrors only the first of those two transports, and the composition is asymmetric in both directions. It builds its own `<name>:sse-in` child and then CONFIGURES two page-wide singletons instead of patroning transports of its own: `_http`, whose `client` it sets, and `_heartbeat`, whose slot lease it arms and drops through the `CONNECTING` / `CONNECTED` / `DISCONNECTED` handlers `ensureChildren()` registers on the SseIn — the handshake carries the slot and lease owner, and those handlers are the bridge that carries one to the other. So a second RemoteLink reconfigures the same two nodes rather than raising a second pair. PHP has no Heartbeat node at all, minting its own `workers.heartbeat` every `HEARTBEAT_INTERVAL` (15s) on the tick described below.

**The channel ticks ten times a second.** `TICK_INTERVAL_MS` is 100, below the Router's live cadence, so the link takes its own Event_Framework slot and `list_timers` shows `event_framework` in its MODE column — expected, not a spinner. `fire()` latches its housekeeping (patrons, staleness, the queued reconnect, the heartbeat mint, the status publish) on the integer wall-second, so that work still runs once a second; the other nine ticks exist for a subclass's fast path, which is what lets `Remote_Source_Node`'s pump drain promptly.

**`fill()` relays outward, and the schema does not say so.** `Remote_Link_Node::fill()` consumes exactly two TYPEs as its own heartbeat reply — `TM_COMMAND|TM_RESPONSE` and `TM_COMMAND|TM_ERROR` — and hands everything else to `send()`, which relays it through the patron `HTTP_Out` to the spoke's `/command` under that link's Vault credentials. `Remote_Source_Node` overrides neither method, yet both inherit `accepts_fill => false`, so the console draws no in-port and the palette invites nobody to wire one. A TSL `connect_node` into a Remote_Source ships local traffic off-site with no visible port and no warning.

**Topic_Probe** (`Topic_Probe_Node`) is a periodic Consumer-stats sweep: each worker process runs one, sweeping ITS local Consumers (`Core::$nodes_by_name`) and emitting one positional `Probe_Record` per tick into the shared `topicprobe.p0` log. That record is parity-pinned to `src/runtime/probe-record.js` by `tests/unit/ProbeRecordTest.php`, exactly as `Jobstats_Record` is to `src/runtime/jobstats-record.js`, but for seven of its twelve slots only — the cursor pair, the partition-end pair and END_BYTES are PHP-write-only, rendered by `CLI::consumer_rows()` for `wp nodes status` — so the JS numbering carries gaps, and closing them to tidy the file misreads every field past the first one closed. The default cadence is 15s, and since that exceeds 1000ms it rides the Router hitchhike. `declared_interval_s()` reads that cadence out of the topology NAMED `topic-probe` — the first `Topic_Probe` node's positional 0 in `Topology_Analyzer::graph_for( 'topic-probe' )`, memoized — and `stale_after_s()` doubles it (`STALE_SWEEPS` = 2), whatever topology declared the running sweep. So a retune holds together only when the new value lands in the file `Topology_Registry::resolve( 'topic-probe' )` returns, and a consumer plugin's own `topologies/topic-probe.tsl` shadows the substrate's, because `register_stock_dir()` unshifts each registered dir to the FRONT of the resolution order. Hand-placing `make_node Topic_Probe <name> 60` inside an application topology instead — which the palette invites, since `node_schema()` publishes `interval_s` under `Monitor` — sweeps every 60 seconds while staleness stays at 30, so every healthy reader reads as departed. An unresolvable or `Topic_Probe`-less `topic-probe` topology falls back to `DEFAULT_INTERVAL_S` (15) and swallows the parse error, never to "never stale".

That log is the ONE live-position source: `wp nodes status` and the dashboards read it, not memcache. It covers the readers the sweep claims, which is `Consumer_Node` and its subclasses in READY state and nothing else. `Tail` and `File_Tail` extend Consumer and are swept; `Remote_Source_Node` reads durably through the same `Durable_Reader` trait but extends `Remote_Link_Node`, implements no `probe_stats()`, and mints no `Probe_Record` at all. Its cursor, backlog and throughput therefore reach none of the three surfaces sharing `CLI::consumer_rows()` — the `wp nodes status` consumer table, the Workers dashboard's offsetlog rows, and the `consumer-lag` alert family behind `wp nodes doctor` — and a hub's spoke pull reports connection health alone, through `Remote_Source_Node::publish_status()`. An empty consumer table on a hub is not a caught-up aggregation.

**Job_Probe** (`Job_Probe_Node`) is its counterpart for `Job_Worker`s, sweeping per-identity job stats into `jobstats.p0` — one record per Consumer for the first, many per worker for the second. Both subclass the abstract `Probe_Node`, which owns the cadence argument, the Router-hitchhike default, the sweep loop and the `Shutdown_Sweeper` flush that emits the partial interval a ~595s recycle would otherwise drop; a subclass declares `probe()`, a `node_schema()` naming `interval_s` as positional 0, and — where its record carries a free-text field — `fit_to_line()`. The schema is not optional, and forgetting it fails QUIETLY rather than loudly: `Probe_Node` declares none of its own, so `parse_schema_args()` falls back to the `interval_ms` positional `Timer_Node` declares — the subclass declaration REPLACES it, because `array_merge` takes `arguments` whole — and token 0 then lands on `interval_ms`, which `arguments()` immediately overwrites with `cadence_ms( 15 )`. The declared cadence is discarded with no error, and the palette files the class under Timer's `Control` category rather than `Monitor`.

A node whose `probe()` throws is skipped rate-limited rather than failing the sweep: `Worker_Should_Stop` re-throws first (ADR-14), and every other `\Throwable` goes out through `print_less_often()` as `<probe> skipped <node>: <message>` while the loop moves to the next node. One broken source costs only its own record for that window — a Consumer that has read no segment yet must not cost its healthy peers theirs — so a reader can vanish from `wp nodes status`'s consumer table and from the dashboards with no error anywhere but a throttled worker log line. A missing row is a reason to read that log, never to assume the reader died.

A `Probe_Record`'s twelve slots split by KIND, and the split decides how a reader uses them:

| # | Field | What it is |
|---|-------|------------|
| 0 | `SOURCE` | What the reader tails — the partition dir's basename, or a `File_Tail`'s filename |
| 1 | `READER` | The offsetlog dir's basename, blank for an ephemeral reader |
| 2 | `CURSOR_SEGMENT` | Position: the segment the cursor sits in |
| 3 | `CURSOR_OFF` | Position: the byte within that segment |
| 4 | `END_SEGMENT` | Level: the newest segment's id |
| 5 | `END_SIZE` | Level: that segment's size |
| 6 | `DISTANCE` | Level: bytes behind, the backlog the overview graph plots |
| 7 | `MSGS_DELTA` | Work: messages sent during `ELAPSED_MS` |
| 8 | `END_BYTES` | Level: the partition's whole on-disk footprint, Σ live segment sizes |
| 9 | `CACHE_SIZE` | Level: the newest offsetlog segment's size |
| 10 | `BYTES_READ_DELTA` | Work: bytes read during `ELAPSED_MS` |
| 11 | `ELAPSED_MS` | The interval the two deltas cover |

The two WORK fields divide by `ELAPSED_MS` within ONE record; differencing consecutive records reads a ~595s worker recycle as a counter reset. Everything else is captured off disk in a single `compute_lag()` read, so a record never pairs a stale cursor with a fresh stat and every level is correct as it stands across a restart. `END_BYTES` in particular is not a rate source — retention deleting a segment makes it FALL — and nothing reads it; a byte rate divides `BYTES_READ_DELTA`. The sweep instant is the Message TIMESTAMP and is deliberately not a field.

The two logs differ in one way that decides how a reader divides them. A Consumer's name carries the partition token, so a `Probe_Record` is distinct per reader. Jobstats is a fan-in: `topologies/job-worker.tsl` names the sink with a literal `jobstats.p0` and the probe node `jobstats` in every partition, so the Message FROM does not tell the writers apart either, and a `Jobstats_Record`'s IDENTITY (`handler:id`) is not process-qualified. At `num_partitions > 1` one identity therefore yields N records per sweep, each covering only that process's own `ELAPSED_MS` window. A fleet-wide rate is the sum of those deltas over the sum of their windows; dividing one record gives one process's rate.

Jobstats also keeps emitting for an identity that has stopped working. `probe_stats()` drains an identity's counters and keeps its row, and fields 8..11 survive that drain, so a quiet identity appears in every sweep with all six deltas at zero over a full `ELAPSED_MS` and last-run detail that goes arbitrarily stale — for the rest of the worker's life. Someone tailing the log by hand reads the repeating zero rows as a broken sweep; someone writing a reader keys the sample on `LAST_TS` and plots every idle identity at the wrong moment. Take the x-axis from the Message TIMESTAMP, which is the sweep instant, and read `LAST_TS` as when that identity last RAN.

**`Line_Fitter::fit( $message, $fields )` is the last-moment PIPE_BUF fit** almost every such emit goes through, and sibling plugins consume it too. It measures `Message::packed_size()` plus the newline against `Partition_Node::MAX_LINE_SIZE`, then halves each listed VALUE field by CHARACTERS — so a cut never splits a multibyte character — until the record fits or the field empties, only then opening the next. `$fields` is therefore a sacrifice order, most expendable first; a bulk field left off the list forces the drop however much is trimmed around it. It returns null — meaning drop — for an empty `$fields`, for an oversize record whose VALUE is not an array, and for one still oversize with every listed field spent. Fitting is what preserves the entry: a fitted line keeps its head, a dropped one is gone.

An entry in `$fields` is either a string key into an associative VALUE — event-logger-nodes fits on `m`, `url` and `user_agent` — or an integer index into a POSITIONAL record, which is how `Job_Probe_Node` fits `Jobstats_Record::LAST_MESSAGE`. List STRING fields only. Every listed field is read through `Core::as_string()`, so one holding an array or an object reads as already spent and is skipped exactly like an emptied one — a record whose bulk lives in a nested structure drops whether or not that key is listed — and one holding a number is read as a string and written back as one, changing both the value and its type on the wire. The sacrifice order is the other limit: it drains one field to empty before opening the next, which is right for an expendable tail or a lopsided pair and wrong for a symmetric pair a reader has to COMPARE. That is why `Settings_Event_Writer` keeps its own loop — at equal sizes this fitter empties an option's `old` excerpt outright where halving both sides together keeps a sample of each, and the record exists to show what a setting changed FROM as well as to.

**Metrics egress** is three nodes, and the chain starts at a `Consumer` of `topicprobe.p0` rather than at a local `Topic_Probe` — reading the shared log is what makes one formatter report the whole fleet instead of one worker's Consumers. That Consumer forwards each record as TM_STRUCT; `Probe_To_Graphite_Node` accepts only TM_STRUCT and ignores everything else, formats `Probe_Record` sweeps into plaintext `path value ts` lines under a metric `prefix` (port of `TopicProbeToGraphite.pm`), and declares `has_target: true`, so the lines go on to `Graphite_Node`, to `Newspack_Log_Node`, or through a `Tee` into both. No shipped `.tsl` in the substrate or in event-logger-nodes mounts any of the three: reaching a collector means authoring the topology yourself.

`make_node Probe_To_Graphite <name> [prefix] [interval]` takes two positionals — `DEFAULT_PREFIX` is `nodes.topics`, `DEFAULT_INTERVAL_S` is 15 seconds, a blank or zero token takes the default (Tachikoma's `||=`), a non-numeric one throws at make_node time, and `Timer_Node::cadence_ms()` floors the cadence at a second so a sub-second request rides the Router hitchhike. That interval is an ACCUMULATION window, separate from the 15s `Topic_Probe` sweep that fills it. `msgs_delta` and `bytes_read_delta` are per-sweep deltas `Consumer_Node::probe_stats()` has already re-baselined, so the window SUMS them across every sweep it caught, while `distance` and `cache_size` are levels and sample the newest record. Set the emit interval longer than the probe cadence and each Graphite point covers several sweeps; a reader that stopped probing drops out of the window rather than emitting a zero. Every line carries the newest folded probe's TIMESTAMP, not the emit instant, so Graphite plots a sample where it was taken.

Two things reshape which series a reader gets. Every run of non-word characters in the reader id becomes a single underscore before it enters the metric path, as `TopicProbeToGraphite.pm` does — and since a reader id is an offsetlog-dir basename shaped `<topology>.<log>.p<partition>`, that rewrites every stock name: `job-router.firehose.p0` reaches Graphite as `nodes.topics.job_router_firehose_p0.msgs_delta`. Anyone matching a series against the reader column in `wp nodes status` or the Workers dashboard applies the same substitution. And a reader configured with an empty offsetlog dir — the ephemeral case, such as the REPL's `reply-in` — writes `Probe_Record::READER` blank, which `fill()` refuses and drops, because admitting a blank id would merge every ephemeral reader in the fleet into one series. Such a reader has no Graphite series at all, the same way it drops out of the status rows.

`Graphite_Node` ships bytestream lines to a `host:port` Graphite plaintext endpoint, fire-and-forget, and it speaks **only** UDP: `arguments()` prefixes the token with `udp://` and `fill()` writes to that, so a collector whose carbon runs the TCP line receiver alone never sees a byte — carbon ships `ENABLE_UDP_LISTENER` off by default, and turning it on is the deployment's job. The endpoint is REQUIRED — `make_node Graphite <name> <host:port>`, and an absent, blank or colon-less token throws `InvalidArgumentException` at make_node time rather than discarding every line for the worker's life — but the check is shape-only, so `graphite1:`, `:2003` and `a:b:c` all pass and a typo'd port fails silently the same way a wrong one does. Nothing in the graph reports the difference, because a connectionless write to a port nobody listens on succeeds and `fill()` bumps `counter` on every accepted message either way, so a climbing `ls -c` is not evidence of delivery; the whisper tree on the collector is. The 4KB PIPE_BUF discipline every other writer here observes does not apply — one message is one datagram, written whole in a single `fwrite` with no cap and no split — so sizing belongs to the formatter in front, which is what `Probe_To_Graphite_Node::LINES_PER_MESSAGE` (16) is for. Anything else wired into a Graphite node owns that sizing itself, and an oversize VALUE becomes a fragmented or failed datagram, never several messages. Only TM_BYTESTREAM is written (a TM_STRUCT array reads as `''` through `Core::as_string()` and takes the empty-VALUE skip), so a struct producer needs a formatter in front.

`Newspack_Log_Node` fires `do_action( 'newspack_log', … )` under a `code` that becomes the Kibana filter key — a no-op where Newspack Manager is absent. `make_node Newspack_Log <name> <code>`: an absent or blank code throws `InvalidArgumentException` at make_node time rather than filing a worker's whole output under the empty string, where nothing could find it. `fill()` files only TM_STRUCT and TM_BYTESTREAM, so a TM_EOF drain or a TM_ERROR bounce is dropped without an entry, and the VALUE's SHAPE rather than the type flag picks the entry's shape: an array rides as the entry's `data` with the code standing in as the message text — so every struct entry from one node reads alike and everything distinguishing them lives in `data` — while any other VALUE rides as the text itself, trailing newlines trimmed. One entry is filed per MESSAGE, not per line, so with `Probe_To_Graphite_Node` in front a single Kibana entry's text holds up to sixteen metric lines. It declares `has_target: false` and forwards nothing, so reaching both collectors means a `Tee` in front of Graphite and Newspack_Log, never a chain through one into the other — and that fan-out is lossy in one direction, since a struct record lands in Kibana and disappears silently at the Graphite leg.

**Terminal I/O** is four nodes, two bare and two dressed. `Stdin_Node` reads lines off a stream and emits TM_BYTESTREAM, then TM_EOF on close, self-pacing at 0ms while busy, 10ms after EOF and 100ms idle — through a RECURRING timer, for the reason `Timer` gives about one-shot re-arms. `Stdout_Node` reads a message VALUE through `Core::as_string()` and `fwrite`s it verbatim through a protected `write()` seam, adding no newline and no framing and branching on nothing — so a TM_STRUCT and a TM_BYTESTREAM carrying the same scalar print identically, while a non-scalar VALUE writes nothing at all rather than the word `Array`. Rendering belongs upstream, so put a `Dumper` in front of a struct producer; the counter bumps on every fill regardless of what was written. `TTY_In_Node` and `TTY_Out_Node` add readline, tab completion and a prompt-aware redraw on top for `wp nodes cli`. Only the cli wires the dressed pair, and a topology line cannot: `TTY_Out_Node::node_schema()` declares `Hidden`, no arguments and no commands, so `make_node TTY_Out <name>` yields a writer that behaves exactly like bare `Stdout`. Every piece of its redraw state — the Shell reference through `set_shell()`, the readline branch through `set_readline_mode()`, the prompt flag — arrives through a PHP setter `CLI_Command::build_repl_graph()` calls after construction, because the writer is mounted before the Shell exists. A consumer graph wanting a terminal with no prompt to protect uses `Stdout_Node`.

Each line goes out as TM_BYTESTREAM whose VALUE is the raw `fgets()` return, terminator included when the stream supplied one, with FROM set to the reserved `Node_Names::STDIN` (`_stdin`) rather than the node's own name — a session leaves its reader unnamed, and `stamp_message()` refuses an empty name — and TO left empty, so the sink decides what a line means. The close emits exactly one TM_EOF carrying the same FROM and no VALUE, guarded so a post-EOF tick can neither re-emit it nor slide the deadline forward. With no sink wired both emits drop the message silently instead of throwing, which is what keeps a half-wired graph from failing on the first keystroke. In the cli graph that `_stdin` stamp is never observed: `Shell_Node::fill()` overwrites FROM with its own reply path, so only a non-Shell sink — reqgrep's `Callback_Node`, a test capture — ever sees it.

Two things about the stream itself bite. The constructor calls `stream_set_blocking( $stream, false )` on a handle the caller owns and nothing ever puts it back, so building one over `\STDIN` leaves the process's real stdin non-blocking for the rest of the run, and any other code sharing that handle afterwards has to set it blocking again itself, as `Ingest_CLI_Command::open_sources()` does before it reads. And because the read is non-blocking, `fgets()` on a PIPE returns whatever bytes are buffered, newline or not: a record straddling a pipe-buffer boundary is emitted as two separate messages and the node reassembles nothing. It is line-oriented over a terminal or a seekable file only. `wp nodes ingest` lost piped records to exactly this and runs its own blocking `fgets` loop instead; event-logger-nodes' `reqgrep` still drives a `Stdin_Node` over a pipe and silently skips anything `Message::unpacked()` refuses. Any consumer reading whole RECORDS off a pipe reassembles them itself or reads blocking.

Driving one takes a sink and a loop. `new Stdin_Node( $stream = \STDIN, float $eof_deadline_s = 5.0 )` needs a sink because `Timer_Node::fire_cb()` returns before `fire()` without one, so a sinkless reader never ticks and never reaches EOF, and it needs either a recurring `set_timer( 0 )` under `Event_Framework::drain( fn () => ! $node->exit )`, as `CLI_Command::run_repl()` does, or a hand-rolled `while ( ! $node->exit ) { $node->fire(); }`, as reqgrep does. The public `$exit` flag is that drain-until predicate — the node flips it `$eof_deadline_s` after TM_EOF goes out, and an owner may flip it early, as the cli's Dumper does on the TM_EOF echo. The footgun is the clock: `send_eof()` arms the deadline from `Core::right_now()` while `fire()` tests it against the cached `Core::$now`, and only the drain loop refreshes that clock, so under a hand-rolled loop a non-zero deadline never expires and the loop spins forever. A batch consumer therefore passes `0.0`, which is why reqgrep constructs `new Stdin_Node( $stream, 0.0 )`.

On the writing side the reserved name `_stdout` is a mount contract as well as a name. `Shell_Node::stdout()` — the one path every Shell builtin's text takes, from `print` and `var` through every usage line and the `got EOF while waiting for tokens` refusal — resolves `Core::node( Node_Names::STDOUT )` and requires an `instanceof Stdout_Node`; anything else, including nothing at all, sends the line to `Node::print_less_often()` and the rate-limited node stderr chain instead. Only `wp nodes cli` mounts `_stdout`, so a worker loading a `.tsl` has no terminal and a refused TSL statement surfaces in the stderr log rather than vanishing — and mounting some other class under the reserved name diverts every builtin there too.

**SSE egress** is two nodes that are also REST controllers. `SSE_Out_Node` registers `GET /newspack-nodes/v1/messages/stream` and names itself `_sse`, so as a Node its `fill()` writes each Message onto the open response while as a controller it builds the Router, the interpreter, the `_output` reply filter (an `HTTP_Filter_Node` bound to this process's pid) and the per-subscription Consumers inside the drain's `try`, and removes them in its `finally`. `Log_Stream_Out_Node` subclasses it and overrides two members — `ROUTE` (`/log/stream`) and `open_subscription()` — so the two endpoints stay byte-identical on the wire and differ only in what a subscription resolves to: a fixed `Log_Sources` registry NAME opened as a `Tail`, never a caller-supplied path, which is why there is no traversal surface. Neither declares a `node_schema()` category, so neither appears in the console palette.

**Command channel** is three nodes around the `/command` boundary. `HTTP_In_Node` registers `POST /newspack-nodes/v1/command` and names itself `_output`: as a controller it decodes the JSONL batch and fills the request-scope interpreter with each envelope in the order posted, serially, and as a Node its `fill()` writes the reply body, so an interpreter's TO=FROM answer walks that boundary back to the caller. It verifies and never signs ([Command authorization](#command-authorization-two-tier)). The reply decides the status: 200 once a synchronous reply is on the wire, 401 when a command in the batch failed verification, 202 when the batch routed onward with its replies due on the client's open SSE stream, and 429 past the per-user burst budget — `RATE_LIMIT_BURST = 30` POSTs per `RATE_LIMIT_WINDOW_S = 1` second, counted in fixed one-second buckets so a steady one-per-second client never climbs, and raisable through the `newspack_nodes/command_rate_limit` filter. `HTTP_Out_Node` is the push-side counterpart — a `Timer_Node` buffering TM_COMMAND envelopes and batching one JSONL POST per drain tick to a remote spoke's `/command` over the cURL-multi, with credentials and url resolved from the `Vault` entry its `<vault-id>` argument names and never from a caller; `probe_command()` runs the same protocol over one synchronous request for an operator action that must return a verdict now (Vault_CI `test`, Aggregator_CI `probe`). A spoke's reply comes back addressed `_output/<hub minter>`, since the spoke's `HTTP_In` stamped `_output` onto the arriving command's FROM — a head the hub's graph does not have and its `_router` would bounce — so `on_curl_message()` strips that one leading `_output/` before forwarding and `accept_inbound()` stamps this transport's own name onto FROM. One mutation on each field, and the TO=FROM round trip resolves on the hub because of them.

The browser end of that boundary recovers from two refusals, on independent paths. A REST error whose code is `rest_cookie_invalid_nonce` makes `commandTransport` call its `renewNonce` callback — `refreshNodesNonce`, which resolves the same `X-WP-Nonce` WordPress checks before `HTTP_In` ever sees the body — invalidate any command-signing session, since the old nonce derived it, and retry the same POST exactly once; a second failure is reported rather than retried. An HTTP 401 is the other case, a failed COMMAND signature rather than a WP nonce, and it calls `renewSession()`, which drops the local signing session and opens a doubling backoff window (`BACKOFF_START_MS` 1000ms, capped at `BACKOFF_MAX_MS` 30s) before the next command may mint — without it a session the server keeps refusing spins at the poll cadence.

`HTTP_Filter_Node` is the `_output` boundary inside an SSE stream process, bound to that process's pid: it accepts a reply whose TO head matches its own `_sse:<pid>`, strips that head, and forwards the remainder to the egress, so a reply reaches the browser tab that minted the command and no other. Everything else is dropped — an unaddressed broadcast as much as another session's reply, because `fill()` compares the whole head before doing anything with the message. That corollary is load-bearing elsewhere: `Core`'s default stderr handler picks its sink `_repl ?? _sse ?? _output`, and inside a stream process, where both `_sse` and `_output` are mounted, an empty-TO stderr line handed to `_output` would be swallowed here and reach the browser only through `error_log()`. The counter is bumped ahead of that comparison, deliberately, so `ls -c` on `_output` there reports what the gate SAW rather than what it passed; a climbing counter is not evidence that replies are reaching the tab. And the gate closes the READ direction alone. A process admits only replies bearing its own `getmypid()`, so no client can make its filter accept another session's traffic, but the head is client-composed — `Command_Auth::canonical()` signs semantics and never routing — so what stands between an ordinary user and another operator's console is the MANAGE default `Service_CI_Node` applies to `Topologies_CI_Node`'s `connect_worker_input`, not this filter.

**Settings_Sync** (`Settings_Sync_Node`) is the hub half of the settings control plane: a `Timer_Node` that re-pushes every registered `<local_option> <TO> <remote_option>` mapping to its connected spokes on an `interval_seconds` sweep (default 300). The mappings come from its `{name}:config add_setting <local_option> <TO> <remote_option>` verb, and `dump_config()` re-emits one line per mapping, so the graph round-trips. The middle token names the SPOKE-side mount that will answer `set`, not anything local: `send_set()` addresses each command at `<target>/<to>`, the Router peels the local `HTTP_Out` node name off the head, and what reaches the spoke's request-scope interpreter is `<to>` — `settings` for the substrate's own `Settings_CI_Node` in `settings-sync.tsl`, `performance` for event-logger-nodes' `Performance_CI_Node` in `hub-control.tsl`. Read that token off the receiving CI's mount name.

`Settings_Event_Writer` is the producer end — a plain static class, not a Node, because the option hooks fire in whatever request changed the setting, where no graph is running: each watched change builds a Partition, appends one record to `settings.p0` and tears it down inside the callback. WATCHED means the option NAME begins `newspack_`, the `WATCH_PREFIX` constant `maybe_emit()` tests first: an option outside it emits nothing — no `settings.p0` record, no Config Audit row, no push to a spoke — and nothing reports the omission, so a consumer plugin naming its option `my_plugin_foo` gets a pipeline that is inert at the very first gate. `init()` arms three hooks over that prefix, each recording a different pair: `on_update` carries both sides, `on_add` a NEW value only, and `on_delete` an OLD value only. The third is the non-obvious one and it is load-bearing, because resetting a setting to its default DELETES the option row — `Reset_Gate` short-circuits the update — so without `delete_option` a reset would fire no event and never reach the spokes. It runs pre-delete, where `get_option()` still returns the old value, and the downstream push then reads the absent option and ships the file default. Three audit rules govern the record itself. The option NAME always rides. Bounded old/new excerpts ride only for options on `newspack_nodes/settings_audit_values_allowlist`, which is a second and narrower gate inside the prefix one — a consumer's option can be allowlisted for excerpts and still be dropped for its name. The encrypted vault option is refused before that filter is consulted, so nothing can opt it back in. A name-only record fits under PIPE_BUF, which is what keeps the append atomic and lockless, and a values record that will not fit drops back to name-only rather than dropping the event.

A worker Consumer tails that log, and Settings_Sync looks each option up and pushes its CURRENT value at consume time — so the excerpts are an audit trail, never the payload a spoke receives. It can push the current value because `push()` drops WordPress's `alloptions` and `notoptions` caches before every `get_option()`, through the `Settings_Sync_Node::$invalidate_options_cache` seam; without that a worker living out its ~595-second lifetime would push the snapshot frozen at spawn and a concurrent admin save or a `Reset_Gate` delete would stay invisible until it recycled. A `set` command carries one token, so an array option is flattened by `scalarize()` as `wp_json_encode( $v, JSON_UNESCAPED_SLASHES )` and never as a join, because an option's array KEYS are data — event-logger-nodes' `custom_events` is `event_name => true`. The wire form for an array-typed synced option is therefore ALWAYS JSON and every spoke-side receiver has to decode it, as `Performance_CI_Node::decode_array_value()` does; a value that will not encode drops with a rate-limited `cannot encode value for <option>; skipping` rather than being pushed, because an empty token would WIPE the spoke's option. **Connect_Queue_Timer** (`Connect_Queue_Timer_Node`, mounted as `_connect_timer`) drains the shared `Remote_Link` connect queue one connect per tick, so a hub reconnecting to many spokes opens them in single file.

**Six `remote_*` config keys carry the spoke geometry a hub pushes**: `remote_segment_size` (64MB), `remote_min_segments` (2), `remote_num_segments` (8), `remote_max_segments` (0, letting the spoke derive twice its count), `remote_min_lifetime` (900s) and `remote_lifetime` (900s). Nothing local reads any of them — a local partition takes its geometry from the unprefixed `segment_size` family instead. `topologies/settings-sync.tsl` registers each one TWICE: once landing as the spoke's matching retention key (`remote_segment_size` → `segment_size`), and once as the spoke's own `remote_*` copy, so a spoke both adopts the geometry and propagates it on to ITS spokes.

## Backpressure (none)

There's no graph-wide ack/retry machinery. Synchronous I/O at every boundary serializes the whole graph onto one CPU: `Topic::fill` blocks on `Partition`'s `fwrite`; `Consumer::fire_cb` blocks on `read_at`; network-driven nodes pace at the network's speed. There's no decoupled queue between producer and consumer that could grow — each step finishes (commits to disk or returns) before the next message is accepted. All substrate-provided producers are fire-and-forget.

The hub pull is the one exception, because it is the one place such a queue exists. `SSE_In` appends to `Remote_Source_Node`'s pump buffer inside the drain loop while the tick drains it, so the buffer accumulates between ticks, and the node runs an edge-triggered hysteresis valve over its byte size: `pump_maybe_disarm()` fires from the `on_message` seam once the buffer crosses `PUMP_DISARM_BYTES` (512 KB), and `pump_maybe_arm()` fires from `get_batch()` once the drain has brought it back under `PUMP_ARM_BYTES` (256 KB). Disarming pulls the easy handle out of the shared cURL multi, so libcurl stops reading, the kernel receive buffer fills and the TCP window closes on the spoke — end-to-end backpressure rather than a local drop. The gap between the two marks is load-bearing: one threshold closes the valve on every buffered line and stop-starts the spoke, which is what makes a hub pull lag.

If an application needs slot-based flow control somewhere specific, build it at that producer. Don't add a graph-wide ack contract at the substrate — given how the I/O model works, it'd be dead weight. Where the problem is volume rather than pacing, the per-edge tools are the sieves: `Age_Sieve` sheds messages already too old to matter, and `Value_Timeout` collapses a repeating VALUE to one inside its window.

## TO=FROM Convention

Forward direction uses `TO=$this->target` (the path `connect_node` put there). Reverse direction (any kind of response, ack, or error) uses `TO=$message[FROM]`. One rule, applied uniformly:

| Direction | Sender | TO field |
|-----------|--------|----------|
| Forward | Producer / forwarder pass-through | `$this->target` |
| Reverse | Forwarder dropping / terminal acking | `$message[FROM]` |
| Reverse | TM_REQUEST handler responding | `$message[FROM]` |
| Reverse | Command_Interpreter_Node responding to TM_COMMAND | `$message[FROM]` |

Path-based routing via `_router` does the rest. Nodes don't track sockets or addresses; they stamp FROM at I/O boundaries on the way in, and reverse direction follows the trail back out.

**FROM stamping at I/O boundaries only**: the substrate's source nodes — **Tail** (`forward_line` sets FROM directly, honoring `stamp_override`) and **Consumer** (`stamp_message`, using `stamp_override` when set — the worker IPC input Consumer stamps `_repl`) — stamp FROM as messages enter the graph. The wire boundaries stamp too: `HTTP_In_Node`, `HTTP_Out_Node::accept_inbound()` and `Remote_Link_Node::deliver_downstream()`, which stamps the SSE_In sibling's name rather than the link's, so a record off a spoke reads `FROM=<link>:sse-in/<remote trail>`. That last one leaves TO alone while the link has no `target`, because an attached worker's reply carries its own TO=FROM breadcrumb and overwriting it strands the reply, and it drops — rate-limited — both an unparseable frame and one whose stamp would pass `MAX_FROM_SIZE`. It is the channel path only: `Remote_Source_Node` replaces the `on_message` seam with its buffering closure and stamps through `Durable_Reader::forward_line()` instead. Internal nodes (Tee, Hook, and any application Node subclass) do NOT stamp. A message flowing `tail -> tee -> request-builder` carries `FROM=tail`, NOT `tee/tail`. There is no `Job` or `Connector` node class in this runtime — `Job_Worker_Node` is a handler dispatcher, not Tachikoma's forked-process Job — so don't look for their stamping behavior either.

## Event_Framework

Per-process drain-loop singleton. Manages timers and one shared cURL multi handle. There is no FD-registration path: local file polling (Tail, Consumer, the cli's stdin reader) is driven by `set_timer`, so the loop always has exactly one blocking waiter regardless of which I/O sources are active.

cURL handles (used for HTTP/SSE clients) hide their underlying socket FDs behind cURL's API and have to be driven by `curl_multi_select` and `curl_multi_exec`. Each node registers its own **easy** handle; they all attach to one lazily-created multi handle, and a completion is routed back to the owning node's `on_curl_message()`. When at least one easy handle is registered, the loop sleeps on `curl_multi_select` (timeout = next-fire deadline); otherwise it sleeps in `usleep` for the same duration. Either way a soon-firing timer wakes the wait promptly.

Drain iteration:

```
0. should_continue(); break on false or on Core::$shutting_down.
1. Compute timeout_us = microseconds until soonest pending timer (or
   IDLE_TIMEOUT_US = 100_000 if no timers; 0 when one is already overdue,
   which skips the blocking wait entirely).
2. If any cURL multi handles registered:
     curl_multi_select($mh, $timeout_us / 1e6)  # sleeps on cURL's internal sockets
     drain_curl_multi()                         # curl_multi_exec + curl_multi_info_read
   Else if $timeout_us > 0:
     usleep($timeout_us)
3. pcntl_signal_dispatch() if pcntl available (SIGTERM/SIGINT -> Core::$shutting_down).
4. Refresh Core::$now.
5. Fire any timers whose next_fire <= Core::$now (oneshot timers unregister
   themselves; recurring timers re-schedule from Core::$now), then loop.
```

Step 3 dispatches whatever signal handlers already exist; it installs none. The SIGTERM/SIGINT → `Core::$shutting_down` mapping comes from `install_signal_handlers()`, and only two callers make it: `Worker_Base::execute()` and event-logger-nodes' `Reqgrep_Command::follow_mode()`. `CLI_Command` and `Rest\SSE_Out_Node` do not, so those two drains take each signal's default disposition and die mid-tick rather than finishing it and running teardown. A new long-running process entering `drain()` installs the handlers itself.

Step 4 is what makes `Core::$now` the clock a node reads. `Core::right_now()` is its one production writer — tests pin the property directly — so inside the drain loop read the cached property, which the loop refreshes every tick. Call `right_now()` only outside the drain, in request or CLI scope, or after a blocking call: `$now` stays frozen at the tick's start for the whole duration of a long `fill()`, so a job handler stamping `Message::TIMESTAMP` from it records when the tick began rather than when the job finished. That is why request-scope substrate code reads `Core::$now ?: Core::right_now()` and why `Job_Worker_Node` brackets a job with `right_now()` at both ends.

There is no deferred-cleanup step in the loop (and no `Core::$closing` queue); teardown cleanup is `Core::cleanup_all_nodes()`, invoked by Worker_Base's shutdown handler / `finally` after `drain()` returns (so Partitions release their locks before the next spawn).

**`pump()` is the cooperative-stop seam.** A long in-process job starves the drain loop, so the worker's own deadline would pass unnoticed; `Event_Framework::pump()` re-runs the parked continue-predicate from inside that job (Partition calls it on every write) and raises `Worker_Should_Stop` when it says stop. It is throttled to once per `PUMP_INTERVAL_S = 1.0` against the live clock — `Core::$now` is frozen for the duration of a blocking job, so routing through `right_now()` also un-freezes message timestamps at pump cadence. It no-ops unless a cooperative-stop drain is active, which is why `drain()` takes the flag: only `Worker_Base` opts in, so cli and SSE drains can never be thrown out of. `stop_check()` is the decision itself, unthrottled — what a caller asks after finishing a unit of work that needs the answer NOW rather than up to a second later, such as a subprocess render that may have outlived the lease. It returns early while `Core::in_stderr()`, because a stderr write is not a stop boundary and logging the stop would self-throw. The `Worker_Should_Stop` it raises unwinds the whole `fill()` stack, because broad drain-path catches re-throw it before handling ([ADR-14](architecture-decisions.md#adr-14-cooperative-stop-propagates-through-broad-catches)).

**`Deferred_Clean_Stop` is the write side of that protocol**, and sibling plugins' snapshot nodes are its consumers. A node that forwards downstream mid-`fill()` — typically into a Partition, which flushes the record to disk before honoring the stop — still owes that message its own bookkeeping, so unwinding there leaves the record durable and the node's state half-updated, and the successor replays a message the restored snapshot already counted. The trait defers instead: `guarded( $forward )` catches a `Worker_Should_Stop` and holds it (first one wins; a non-stop throwable propagates to the Consumer's dead-letter path), and `raise_pending_stop()` re-raises it at exit as a FRESH `Worker_Should_Stop_Clean`, which `Durable_Reader::drain_buffer()` reads as permission to commit PAST the record rather than replay it. A using `fill()` must call `clear_pending_stop()` at entry and `raise_pending_stop()` at every exit — a stop held over from an earlier message would otherwise raise at a later one's exit, committing past a record nothing forced to disk.

Registration API:

```php
// Timers: subclass Timer_Node and arm the timer FROM the node — never call
// Event_Framework's timer method directly. Timer_Node::set_timer() picks the
// mode (own slot vs Router hitchhike) and hands $this to Event_Framework.
class My_Timer_Node extends Timer_Node {
    protected function fire(): void { /* periodic work */ }
}
$node->set_timer( $interval_ms, $oneshot = false );   // Timer_Node::set_timer
$node->stop_timer();                                  // Timer_Node::stop_timer

$ef = Event_Framework::instance();        // per-process singleton
$ef->drain( $should_continue, $cooperative_stop = false );
$ef->pump();                              // re-check the predicate mid-job, throttled
$ef->stop_check();                        // …the same decision, unthrottled
$ef->register_curl_easy( $node, $easy );  // \CurlHandle, attached to the shared multi
$ef->unregister_curl_easy( $easy );
$ef->curl_handles();              // per-node rows for `list_handles`
$ef->install_signal_handlers();   // SIGTERM/SIGINT -> Core::$shutting_down
$ef->is_running(): bool;          // true while inside drain()
Event_Framework::reset();         // drop the singleton (tests)
```

A test harness between cases calls `Core::reset()`, not this one: `Core::reset()` calls `Event_Framework::reset()` itself, so an orphaned node's armed timer cannot outlive the graph that armed it. It returns the process to boot state — the node registry, the shutdown flag, the 100-line `dmesg` ring and its rate-limiter timers, the stderr re-entry guard, the Shell `var` map, `$memd`, `$secure_level`, the memoized log host and `Cache_Backend`'s memoized site, salt and machine — then reinstalls the default stderr handler and restamps `$init_time`. Four members survive, because they are process wiring rather than per-run state: `$config_resolvers`, since nothing re-registers a namespace after boot and dropping the map would leave every `<ns:key>` token unresolvable, plus `$curl_exec`, `$verify_spawn_tls` and `$log_timeout`. `class-core.php` calls `Core::reset()` at load, so requiring the plugin is enough to have a usable Core.

`Event_Framework::$curl_poll` is the poll seam: a closure standing in for the `curl_multi_exec` + `curl_multi_info_read` pair, so a test scripts completions without a network while the ownership lookup and dispatch stay real production code. A completion is routed by the handle's `spl_object_id` to its owner's `on_curl_message()`; a node without that method is skipped rather than fataled, since `Node` does not declare it.

PHP I/O quirks the implementation handles:

- Never `ftell` — the substrate does not call it anywhere. PHP's stdio caches the handle position, so it reports stale values after an external append; a reader carries its own byte cursor instead and every read is an absolute `fseek( $fh, $offset )` before the `fread`.
- `clearstatcache(true, $path)` before every stat in poll loops — PHP caches stat results aggressively per request, so a peer's append or a rotation would otherwise be invisible.

## Lock

Mkdir-based advisory locking with a PID-stamped heartbeat file. Used by workers and `Partition::allow_large_writes()`. Atomic on every filesystem we ship on (NFS, tmpfs, ext4 — `mkdir(2)` is the POSIX-mandated atomic primitive). No `flock`, no daemon, no DB row.

The surface (`includes/class-lock-node.php`):

```php
class Lock_Node extends Node {
    public const STALE_TIMEOUT  = 60;          // seconds without heartbeat → stale
    public const ORPHAN_GRACE_S = 1;           // dir-but-no-heartbeat grace before stealing
    public const HEARTBEAT_FILE = 'heartbeat'; // contains the holder's PID
    public const STARTED_FILE   = 'started';   // acquire() timestamp
    public const RESTART_FLAG   = 'restart';   // restart sentinel: exit, then refill the slot
    public const STOP_FLAG      = 'stop';      // stop sentinel: exit and leave the slot empty
    public const RELOAD_FLAG    = 'reload';    // config-reload watermark the _fleet scan takes

    public function __construct( string $lock_path, int $stale_timeout = self::STALE_TIMEOUT );

    public function acquire( int $max_wait_ms = 0 ): bool;
    public function acquire_failure(): string;    // 'lock_held' = contention; anything else is an I/O diagnosis
    public function release(): void;
    public function heartbeat(): bool;            // verify_ownership() then touch
    public function verify_ownership(): bool;     // read PID, compare to getmypid(); flips is_held on mismatch
    public function is_held(): bool;
    public function restart_reason(): string;     // '' to keep running; else why it should exit
    public function stop_requested(): bool;       // the stop sentinel alone

    public static function force_release_at( string $lock_dir ): void;   // UNCONDITIONAL clear
    public static function request_restart_at( string $lock_dir ): bool;
    public static function request_stop_at( string $lock_dir ): bool;
    public static function request_reload_at( string $lock_dir ): bool;
    public static function clear_stop_at( string $lock_dir ): void;
    public static function is_restart_pending( string $lock_dir ): bool;
    public static function heartbeat_is_stale( string $lock_dir, int $now, int $stale_timeout ): bool;
    public static function stale_timeout_of( array $descriptor ): int;
    public static function get_started_time( string $lock_dir ): ?int;
}
```

`Lock_Node` extends `Node`: its `fill()` refreshes the lock on a `KEY='heartbeat'` message and forwards anything else via `parent::fill`. Release is unconditional via the static `force_release_at()`, which unlinks all five files this class writes — `heartbeat`, `started`, `restart`, `stop` and `reload` — before the `rmdir`; there is no instance `force_release()`. The list has to be exhaustive because `rmdir()` removes only an empty directory, and one survivor turns every clean release into an orphaned lock dir peers steal through the `ORPHAN_GRACE_S` window. That is why the `reload` watermark goes too, though its consumer never unlinks it (losing it costs nothing: the successor boots on fresh config), and why the `stop` flag goes with the dir, leaving the persisted deploy hold as the only thing keeping the slot empty afterwards. The `restart` flag has no explicit `clear_restart()`. Three paths clear it: `write_acquire_files()` unlinks it on the next successful `acquire()`, `release()` takes it through the static above, and `steal_atomically()` destroys the whole dir.

**Acquire**: atomic `mkdir`. If the dir already exists, `try_steal_orphan_or_stale()` decides whether to take over — an *orphan* dir (no heartbeat file → possible mid-acquire) is honored for `ORPHAN_GRACE_S` then stolen if still empty; a *stale* dir (heartbeat mtime older than `stale_timeout`) is stolen immediately; otherwise back off, and either return false or retry every 100ms until `$max_wait_ms`. On success it writes the `heartbeat` (PID) + `started` (timestamp) files and clears any inherited `restart` flag. The steal itself is a `rename()` of the dir aside, then a `mkdir` of the canonical path: of two racers exactly one rename succeeds, and the single-holder guarantee still rests on that final `mkdir` — a third process racing the brief absence hits the same path and one of them loses. `acquire_failure()` distinguishes contention (`lock_held`) from an I/O refusal, which is what lets a skipped spawn stay quiet while a broken directory gets logged. A symlink planted at `heartbeat` / `started` is refused rather than followed.

**Heartbeat**: workers touch their heartbeat every 10s during drain. `heartbeat()` calls `verify_ownership()` first; if the on-disk PID no longer matches `getmypid()` (someone stale-stole us), it flips local `is_held=false` and returns false so `release()` becomes a no-op and the displaced holder stops writing. `Partition::fill()` calls `heartbeat()` inline on the no-event-loop large-write path.

**`release()` verifies too, and fails closed.** It re-reads the heartbeat PID rather than trusting the local `is_held` flag, and that asymmetry is load-bearing: `restart_reason()` reports `lock stolen by pid N` while deliberately leaving `is_held` alone, so a flag-only check would have an evicted holder `force_release_at()` the SUCCESSOR's directory — the successor then dies of `lock heartbeat gone` on its next tick and both respawn, turning a self-correcting handoff into a restart loop. Failing closed leaks a dir at worst, and a leaked dir goes stale and is stolen normally.

**Stale takeover**: once `STALE_TIMEOUT` elapses without a refresh, the next acquirer steals the dir and the displaced holder fails its next heartbeat and exits. This is what the peer scan relies on, and it's how concurrent `wp nodes restart` invocations don't fight over slots.

**`restart_reason()`**: workers call it on every drain tick and exit cleanly on any non-empty answer. Three unrelated situations end a worker through this one channel, and each names itself rather than reporting a bare "restart requested" an operator cannot place: `restart requested` (the `restart` sentinel is present), `lock heartbeat gone`, and `lock stolen by pid N` (PID-content theft). Every stat clears the cache first, since a long-running worker otherwise never sees a flag another process wrote.

Three statics let a stranger — an admin request, a peer's scan, the cron sweep — signal into another process's lock dir with no `Lock_Node` instance. `request_restart_at()` writes the `restart` sentinel, so the slot is refilled; `request_stop_at()` writes `stop`, which `should_continue()` checks FIRST and which leaves the slot empty; `request_reload_at()` writes the `reload` watermark the `_fleet` scan takes to invalidate the config cache.

All three funnel through `write_flag_at()`, which refuses on two conditions before touching disk: the lock dir does not exist, and `Config::write_denied()` — running as root, where the file would land root-owned and unwritable by the workers. The first means the lock dir IS the signal channel, with no queue behind it: a slot reading `down` or `idle` in `wp nodes status` holds no dir, so a restart or reload aimed at it writes nothing and evaporates. That is harmless — a slot with no holder respawns onto fresh config anyway — but it is why `Requested restart for N worker(s)` can name fewer workers than the fleet declares.

The `reload` flag is the odd one of the three, and treating it like the other two breaks it. `restart` and `stop` are sentinels whose PRESENCE is the signal; `reload` is a watermark compared by CONTENT. `request_reload_at()` writes a fresh `time().'.'.bin2hex( random_bytes( 6 ) )` on every call, unconditionally rewriting whatever stands there, and `Fleet_Node::take_reload_watermark()` acts whenever the content differs from the one it last acted on — it never unlinks. Mtime cannot carry the signal, because the filesystem resolves to a second and one settings save writes several options in one request, so a second request inside that second would be lost rather than merely late; consuming by unlink would lose a request landing mid-reload, and comparing survives a lock steal.

## Topologies (TSL)

A worker's graph is described in a `.tsl` file — a script of the same shell verbs the REPL speaks, executed at boot against the worker's `_command_interpreter`. Nothing about a topology is a data structure the runtime interprets; it is commands, run once, and the graph they leave behind in `Core::$nodes_by_name` is the worker.

```
# topologies/topic-probe.tsl
make_node Topic_Probe topicprobe 15
make_node Partition  topicprobe:log <config:logs_dir>/topicprobe.p0 1048576 2 8 0 86400 86400
connect_node topicprobe topicprobe:log
secure
```

**`Topology_Registry` answers where a name lives.** A plugin calls `register_plugin( $namespace_prefix, $topologies_dir )` once at boot, which registers both its class namespace with `Command_Interpreter_Node` and its stock topology dir. Stock dirs OWN their names and resolve newest registration first, with the substrate's own bundled dir appended last, so a consumer overrides a builtin by shipping a same-named `.tsl`. The writable per-deployment user dir serves only names no stock dir provides, because a writable directory that can shadow a stock topology is code execution. `activate()` and `deactivate()` are the one primitive behind both the `topologies` CI verb and `wp nodes activate` / `deactivate`: write the option, invalidate the config cache, then spawn the fleet or kill its readers. `activate()` refuses a write-conflicting set BEFORE it is persisted.

Both compute the next set from `array_keys( Bootstrap::get_topologies() )` — the EFFECTIVE set — and `update_option()` writes that whole list, so neither write is a targeted add or remove, and two consequences follow. The option layer resolves by PRESENCE, so the first `activate` or `deactivate` on an install promotes every name the shipped config file (or `LOCAL_NEWSPACK_NODES_CONF`) contributed into the option row, after which edits to that file's `topologies` key are inert — a `deactivate` of the last topology stores `[]` and masks the file entirely. And `get_topologies()` drops any selected name `synthesize_entry()` cannot resolve to a `.tsl`, so deactivating topology B permanently removes from the persisted set any active name whose provider plugin was deactivated or whose file was deleted; re-enabling that plugin does not restore the activation, and `wp nodes status` is the only place the loss shows, as `inactive`.

**`Topology_Loader::load( $name, $partition, $sink )` binds the two tokens a topology cannot know about itself.** `<partition>` and `<topology>` go into `Core::$var` before the file is evaluated; every `<ns:key>` token (`<config:logs_dir>`) resolves through the resolver its namespace registered at boot, so the loader installs no config of its own. `<topology>` names the FLEET, and that is what lets two topologies declare BYTE-IDENTICAL Consumer lines — composing them with `include` then collapses to a single reader — while each standalone fleet still gets its own offsetlog. The Shell it builds runs with `want_reply( false )`, so no boot reply routes to an `_output` no worker has, and `fatal_errors( true )`, which converts exactly two conditions into throws: an include cycle, and input still pending at end of file (an unterminated quote or a backslash continuation). Nothing else is fatal. A per-statement failure — a typo'd node type, a `make_node` redeclaration conflict, a `connect_node` naming a node nothing built, a verb the `secure` level refuses — is caught by `Command_Interpreter_Node::interpret()`, turned into a reply, and diverted by `want_reply( false )` to stderr as `error from TM_NOREPLY command: …`, so the rest of the file runs and the worker still reports `ok`. A half-built graph is the normal outcome of one bad line; the stderr is where it says so.

**Frontmatter is `var` lines the runtime reads statically**, without executing the file. `Topology_Analyzer::frontmatter()` parses them and `Topology_Registry::synthesize_entry()` folds three into the catalog entry: `num_partitions`, `stale_timeout` and `on_demand_idle`. Each is read through the VALIDATED `Core::num_int`, and a `num_partitions` or `stale_timeout` declared zero or negative takes the fleet default instead — zero partitions is no fleet at all, and a zero stale timeout makes every worker read as instantly stale, which is continuous respawn churn. `on_demand_idle` is exempt, because 0 is its meaningful "stay resident" value.

Those same three keys are the only ones with typed controls in the topology console's edit-mode Settings panel, so a frontmatter change need not be hand-typed into the file: each gets a number input whose placeholder is the value the key would inherit from config, `num_partitions` is clamped client-side to `Spawn_Coordinator::MAX_PARTITIONS` (16), and every other `var` gets a generic name/value row. The panel edits the secure level beside them through a select, because that is a STATEMENT rather than frontmatter and rides the interpreter's `secure` / `insecure` / `clearSecure` instead of the frontmatter map.

**`Topology_Analyzer` reads a topology without running it.** It flattens the include tree (cycle guard, `#pragma once`, `make_node` dedup-or-conflict), builds two node-and-edge graphs (`graph_for()`, the flat structural one behind `Workers_CI`'s `dump_graph` payload, `Restart_Planner`, `Log_Sources` and the event dashboards, whose edges are bare from/to pairs; and `expand()`, the include-set composition carrying per-node provenance that the topology console edits against through the `topologies` CI's `expand` and `get` verbs), resolves the directories a topology declares (`resolved_resource_dirs`, `resolved_node_dirs`), and derives the WRITE SET that `find_conflicts()` and `Log_Cleaner` gate on. Two topologies whose write sets overlap would put two worker processes on one file: a partition BOTH declare with the same `make_node` line is a deliberately shared multi-writer log and is not a conflict — appends at or under PIPE_BUF are atomic, the rotate lock covers the rest — unless either side lifts the write cap, which asserts a sole writer. Offsetlogs and dead-letter dirs stay sole-writer, so any overlap there conflicts. It sits apart from `Topology_Registry` so that READING a topology pulls in none of the spawn path's dependencies.

**`Shell_Node::parse_statements()` is the static TSL front-end underneath all of that** — the one the analyzer, `Topologies_CI_Node`'s `save` and `expand` verbs and the browser topology editor all read, with the live Shell's grammar and tokenizer but no interpolation, no `Core::$var` reads, no dispatch and no node construction. Each statement comes back as `{ verb, values, spans, raw, line }`: `verb` is the canonical verb after `VERB_ALIASES`; `values` the quote-stripped tokens, with `values[0]` the verb and a minting verb's path argument already cwd-resolved; `spans` those same tokens with their quote characters and escapes verbatim, which is what a round-trip must emit so a deferred `'<partition>'` is never rewritten as an eager `"<partition>"`; `raw` the canonical single-line form two topologies are compared on; and `line` the 1-based first physical source line. A quote or a backslash continuation left open throws `got EOF while waiting for tokens`, which is what makes `topologies save` answer `validation failed: …`. The cwd is the caveat: a statement written after a `cd` comes back rewritten as `command_node <cwd> <verb> …`, so a consumer keyed on `'make_node' === $statement['verb']` skips it silently.

Every declared-directory NAME in the substrate comes from one call, `Core::first_level_dir( $concrete, $root )` — the first path segment of a resolved template under the logs or offsets root — so a nested template such as `<config:logs_dir>/req/<partition>` is declared, retained and swept as `req` rather than as its leaf. `segment_size_overrides_for()`, `resolved_resource_dirs()` and `Log_Cleaner`'s declared and producer sets all reduce through it, which is why an override and the directory it describes cannot be spelled differently and why the retention sweep matches no `.p{N}` suffix. A template resolving outside the root yields `''` and declares nothing, which is legitimate rather than a failed expansion — with one exception: in `Log_Cleaner::producer_log_dirs()` a registered producer declaring nothing under the root anywhere in the partition range fails the whole sweep closed, rather than letting that producer's live dirs read as orphans.

**A broken `.tsl` throws, and who catches it decides what the failure costs.** `statements()` — the flatten every other reader goes through — raises `\RuntimeException` on an unknown topology, an unknown or cyclic `include`, or a `make_node` two files declare differently, and `write_set()`, `find_conflicts()`, `resolved_resource_dirs()`, `resolved_node_dirs()`, `segment_size_overrides_for()`, `declares_node()` and `includes()` all let it out. That is deliberate: an empty write set reads as "no conflict" to `find_conflicts()` and as "every one of these logs is an orphan" to `Log_Cleaner`, so a gate that swallowed the exception would corrupt or delete instead of refusing. The safety gates therefore let it through — `Topology_Registry::activate()` refuses the activation, and `Spawn_Coordinator::spawn_each()` spawns nothing for the whole set — while the display surfaces catch, so one bad file cannot take out wp-admin: `graph_for()` catches internally and answers an empty graph, and `Log_Cleaner::declared_dirs()` and `Workers_CI_Node::collect_segment_size_overrides()` catch at their call sites, the first failing CLOSED by skipping the sweep entirely. An unknown NAME is the asymmetry to know: `graph_for()`, `write_set()`, `segment_size_overrides_for()` and `includes()` return empty for one, where `statements()` throws.

**A `cmd <node>:config set_*target <target>` line is a routing edge, not a config verb.** Both `expand()` and `graph_for()` treat a `command_node` addressed at `<node>:config` whose verb matches `/^set_\w*target$/` as an edge from that node to the argument, resolved through `Core::resolve_config_tokens()`; every other `:config` verb rides on the node as a `{verb, args}` entry the Inspector shows. Setting the same slot again MOVES the edge, because `set_config_edge()` clears that slot from the node's other edges first, and an empty target clears the slot and adds no edge. Nothing about that is a corner case: event-logger-nodes' `request-builder.tsl` routes four of its five outputs with `set_alerts_target`, `set_errors_target`, `set_inflight_target` and `set_completed_target`, so a reader who believes `connect_node` is the only routing verb sees one output where the node has five. The static graph mirrors the runtime's replace-versus-append rule too: `connect_edge()` replaces a non-fan-out source's single target while a source whose class uses `Fanout_Targets` — asked through `type_fans_out()`, Tee-token first — appends. And `disconnect_node` with no target is a no-op on a fan-out source, because at runtime an omitted target there means the issuing command's FROM, which a static walk has no way to know.

**Every stock topology ends with `secure`.** Once the graph is built, nothing should be able to rebuild it — see [Secure levels](#secure-levels). The substrate ships four: `job-worker.tsl` (the job pool), `job-intake.tsl` (drains the large-write ingress on substrate-only installs), `settings-sync.tsl` (the single-instance hub control plane) and `topic-probe.tsl` (the consumer-stats sweep, which the others `include`).

**Reserved node names** live in `Node_Names`, one constant per underscore-prefixed name the substrate claims: `_router`, `_command_interpreter`, `_fleet`, `_repl`, `_output`, `_stdout`, `_stdin`, `_shell`, `_completion`, `_cwd`, `_dmesg`, `_heartbeat`, `_http`, `_metadata`, `_sse`, `_uptime`, `_connect_timer`, `_settings:log`. Sixteen of the eighteen name a node something in the tree mounts, and which RUNTIME mounts each is what separates a category error from a bug: `Core::node( Node_Names::METADATA )` answers null in every worker, by construction. Five are mounted on both sides — `_router`, `_command_interpreter`, `_output`, `_shell`, `_stdout`. Four are PHP-only: `_fleet` and `_repl` from `Worker_Base`, `_sse` from `SSE_Out_Node`, `_connect_timer` from `Connect_Queue_Timer_Node`. Seven exist only in the browser graph: `_http` and `_heartbeat` from `mountExospine`, `_completion`, `_cwd` and `_metadata` from the debug overlay's REPL hook, `_dmesg` and `_uptime` from the topology console's graph hook — though PHP's `HTTP_Out_Node` still stamps `_http` into FROM. The last two mount nothing at all. `_settings:log` is held in reserve and nothing registers under it, so a grep for the value finds the constant and its JSON twin alone; `_stdin` is claimed as a STAMP, written into FROM on the lines and the TM_EOF marker `Stdin_Node` emits, and never handed to `name()` — the cli leaves its `TTY_In_Node` reader anonymous. A topology naming its own node one of the mounted names collides with the scaffolding at construction time.

`src/runtime/reserved-node-names.json` is the CANONICAL map and `Node_Names` its PHP half, held together by `tests/unit/NodeNamesTest.php`, which asserts the mapping in both directions — every JSON key has a same-named const with the same value, and every string-valued const appears in the JSON. Neither file is generated from the other, so adding a reserved name means editing both by hand. The guard filters to string-valued constants, which is why the array-valued `SESSION_SCAFFOLDING` is deliberately absent from the JSON and the JS keeps no equivalent list.

The `SESSION_SCAFFOLDING` subset is doubly protected: `dump_config` skips those names (a replay already has them, so emitting one would build it twice) and `remove_node` refuses them, because destroying `_router` makes no addressed message deliverable and destroying `_command_interpreter` runs no further verb. It holds eight — `_command_interpreter`, `_connect_timer`, `_fleet`, `_router`, `_output`, `_shell`, `_stdin`, `_stdout` — and no single session mounts all eight, so read it as the protected set rather than as "what a session mounts for itself". Two per-session egress names sit OUTSIDE it: `_repl`, the output Partition `Worker_Base` mounts, and `_sse`, which `SSE_Out_Node` names itself. Neither has a patron, so a worker's `dump_config` emits a `make_node Partition _repl …` line carrying that worker's own IPC output directory — which a console replay would rebuild pointing into another process's IPC dir — and `remove_node _repl` succeeds, severing the reply path any attached `wp nodes cli` is reading.

## Worker Lifecycle

A worker is an HTTP request that outlives its caller. `Core::fire_and_forget_post()` POSTs to `/newspack-nodes/v1/workers/spawn` on a 250ms budget (`SPAWN_POST_TIMEOUT_MS`) and hangs up; the handler survives that abort on `ignore_user_abort( true )` + `set_time_limit( 0 )`, runs the worker inline for its whole lifetime, and writes its `WP_REST_Response` only once the graph is torn down. Nothing detaches from FPM or the process group — the process holding the spawn connection IS the worker. Lifetime is ~595s (`Cooperative_Stop::DEFAULT_MAX_RUNTIME`, just under 10 minutes, sized for Atomic's 15-minute request cap with margin).

`fastcgi_finish_request()` is deliberately absent: completing the response early hands WordPress one it can no longer send, and no caller waits for the reply anyway ([ADR-8](architecture-decisions.md#adr-8-worker-zombie-pattern)).

```php
// Worker_Base::execute( callable $topology, string $spawn_url, string $token )
if ( ! $this->acquire() ) return [ 'status' => 'skipped', 'reason' => $this->lock->acquire_failure() ];

register_shutdown_function( /* handoff + cleanup_all_nodes + release + self_respawn */ );
usleep( LOCK_CHECK_GRACE_S * 1e6 );             // 250ms: let a racing spawn read the lock as held

try {
    $ci = $this->build_scaffolding();           // _router, _command_interpreter, _fleet, _repl, IPC input
    $this->run_topology( $topology, $ci );      // a bad .tsl: log, release, return 'load_failed', NO respawn
    $this->baseline_memory = memory_get_usage( true );
    $ef = Event_Framework::instance();
    $ef->install_signal_handlers();
    $ef->drain( fn ( bool $mid_work = false ) => $this->should_continue( $mid_work ), cooperative_stop: true );
} finally {
    $this->shutdown_handoff();                  // sweep the Shutdown_Sweepers, then checkpoint each durable reader
    Core::cleanup_all_nodes();                  // tear down Partitions -> release write_locks
    $this->release();                           // release BEFORE spawn
    if ( $this->should_self_respawn() ) {
        $this->self_respawn( $spawn_url, $token );  // POST /spawn (fire-and-forget)
    }
}
```

Lock release happens **before** the spawn POST inside `finally`. Because the spawn handler is fire-and-forget, the new worker reaches `acquire()` before this process has even fully exited; the slot is immediately free. No retry loop, no waiting.

`release()` is itself two ordered steps, and the order is as fixed as the one above. It calls `Partition_Node::flush_pending_wakes()` first, while the lock still reads HELD, and only then drops the lock. `Spawn_Coordinator::wake_on_demand()` judges a reader absent by its lock dir, so a wake flushed after the release — for a partition this worker itself tails, its own IPC input included — would find the slot free and spawn a duplicate alongside the `self_respawn()` that follows.

The `$token` handed to `execute()` was minted when this worker was spawned, so by respawn time it is roughly `max_runtime` old, far outside the endpoint's current-and-previous 10-second HMAC windows. `self_respawn()` therefore mints a current-window token through the `Worker_Base::$token_provider` closure, which `Bootstrap::ensure_runtime_wired()` points at `Spawn_Coordinator::generate_spawn_token( time() )`, and falls back to the boot token only when that seam is unwired, which is the bare-test case. Leave it unwired in a real runtime and every self-respawn POST is refused as an invalid spawn token, degrading succession silently to the `_fleet` peer scan and the cron tier.

The `register_shutdown_function` + `finally` block both check `$this->shutdown_handled` so a clean `exit()` doesn't double-run the cleanup; whichever path fires first wins.

`should_continue( bool $mid_work = false )` lives in the `Cooperative_Stop` trait, owns every stop trigger for every worker type, and is the only thing that beats the lock. It returns false when, in this order:

- the lock is no longer ours, or its directory is gone.
- `Lock::stop_requested()` — checked BEFORE restart, because a stop leaves the slot empty while a restart refills it. Category `stop`.
- `Lock::restart_reason()` is non-empty — the restart flag, a vanished heartbeat, or a stolen lock, each named.
- max_runtime (`DEFAULT_MAX_RUNTIME = 595`s) reached — category `timeout`.
- memory ≥ `MEMORY_WATERMARK_PCT = 0.80` of `memory_limit` (PHP fatal-on-OOM bypasses `finally`; bail proactively) — category `memory`.
- the DB liveness probe failed `DB_CHECK_MAX_FAILURES = 3` times consecutively.
- every `Idle_Reporter` in the graph has been idle for the whole on-demand window — category `idle`, and skipped under `$mid_work`.

The predicate runs on every drain iteration, and again from `pump()` (at most once a second) while a long job is starving the loop. Three of its branches are throttled inside it: the heartbeat touch fires every `HEARTBEAT_INTERVAL_S = 10` seconds, the DB liveness probe every `DB_CHECK_INTERVAL_S = 30`, and the idle scan every `IDLE_CHECK_INTERVAL_S = 1` (it lists segments and stats the newest, so per-tick disk I/O would spend more than the residency it gives back). `$mid_work` skips the idle branch outright: work is in flight by construction, so "has everything been quiet for the whole window?" can only answer wrongly. `LOCK_CHECK_GRACE_S = 0.25` is not a throttle — it is a one-shot pre-drain pause, so a spawn racing this one reads the lock as held before it retries.

**`shutdown_handoff()` runs two steps in order.** It first sweeps every node implementing `Shutdown_Sweeper`, flushing accumulated-but-unreported state while the graph is still intact, and only then checkpoints the durable readers' cursors. Opting in is the whole contract — `Worker_Base` names no class, and the probes use it to emit the partial interval a ~595s recycle would drop — but the sweep walks `Core::$nodes_by_name`, so an implementor that never took a name is never swept. Do the work synchronously: the drain loop has ended, so a timer armed from `shutdown_sweep()` never fires. A sweeper that throws is caught, logged rate-limited and skipped, because the cursors matter more than any one sweep.

`timeout` and `memory` are the *cooperative* categories, and the shutdown handoff treats them differently from an operational stop: both route each durable reader through the fair-shot rule, which strikes an in-flight poison message and clears an innocent one; everything else is a clean graceful checkpoint ([ADR-12](architecture-decisions.md#adr-12-dead-letter-poison--crash-lifecycle)). A `memory` stop whose fresh post-reset baseline was already past `BASELINE_WATERMARK_PCT = 0.50` blames a leak or an undersized `memory_limit` instead — it alerts and strikes nothing. On a FATAL shutdown (`is_fatal_shutdown()`) the handoff is skipped entirely, which is what lets a deterministic poison message climb toward the crash threshold.

The shutdown handler catches `exit()` / `die()` calls that bypass `finally`, releases the lock, and lets a peer respawn it quickly.

**Memory watermark rationale**: `wp_generate_attachment_metadata` loads full-resolution images into GD; per-job residue accumulates; PHP's fatal-on-OOM is uncatchable and bypasses `finally` / `self_respawn` / offsetlog flush. 80% watermark lets workers exit cleanly before OOM.

## Fleet Revival

There is no supervisor process. Every worker revives its peers, and WP-Cron catches a fleet
with nothing left running.

`Worker_Base::build_scaffolding()` mounts `_fleet` (`Fleet_Node`, a `Timer_Node`) alongside
`_router`, `_command_interpreter`, the `_repl` output Partition and the anonymous IPC-input
Consumer. It hitchhikes the router heartbeat but arms at
`SCAN_INTERVAL_MS = 15000`, so `Timer_Node` throttles it to one pass every 15 seconds:

```
every 15s:
    if a reload watermark landed in this worker's lock dir:
        Topology_Registry::invalidate_config_cache() + notify RELOAD
    re-read the active fleet,
    defer newly-appeared types NEW_TYPE_SPAWN_DELAY_SCANS = 1 scan,
    drain every worker if the last topology was deactivated
    for each active-fleet worker, at most MAX_SPAWNS_PER_TICK = 4 per pass:
        if worker_needs_spawn (a stale heartbeat, or a missing lock dir on a
                topology that is not on-demand):
            if last_spawn for this worker > 15s ago, and past any new-type deferral:
                POST /spawn   (fire-and-forget)
```

A faster scan would only reach a MISSING lock dir sooner — the stale-heartbeat case is
dominated by `stale_timeout` (60s default) either way — and a crashed worker's queue is
durable, so that lag costs nothing. `Topology_Registry::invalidate_config_cache()` is the one
shared definition of what a reload drops: the options cache, `Config::reset()`, the on-demand
reader memo and the probe cadence. The watermark gates it because `Config::reset()` fires
`Config::RESET_ACTION`, whose subscribers drop the parsed-TSL caches — run every pass, that
makes each worker re-glob both topology directories and re-parse every `.tsl` to reach the
value it already held. The watermark IS the signal that makes the cached fleet stale, so
without one the cache is current by definition.

`_fleet` publishes the two events a node may `register()` on, both declared in its `node_schema()`. `RELOAD` fires only after `Topology_Registry::invalidate_config_cache()` has run and carries the watermark string, so a subscriber reading config inline sees the values the reload delivered; it goes out through `notify()` rather than `set_state()`, so a node built after a reload gets no replay. That is the in-graph channel for dropping state DERIVED from config or the Vault rather than read fresh — `Remote_Link_Node::subscribe_reload()` registers a closure that drops its patrons, without which a rotated credential reconnects a healthy stream under the old password. `FIRE` carries the pass clock and is notified BEFORE the `base_dir` and `Bootstrap::is_fleet_enabled()` guards and outside the `try` that swallows scan failures, so it ticks on schedule even when the scan does nothing — and a `FIRE` subscriber that throws unwinds through the Router into `Worker_Base::execute()`, which catches only `Worker_Should_Stop`, ending that worker's drain loop on every pass and in lockstep across the fleet.

The scan is revival and nothing else. Housekeeping runs in the cron pass below, so it depends
on no live worker — which is the point: retention and orphan reaping run even when the fleet
is down.

**Spawn endpoint auth**: an HMAC token rotating every `Internal_Request_Token::WINDOW_S = 10` seconds, accepted for the current AND previous window for race tolerance. `Internal_Request_Token` keeps the purposes apart — a spawn token is not a health-cache token, because the purpose string is inside the HMAC:

```php
$window = (int) floor( $now / 10 );
$token  = hash_hmac( 'sha256', "newspack_nodes_{$purpose}:{$window}", $salt );  // purpose: spawn | health-cache
```

`Spawn_Controller` also accepts an external request from a user holding the MANAGE capability with a valid WordPress nonce, behind a `RATE_LIMIT_S = 2` per-user window, and validates the type and partition against the active fleet before spawning anything.

**Spawn rate limit**: `MIN_SPAWN_INTERVAL_S = 15` per `{type}|{partition}` key. Prevents thundering-herd respawns when locks flap, and it is what makes N peer scanners as safe as one. The **endpoint** is the one gate every spawn path crosses — self-respawns, peer scans, and cron alike — so it both checks the window and records the accepted spawn, persisted through `Cache_Backend::shared_first()` (transient fallback) at twice the interval. A throttled request answers 429. A scanner records its own POSTs in memory only: persisting there would make the endpoint reject the very POST the record announces. `Spawn_Coordinator::spawn_each()` carries the other refusal every path shares — the cron pass, `spawn_fleet()` on activation, a peer scan and both on-demand wakes alike. It reads the configured active topology set for a write-conflict (two fleets on one partition) and suppresses the whole pass rather than the conflicting members. That walk runs AFTER the throttle has filtered the due list, and returns early when nothing survived it, because the walk parses every configured `.tsl` and an on-demand wake is driven by a write: judging the other way round would make every writing request pay a full topology parse.

**Deploy hold**: the same endpoint refuses every spawn with 409 while `Spawn_Coordinator::hold()` is non-zero, so a plugin update can swap `includes/` with no worker running against a half-old directory. The hold is the non-autoloaded `newspack_nodes_hold` option rather than a file under the base directory, because a reinstall may wipe operator storage and a hold that evaporates halfway through the thing it protects is worse than none. `wp nodes stop` places it FIRST, then flags every live worker and polls until no lock dir and no in-flight spawn remain, giving up after `--timeout` seconds (`STOP_TIMEOUT_S = 90`) with the hold still standing and the stragglers named; `wp nodes start` clears it and spawns the fleet. While it stands `wp nodes status` renders every slot `held` and `wp nodes doctor` grows a `fleet-hold` row.

**Worker-registry refresh**: plugin activation/deactivation changes which workers are registered via the `newspack_nodes/topologies` filter. Each `Fleet_Node` rebuilds worker descriptors from `Bootstrap::expand_workers()` every 15s, deferring a type that has just appeared by `NEW_TYPE_SPAWN_DELAY_SCANS = 1` scan interval so a still-exiting predecessor can flush; a cold start skips the deferral.

That rebuild is not what carries an active-set change into a running worker. Its active-set half is `Config::value( 'topologies' )`, memoized for the life of the process and dropped only when a reload watermark lands in this worker's own lock dir, and the worker's loaded plugin set is fixed at boot besides — so a plugin activated afterwards contributes nothing to the filter in that process. Request scope does the work instead: `Topology_Registry::activate()` spawns the new group through `Spawn_Coordinator::spawn_fleet()`, `deactivate()` flags its lock dirs through `kill_readers()`, and the minute cron pass catches whatever neither reached. The scan's own drain branch fires on one condition only — an expansion that comes back empty after a pass that saw workers, which is the last topology being deactivated. Reaping belongs to the cron pass too: `Spawn_Coordinator::reconcile_lock_dirs()` removes lock dirs outside the active fleet plus any `*.lock.d.stealing.*` scratch a killed steal leaked.

That reap does not kill a surplus worker outright. For each `{type}.p{N}.lock.d` whose partition index is at or above the type's current count it first calls `remove_stale_directory()` against the FIXED `Lock_Node::STALE_TIMEOUT` of 60 seconds — a partition outside the fleet has no descriptor to read a declared `stale_timeout` from — and only then raises `Lock_Node::RESTART_FLAG`, so a live surplus worker exits on its own next drain iteration and `Spawn_Controller::validate_partition()` refuses its self-respawn at the endpoint. It retires within one lifetime, and that 60-second figure is the sharp edge: shrinking `num_partitions` on `job-worker`, whose `var stale_timeout = 600` exists because a CPU-bound handler reaches no heartbeat point, can strip the lock dir from a surplus partition mid-handler, which the worker then reads as `lock dir gone` and the job replays. The two janitors also disagree about an empty fleet. `reconcile_lock_dirs()` returns immediately when `Bootstrap::expand_workers()` comes back empty — with no known fleet every directory would read as an orphan — which skips the `*.lock.d.stealing.*` sweep it carries along with it, while `cleanup_orphan_ipc()` has no such guard and deletes every `ipc/*.p*` directory no live lock dir backs. With the last topology deactivated the IPC trees are therefore swept while any lock dir a crash left behind stands indefinitely.

**WP-Cron reconciliation pass**: the `newspack_nodes/reconcile` action runs on a registered 60-second schedule (`newspack_nodes_minute`). `Bootstrap::reconcile_fleet()` runs seven steps and returns; it takes no lock and enters no loop.

| Step | What it does |
|---|---|
| `before` | `do_action( 'newspack_nodes/before_reconcile' )` — third-party surface, so it gets its own step |
| `spawn` | `Spawn_Coordinator::spawn_due_workers()` — the revival path, and the only time-critical step |
| `backlog-wake` | `Spawn_Coordinator::wake_readers_with_backlog()` — revival too: the only pass that notices an external producer's write |
| `lock-dirs` | `Spawn_Coordinator::reconcile_lock_dirs()` — reap lock dirs outside the active fleet |
| `retention` | `Log_Cleaner::cleanup_orphan_partitions()` |
| `orphan-ipc` | `Spawn_Coordinator::cleanup_orphan_ipc()` |
| `periodic` | `do_action( 'newspack_nodes/periodic' )` — alert emission and the delayed-jobs sweep |

Spawn runs ahead of every janitorial step, so housekeeping can never preempt the revival path by throwing; only `before_reconcile` precedes it, in its own guarded step, because it is third-party code. Each step is wrapped alone, so a `topologies` provider or a `periodic` subscriber that throws costs only its own step, and `newspack_nodes/after_reconcile` fires in the `finally` whatever happened. Steady state, every live worker's peer scan keeps the fleet up and the spawn step finds nothing due, while the four chores get the cadence they need. `wp nodes doctor`'s `housekeeping` result reports whether this event is scheduled, because a missing one stops all of it silently. Because a vetoed schedule is silent, `Bootstrap` logs any short-circuit of this event on `pre_schedule_event` / `pre_reschedule_event` / `schedule_event` with the callback chain that swallowed it, and `admin_init` re-arms the event if it went missing. On multisite only the main site runs the fleet: locks, IPC, and logs carry no blog namespace.

**On-demand workers**: a topology can scale to zero instead of staying resident, and
`var on_demand_idle = <seconds>` sizes the window. It defaults to 0 — the `on_demand_idle` setting's own default — which keeps the worker resident, so scaling to zero is something a topology or an operator opts into. The value rides the `stale_timeout`
path — `Topology_Registry::synthesize_entry()` into the catalog entry, `Bootstrap::expand_workers()`
onto each worker descriptor — and changes three places that otherwise read absence as death:

- `Spawn_Coordinator::worker_needs_spawn()` returns false for a cleanly MISSING lock dir. A
  *stale* one still spawns: staleness means a worker died holding it, which is a crash whether or
  not the type is on-demand.
- `Alerts::evaluate()` raises nothing for such a worker (`Workers_CI` derives the `idle` flag once,
  so alerting and the dashboards cannot disagree about what absence means).
- `wp nodes status` renders it `idle`, distinct from `live`, `stale` and `down`.

The worker exits when EVERY `Idle_Reporter` in its graph has been idle for the whole window, timed
from the LATEST reporter's `idle_since()` — the same fold `SSE_Out_Node::opened_at_eof_since()`
applies to its consumers. A reporter answering null is BUSY, and one such answer vetoes the exit
outright. `Consumer_Node` already implemented that method and opts in.
Nodes report their own idleness so the substrate names no application class, and a graph with no
reporter has nothing to measure and never idle-exits. EOF alone would not do: a request that logs
its start and then goes quiet leaves a builder holding an envelope while its consumer sits at EOF,
and exiting there abandons a started span. An idle stop sets stop category `idle`, one of the two
categories `Worker_Base::should_self_respawn()` refuses — respawning would undo the exit. The other
is `stop`, the operator's `wp nodes stop`, which leaves the slot empty on purpose.

Bringing it back happens at the WRITE boundary. Every producer reaches disk through a
`Partition_Node` — `Job_Intake` writes one, a `Topic` fans into them, a `Log` extends one, a
worker's IPC is one — so `fill()` marks the resolved directory and a flush wakes whoever tails it.
Marking is deliberate cheap (no lookup, no I/O) because it runs per message; the flush runs on the
router tick inside a drain loop and at shutdown in request scope, so a web request never pays it on
the way out. Putting the wake in producer helpers instead covered only the FIRST hop — a job routed
firehose → jobs, or drained jobintake → jobs, landed where nothing woke its reader.

`Bootstrap::on_demand_wake_map()` answers which on-demand workers tail a directory. It is built by
substitution through `Core::resolve_partition_template()`, never by parsing a `.p<N>` out of a
path, so a TSL template that puts `<partition>` elsewhere still resolves; it is cached in APCu via
`Cache_Backend::local_first()`, keyed on the active-topology option with a 60s TTL for edited
`.tsl` files. IPC takes the one branch it needs — its path names its own worker, and that layout is
the substrate's rather than a user's template. A partition nothing tails is absent from the map, so
offsetlogs, deadletter dirs and scratch need no exclusion rule; a delayed job wakes nothing because
nothing consumes `jobdelay`.

**Two-tier safety net**:

- Workers self-respawn, and every live worker's `_fleet` scan catches a peer whose lock is missing or stale.
- WP-Cron catches a fleet with nothing left running (cold start, `kill -9`, host outage).

Supervision survives the loss of any single process; only total fleet death falls through to cron cadence.

**Fleet health** is two classes with distinct audiences. `Alerts::evaluate()` computes worker-down, consumer-lag and dead-letter-growth conditions from the snapshot `Workers_CI` already builds — three families (`worker-liveness`, `consumer-lag`, `dead-letters`) at two severities, `warning` and `critical` — and `Alerts::emit()`, hooked on `newspack_nodes/periodic`, journals them rate-limited into `alerts.p0`. Every row `evaluate()` mints carries four required fields — `key`, `family`, `severity` and `message` — and `Health_Checks::fleet_results()` throws `UnexpectedValueException` on a row omitting any of them, and on any severity but `warning` and `critical` — which is why the taxonomy is declared at mint time rather than parsed back out of the key prefix. Each family adds its own detail tail: `reader` plus `distance` in bytes for consumer lag, `reader` plus `count` in segments for dead letters, and `type` plus `partition` for a worker. A consumer rendering its own notice reads those. The doctor and Site Health do not: `fleet_results()` normalizes each row to `key`, `message` and `severity`, and the result's `messages` is the `message` column alone, so anything an operator must see belongs in the message text.

`Alerts::journal_event( $key, $text, $severity )` is the write itself, and the entry point a producer outside the fleet path uses — `emit()`'s transition rows and Job_Worker's batch completion both go through it. `$key` is a stable per-condition key consumers dedupe on, and the vocabulary is five spellings: `worker_down:{type}.p{N}` and `worker_missing:{type}.p{N}` for liveness, `consumer_lag:{reader}`, `deadletter:{reader}`, and `batch:{id}` from Job_Worker. When a condition clears, `emit()` journals a row under the SAME key at severity `resolved` with `m` reading `resolved: {key}`, which is how a consumer closes an open alert — but a worker moving from never-started to stale-heartbeat CHANGES key, so the journal shows a `resolved: worker_missing:…` beside a fresh critical raise rather than one key changing severity. A failed write throws rather than being swallowed, so the caller owns that decision. Two record shapes share the log, and a reader has to expect both: a substrate row from `journal_event()` puts the condition key in KEY and `{ n: 1, k: 'alert', m, ts, severity }` in VALUE, where `n` is a constant 1 because an alert belongs to no request sequence and no `url` rides at all; event-logger-nodes' `Request_Builder_Node` appends to the same directory through its `alerts_target`, forwarding firehose entries whose keyword is `alert`, and there KEY is the REQUEST id and VALUE is the firehose entry plus `url` and `method`, with no `severity` field. Treat `severity` as optional, and never assume KEY names a condition.

`Health_Checks::evaluate()` is the environment report behind both Site Health and `wp nodes doctor`: eight results — cache backend, filesystem, ownership, housekeeping, config keys, plus one per alert family — with two more appearing conditionally: `fleet-hold` while a deploy hold stands, and `other-alerts` when a row declares a family no bucket claims. Declaring a check there is what keeps the two surfaces in sync. The test registers under `Bootstrap::SITE_HEALTH_TEST` = `newspack_nodes_fleet`, which WordPress echoes back as the result's `test` field, so anything reading a result programmatically matches that literal. An unrecognized SEVERITY throws, because it would quietly demote a critical condition to a recommendation — and `resolved` is one of them: that third severity is journal-only, minted by `emit()` for a condition that has stopped firing and by `Job_Worker_Node` for a batch that completed without errors, never by `evaluate()`; an unrecognized FAMILY only picks a bucket and must never throw, since this runs as a `direct` Site Health test and a throw would lose the cache, filesystem and ownership results with it. `Health_Probe_Client` fetches the WEB runtime's cache result over the loopback, since a CLI process sees a different posture; `Health_Cache_Controller` is the other half, answering `POST /newspack-nodes/v1/health/cache` behind an `Internal_Request_Token` — the caller is the site itself and carries no user session, so a capability gate would refuse every legitimate request. Nothing on its permission path reads the cache, the base directory or a worker, and `Bootstrap::register_rest_routes()` registers it first, so the probe still answers on the broken install the doctor was run to diagnose.

What comes back is whitelisted rather than sanitized, because doctor prints the message straight to a terminal. `Health_Probe_Client::valid_result()` accepts only a map carrying exactly `id`, `label`, `messages` and `status`; an `id` and `label` identical to `Health_Checks::CACHE_ID` and `CACHE_LABEL`; one of the three `STATUS_*` constants; and a `messages` list of exactly ONE string, 1 to 512 bytes, valid UTF-8, carrying no control, line- or paragraph-separator character able to rewrite the surrounding output. Anything else — an oversized body too, since the request caps the reply at 2048 bytes and truncation breaks the decode first — becomes a locally authored `recommended` "malformed result". The shape of `Health_Checks::cache_backend()` is therefore a wire contract with its own client: adding a second message, renaming the id or the label, or letting a diagnostic grow past 512 bytes costs doctor the real cache verdict and leaves a transport-flavoured warning in its place.

`Admin::render_alert_notice()` is the third reader of `Alerts::evaluate()`. On `admin_notices` it renders ONE summary — the alert count and `Alerts::worst_severity()`, styled `notice-error` at `SEVERITY_CRITICAL` and `notice-warning` otherwise — linking to Site Health for the detail. One summary rather than a notice per alert, because `evaluate()` returns an entry per worker, per lagging consumer and per dead-lettering reader, so a fleet-wide problem would fill the screen. It renders only where the `?page=` slug begins `newspack-nodes`, only for a user `Admin::current_user_allowed()` admits, and not at all while the fleet is clean.

## Job_Worker_Node

`Job_Worker_Node` is the generic async-job dispatch Node. It keeps two handler maps — `local_handlers` and `remote_handlers` — eagerly loaded in the constructor from the `newspack_nodes/job_handlers` and `newspack_nodes/remote_job_handlers` filters (by topology-evaluation time `plugins_loaded` has fired, so every registered handler is in place; eager load saves a `load_handlers` line in every TSL). The entry's `k` field picks the map: `k='job'` takes the local handlers every host's own worker runs, `k='remote_job'` the remote ones only a hub's worker runs. Each `fill()` invokes the matching handler as `( string $id, array $parameters )` — `$id` FIRST, because it is what the request context is named for. The id is optional: `Job_Intake::write_job()` declares `?string $id` and omits the key from the entry when it is null or empty, and `fill()` reads it back as `''` and hands the handler that. What omitting it costs is the stats identity, which falls back from `handler:id` to the bare handler name, folding every job under that handler into one row. Its CARDINALITY costs the other way, which is why omitting it is sometimes the right call: the accumulator holds one entry per distinct identity and nothing ever removes one, so a producer passing a post id, a uuid or a per-job token mints a new identity per job, and a worker that has seen N of them writes N records into the shared `jobstats.p0` on every 15-second sweep however few jobs ran. Keep the id to something bounded — a template or queue name — and let a ~595s recycle be the only thing that clears the map; event-logger-nodes' `Job_Router_Node` drops an empty id on purpose so `Job_Worker_Node` keys jobstats by handler alone. The call is bracketed by `apply_filters( 'newspack_nodes/job_worker/before_job', true, $handler, $id, $message )` and `do_action( '…/after_job', $handler, $id, $outcome )`; before_job is a FILTER so a listener that will not set a context up for a job — one addressed to another host — can return `false` and DECLINE it, and only an explicit `false` does so. The after-action always fires (even when the handler throws, and for a declined job) so applications can hook per-job request context (logger suspend, synthetic `$_SERVER` rewrite) without that being a substrate concern — and that pair is the ONLY place a job's context is managed, so a handler neither opens one nor needs the Message to. The argument order is load-bearing: reverse it and a handler receives a string where it declared an array, dying at the boundary, so the substrate and every handler ship together. `$id` follows `$handler` everywhere for the same reason — the hooks above, and `Job_Intake::queue()` / `feed()` / `write_job()` / `write_feed()`, which take `( $handler, $id, $parameters, … )`.

**A handler's RETURN VALUE is its outcome.** `classify_outcome()` reads `$result['stats']['success_count']` — defaulting to the `-1` "no stats reported" sentinel — and `$result['stats']['error_count']`, defaulting to 0, and looks at nothing else. Errors beside an EXPLICIT `success_count` of 0 is the only combination that reads `error`; errors beside processed items, and errors beside the sentinel (a handler returning just `[ 'stats' => [ 'error_count' => 3 ] ]`), both read `success` carrying "Completed with errors: N processed, M error(s)", leaving the failure visible only in `ITEMS_ERR_DELTA`. So `Jobstats_Record::LAST_STATUS` sorts two values and never `partial`, where pyrobase's `CronManager::job_handler()` grades the same counters on three — so a reader arriving from pyrobase expects a `partial` the substrate never emits. A handler that returns nothing always reports `success`, which makes throwing the only way to signal failure, and an author who catches his own errors ships a permanently green Jobs dashboard. The classified array is also what reaches applications as the `$outcome` argument of `after_job`.

**A `before_job` listener that THROWS is not a decline.** A decline (an explicit `false`) skips the handler, counts nothing and settles no batch. A throw is caught, logged rate-limited and the handler skipped, but the job is NOT marked declined: an entry carrying a `batch` settles with a null outcome, which increments the batch ERROR counter, and both `jobs_executed` and the cache-flush counter advance though no handler ran. That is deliberate — the job failed HERE and no other host will run it — and it is the opposite of the decline path, so a listener must never throw as a way of refusing work. `Worker_Should_Stop` is the exception: it is re-thrown at both the listener catch and the handler catch, recording no stats, scheduling no retry and settling no batch, so the successor replays the message.

After each job it bumps counters, `gc_collect_cycles()`, and — every `cache_flush_interval` jobs (its one positional argument, `CACHE_FLUSH_INTERVAL = 50` by default, clamped to at least 1) — `wp_cache_flush()`, because an object-cache flush extends per-process runtime by orders of magnitude. Memory is the *worker's* business, not the node's: `Worker_Base::should_continue()` owns the 80% watermark that ends the process before PHP's uncatchable fatal-on-OOM bypasses cleanup. A `GET_HEALTH` request (declared in `node_schema()['requests']`) reports memory used and limit, handler counts, cache-flush progress, and the counter.

A throwing handler is poison by default — it propagates to the Consumer, which dead-letters the entry ([ADR-12](architecture-decisions.md#adr-12-dead-letter-poison--crash-lifecycle)) — unless the entry opted into retries. With `retries` set and attempts left, the job is re-parked in `jobdelay.p0` at `RETRY_BASE_S * 2^attempt` seconds (`RETRY_BASE_S = 30`), capped at `RETRY_MAX_S = 3600`; a failed requeue write falls back to the poison path, because a job must never vanish into a swallowed error. The re-park loses one field. `schedule_retry()` builds a fresh `Job_Intake` and calls `write_job()`, which hardcodes `'k' => 'job'`: it carries `handler`, `id`, `parameters`, `key`, `retries`, `attempt + 1` and `batch` across, but not the KIND, so a hub-side `remote_job` that throws with attempts left comes back as a local job and resolves against `local_handlers` on its next attempt. A handler registered on both maps therefore runs its LOCAL callable on the retry, and one registered only remotely has that retry swallowed by the unowned-handler path — the job vanishes instead of dead-lettering. An entry carrying a `batch` id settles its fan-in counter on completion (a poisoned member deliberately does NOT settle — the crash lineage re-runs it, and double-settling would miscount), and the decrement that reaches zero fires `newspack_nodes/job_worker/batch_complete` plus one `alerts.p0` row. Per-identity counters (`handler:id`) accumulate in memory and are swept into `jobstats.p0` by a `Job_Probe`, exactly as `Topic_Probe` sweeps Consumers. The record is `Jobstats_Record`, a positional VALUE parity-pinned to `src/runtime/jobstats-record.js`, whose thirteen slots run:

| # | Field | What it is |
|---|-------|------------|
| 0 | `IDENTITY` | `handler:id`, or `handler` alone when the dispatch resolved no id |
| 1 | `HANDLER` | The id-free half, carried so a reader groups a handler's ids without re-splitting |
| 2 | `RUNS_DELTA` | Runs during `ELAPSED_MS`, successful and failed alike |
| 3 | `ERRORS_DELTA` | The subset of those that classified `error` |
| 4 | `DURATION_MS_DELTA` | Sum of run durations, milliseconds |
| 5 | `QUEUE_MS_DELTA` | Sum of dispatch-minus-enqueue latencies, milliseconds |
| 6 | `ITEMS_OK_DELTA` | Sum of handler-reported `success_count`, the -1 sentinel clamped to 0 |
| 7 | `ITEMS_ERR_DELTA` | Sum of handler-reported `error_count` |
| 8 | `LAST_TS` | Wall-clock second the last run ended |
| 9 | `LAST_DURATION_MS` | Duration of that run |
| 10 | `LAST_STATUS` | `success` or `error` — never `partial` |
| 11 | `LAST_MESSAGE` | Its one-line summary, capped at `Job_Worker_Node::MAX_STAT_MESSAGE_LEN` |
| 12 | `ELAPSED_MS` | The interval fields 2..7 cover, opening at this identity's FIRST run |

Fields 2..7 are DELTAS since that identity's previous sweep under an `ELAPSED_MS` covering them, so a reader divides one record and a ~595s worker recycle is another window rather than a counter reset; fields 8..11 are last-run detail that SURVIVES the drain. An error rate is `ERRORS_DELTA / RUNS_DELTA`, never over their sum. `QUEUE_MS_DELTA` contributes zero for an entry carrying no `ts` or one stamped after dispatch, understating the wait rather than inventing one, and `LAST_MESSAGE` is the record's only free text — the sole field `Job_Probe_Node::fit_to_line()` sacrifices to `Line_Fitter`, since halving an identity would corrupt what readers key on.

What `RUNS_DELTA` counts is work COMPLETED, not entries dequeued. A job the `before_job` filter declined, a job whose before_job listener threw, and a job a cooperative stop aborted mid-run all record nothing at all. A throwing handler does record: the stats are written inside the catch, before the poison-versus-retry decision, so the run counts in both `RUNS_DELTA` and `ERRORS_DELTA` — and because an opted-in retry re-parks a fresh entry, each attempt records its own run and its own error. Dashboard runs therefore fail to reconcile against the jobs Topic's consumed message count in either direction, and one job that failed three times before succeeding shows four runs and three errors for one unit of work.

The entry those fields are read off is `k` (`job`), `handler`, an optional `id`, `parameters` and `ts`, plus `retries` and `attempt` when non-zero, `batch` when tagged, `key` when the write was keyed, and `not_before` on the delay path. Four of them — `retries`, `attempt`, `batch`, `key` — are `Job_Intake::DISPATCH_FIELDS`, the canonical constant `Job_Delay` and an application's own job router both iterate. Anything normalizing an entry onto `jobs` OVERLAYS them onto its record rather than rebuilding a fixed shape: `Job_Worker_Node` reads them back to decide a retry and settle a batch, so a normalizer that drops one disables retry and batch fan-in silently for every entry it touches.

**Ingress is `Job_Intake`, across three logs.** `queue()` writes the LOCKED `jobintake.p<N>` path, which admits an entry up to `MAX_JOB_SIZE = 32 MiB` and which a Consumer drains into `jobs` for the pool — `topologies/job-intake.tsl` on substrate-only installs, an application's own router otherwise. `feed()` writes the UNLOCKED `jobfeed.p<N>` path, bounded by PIPE_BUF and rotating at `FEED_SEGMENT_SIZE = 1 MiB`, so a job router tails jobs alone instead of the whole firehose. `queue_many( $jobs, $key, $batch )` is the bulk form — pyrobase's image migration writes through it — taking a list of `{handler, parameters, id}` entries, skipping any whose handler or parameters has the wrong type, and returning the number actually written. It is also what OPENS a batch, and it seeds TWO site-scoped cache entries rather than one: `job-batch:{id}` holds the outstanding count, set to the valid-entry count before the first write, and `job-batch-err:{id}` the failure tally, both at `BATCH_TTL_S` = seven days. `Job_Worker_Node::settle_batch()` increments the error key for a failed or skipped job, reports its value in the `batch_complete` alert row, and deletes both when the count reaches zero — so a batch whose members never all settle leaves both keys standing for a week, and re-using that id inside the window throws `RuntimeException`. A `$batch` with no claim store (Memcached or APCu) selected throws `LogicException` instead. Compare the return against your job count — a write that fails after the seed leaves the batch open. The three key builders are public statics (`batch_count_key()`, `batch_err_key()`, `unique_key()`) precisely so an operator can read the live counters with `wp nodes memcache get`.

`unique` and `unique_ttl` are the dedup pair — a token and its window in seconds. `write_job()`, and the static `queue()` wrapping it, claims the site-scoped slot `job-uniq:{handler}:{token}` with an atomic `add()` on `Cache_Backend::shared_first()`, so a duplicate enqueue inside the window returns false. The claim is taken EARLY, ahead of the encode and the `MAX_JOB_SIZE` check, so an entry that wins the slot and is then refused for size holds it for the whole `unique_ttl` and no retry of that token is admitted until it expires. It is also fail-closed by design: a false `add()` means either a genuine duplicate or a backend failure, and both drop the enqueue, so a sick memcached reads as "already queued". Pick a `unique_ttl` no longer than the window you are willing to lose. Misuse throws instead: `unique` without a positive `unique_ttl` raises `InvalidArgumentException`, and `unique` with neither memcached nor APCu selected raises `LogicException`. Both travel out through `queue()`, which turns only a `RuntimeException` — the write lock's contention signal — into a `false` return.

Four conditions make a write return `false` rather than throw, so the job is never queued: a handler name failing `HANDLER_NAME_PATTERN` (a letter, then letters, digits, underscores and hyphens, 64 characters at most), an `id` longer than `MAX_JOB_ID_LEN` = 128 bytes — it rides in the job's jobstats IDENTITY, and `Job_Worker_Node` enforces the same bound on the way back — a payload that will not `wp_json_encode` or whose encoding exceeds `MAX_JOB_SIZE`, and a `feed()` entry whose packed record plus its newline exceeds `Partition_Node::MAX_LINE_SIZE`. The last three write a `[Nodes] JobIntake: …` line to the node stderr chain; the bad handler name writes nothing at all. Check the boolean — a caller that fires and forgets loses those jobs silently.

An intake INSTANCE memoizes one `Partition_Node` per `{basename}.p{N}` slot and, on the locked path, holds that partition's write lock from its first write until `close()` or the destructor runs; every other writer to that partition then waits `Partition_Node::DEFAULT_LOCK_WAIT_MS` and gets a `RuntimeException`. `close()` is also what makes the entries durable, because `Partition_Node::fill()` only accumulates into a batch: it flushes each Partition and calls `remove_node()` to drop the lock and the heartbeat. The static `queue()` and `feed()` close in a `finally`; `queue_many()` does NOT, which is why pyrobase's image migration calls `close()` immediately after it. An intake held open across a long run is blocking the web requests that enqueue to those partitions.

`feed()` accepts no options at all, so scheduling, retries, batch fan-in and dedup all belong to `write_job()`. No `.tsl` declares any of the three dirs, so `Bootstrap::register_log_producers()` states each one's layout on `newspack_nodes/registered_log_producers` — alongside the `alerts.p0` journal — and `Log_Cleaner` leaves queued jobs alone.

An entry carrying `not_before` or `delay` parks in the single hardwired `jobdelay.p0` instead, and `Job_Delay` circulates it: `sweep_action()` is hooked on `newspack_nodes/periodic` and reports a failure rather than propagating it, so a throw here costs no other subscriber its turn. Each pass drains the delay log with a durable-cursor Consumer, delivers the due entries into the live intake with their delay fields stripped and their partition key re-hashed, and re-appends the rest to the tail before checkpointing. Granularity is therefore the minute reconciliation pass, and late is correct — `not_before` means not before, so firing early is the bug. Held entries re-append BEFORE the commit, so an abort replays the sweep, which duplicates and never drops. A circulating buffer is what makes a delayed job restart-safe with no new storage and no new timers.

A failed delivery splits two ways, and neither is the dead-letter path ADR-12 gives every other job. A `Job_Intake::write_job()` returning FALSE — one of the false-return refusals above — is treated as permanently undeliverable: one stderr line, and the cursor advances past the entry, so the job is gone with no dead-letter record. A delivery that THROWS `\RuntimeException`, which is the `jobintake` per-partition write lock timing out, is held and re-appended instead, and nothing counts attempts on that path, so an entry that keeps failing recirculates once a minute indefinitely. The false-return drop applies to the re-append leg too: a held entry whose circulation write is refused is logged and lost, because the checkpoint commits past it either way. The four `DISPATCH_FIELDS` survive the hop, overlaid onto both the delivery and the circulation — `attempt` has to, or every retry would re-enter at attempt 1. `ts` does not: `write_job()` stamps a fresh one on each hop, so an entry's `ts` records its last circulation and the `QUEUE_MS` field of its `Jobstats_Record` measures queue time from delivery, excluding the whole delay window.

Ships with a stock `topologies/job-worker.tsl` in the substrate's built-in dir. `newspack-nodes.php` registers that dir at LOAD time through `Topology_Registry::register_builtin()`, beside where consumers register theirs, and deliberately not from `Bootstrap::ensure_runtime_wired()`: a plain frontend page view never reaches the runtime tier, so a builtin registered there would leave a consumer topology's `include topic-probe` unresolvable on exactly the requests where the consumer's own dir did resolve. What `ensure_runtime_wired()` registers is the writable per-deployment user dir, `Bootstrap::base_dir() . '/topologies'`. `register_stock_dir` is the per-plugin analog `register_plugin` uses.

## REPL: wp nodes cli

`wp nodes status` (alias `ls`) — fleet overview: one row per partition of each ACTIVE topology, carrying State, heartbeat age and uptime (the lock dir's `started` file), then the consumer-lag table from the Topic_Probe snapshot, whose stale rows `CLI::consumer_rows()` re-measures off disk. A slot holding a lock reads `live` or `stale` from its heartbeat; one holding none reads `held` under a deploy hold, `idle` when the topology declares an `on_demand_idle` window, and `down` otherwise. A catalog topology outside the active set reads `inactive`, and a leftover lock from a deactivated type reads its own state plus `(inactive)`.

The dashboards reach the same fleet through a different shape, and a dashboard author reuses the fold rather than writing a fourth copy of it. `reconstructWorkers()` emits one worker ROW per handler per partition, so a consumer fanning its reads through a Tee to three processors contributes three rows describing one process and a row count reports a single-partition topology as three workers. `partitionSummaries()` (`src/event-dashboards/partitionSummaries.js`) is the one fold that collapses those rows back to a summary per partition, and `TopologyRow`, `fleetSummary` and `useTopologyManager` all read it instead of each deriving worker counts and health for themselves.

`wp nodes cli` — open an interactive REPL. Two modes:

**Bare mode** (no `<reader>` arg) — runs a self-contained graph in the current process:

```
wp nodes cli
/> ls
/> dump_config
/> ^D
```

`build_repl_graph()` builds the local graph at REPL start (bare):

```
(anonymous Shell)  ->  _shell (Tap)  ->  _command_interpreter  ->  _router
                                                                     |
                                                    _output (Dumper) -> _stdout (TTY_Out)
```

`_router` is a `Router_Node` and `_command_interpreter` a `Command_Interpreter_Node` sinking into it. `_shell` is a `Tap_Node` — the console tap, there so a session can watch what the Shell sends — and the `Shell_Node` itself is **anonymous** (`Shell::name()` throws on any name; see [ADR-7](architecture-decisions.md#adr-7-sink-vs-target-and-tofrom-replies) on unaddressability as a security boundary) and sinks into it. `_output` is a `Dumper_Node` sinking into `_command_interpreter` with `target = _stdout`, so its rendered lines route to the `TTY_Out_Node` writer by path like everything else. Replies reach it because the Shell stamps `FROM = _output/<pid>`. (Topology lines and `make_node` refer to these by their *shell name* — the class short-name minus `_Node`: `Router`, `Command_Interpreter`, `Dumper`, `Tap`.)

**Attached mode** (`wp nodes cli job-worker.p0`) — the SAME local nodes, plus the IPC pair and a `path` cd. A `Partition_Node` named after the worker (e.g. `job-worker.p0`) writes to the worker's input IPC dir (sink = `_command_interpreter`). An unnamed `Consumer_Node` (the `reply-in`) tails the worker's output IPC dir with `next_offset('end')` and `set_stamp_as( '{worker-id}' )`, sinking into an anonymous relay `Node` whose `target` is `_output` and whose sink is `_router` — the relay is what turns each replayed line into an addressed message without giving the Consumer a name of its own. The Shell's sink stays `_shell`; the cd is purely `$shell->path = "{worker-id}"`, so a default command carries `TO={worker-id}` and `_router` dispatches it to the worker-id Partition (which writes it to disk) instead of running locally. The Shell signs every command it mints inline via `Command_Auth::sign()` — there is no separate signer Node — so locally-minted commands carry the HMAC envelope verifier CIs require.

```
local Shell -> _shell -> _command_interpreter -> _router -> worker-id Partition (on-disk) -> worker input
worker output -> reply-in Consumer (on-disk) -> relay -> local _router -> _output (Dumper) -> _stdout
```

IPC layout (always single-partition):

```
{base_dir}/ipc/{reader}/input/{seg}.log     # shell -> worker
{base_dir}/ipc/{reader}/output/{seg}.log    # worker -> shell
```

Reader id form: `{type}.p{N}`, e.g. `job-worker.p3`. Dot-and-`p` keeps it a single path segment — `job-worker/3` would route as "find node `job-worker`, pass remaining path `3`," which is wrong. `wp nodes status` lists the types a deployment actually runs.

**No cryptographic handshake gates the IPC directory itself** — filesystem permissions on `/tmp/newspack-nodes/ipc/` do (which is why `wp nodes cli` refuses to run as root: root-owned IPC dirs lock the web-user fleet out). The commands written into it are still signed and verified like any other wire command. `CLI::attach_to_worker( $worker_id )` resolves the IPC paths: it parses `{type}.p{N}` (the type match is greedy, so `foo.bar.p3` is partition 3 of `foo.bar`) and looks for `{base}/locks/{worker_id}.lock.d`. A missing lock dir is not by itself a missing worker — an on-demand worker sleeps holding none — so the miss falls through to `Spawn_Coordinator::wake_sleeping_worker()`, and only a refusal there throws `InvalidArgumentException` with `"no worker '{worker_id}' (run \`wp nodes status\` to list active workers)"`. Staleness is never checked, so a mid-restart worker still attaches. It returns `{input, output, type, partition}`. `build_repl_graph()` then constructs the IPC pair directly — `new Partition_Node()` configured via `Worker_Base::ipc_partition_args( $ipc['input'] )` (the full seven-slot geometry, so a scratch partition is bounded by COUNT and never inherits an hour-long `min_lifetime` from config) and `new Consumer_Node()` against `$ipc['output']` — not via `make_node`.

The worker's half of that pair writes under `void_warranty()`. `build_scaffolding()` lifts the cap on the `_repl` output Partition with no rotate lock, on the assertion that the worker is its sole writer, and that is what lets a `dump_graph` or `dump_metadata` reply reach an attached cli instead of being dropped by the 4096-byte oversize rule. Nothing enforces the assertion: `_repl` is scaffolding rather than a topology-declared partition, so it never enters `Topology_Analyzer`'s write-set conflict check, and a second writer there is the silent torn write [ADR-4](architecture-decisions.md#adr-4-pipe_buf-atomic-writes) warns about.

**Wire / dispatch specifics**:

- **IPC messages use TM_COMMAND**: replies route via the FROM/TO breadcrumb — Shell stamps FROM=`_output/$pid`, the worker's Command_Interpreter_Node sets TO=`$message[FROM]` when responding, and Router dispatches the reply by name. No ID-correlation table; the path itself is the addressing.
- **`Command` struct in VALUE is a LIVE PHP array, NOT JSON-encoded.** Inbound TM_COMMAND VALUE is `['name'=>, 'arguments'=>]` — `arguments` a flat **token array** (`list<string>` argv), tokenized ONCE at the Shell/producer boundary and carried verbatim (plus an `'auth'` HMAC envelope when wire-issued — see command authorization); the response VALUE is `['name'=>, 'arguments'=>, 'payload'=>]`. The struct rides through `packed()`/`unpacked()` as a nested object inside the whole-message envelope — the envelope (and the SSE/REST body) is the ONLY place JSON serialization happens. Verb results are likewise live structures; the cli Dumper json-encodes array payloads only at the render boundary. The signature has no field of its own on the message: it rides inside VALUE as `auth`, so it survives the IPC round-trip that strips `LOCAL`.
- **TO at the root prompt is empty.** Command_Interpreter_Node dispatches a TM_COMMAND only when TO is empty; non-empty TO routes through Router as a normal addressed message.
- **`pwd` reply via the `prompt` intercept**: the Shell `pwd` builtin sends a TM_COMMAND `name=pwd`; `cd` is purely local (no message). When a response carries `name === 'prompt'`, Dumper sets `$shell->prompt` and renders nothing. (The Shell does not emit a `name=prompt` command itself; that path is a convention for a worker that wants to drive the cli's prompt.)

**Shell** supports quote-aware tokenization (single, double, backtick), single-tier interpolation of `<varname>` and namespaced `<ns:key>` tokens, backslash line-continuation, and an `include` builtin. Inside a quote, `\` escapes the next char, so the tokenizer is the exact inverse of `Node::serialize_args()`/JS `serializeArg` — a token bearing whitespace, a quote char, a backtick, a backslash, `#`, `;`, `<`, or emptiness round-trips losslessly (the JS `quoteToken` delegates to `serializeArg`; there is no "unrepresentable" token). `tokenize()` yields the flat token array the command envelope carries. There are no conditionals, loops, function definitions, pipes, or `eval` — and no syntax-error rejection for them either: an unrecognized verb falls through as a TM_COMMAND (below). Quote-aware tokenization and line-continuation are what let a topology file parse at all — `<config:logs_dir>/jobs.p<partition>` expands the dir now and defers `<partition>` only when the author quotes it.

`include <file>` reads a file and evals each line through this same shell, as though typed. The argument is a registered topology NAME and nothing else (`include topic-probe`): `resolve_include()` refuses any token carrying a slash, a backslash or `..`, then asks `Topology_Registry::resolve()`. There is no literal-path fallback, because a worker boot evaluates admin-authored TSL — anything an include could reach would be executable by whoever can save a topology. A repeat within the current ancestor chain is a cycle, and a file already evaluated within the current top-level script is a no-op (`#pragma once`, scoped per top-level script so a long-lived REPL can re-run an edited file). `secure` / `insecure` lines inside an included file are ignored: the policy belongs to the topology being loaded, and an include that declared one would both decide on its parent's behalf and disable `make_node` mid-load. A REPL logs a cycle and continues; `fatal_errors( true )` — what `Topology_Loader` sets — throws instead. An include naming no registered topology, or a file that will not open, prints through `print_less_often()` at either setting and the load carries on.

Shell also intercepts the **path-composing builtins** before they reach the message bus: `cd`/`chdir` updates `$this->path` (the cwd) and emits no message; `tell_node`/`tell` (TM_INFO), `send_node`/`send` (TM_BYTESTREAM, VALUE newline-terminated), `send_struct`/`send_struct_node` (TM_STRUCT, VALUE decoded from JSON — a decode error prints and sends nothing), `send_eof` (TM_EOF), `command_node`/`command`/`cmd` (TM_COMMAND), `request_node`/`request` (TM_REQUEST), `ping` (TM_PING, VALUE = now) all build TO via `prefix( <path> )`; `pwd` sends TM_COMMAND `name=pwd` with TO = `$this->path`. Four more are purely local, minting nothing: `clear` writes the ANSI wipe-and-home sequence, `debug_level` sets the local Dumper's verbosity, `status` prints this session's mode summary, and `show_parse` toggles the parsed-command dump. **A verb that matches no builtin falls through as a TM_COMMAND** with the verb as the command name and `TO = prefix('')` (i.e. the cwd itself). Every emitted message is stamped `FROM = _output/$pid`. `prefix($arg)` is just `join('/', filter([$this->path, $arg]))`, and `cd` resolves relative/absolute/`..` paths into `$this->path` with slashes trimmed.

**`print` writes verbatim; there is no `echo`.** `print <message>` sends its argument to the REPL with nothing appended — the usage line is `print "<message>\n"`, because the newline belongs in the value. This is why a `var` read of a value lacking a trailing newline leaves the prompt on the same line.

**`var` is the shell's variable scope.** Bare `var` lists every var as `name=value` (sorted); `var <name>` prints the value and *defines* it as empty if it was unset; `var <name> =` with no value **deletes** it — the branch keys on whether a value TOKEN followed the operator, so `var foo = "\n"` SETS foo empty rather than deleting it; `= .= += -= *= /= //= ||=` and valueless `++` / `--` all apply. A name followed by junk where an operator belongs is an error (`unexpected token in assignment`). A read prints its value verbatim: an empty one prints nothing, and a value with no trailing newline leaves the prompt on the same line — put the newline in the value. Interpolating a var that was never defined prints `WARNING: use of uninitialized value <name>` RAW to stderr — no timestamp, hostname, or pid — and still yields `''`; a var defined as empty is silent, and `message.*` reads are silent by design.

Four operator details are worth pinning. `.=` joins with a SPACE when the key already exists and assigns bare when it does not, so `var s = ab` then `var s .= cd` yields `ab cd`. `//=` assigns only when the key is absent, where `||=` also assigns over `''` and over the string `'0'`. `/=` with a zero right-hand side prints `var: division by zero` and leaves the value untouched. And arithmetic renders an integral result with no fractional part, so `var n ++` on an unset var yields `1` rather than `1.0`. A name containing `:` is refused outright — `':' is reserved for namespaces like config:` — so `var config:foo` cannot shadow a `<config:…>` token.

**Comments and escapes are resolved by the tokenizer.** An unquoted `#` comments out the rest of the line wherever it appears, not just in column 0 — and because our pipeline interpolates a whole line before tokenizing it, the comment tail is recognized at all three stages: the `;` statement split, interpolation, and tokenizing. So a comment may contain a `;` or a `<token>` without either taking effect. Outside a quote, `\X` is a literal X, which is how `\#`, `\;`, `\<`, and an escaped space reach a token. A line continues only on an ODD run of trailing backslashes: `a\\` is one escaped backslash and a complete statement.

**Escapes are quote-typed, like interpolation.** Inside double quotes `\e` `\n` `\r` `\t` expand, and `\"` `\\` `\<` `\>` unescape. Inside single quotes and backticks only `\'` / `` \` `` and `\\` unescape, so a deferred `<token>` survives verbatim. An unlisted `\X` keeps both characters. `Node::serialize_args()` emits single quotes escaping only `\` and `'` — squarely inside those rules — so the tokenizer stays its exact inverse. Backticks do NOT execute anything; they are a third quote character.

**Four `message.*` vars stamp the fields no verb takes.** At the mint, the Shell reads `message.from`, `message.key`, `message.id`, and `message.timestamp` out of var scope (`var message.key = trace-77`) and stamps them onto the outgoing message. Unset leaves KEY and ID empty, FROM at `_output/$pid`, and TIMESTAMP at the mint clock; setting FROM re-routes the reply away from this session's Dumper, which is the point of exposing it. ID and TIMESTAMP are deliberately forgeable, because replaying a message with an arbitrary ID or timestamp is exactly what debugging time-dependent or correlation-dependent nodes requires. The browser composer writes the same four fields per-message (`applyComposeFields`) without touching session vars, laid out in Message field order — TYPE(0), TIMESTAMP(1), FROM(2), TO(3), ID(4), KEY(5), VALUE(6).

**The cd to a remote/other worker is just `$this->path`** — a TO prefix, nothing hardwired. At the root prompt `path=''` so default commands carry empty TO and the local `_command_interpreter` handles them; after `cd jobs:partition` the same default command carries `TO=jobs:partition` and `_router` dispatches it. In attached mode the Shell's sink is unchanged; `build_repl_graph` sets `$shell->path` to the worker id, so default commands carry `TO={worker-id}` and `_router` routes them to the worker-id Partition that writes them to the worker's input IPC dir instead of running locally.

**`list_nodes` (alias `ls`) flags are `-a c l s t`** (matched by `^-([aclst]+)$`), NOT `-celos`: `-a` all-nodes (optional regex glob), `-c` counters, `-s` sinks, `-t` targets, `-l` = `-ct`. Without `-a`, a bare name lists nodes whose sink IS that node; no arg lists this interpreter's siblings.

**Event-loop introspection verbs (`list_timers` / `list_handles`).** Both are static Command_Interpreter_Node verbs that tabulate current `Event_Framework` state — useful for diagnosing a spinning drain loop without redeploying. `list_timers` lists every registered timer (ID, ACTIVE, INTERVAL, MODE, NEXT, ONESHOT, FIRES, TYPE, NAME); a `NEXT <= 0` with a climbing `FIRES` is a spinner, and MODE distinguishes an own Event_Framework slot from a Router hitchhike (whose NEXT reads `-`, having no own `next_fire`). `list_handles` lists the registered cURL handles the drain loop selects on (ID, COUNT msgs, TYPE, NAME). Each takes `-s`, which returns the same rows the table is built from instead of the rendered text — one source of truth, two renderings, so a view sorts them without parsing a fixed-width table. Both are mirrored in the JS interpreter (`src/runtime/command-interpreter-node.js`), where `list_handles` lists nodes holding an `EventSource`.

**Completion-query mode (`KEY='completion'`).** Both `help` and `ls` short-circuit when the inbound message carries `KEY='completion'`: they return a bare newline-separated candidate list (sorted verb names for `help`; bare node names for `ls`, which lists every node the way `-a` does — honoring a glob argument, never the siblings default — with the `-clst` columns dropped) instead of the tabulated human output. The KEY stands in for Tachikoma's `TM_COMPLETION` type flag, which this runtime does not carry, and both ports implement it identically (same set, same ordering) so tab-completion works against the browser-local graph and live workers alike. Tab-completion is built on top: both REPLs fire a `help` and an `ls` command carrying `KEY='completion'`, complete to the longest common prefix on the first Tab, and list the ambiguous candidates on a second consecutive Tab. They collect the answers differently. The browser mounts a `_completion` node and addresses the replies to it, publishing each parsed answer as `{ candidates, seq }` on its `candidates` state slot, which `ReplFooter` and the debug overlay's `InspectorTab` each bind through `useNodeState`. The `seq` is a publication counter rather than a value hash, so a second Tab yielding an identical list still notifies: a subscriber acts on a new `seq` instead of diffing the array. `wp nodes cli` (readline-backed) mounts none — `TTY_In_Node::send_completion_queries()` fills the pair straight into its sink, and a closure `CLI_Command::run_repl()` installs through `Dumper_Node::set_completion_sink()` hands each reply to `TTY_In_Node::ingest_completion_reply()` and returns true so the Dumper renders nothing. Its pair goes in as REPL INPUT rather than as finished commands, so the Shell parses, signs and addresses each at the session's cwd exactly like a typed line, and the candidates describe the graph the prompt points at. A `help` reply REPLACES the verb cache and any other name the node cache; `complete()` then serves verbs at token index 0 and node names at every later token, and readline itself does the extend and the listing. In the cli that cache is never read synchronously: the readline callback fires both queries and returns the CACHED candidates, so the list a Tab shows is the graph as of the PREVIOUS Tab — make a node and it appears on the second Tab, not the first. `CLI_Command::run_repl()` therefore seeds the cache once before the drain begins, and only under readline, so the first Tab is not empty; the seed comes strictly AFTER `Dumper_Node::set_completion_sink()` is wired, because a reply arriving with no intercept in place renders the raw candidate list on the operator's terminal. The REPL also keeps a command history (up/down recall).

**`make_node` resolves by namespace prefix, not a class registry.** There is no `register_class` / `class_map`: plugins call `Command_Interpreter_Node::register_namespace( 'Newspack_Nodes\\' )` once at boot (the substrate also registers the `Newspack_Nodes\Rest\` sub-namespace so the service CIs resolve by short name). `make_node( $type, $name, ...$ctor_args )` loops the registered prefixes and constructs the first `{$prefix}{$type}_Node` that exists and is a concrete `Node` subclass — abstract subclasses (e.g. `Service_CI_Node`) are skipped (the loop continues to the next prefix), and unknown types resolve to `null` rather than fatal once every prefix has been tried. So `make_node('Tee')` → `Newspack_Nodes\Tee_Node`. The base `Node` class is a special case: `make_node('Node')` resolves to `{$prefix}Node` (no `_Node` suffix), used by routing/fan-in primitives like the SSE-stream `_default_route` whose `fill()` is just the base `target` stamp + sink forward. The inverse, `shell_name_for( $node )`, is the class short-name minus the `_Node` suffix (`Tee_Node` → `Tee`); a short name without `_Node` (the base `Node` itself, or an ad-hoc test class) is returned unchanged. `dump_metadata`'s `class` field and `dump_config`'s `make_node` line both emit this shell name, so a GUI or topology round-trip never has to know the FQCN.

**No-arg constructor plus `arguments()`.** Every `make_node`-constructible Node has a constructor `new $fqcn()` satisfies. The four that require parameters — `Callback_Node` (a callable), `Lock_Node` (a lock path), `HTTP_Filter_Node` (the session pid) and `TTY_In_Node` (its Shell and writer) — are all `Hidden`-category primitives built directly in PHP, never from a topology line. `make_node` instantiates with `new $fqcn()`, then calls `$node->name( $name )`, then `$node->arguments( $arg_tokens )` — where `$arg_tokens` is `array_filter( $ctor_args, '\is_scalar' )` re-indexed and `array_map`ped to strings, a flat **token array** (`arguments()` takes and returns `list<string>` argv, NOT a space-joined string) — then `$node->sink( $this )`, a uniform construction sequence. If naming or configuring throws, the half-built node is removed rather than left orphaned in the registry under a name it never earned. The base `arguments()` just stores the token array; a node wanting its declared positional args assigned to props overrides `arguments()` and runs the tokens through `parse_schema_args()` (below). Programmatic object dependencies (e.g. `Workers_CI_Node::$cli`, a registry) are public properties the caller assigns AFTER `make_node` returns — the `is_scalar` filter drops them from the variadic spread (logging once that it did) because they aren't round-trippable as `arguments` tokens.

**Redeclaring a name collapses or throws — it never silently rebuilds.** `make_node` on an existing name returns the existing node when the class AND argument tokens match exactly (so a topology included twice is idempotent), and throws `make_node conflict: '<name>' already declared as …` when either differs. That is what turns a copy-paste name collision into a boot-time error instead of a graph whose second declaration quietly won.

**`parse_schema_args()` is the single source of truth for positional config.** A schema-consuming node overrides `arguments( ?array $args )` to run the token array through `parse_schema_args( array $args )` (the `trait-schema-reflection.php` half), which walks `node_schema()['arguments']` and assigns each declared positional to `$this->{$name}` coerced to its type, then records the token array into `$this->arguments` (so `dump_config()` round-trips). A missing token falls back to that arg's schema `default`, or **throws** if the arg is `required` — so an under-argged `make_node` (e.g. omitting a required `source_file`) fails loudly at construction rather than silently deriving against declaration-default props. Tokens beyond the declared positions are ignored, and a node with no declared `arguments` is a no-op. Args are a list, not a string, so there is no empty-string early return to mirror: a subclass that needs derived state (e.g. `Partition_Node` deriving `partition_dir`) computes it after the schema assignment, gating only on the pure-getter `null === $args` call, and the `required`/`default` policy lives entirely in the schema declaration (cross-check [ADR-11](architecture-decisions.md#adr-11-make_node-construction-sequence)).

The palette catalog (`Classes_CI`'s `list` verb) reads no registry — it scans the composer classmap (`\Composer\Autoload\ClassLoader::getRegisteredLoaders()`) for FQCNs under a registered prefix whose short name ends `_Node`, are concrete `Node` subclasses, and whose `node_schema()` declares a non-`Hidden`, non-empty category and no `hidden` flag. (A class that inherits `Node`'s empty-category default — e.g. `SSE_Out_Node`, a pure HTTP response writer — is not a palette participant.) This requires `composer dump-autoload -o` after adding/renaming a class so the classmap is complete.

**Service CIs (the GUI/REST verb surface).** The substrate ships ten service interpreters — `Classes_CI_Node` (`classes`), `Layouts_CI_Node` (`layouts`), `Topologies_CI_Node` (`topologies`), `Raw_Logs_CI_Node` (`raw-logs`), `Workers_CI_Node` (`workers`), `Vault_CI_Node` (`vault`), `Aggregator_CI_Node` (`aggregator`), `Settings_CI_Node` (`settings`), `Status_CI_Node` (`status`) and `Sessions_CI_Node` (`sessions`) — that derive their verb table from `node_schema()` via the abstract base `Service_CI_Node`. They are mounted onto the request-scope interpreter by `newspack_nodes_mount_substrate_cis()`, hooked on `newspack_nodes/request_graph_ready` (the action a request graph fires once it's wired). `Workers_CI_Node` needs the substrate `CLI` assigned as a public property AFTER `make_node` returns. Its `heartbeat` verb validates the exact `[ slot, owner ]` lease and refreshes it through `SSE_Slot_Pool::touch()`, which selects `Cache_Backend::shared_first()`; there is no cache handle to inject. Because `Service_CI_Node` is abstract, `make_node` skips it during prefix resolution — only the concrete `*_CI_Node` subclasses construct.

**`Command_Args` is the one argument grammar those verbs read.** Inside the flat token array, required values ride positionally in the order the verb declares, an optional one is `--key=value`, a boolean flag is a bare `--key`, and a list is comma-separated inside one value. `parse( list<string> )` classifies the tokens into positionals plus options — only the first `=` splits, so `--expr=a=b` carries `a=b`, and a repeated key keeps its LAST occurrence, so a hand-typed REPL line carrying a duplicate silently drops the earlier one. It restores the positionals and the option NAMES but not the types: the return is `array{positional: list<string>, options: array<string,string|true>}`, so only a bare `--key` survives as a boolean `true` and every named value comes back a string. `if ( $options['enabled'] )` is therefore TRUE for `--enabled=false`, the opposite of what the operator asked; a verb reading a boolean option compares the string itself, and the substrate ships no `option_bool()` to pair with `option_int()`. The one implementation in the tree is event-logger-nodes' private `Performance_CI_Node::flag()`, which answers false for an absent key and for `'0'` or `'false'` case-insensitively, and true for a bare flag or anything else.

`format()` is the inverse, so a minting producer and a handler read the same shape, and its four rules are worth knowing: `true` renders as a bare `--key`; `false` renders as an explicit `--key=false` rather than being omitted, because the bare form already means true and dropping the option would leave the handler's own default standing; an array renders as its members `strval`'d and comma-joined; every other scalar renders as its string cast. That comma join has no escape, so a member containing a comma is indistinguishable from two once a handler splits the value apart — carry such a list as repeated positionals or a JSON blob token instead. Nothing there tokenizes, unescapes or quotes: token boundaries are the array's, set once by whoever split the line, a value carrying spaces stays whole inside its own array element, and quoting belongs to `Node::serialize_args()` at the `dump_config` anchor. A structured blob (a `.tsl` body, a layout's positions JSON) rides as two discrete tokens through `Service_CI_Node::split_first_token()` instead. Read an operator-supplied number through `Command_Args::option_int()`, the refusing read — every `Core` coercion family resolves to a number, so `--partition=abc` would otherwise pick p0 and restart the wrong fleet — then report the null in your layer's voice (`CLI::require_flag_int()` for a WP-CLI flag, `Service_CI_Node::require_option_int()` for a verb).

**Command_Interpreter_Node** dispatches by verb. Aliases share the same `cmd_foo` static; e.g. `make` → `cmd_make_node`, `rm`/`remove` → `cmd_remove_node`, `dump` → `cmd_dump_node`, `ls` → `cmd_list_nodes`. A subclass that installs a custom verb table without a `help` verb gets a default `help` injected by `commands()` (returns the sorted verb names) — that's how the REST service CIs get a working `help`. After command topics, `help <NodeType>` resolves the same class registry as `make_node` and hands the schema to `Node_Schema_Help::render()`, which lays out a `### Type — Category ###` heading, the description, the `accepts_fill` / `has_target` flags, then ARGUMENTS, COMMANDS and REQUESTS as tables through `Command_Interpreter_Node::tabulate()`, the ONE text-table renderer, and REGISTRATIONS as a single comma-joined line. Each section is omitted when the schema declares nothing for it. Reading the schema is what stops help from describing arguments `parse_schema_args()` does not parse; PHP and the browser-local JS interpreter use the same section order and table alignment. CI dispatches a TM_COMMAND (not TM_RESPONSE) only when TO is empty — non-empty TO means the command is mid-route toward a downstream node, so CI forwards to its sink (Router). Verbs may throw freely; `interpret()` catches `\Throwable` and builds the response as `TM_COMMAND|TM_ERROR`. CI also bounces TM_PING and TM_EOF with empty TO back along FROM — the latter is the cli's stdin-close drain marker (cli emits TM_EOF when stdin EOFs, waits for the bounce so all preceding output has been drained off the reply partition before the cli exits).

Help reports the DECLARATION, where two other surfaces report the effective value, and the difference shows twice. The flags line tests each of `accepts_fill` and `has_target` with `isset()` and omits the whole line when the schema declares neither, while `Classes_CI_Node`'s palette projection and `dump_metadata()` both read those keys through `?? true` — so a class returning a bare literal instead of `array_merge( parent::node_schema(), … )`, as `Tee_Node`, `Tap_Node`, `TTY_In_Node` and `Router_Node` do, prints no flags line under `help` while the console canvas draws both ports as present. And the ARGUMENTS default column prints what was written: a bool as `true`/`false`, any array as the literal `[]` (contents elided to hold the column alignment), and every other scalar verbatim — so `help Partition` and `help Log` show `=<config:min_segments>` rather than the number `Schema_Reflection::resolve_default()` resolves at construction. `wp nodes doctor` and the Nodes Runtime settings page hold the effective values. `required` also wins over `default` in that column, so a required argument prints `required` and never its default.

The response envelope: `TYPE = TM_COMMAND|TM_RESPONSE`, or `TM_COMMAND|TM_ERROR` on a throw — the error flag REPLACES the response flag rather than joining it — with `TO = $message[FROM]`, `FROM = $this->name` (self), `ID`/`KEY` copied from the inbound message, and `VALUE = ['name' => $cmd_name, 'arguments' => $cmd_args, 'payload' => $result]` as a **live array** (never separately json-encoded). An empty-string result emits no response.

**`commands()` differs across ports — a real divergence.** PHP `commands($table)` **REPLACES** the instance verb table (`$this->commands = $table`); patron Node ctors install a fresh per-instance table this way. JS `commands(table)` **MERGES** via `{ ...this._commands, ...table }` so callers layer verbs. Don't assume one from the other.

`make_node`/`arguments()` populate `$this->arguments` — a flat **token array** (`list<string>`), one element per ctor arg. `dump_config()` reads that and re-joins it with `Node::serialize_args()`, the ONE re-join anchor, to emit a round-trippable `make_node <type> <name> <args...>` line; `make_node` round-trips via the same `arguments()`. `serialize_arg()` single-quotes an empty token and any token carrying whitespace, a quote, a backtick, a backslash, `#`, `;` or `<`, escaping `\` and `'` inside, so the line re-tokenizes losslessly. `<` is on that list for a reason that is not tokenizing at all: interpolation runs BEFORE tokenizing, so the quotes are the only thing keeping a stored deferred token such as `<config:logs_dir>/jobs.p'<partition>'` unexpanded on the next load ([ADR-11](architecture-decisions.md#adr-11-make_node-construction-sequence)). No separate `dump_config()` override per class.

### Secure levels

`Core::$secure_level` is this process's command-surface policy. It is a **ratchet**: it climbs and never descends, and each level removes a class of management verbs from every interpreter in the process **and keeps every class the levels below it removed**. The table below lists what each level adds; enforcement is the running union, so level 3 refuses all three classes.

| Level | Meaning | Verb class removed at and above this level |
|-------|---------|--------------------------------------------|
| `null` | No command surface at all — a graph-only script (`wp nodes ingest`) that never names an interpreter. Nothing to declare, nothing warned about. | — |
| `0` | Armed but undeclared: naming an interpreter created a surface and nobody has said what policy it is under. The Router tick warns, rate-limited. | — |
| `-1` | `insecure` — deliberately unratcheted. Refused once secured, so the declaration can't be walked back. | — |
| `1` | `secure` | `make_node` — the verb plus `make`, `move_node` / `move` / `mv`, `remove_node` / `remove` / `rm`; construction covers teardown and renaming |
| `2` | `secure 2` | `command_node` — the substrate's one member is `reply_to`, which runs a command HERE and routes its reply elsewhere |
| `3` | `secure 3` | `connect_node` — the verb plus `connect`, `disconnect_node` / `disconnect`, `set_sink`, `register`, `unregister` |

A refused verb answers `<verb> is disabled at secure level <n>` instead of dispatching. `secure` bare climbs one level (capped at 3), `secure <n>` sets an explicit one and refuses to descend, and `insecure` is refused once anything has secured. The ladder freezes *definitions*; it never disables the machine — reads still read, wired flow still flows, and verbs already defined still run. That is why the stock topologies end with a bare `secure` line: once the graph is built, nothing should be able to rebuild it. A node classifies its own verbs into these classes through `node_schema()['verb_classes']`, so a consumer plugin joins a class without editing the substrate. Signing is not one of the things a level buys: HMAC costs microseconds, so every tier signs at every level.

### Command authorization (two-tier)

The *same* `Command_Interpreter_Node` runs in two trust roles, so the gate is a per-instance `authorize` closure (`$this->authorize ?? self::$default_authorize`), checked for **every** command in `interpret()` — a failure returns `unauthorized: <verb>` rather than dispatching. Nothing legitimate is gated out: the browser and the bare cli mint their commands in-process (all `LOCAL`) from a `Shell`, every wire command is signed by whoever minted it, and the browser's SSE receive path delivers `TM_RESPONSE`s to `_output`/`_metadata`/`_uptime`. The SSE-stream *process* itself runs a verifier CI (server tier, below) so a worker can drive it — but only a command addressed to `_command_interpreter` (TO=`_repl/_command_interpreter`, empty after the worker peels `_repl`) routes to it; broadcasts get a `_sse` target from the `_default_route` Node and go to the egress.

- **Client tier** (browser interpreter, bare `wp nodes cli`): commands are minted in-process by a `Shell_Node`, which sets `Message::LOCAL` (index 7, appended *after* the canonical 7 fields). The default `authorize` is `isset( $message[ Message::LOCAL ] )`. `packed()` / `pack()` slice to `LAST_VALUE_INDEX + 1`, so `LOCAL` is dropped at every wire/IPC boundary (HTTP POST, SSE, Partition IPC, the `HTTP_In_Node` echo) — an injected off-process command inherently lacks it.
- **Server tier** (worker CIs, the `/command` request-scope CI, the SSE-stream process CI): these legitimately receive commands over the wire, so they can't lean on `LOCAL`. They install `Command_Auth::verifier()` as their `authorize` — a closure that accepts an in-process (`LOCAL`) command OR one carrying a valid HMAC envelope in `VALUE['auth']` (it rides *inside* VALUE so it survives IPC, unlike the stripped `LOCAL`). `sign()` / `verify()` decide "is this a command?" by the **message TYPE bit** — they require `TM_COMMAND` set, NOT `TM_RESPONSE`/`TM_ERROR`, plus a numeric TIMESTAMP and an array VALUE — never by sniffing a `name` key (so a command whose VALUE lacks `name` is still signed and verified, and a non-command carrying a `name` key is left alone). TYPE only gates signability; it is not part of the canonical signature, so a `TM_COMMAND | TM_NOREPLY` boot command signs and verifies like any other. The canonical string is `JSON.stringify([ ts, name, arguments, nonce ])` — semantics, never routing, because Router peels TO and nodes stamp FROM in transit. PHP encodes it with `JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE` to match JS byte-for-byte; `tests/fixtures/signatures.json` pins that parity from both languages, since each port's own suite stays green through a drift neither can see. Freshness is an age/skew check (up to `MAX_PAST_S = 20` seconds old, `MAX_FUTURE_S = 10` seconds ahead), separate from the spawn and health purpose tokens' discrete current-and-previous 10-second windows. On any verification failure `verify()` logs the rejection through the *handling* interpreter's `drop_message` (`verification failed: …`) and returns false (fail closed). Single-use replay protection claims the nonce with an atomic `add()` through `Cache_Backend::local_first()` at `NONCE_TTL_S = 60`; a replay or an unavailable backend is refused.

**Authenticity and authority are two questions.** Signing says the command came from somewhere trusted; `Capabilities` says whether this user may run this verb. Three roles cut by blast radius answer the second — `read` (dashboards, the SSE streams, read-only introspection), `tune` (declared configuration and application data) and `manage` (fleet control, the credential vault, issuing sessions) — each resolved to a WordPress capability through the filterable `newspack_nodes/capability_map`, which defaults all three to `manage_options` until `wp nodes caps install` migrates them onto `newspack_nodes_{read,tune,manage}`. `Roles` owns that migration: it grants all three capabilities to every role already holding `manage_options`, so nobody loses anything, and creates `newspack_nodes_hub` — read plus tune, nothing else — for the log aggregator's dedicated user, whose application password is then structurally incapable of restarting the fleet or reading the vault. The autoloaded `newspack_nodes_granular_caps` option is the switch, and its presence IS the statement that the capabilities exist; `uninstall()` puts the map back and drops the role. A verb names its role in `node_schema()`, `Service_CI_Node` wraps every handler in `Capabilities::require()`, and a verb naming none gets MANAGE — the strictest, never the loosest. `Capabilities::$session_scope` is the ceiling over one command: `verify()` installs the session's scope, `Command_Interpreter_Node::interpret()` restores what stood before, and a refused verification installs `NONE`. A scope can only ever SUBTRACT, so it never buys authority the authenticated user lacks. Know what `read` grants: its live surface is the raw log firehose — request URLs, hooks, payloads — and worker IPC output, not shaped dashboards alone.

**The minter signs, never the ingress.** A client establishes a session first: `POST /newspack-nodes/v1/auth` (`Auth_Controller`, gated on the fleet site and then on the READ role — a scope is a ceiling, so a read-only user's session can only ever do read-only things) returns `{ handle, key, scope, expires_in, now }` — a random 32-byte key under a random 16-byte handle, stored via `Cache_Backend::shared_first()->add()` under a site-namespaced address. The request's optional `scope` is CLAMPED to the highest role the minting user holds, and its optional `ttl` to `SESSION_TTL_MIN_S = 60` … `SESSION_TTL_MAX_S = 86400`, defaulting to `SESSION_TTL_S = 3600`. `add()`, never `set()`, so a colliding handle fails rather than displacing a live session; the TTL is never slid on use, so a leaked handle expires on a bounded schedule; and the response is the only place the key is ever disclosed (`now` lets the client align its TIMESTAMP to the minter's clock). The client then signs each command it mints with that key, stamping `{ nonce, sig, handle }`, and the verifier resolves the key by handle. `Sessions` is the durable directory beside the cache — a non-autoloaded option holding one row per LABELLED handle, with its scope, label and stated expiry — because a cache store cannot enumerate what it holds, so nothing else could tell an operator what is connected. `record()` returns before touching the option when the label is empty, which keeps the automatic `/auth` mints out of the directory: several per dashboard load, live and connected but unlisted, and at `MAX_ROWS = 50` they would evict the sessions an operator issued on purpose. The `sessions` verb lists, mints and revokes through it while the cache stays the authority on liveness, which is why a row whose lease is gone reports dead rather than vanishing. The directory takes no claim protocol: `record()` reads the option, prunes, inserts and writes it back, so two mints landing in the same instant can lose a row. The cost is bounded on purpose — a live session missing from the Sessions tab, not a broken session, and the missing row is still revocable by handle through `sessions revoke`, which drops the cache lease whether or not the directory ever held it. `SSE_Slot_Pool` needs its claim protocol because ownership rides on the slot; an operator listing does not. The key itself never lands there, and cannot be hashed either — verification recomputes the HMAC, so it has to stay recoverable, which is the whole argument for short TTLs over long-lived tokens. **`HTTP_In` does not sign** — it decodes the batch, routes it, and verifies: conferring authority at the ingress made the boundary an oracle, since anything that reached it acquired authority regardless of what put it there. An unsigned wire command is therefore refused, and `HTTP_In` latches the refusal so a batch containing one answers **401** rather than a reassuring 200/202. The browser signs synchronously with `@noble/hashes` rather than `crypto.subtle`: awaiting a promise would make the Shell's dispatch async and move every graph mutation a microtask later.

Two signing keys exist, and which one a signature uses is itself the destination binding. `Command_Auth::sign()` uses the per-site secret (`hash_hmac('sha256', 'nodes-command-v1', wp_salt('nonce'))`) and stamps no handle — that is what the attached cli's `Shell` uses inline, same-host over the IPC partition. `sign_for( $destination )` signs under the session key established with one remote and stamps its handle; a signature under one remote's key verifies only there, which pins a command to its destination without signing TO. No session means no signature and a refusal downstream — a minter waits for the session rather than emitting something that will rot before it can be believed.

The sessions `sign_for()` draws on live in a private static map that is per-PROCESS and keyed by VAULT ENTRY ID, never by url: two Vault entries pointing at one host stay two sessions, and editing an entry's url keeps its session. Every caller therefore passes the vault id, which is what `HTTP_Out_Node::vault_id()` exists for and what event-logger-nodes' `Discovery_Collector_Node` obeys. The map dies with the process, so each worker respawn costs one `/auth` handshake per spoke and a spoke's access log showing a `POST /auth` every ten minutes is by design. `HTTP_Out_Node` is what establishes a session — the async `fire()` / `ensure_session()` path, or the blocking `establish_session()` behind `probe_command()` — landing in `Command_Auth::remember_session()`, which throws rather than storing a partial session when the spoke returns a malformed `/auth` body. Three things drop one: a 401 from the spoke's `/command`, process exit, and a Vault change.

A Vault write fires `newspack_nodes/vault/changed`, and `Bootstrap` listens twice. `forget_command_session()` drops the session so the next command re-auths; `reload_vault_consumers()` writes the `reload` watermark (`Lock_Node::request_reload_at()`) into every partition's lock dir for every active topology whose parsed graph declares a `Remote_Link` or `Remote_Source`, so workers re-read credentials on their next `_fleet` scan instead of serving stale ones for the rest of their ~595-second life. It is the RELOAD channel and never RESTART, because a credential change must not cost a process recycle, and the target set is DERIVED from node classes through `Restart_Planner::topologies_for()` rather than from topology names — a name is deployment config, and a name-keyed signal drifts into a silent no-op. The signal is best-effort: a `\Throwable` reports through `Core::print_less_often()` so a Vault save never fails on the thing it triggered, and the whole pass returns immediately on a multisite subsite.

There is no asymmetric (public-key) signing anywhere in the substrate; every tier is HMAC-SHA256.

**Dumper** dispatches by TYPE flag and renders payloads **plain — no `ERROR:` or `INFO[from]:` prefix**, because the `debug_level 1` header already identifies the kind. Every rendered type goes out the same way: `emit()` mints a TM_BYTESTREAM and forwards to `$this->target` — there is no stderr branch. It forwards through `parent::fill()`, so the Dumper's counter tracks lines EMITTED rather than messages arriving: one message at `debug_level 1` emits the header and the render and bumps it by two, and a message the TO filter or the completion sink consumes bumps it by none. Reading `ls -c` on `_output` as a count of replies gives a different number than an operator expects, the way the Router's NOT_AVAILABLE re-fill does. That dispatch is the LAST of four stages, though, and a reply that does not reach the terminal was consumed by one of the first two: the multi-session TO filter drops another session's reply, and the completion intercept `set_completion_sink()` installs consumes a `KEY='completion'` answer by returning true. The third stage, the `debug_level` header, emits ahead of every branch below rather than replacing one. On a piped stdin no completion sink is installed at all, so a completion reply there renders like any other message:

- **TM_COMMAND|TM_RESPONSE** → unwrap the live `['name'=>,'arguments'=>,'payload'=>]` VALUE; if `name === 'prompt'` *and the response is trusted*, set the Shell's prompt and render nothing; otherwise render the payload (array payloads pretty-printed JSON, at the render boundary only). `prompt` is the one response that mutates state instead of rendering, so it is the one worth spoofing — a peer that repoints the prompt makes an operator believe they are attached elsewhere and type the next command there. FROM is X-Forwarded-For: the IPC Consumer stamps the worker id at the HEAD and everything after it is whatever the worker wrote, so `prompt_is_trusted()` requires that head to equal the Shell's whole cwd. The cwd is the gate, not the session mode. An empty cwd trusts every sender, so an attached session that types `cd /` — or walks there with `cd ..` — drops the guard while its Consumer keeps delivering that worker's replies; and a cwd deeper than the worker, `cd job-worker.p0/foo`, can never equal the head `job-worker.p0`, so every `prompt` response there renders as ordinary text instead of setting the prompt.
- **TM_COMMAND|TM_ERROR** → render the `payload` field, plain.
- **TM_ERROR** → render VALUE, plain.
- **TM_EOF** → fire the registered `on_eof` callback (the cli's drain-marker exit hook), render nothing. The callback fires ahead of the level-2 early return, so the drain marker reaches the cli at every verbosity rather than leaving the session to wait out the reader's five-second deadline; "render nothing" holds at levels 0 and 1 alone, since level 2 has already emitted the envelope dump above.
- **TM_PING** → rewrite VALUE (original send timestamp) into `round trip time: %.2f ms` and write to stdout.
- **TM_STRUCT** → json-encode the array VALUE to stdout.
- **TM_INFO / default TM_BYTESTREAM** → write VALUE to stdout, plain.

Stdout writes go through a prompt-aware async path that wipes-and-redraws when a prompt is on screen and stdout is a TTY; non-TTY output is plain (no ANSI). Three conditions have to hold together for the redraw: the owned stream is a terminal, settled once at construction from `posix_isatty()`; a prompt is on screen; and a `Shell_Node` is wired through `set_shell()`. Any one missing sends the text down `Stdout_Node`'s plain `fwrite`. The prompt string is read off the Shell on every redraw rather than copied at wiring time, so a `cd`, a held quote or brace continuation and a trusted worker `prompt` response each take effect on the next write — a copy would keep redrawing the prompt of a worker the session has left. `TTY_Out_Node` is the single owner of the prompt-on-screen flag: `write_prompt()` and `mark_prompt_displayed()` raise it, and `TTY_In_Node` clears it directly when readline hands over a submitted line, the terminal having already echoed that line's newline. The prompt is re-issued only when the written text ends in a newline, which is the mechanism behind `print` and `var` leaving it mid-line; Tachikoma's `Dumper.pm` gates `update_prompt` on the same test. `debug_level` 0/1/2 layers a per-message header (1) or a full structural envelope dump that replaces the normal render (2). The multi-session TO filter renders only when TO matches `_output/$pid`, bare `$pid`, or is empty. Level 2 routes VALUE through `stringify_value()`, which `json_decode`s a string beginning `{` or `[` before pretty-printing it, so a packed envelope carried inside VALUE reads as structure rather than one long escaped line. The failure case is the footgun: a string that opens with a brace and does not parse decodes to null and renders an EMPTY `value:`, which an operator reads as a message with no payload. Levels 0 and 1 emit a string VALUE verbatim, so the same message can look empty at level 2 and correct at level 0.

**Multi-session via FROM-trail**: each cli stamps `FROM=_output/$pid` (its wp-cli process PID). The worker's input-Consumer prepends `_repl`, so by the time the interpreter sees the message, `FROM=_repl/_output/$pid`. Replies follow `TO=$message[FROM]`, carrying `TO=_repl/_output/$pid`. The worker's `_router` splits TO on `/`, looks up `_repl` (a Partition), updates TO to `_output/$pid` (the post-strip remainder) and writes the envelope to disk. The cli's local `_router` reads the entry, splits again, looks up `_output` (the cli's Dumper), and forwards with `TO=$pid`. All cli sessions read the output Partition; each cli's Dumper filters: render iff TO matches its own `$pid` (or the pre-peel form `_output/$pid`), OR TO is empty (async broadcasts). No lock, no EBUSY; concurrent shells just work.

### Browser topology-console (`src/topology-console/`, `src/runtime/`)

The same Shell + Command_Interpreter_Node + Router + Dumper graph runs in the browser, ported to JS (`src/runtime/`) with full Shell-builtin parity and every interpreter verb but three: `secure` and `insecure` ratchet a command surface a browser tab does not have, and `taillog` reads log files it cannot reach. Two differences sit outside that verb list. One is the `commands()` merge-versus-replace divergence above; the other is the Dumper. PHP's intercepts a trusted `prompt` response and writes the Shell's prompt instead of rendering it, where the browser `DumperNode` holds no Shell reference at all and renders every `TM_COMMAND|TM_RESPONSE`, a `prompt` included, as an ordinary received line. The console takes its prompt from its own cwd, so nothing arriving on the wire can repoint it and the spoofing `prompt_is_trusted()` gates never reaches the browser. On top of that the console adds:

- **`cd` navigation** across the cwds `buildPathOptions()` offers: `''` for the browser-local graph, `_http` for the request scope, and one `{topology}.p{N}` per partition of each ACTIVE topology — an inactive one has no worker listening, so its path would name a destination that answers nothing. `cd job-worker.p0` mounts that worker exactly like picking it from the Path menu, resolving it by longest worker-prefix match so a deeper path still lands on the right reader. Every typed statement echoes into the transcript verbatim, `cd` included, and the prompt renders the cwd slash-prefixed. Which scope the canvas is in comes from the cwd through `scopeFromCwd()` (`utils/scope.js`), never from React state, and every per-scope surface — the localStorage layout and viewport, the canvas reset key, the metadata cache seed, and the `layouts get` / `save` name — is keyed on the `key` it returns, which is what stops a layout save landing under the previous worker's key right after a `cd`. That key is `local` for the empty cwd, `<topology>.p<N>` for a worker, and the raw cwd otherwise; the worker pattern anchors to the FIRST segment, so `_http/foo.p3` is a node path under `_http` rather than a worker scope. The scope also carries `isWorker`, which is what admits the server-saved layout and the `topologies/<label>.tsl` catalog line, and a `label` — the topology name at a worker scope — with any leading `_` stripped for display.
- **Tab-completion** identical to the cli: longest-common-prefix extend on the first Tab via a `_completion` node firing `KEY='completion'`, list the candidates on a second consecutive Tab. Plus command history (up/down recall).
- **Live-mode Inspector verb modals**: a node's `node_schema()` verbs are surfaced as forms in the Inspector so an operator can invoke a verb (with its declared arg fields) against a live node.
- **`dmesg` / `uptime` / per-node logging** in the browser interpreter, off the `Core.recentLog` tail and the `Core.initTime` baseline, matching the cli surface. The `_dmesg` node (`DmesgNode`) polls that verb every 10 seconds and tallies the returned tail into the per-level counts the Inspector's process-stats header shows, classifying each line by the stderr prefixes substrate callers already write: a line carrying `WARNING:` counts as a warning even when it also carries `ERROR:`, one carrying only `ERROR:` counts as an error, and everything else counts as debug. The poll is aimed at `_cwd`, so the counts describe the process being VIEWED — a worker's PHP stderr tail while the cwd names one — rather than the browser's own.
- **Worker attach through `RemoteIpcNode`.** A cwd naming a worker mounts one `RemoteIpcNode` for it, and every command that node forwards has FROM rewritten to the private reply address `_sse:{pid}/{node}`, so the server's `HTTP_Filter` demuxes the async reply back to this session's stream. Each send also rides a leading `connect_worker_input {reader}` inside the SAME POST, mounting the worker's input Partition on the stateless request-scope graph before the command routes to it; `HttpOut`'s `onceInBatch` / `claimInBatch` claim, keyed `mount:{reader}`, is what makes that mount ride once per POST rather than once per send. Only ONE stream is open per browser session: a send on a second worker's link closes whichever `RemoteIpcNode` holds the live one (`RemoteIpcNode.active`), because SSE slots are a finite host-wide pool. PHP has no `Remote_IPC` and steals nothing — each `Remote_Source` patrons its own `HTTP_Out`, so several links connect at once.
- **Runtime drift, painted.** `driftNodeIds()` compares the live graph against the registered `.tsl`, and `SchematicCanvas` paints anything present in the first and absent from the second `is-drift` — a node built ad hoc through the REPL, or one left over after a topology edit nothing has redeployed. It answers only in view mode; in edit mode `driftIds` is null, since a draft has no live worker to diverge from. The declared set is the file's own `make_node` lines plus everything its `include`s bring, and an underscore-prefixed name never counts as drift — that is console infrastructure the worker mounts, which no topology file carries a line for. Until the `.tsl` answer lands, and for any cwd with no registered `.tsl` behind it, `driftNodeIds()` answers null rather than an empty set, and a caller reads that as no drift information rather than painting every node on the canvas.
- **Chrome shared with the debug overlay.** Both surfaces mount `ConsoleShell`, and one hook — `useGraphSurface()`, composing `usePanelChrome()` — holds the palette collapse, the inspector collapse, the height the REPL transcript overlay covers and the REPL expand and focus state, so a new palette, inspector or transcript behavior cannot land on one surface and miss the other. The palette persists a separate key per mode (edit opens, view starts collapsed) while the inspector keeps one key everywhere. The skin is not part of that chrome: it is the single `theme-<slug>` class on `<html>` that `applySkin()` sets, from the fifteen skins `@newspack-nodes/shared/theme` registers for every sibling dashboard.

**A typed statement leaves the Shell through `OutgoingGateNode`** (`src/topology-console/core/outgoingGate.js`), the JS analog of the anonymous Shell sinking into the `_shell` Tap above. It is unnamed and unaddressable by contract — `has_target: false`, category `Hidden`, absent from `includeNodes` — which is what makes it the safe place for the two outbound-only concerns that would be wrong on anything a message could be addressed TO: stamping the Compose modal's reply fields onto the statement in flight, and refusing a send at a worker while no SSE session is up to carry the reply home. The guard runs before the stamp, so a refused message is never mutated and the operator resends the same line once the session is up. The console assigns all three hooks (`sseGuard`, `beforeSend`, `onRefused`); the debug overlay assigns `beforeSend` alone and leaves the gate pass-through.

**What a canvas paints from is one hook, `useGraphSource()`**, shared by the console and the debug overlay so both go through one precedence rule. It prefers the graph `_metadata` publishes, and adopts it only once that graph carries a node: a published graph of zero nodes means no reply has landed yet rather than an empty graph, so a poll returning nothing cannot blank a canvas already drawn. Below that the two surfaces differ by one flag. The overlay leaves `coreFallback` on and falls back to `coreToGraph()`, the page's own live registry, because its Core holds the complete local graph; the console passes false, since its canvas is scoped to one worker and `coreToGraph()` would surface the browser's own reserved scaffolding, which no worker graph contains. The hook's `hasNodes` is true only when the graph holds something besides the backbone — `_shell`, `_http`, `_heartbeat` and the worker's auto-mounted `_repl` — because the console mounts `_repl` before the first `dump_metadata` reply arrives, and counting scaffolding as content would run `autoLayout` once against it and stack every real node arriving on the next poll below it in one column. It is a necessary rather than a sufficient signal: the overlay ANDs in `replReady` and the console `serverFetchResolved` before either paints.

**Every canvas gesture repaints ahead of the next poll** by patching `_metadata`'s local raw map (`useGraphHandlers`), and the patch mirrors the server's exact effect rather than approximating it: `connect_node` APPENDS on a Tee, so the patch appends too, where replacing would erase the fan-out's other edges until the next poll put them back. A new graph-mutating gesture owes the same mirroring. The Inspector's per-node connect/disconnect toggle — tailing a live node into this session — reads the console's own reply path out of `_header.pwd` in the last `dump_metadata` payload, and that raw path ends in the POLLING node's reply segment (`…/_sse:{pid}/_metadata`) rather than the `…/_output` tail a shell `connect_node` produces. `canonicalReverseCwd()` (`src/runtime/metadata-node.js`) rewrites that last segment to `_output`, and both the toggle's on/off reading and its optimistic patch compare on that canonical form; anything else reading `_header.pwd` for this purpose canonicalizes first or adds and removes the wrong string.

**Edit mode is the same console over a draft `.tsl`.** The commands are identical; what changes is which interpreter receives them, which is a cwd. Edit mode runs a `DraftInterpreterNode` — a `CommandInterpreterNode` subclass whose nodes live in a `NodeRegistry` of its own, with a third registry holding its own `_command_interpreter` name — so a draft `firehose` neither collides with nor is visible to the live graph's, and the two can be open side by side. Isolating a namespace is what a second registry is for; the clock, the rate-limited stderr and the rest of `Core` stay shared. A class the bundle cannot build — `Partition`, `Topic`, `Consumer` and `Job_Worker` are server-only — becomes a `StubNode` rather than an error: it carries the declared class, which `dump_config` and `dump_metadata` emit in place of `Stub`, the constructor tokens verbatim, and the catalog's `fans_out` flag, so `connect_node` appends or replaces the way the real class would. Its `fill()` counts the message and drops it, because a stub describes a node instead of running one, and a stub that routed would surface as a routing bug far from its cause. The seam carrying that declared class is `Node.shellClassName()`, which prefers a node's own `shellName` and only falls back to stripping the `Node` suffix off the constructor name, so a round trip names the class a node STANDS FOR rather than the class the bundle built. `move_node` diverges for the same editorial reason: live it renames the node and strands every reference, faithful to Tachikoma and indefensible in an editor, so the draft interpreter rewrites all three kinds — the seeded edges, other nodes' `target`, and any `node_name`-typed verb argument the catalog declares. Four verbs the live interpreter does not answer belong to a FILE rather than a graph and touch no node table: `var`, `include`, `remove_include` and `secure`, which edits a line in both directions here where live it is the one-way ratchet [Secure levels](#secure-levels) describes.

`DraftContext` publishes the whole editor surface — `run`, `load`, `reseed`, `dump`, `replaceVerbs`, `replaceFrontmatter`, `clearSecure`, `setCatalog`, `assertResolved` and `revertIncludes` — and nothing outside it touches the interpreter, because a second way to change the document is a second spelling that drifts from the first. `run( line )` is the command face, identical to live mode. The rest exists because TSL edits one thing per line while an editor holds the whole map: `command_node` only appends and has no removal spelling, so "these are now the verbs" needs `replaceVerbs`, and `secure` / `insecure` / undeclared is a three-state field where `insecure` declares the third state rather than removing the line, so "undeclared" needs `clearSecure`. `graph` is a READ of the interpreter, re-derived through `draftToGraph()` after every change and never mutated directly.

Dirty state is that graph's serialization compared against a baseline the document carries. `load()` records what it loaded, which is what makes a loaded document clean; an upload records `null`, matches no serialization, and is therefore dirty from its first render, since it has no stored copy to be equal to. `markSaved()` is stamped with what was SENT rather than with what the reply carries — a save takes seconds while the canvas stays live, so baselining on reply would adopt an edit made in flight as already written. The last three answer what no single command line can spell. `reseed( from, to )` dumps the document against the expansion it currently holds and re-loads it against a new one, which is how the borrowed half changes without losing the document. `assertResolved()` throws when a `<ns:key>` config target has no server-resolved edge to name — the same guard the live seed applies, so the editor and the canvas cannot disagree about which file is loadable — and only a server-backed load can run it, because an uploaded file carries tokens nothing client-side resolves. `revertIncludes( lastGood )` is the expand-error backstop, dropping the includes a last-good tree lacks and committing only when one actually went, so a caller re-running on graph identity does not spin on a persistent expand error.

`draftToGraph()` is the read counterpart of the interpreter's `dumpDocument()`, walking the draft registry into `{ nodes, edges, includes, frontmatter, secureLevel, configOverrides, resolvedConfigEdges }`; `graphFromTsl()` wraps it for stored TSL plus its expansion, and `DraftContext` is its only caller for a live document. Node `x` and `y` are always zero and the worker's auto-mounted `_repl` anchor is never synthesized, because coordinates and that anchor are canvas facts no topology file states. An invocation an include supplied is marked `seeded`, which is what locks its Inspector row and drops it from the half a save writes back, and a `set_*target` verb on a borrowed node becomes a `configOverrides` entry rather than a bare edge, since the include may already have wired a config-role edge for that slot and an edge list cannot express vacating one.

`dumpDocument()` writes the document back in the one order a topology file requires: frontmatter, includes, then per node its `make_node` declaration (skipped for a borrowed one), any non-default `set_sink` line and its declared `command_node` invocations, then the edges, then `secure` LAST — because `secure` disables `make_node` for everything after it. A baseline routing edge the document no longer declares is written as an explicit `disconnect_node` line rather than left out, since a fan-out node's `connect_node` only appends and cannot express removal by absence. Loading takes two steps, because only the server can resolve an include and the borrowed half has to be in hand before the file's own statements run: the caller first asks the static `DraftInterpreterNode.includesOf( tsl )` which topologies the file includes, fetches their `topologies expand` result, and only then calls `load( tsl, baseline, resolvedConfigEdges )`, which seeds the borrowed half of the graph from that baseline before running the file's own statements. Calling `load()` with no baseline silently treats the file as though it includes nothing.

`augmentWithVirtualEdges()` (`utils/virtualEdges.js`) closes the one gap a draft graph has that a live one does not. `connect_node` is the only edge-producing line a document holds, so a node reached solely through a `node_name`-typed verb argument — Request_Builder's `set_errors_target errors:partition` — arrives as an invocation and as no edge at all, and `autoLayout` then reads it as a source and pins it to column 0 instead of placing it downstream of its producer. The pass scans each node's verb invocations against the class catalog and synthesizes one `virtual: true` edge per `node_name` argument, resolving a `<ns:key>` config token through the server-supplied `resolvedConfigEdges` since only the server can resolve one. The canvas dims a virtual edge and refuses click-to-delete on it, because the `disconnect_node` a deletion issues would not remove the verb line that named the target. Live mode needs none of this: the node declares the destination through `extra_targets()` and `dump_metadata` ships it in the `targets` display union ([ADR-19](architecture-decisions.md#adr-19-a-node-may-declare-a-destination-it-writes-without-routing)).

A draft keeps its arguments as raw SPANS, so `serializeDraftArg()` rather than `quoteToken` is what writes one back: a value that already tokenizes to itself as a single span is emitted verbatim, because re-quoting would change what it MEANS — double quotes interpolate `<name>` where single quotes and backticks defer. Two spans are quoted anyway: an unbalanced quote, which scans self-identical and would corrupt the file, and a bare span carrying `#` or `;`, which changes the LINE rather than the token by commenting out the rest or splitting the statement. `parseStatements()` is the side-effect-free reader on that same tokenizer — no interpolation, no vars, no node construction — and it deliberately models neither of the two builtins the live `ShellNode` owns alone, `list_skins` and `set_skin`: every caller of it reads a topology, and a topology runs on the PHP loader, so a `.tsl` naming one gets the cwd command PHP will really send.

Quoting is per token; the slot-filling above it lives in `utils/tslArgs.js`, which writes the schema DEFAULT into every positional the operator left blank before serializing, then drops the trailing slots still empty. It has to: PHP's `parse_schema_args()` reads `$args[ $i ] ?? null`, so an emitted empty token counts as SUPPLIED for a `string` or `bool` argument and overrides the default the schema declares — only a blank `int` or `float` token does the trait null back to "not supplied". Trailing empties alone come off, because a positional is indexed and dropping an interior blank would shift every argument after it into the wrong slot; an interior hole takes the default, or an explicit empty token where the schema declares none. Both surfaces that write arguments run the same `applyDefaults` / `trimTrailingEmpties` / `serializeCtorArgs` trio — the palette drop's new-node modal emitting a `make_node` args string, the Inspector's `setArgumentsLine` emitting `set_arguments` — which is what makes a node dropped from the palette and one later edited in the Inspector produce the same TSL.

**Composition is drawn rather than flattened.** The `topologies` CI's `expand` verb composes a document's `include` set into `{ nodes, edges, tree, hulls }`, and the draft interpreter seeds the borrowed half of its graph from that result. A node an include supplied carries `origin` — the directly-declared includes providing it, all of them where two includes both do — and `via`, the include chain the Inspector renders as a breadcrumb. A non-empty `origin` is what makes a node borrowed: the canvas draws it locked, `GraphView` refuses the delete key on it, and the Inspector renders its form read-only. A live `dump_metadata` poll carries no provenance, so `stampOrigins()` derives the mark from the same hull membership in both modes, which leaves the mark and the hulls unable to disagree. Re-declaring a borrowed name in the edited file CLAIMS it: the borrowed node is torn down, the replacement inherits its outgoing edges, and a failed build puts the original and its edges back. That claim is how a save states a node an include already owns without re-declaring it.

Expansions are cached at module scope under the joined include list, order included — an edge's `origin` list is ordered by declaration, so a reordered set is a different answer. `topologies get` ships the expansion beside the file it opens and primes the cache with it, so opening a document costs no second round trip, while saving or deleting ANY topology clears the whole cache, because either can change what an `include` resolves to. A refusal — a cycle, a conflicting `make_node`, an unknown include name — arrives as an error with the expansion left empty, which a caller must not read as a valid empty graph. The edit-mode Palette offers every catalog topology as a draggable tile and disables three: the topology being edited, one it already includes, and one whose own include closure reaches it. That last is a client-side mirror of the cycle guard `Topology_Analyzer` enforces on load, and the two have to move together. Saving is the one write: `topologies save` writes the user `.tsl` and restarts every fleet running that topology, so it goes exactly once, and the console then re-baselines the draft against what was WRITTEN rather than what the canvas holds — offering to activate a brand-new topology, which a save leaves inactive.

**A hull is the soft boundary the canvas draws around one include's members** — the convex hull of their padded rects, joined with quadratic curves so it reads as a blob. Every include gets one at whatever depth it sits, parents painted under the children they bring in, and hulls overlap freely: a node two includes both provide sits in the intersection rather than being assigned to one, which is the diamond `HullPanel` surfaces since the canvas shows it only as overlap. Siblings at one depth paint biggest-first, so the smaller region stays on top and clickable, and the size they sort on is the polygon's own AREA rather than its bounding box's — two members far apart span a large box around a thin hull, and a box would call that hull the biggest, paint it first and bury it. `hullGeometry()` is the geometry, and it yields an empty path when fewer than three points survive, which the canvas drops. Everything scoped to a selected hull reads its members through the one `hullNodes()` selector — the header totals in `processStats` and the sparklines in `aggregateSeries` alike — so the two surfaces cannot disagree about what the boundary encloses.

`HullPanel` is the inspector for a selected hull, and it shows what the drawing cannot. It lists the includes this one brings in, the recursion the canvas flattened out of the drawing. It names each diamond node beside the UNRELATED include that also provides it, an ancestor or descendant sharing a node being containment rather than sharing and so left unnamed. And it lists the hull's interface: `boundaryEdges()` keeps the edges with exactly one endpoint inside the member set and splits them by which endpoint that is, inbound where the edge LANDS on a member and outbound where it leaves one, while an edge with both endpoints inside is the include's private wiring and one with neither belongs to another scope. Its two actions are `Open <topology>.tsl`, which drills into the hull's own topology, and, in edit mode only, `Remove include` — gated to a directly-declared include, because a nested one has no line in this file to remove. The panel's Activity and Throughput figures roll its members up by the same source/sink accounting the whole-graph header uses, so an include made only of pass-through nodes reads 0/0 messages while its byte totals still sum: that traffic is interior to some other scope's boundary. Both roles are read off the port flags `dump_metadata` reports rather than off a class name, each missing flag defaulting to true: a source declares a target and accepts no fill, a sink accepts fill and declares no target, and a node holding both ports is a through-node counted at neither edge.

The Inspector renders the same include structure for the whole edited file as a nested `IncludeTree`. A root row is an include the open file declares itself and carries a remove control; a row nested under it comes from another file's declaration and is read-only, because acting on it means editing a file this tree is not showing. That distinction is how a diamond gets resolved: "which include provides this node" is a SET, while "remove this include" is one line, so an include the operator has not selected comes out through the tree. All three affordances — an `IncludeTree` root row, the hull panel's button and the Delete key on a selected hull — funnel through the same `onRemoveInclude`, which sends `remove_include <name>` to the draft interpreter.

Class resolution is where the two ports part company. PHP walks registered namespace prefixes ([ADR-10](architecture-decisions.md#adr-10-class-naming--make_node-namespace-resolution)); JS resolves a shell name through `CommandInterpreterNode.includeNodes`, a flat name→class table each bundle extends at import time via `registerNodeClasses()`. That table is a per-bundle static, so two bundles on one page hold two copies and a name registered in one does not resolve in the other. The browser `make_node` verb builds a real node through it, and `resolveClass()` refuses anything that is not `Node` or a subclass. A programmatic builder sidesteps the table by handing `makeNode` the class itself ([ADR-16](architecture-decisions.md#adr-16-js-node-class-resolution--names-are-the-tsl-surface-classes-are-the-api)).

The two catalogs part company on `fans_out` for the same reason. PHP asks `Core::class_fans_out()`, which tests for the `Fanout_Targets` trait, so `Settings_Sync_Node` fans out while extending `Timer_Node`; the browser has no mixin to test, and `useJsCatalog` derives the flag by prototype descent from `TeeNode`. A JS node that keeps a target LIST without extending `TeeNode` therefore reports `fans_out: false` in the local and debug-overlay catalog, and the draft interpreter then wires it as a single target and drops every edge past the first.

**The JS runtime (`@newspack-nodes/runtime`) re-exports the substrate's node primitives for application dashboards to mount:** `Core`, `Node` (plus the `truthy` helper), `RouterNode`, `TeeNode`, `HookNode`, `CallbackNode`, `EchoNode`, `TimerNode` (plus `GRID_PHASE_MS`), `HeartbeatNode`, `CommandInterpreterNode`, `StubNode`, `DraftInterpreterNode`, `SseInNode`, `RemoteLinkNode`, `RemoteIpcNode`, `HttpOutNode`, `CompletionNode`, `DumperNode`, `UptimeNode`, plus the `mountExospine` factory, the `nodesData` catalog and the `reservedNames` map, the `commandTransport` / `defaultTransport` egress transports, the `formatCommandArgs` / `parseCommandArgs` command-arg helpers, the command-auth surface (`ensureSession`, `hasSession`, `readyToMint`, `renewSession`, `forgetSession`, `invalidateAuth`, `markLocal`, `signCommand`, `__setAuthFetch`), and the `useNodeState` / `useNodeEvent` / `useNodeFill` / `useGraphGeneration` React hooks (all `Message::*` constants are re-exported via `export * from './message'`). Node classes ship as CLASSES: a consumer subclasses `Node`, hands its own classes back through `CommandInterpreterNode.registerNodeClasses`, and may pass a class straight to `makeNode` rather than a shell name ([ADR-16](architecture-decisions.md#adr-16-js-node-class-resolution--names-are-the-tsl-surface-classes-are-the-api)).

That list IS the cross-repo contract — knip counts the entry file as an entry, so a dead export there raises no finding and removing a name needs a manual sweep of the siblings. Everything else in `src/runtime/` is reached by relative path from the substrate's own bundles: `poller-node`, `probe-record`, `jobstats-record`, `shell-node`, `io-telemetry` and the rest. The `MetadataNode` class and `parseMetadata` helper are in that second group — consume them via the file path if an application needs them. An application wanting the browser's own live graph already parsed reaches for `coreToGraph()` (`src/topology-console/utils/coreToGraph.js`) instead of pairing `dumpMetadataPayload()` with `parseMetadata()` itself: the two halves describe one wire shape, and keeping the pairing in one place is what stops a field being taught to one of them alone.

`Core` heads that export list and is a per-PAGE singleton parked on `window.__newspackNodesCore`, for the reason `IoTelemetry` is parked on `window` below: every consumer bundle inlines its own copy of `core.js`, so a module-scoped instance would give each bundle a private name table whose nodes could not address each other's. Parking it is what makes one graph per admin page true, and what lets the debug overlay mount its `_output` and `_metadata` into the registry a dashboard already built. Two of the four hooks are easy to misread. `useNodeFill( name )` returns a callback stable on the name alone that resolves the node at CALL time and DISCARDS the message while no node holds that name, because a UI handler can fire before the graph it addresses is built and a throw there takes the page down — a caller waiting on an answer wants the command path instead. `useGraphGeneration()` reports Core's full-rebuild counter, which a hand-rolled graph-building effect puts in its dependency array so the cleanup tears its nodes down and the body builds them again in place; a dashboard on `useBatchedPoll` never touches it.

**`IoTelemetry` (`src/runtime/io-telemetry.js`) accounts for the page's wire traffic.** Inbound SSE frames and HTTP command responses accumulate as "in", outbound command requests as "out". Four feeders write it — `SseInNode`, the command transport, `HttpOutNode` for wire error frames, and `Core.stderr` for classified WARNING / ERROR / debug lines — and two surfaces read it: the debug overlay's Overview tab, and the topology console Inspector's header while the graph on screen is the browser's own. Both therefore report one set of numbers instead of two roll-ups of the same local traffic.

The accumulator is per PAGE, parked on `window.__newspackNodesIoTelemetry`, and both halves of that are load-bearing. Every consumer bundle inlines its own copy of the module, so a module-scoped instance would leave each chart drawing a fraction of the page's traffic. Per node it would fare worse still: boundary nodes are torn down and rebuilt on every tab switch and the live SSE node is anonymous, so node-local counters would zero themselves under the chart. Cumulative counters last a page-load; only the rate series persists, to the `newspack-nodes:debug:overview` localStorage key, trimmed to one hour by age AND by row count — a clock stepped backwards leaves every row reading as recent, so the age cutoff drops nothing and the count is the only bound left. The rows are sampled by the debug overlay's own ref-counted interval (`SAMPLE_INTERVAL_MS = 5000`), which runs whenever debug is enabled, panel open or not, and deliberately does NOT ride the Router tick: its job is to keep sampling while a graph is torn down or was never mounted. `io-telemetry.js` must import no `Core` — `Core` imports IT, to classify its stderr lines — so it inlines its own seconds clock rather than closing the cycle.

The Overview tab reads that accumulator two ways, on two cadences. Its cards do not read the 5-second ring at all: `useOverviewStats` runs a bare 50ms `setInterval` — no `useRouterTick` passenger and no graph node, so `list_timers` cannot see it — diffing the cumulative counters through a per-stream `RateSmoother` (a 10-second window plus an EMA), and it sits outside the graph for the reason the 5-second sampler does: it has to keep reading while the page's own graph is torn down, rebuilt, or never mounted. Only the two In/Out charts below stay on the sampled ring, re-rendered once per `IoTelemetry.revision` bump so the fast card tick never thrashes the redraw. `overviewChartSeries()` (`src/debug-overlay/overviewChartSeries.js`) is what makes those charts the shared component rather than a second one: it reads each ring row as `[t, msgInRate, msgOutRate, byteInRate, byteOutRate]` and reshapes it into the same `{ [label]: { points, max, avg } }` model `topicChartSeries` builds for the event dashboards, over two labels and two panels, so both feed one `TopicsChart`. Its points carry no `weight` on purpose — `TopicsChart`'s default rate mode reads an absent weight as 1 and degrades to a plain per-bucket mean, which is what one fixed 5-second cadence wants. The tab's `Reset stats` button is the only production caller of `IoTelemetry.clear()`, and one click zeroes every cumulative counter and the classified-message ring AND removes the localStorage entry, so the persisted hour of chart history is not durable against an operator's own reset.

**Per-node rates are derived, because `dump_metadata` reports CUMULATIVE counters.** `useGraphRates` keeps every node's previous reading and divides each delta by the wall-clock time that actually elapsed, so a slower poll on a large graph does not read as a busier node. Two rules keep that honest. A node's first reading carrying data is a BASELINE and is never plotted: the canvas paints a node before the poll backfills its counters, and reading that backfill as one interval's traffic plots the node's whole lifetime as a spike, which then sets the scale every real sample is drawn against. A negative delta clamps to zero, since that is what a worker respawn restarting its counters produces, and the `hasMessages` / `hasRead` / `hasWritten` flags are sticky for the same reason, so a respawn does not pull a row out of the Inspector. `aggregateSeries()` rolls any node set's histories into the four series a sparkline plots, summing them right-aligned at the most recent poll because a node starts recording only once its first data arrives; `in` and `out` are restricted to the scope's sources and sinks, so a message moving between two members is counted at neither edge and the sparkline cannot disagree with the header totals built the same way. The Activity window is not a fixed duration — it is `RATE_HISTORY_MAX` (60) samples times the current metadata poll interval, so it widens as a topology grows past the five-second floor. And the series is live per-node state rather than a record: a node that leaves the graph takes its history with it, and the scope then reads as though it always ran without that node.

## Bootstrap Wiring (two lazy tiers)

Nothing in the substrate wires itself on every request. `Bootstrap` splits the work in two, by whether it has to resolve storage.

`ensure_diagnostics_wired()` resolves none: it sets `Core::$verify_spawn_tls` from `spawn_verify_ssl`, builds the shared `\Memcached` handle through `init_memcached()`, and registers the Site Health test. That is what lets Site Health and `wp nodes doctor` still report on a misconfigured base, and admin and WP-CLI requests call it at load. `ensure_runtime_wired()` is the storage tier: the `Newspack_Nodes\` and `Newspack_Nodes\Rest\` `make_node` prefixes, `Config::register_token_namespace()`, the user topology dir at `base_dir() . '/topologies'`, the `registered_log_producers` and `segment_size_overrides` filters, `Worker_Base::$token_provider`, the two `newspack_nodes/vault/changed` subscribers, and the `newspack_nodes/periodic` subscribers `Alerts::emit()` and `Job_Delay::sweep_action()`. It resolves the base directory and throws when that is unusable, so each entry point that can tolerate a broken base — the cron pass, `register_rest_routes()`, `self_heal_reconcile_cron()` — asks `runtime_base_is_available()` first, reports once through `Core::print_less_often()` and returns. Both tiers set their `_wired` flag LAST, so a throw leaves the tier retryable rather than half-wired for the process's life.

A plain frontend page view reaches NEITHER tier. A consumer plugin doing substrate work from a frontend hook therefore calls `ensure_runtime_wired()` itself — nuclear-gyrobase's `newspack_nuclear_gyrobase_spawn_env()` is the live example — or its `make_node` prefixes and `<config:*>` tokens are simply not registered when the hook fires.

## Config System (declarative settings)

Substrate settings are declared once in a shared **Config System** (`includes/config-system/`, namespace `Config_System\`) instead of in parallel hand-maintained lists. One `Config_System\Field` per setting carries its key, type, label (a string or a `fn(): string` thunk, resolved lazily so building the schema never requires `__()` to be defined), section, sanitizer, renderer, blank-delete policy, worker-restart class, and a `ui` flag, where `ui: false` declares an overlay-only key with no settings-page row. There is no per-field overlay opt-out: `Schema::overlay_keys()` returns every Field with a non-empty key, so only the keyless display-only Fields stay out of the per-request overlay. `Config_System\Schema` derives every consumer from those Fields: the per-request overlay key-list, option names, delete-on-blank set, reset list, worker-restart classification, and the register/render loops. `Settings_Schema` (`includes/class-settings-schema.php`) is the substrate's own `Schema` declaration, and `Config` and `Admin` both derive from it rather than keeping parallel option lists in lockstep. The label's thunk is the only lazy member: `Field::__construct()` runs `is_callable()` over the declared `sanitize` and `render`, which autoloads an array callable's class then and there rather than when the callback runs. Every process that builds `Settings_Schema` constructs every Field — a worker computing `overlay_keys()` as much as wp-admin rendering the page — so a heavyweight renderer class declared as `[ Some_Class::class, 'method' ]` loads on all of them. `Config_System\Options_Overlay` applies the presence-based per-request config overlay; `Reset_Gate` + `Field_Reset_Assets` drive per-field reset; `Settings_Renderer` renders the settings page; `Restart_Planner::plan()` is the whole settings-save recipe — recycle the workers the field's classification names, then write the reload watermark so every live worker re-reads the config it froze at boot. It is best-effort by contract, because a save must not fatal on an unusable base directory, and the next worker generation boots on the new config regardless. Only two substrate settings classify as `'all'` — `base_directory` and `memcache_servers` — because long-lived workers resolve every path off the base and hold the one Memcached handle, so saving either recycles every active topology. Only the six storage-retention keys (`segment_size`, `min_segments`, `num_segments`, `max_segments`, `min_lifetime`, `lifetime`) name node types, `[ 'Partition', 'Topic', 'Log' ]`. Everything else classifies empty, `num_partitions` included: the fleet scan re-expands the worker list every pass, so growing the partition count adds workers without recycling any, and the alert thresholds and `log_sources` resolve live per invocation.

**Per-field reset is a DOM contract the browser only previews.** A resettable field is a `[data-nn-reset="<marker name>"]` wrapper holding its controls and a `[data-nn-reset-toggle]` button — `Settings_Renderer` emits it for the substrate and event-logger-nodes, and pyrobase hand-writes the same attributes in its own admin markup, so the attribute names are a cross-plugin contract rather than a local detail. Clicking the toggle snapshots the controls, clears them to preview the default (a checkbox reads `data-nn-reset-default`, so a box whose default is checked previews checked rather than showing the operator the one state they did not ask for), adds the `is-marked` class `Field_Reset_Assets::highlight_style()` paints red, and injects a hidden input under the marker name. That input's PRESENCE in the POST is the whole signal: `Reset_Gate` deletes the option row on it, and deleting the row is how the code default wins again. Editing a marked control drops the mark and keeps what was typed, because typing a value is setting it rather than resetting it. Hidden inputs inside the wrapper are never cleared or restored — the marker itself, a checkbox's off-sentinel, a React-owned field's JSON carrier — so a `react_mount()` field's toggle turns red without previewing a value change, and a component wanting that preview restores its own default. `initFieldReset( root )` is idempotent per wrapper, so a subtree that re-renders can be re-wired by calling it again.

Exactly two callers reach `Restart_Planner::plan()`, and the scoping of the first is a footgun. `Admin::maybe_request_worker_restart()` is hooked on BOTH `updated_option` and `added_option` for every option carrying `Admin::OPTION_PREFIX` (`newspack_nodes_`) — both, because WordPress fires `added_option` on a field's very first save and hooking only the first would skip the restart once per setting — and it calls `Config::reset()` before planning, dropping the per-request config cache and firing `newspack_nodes/config_reset`. But `newspack-nodes.php` constructs `Admin` only inside `is_admin()`, so a `newspack_nodes_*` option written from WP-CLI, from a worker, or by a consumer plugin resets no cache and signals no worker: the change lands only when the next worker generation boots. `Settings_CI_Node::cmd_set()` is the second caller and repeats the recipe by hand for exactly that reason.

**Four layers resolve weakest first**: the `Settings_Schema` default, the shipped `newspack-nodes-config.php`, the file named by the `LOCAL_NEWSPACK_NODES_CONF` environment variable (CLI and testing), then a stored `newspack_nodes_<key>` option. PRESENCE decides the option layer, so a stored `''`, `[]` or `false` beats both files. `Config::load_config_defaults()` folds the first three and memoizes them; `Options_Overlay::apply()` lays the fourth over the result.

**Every rendered numeric setting declares an inclusive min and max**, and those bounds bind at the two SAVE doors alone, never on read. The settings page CLAMPS silently — `Field::sanitize_callback()` derives a clamp for any bounded `int`, so typing 900 into Num Partitions stores 16 with no notice — while `Settings_CI_Node::cmd_set()` REFUSES with `invalid value for setting: <key>`, because a programmatic caller has to be told rather than handed a different number. A value written straight into `newspack-nodes-config.php`, into the file `LOCAL_NEWSPACK_NODES_CONF` names, or into the option row is taken as written and nothing clamps it: `Partition_Node` throws only below a `segment_size` of 1, so a config file naming 5 gives five-byte segments. `SSE_Slot_Pool` is the one family that re-clamps on read.

| Setting | Range |
|---|---|
| `num_partitions` | 1 – 16 |
| `segment_size` | 1 MiB – 512 MiB |
| `min_segments`, `num_segments` | 2 – 32 |
| `max_segments` | 0 – 64 |
| `min_lifetime`, `lifetime` | 0 – 604800 s |
| `remote_segment_size` | 1 MiB – 256 MiB |
| `remote_min_segments`, `remote_num_segments` | 2 – 16 |
| `remote_max_segments` | 0 – 64 |
| `remote_min_lifetime`, `remote_lifetime` | 0 – 604800 s |
| `alert_lag_threshold` | 0 – 10 GiB |
| `alert_deadletter_threshold` | 0 – 4096 segments |
| `alert_emit_interval` | 1 – 86400 s |

The remote geometry a hub pushes caps lower than the local family it mirrors — 256 MiB against 512 MiB, 16 segments against 32 — so a hub running a 512 MiB `segment_size` cannot push that number through `remote_segment_size`. The six `sse_*` bounds live in [sse-host-budget.md](sse-host-budget.md).

**A default lives in CODE** ([ADR-20](architecture-decisions.md#adr-20-a-config-default-lives-in-code-every-config-file-is-an-override-surface)): `Settings_Schema` carries every default, and `newspack-nodes-config.php` ships an empty array as a pure override surface. A key the schema does not declare is REPORTED there — `Config::unrecognized_keys()` feeds the `config-keys` health check — never thrown, because the deploy copies the operator's own file over that path and a fatal at first read would take wp-admin down with it. Read a required key through the fail-loud `Config::value()`, never `$config['key'] ?? $default`. `Config::reset()` fires `Config::RESET_ACTION`, whose three subscribers drop the on-disk log inventory (`Log_Discovery::reset`), the parsed-TSL caches (`Topology_Registry::reset_basename_cache`) and the Vault credentials (`Vault::reset`).

`Config::invalidate_options_cache()` is the `@api` companion every settings-mutating path calls, and where a `Config::reset()` follows it must run FIRST: reset only re-arms the next `load_config()`, whose option layer resolves through `get_option()`, so a purge afterwards leaves any read landing in between memoized on the stale snapshot. It purges `alloptions` and `notoptions` AND each schema key's own `options` entry, because WP core caches an option under its own key as well — without that a long-running worker keeps serving a value it read once, however often reset runs. `Topology_Registry::invalidate_config_cache()`, the topologies CI's `activate` and `deactivate` verbs and event-logger-nodes' `Auto_Tuner_Node` all depend on that pairing.

**`Config_Utils` is the file half of that, shared with every sibling plugin's own `Config`.** `load_config_file()` returns the base config untouched when no file exists, and otherwise `require`s the file INSIDE a static closure — a bare `require` runs in the including scope, where an operator file assigning `$config` would overwrite the method's own parameter and drop every default it was handed — then layers the returned keys over the base. That layering is the spread `[ ...$config, ...$parsed_config ]`, one level deep: a file naming a key that holds an ARRAY replaces the array entirely, and nothing from the weaker layer survives inside it. Which is what makes the map-shaped keys sharp — `vault`, whose entries `Vault::get_all()` reads as an id-to-server registry, plus `memcache_servers`, `topologies`, `log_sources` and `allowed_users` — because a `LOCAL_NEWSPACK_NODES_CONF` naming one vault server drops every server the shipped `newspack-nodes-config.php` declared, with no warning. `validate_config_values()` gates that return: a tree of scalars, nulls and arrays nesting at most ten deep, so no object, closure or resource rides into a `Config::value()` reader and no self-referential array spins the walk. A file yielding no usable tree throws, which is the one case ADR-20's report-never-throw rule does not cover. `validate_config_path()` handles the environment-supplied path (`LOCAL_NEWSPACK_NODES_CONF`): it refuses a null byte first, since `realpath()` raises on one, and retests the `.php` suffix AFTER resolving, because a symlink named `config.php` can point anywhere; a failure logs a control-character-stripped path and returns null, leaving the caller to decide whether a bad path is fatal.

**Deleting the plugin — never deactivating it — runs `uninstall.php`**, which requires `includes/uninstall-cleanup.php` by path, since those are plain functions a classmap autoloader cannot map. `uninstall_cleanup( 'newspack_nodes_' )` removes the disk tree first (its location is read from an option the same pass deletes), then every prefixed option row and its transient variants on every site, matching by PREFIX so `autoload=off` rows a hardcoded list would miss go too; `Roles::uninstall()` handles the capabilities, which live in WordPress's own roles option and no prefix sweep reaches. Two rules keep that from becoming a delete primitive. `runtime_base_directory()` resolves only an EXPLICITLY configured base — the option overlay, the `LOCAL_NEWSPACK_NODES_CONF` file, then the shipped config — and never the schema default, which every unconfigured install on a host shares; a leftover tree is the cheaper mistake than deleting another site's live logs. `delete_runtime_tree()` then refuses a symlinked base and removes only the six known subtrees (`logs`, `locks`, `offsets`, `ipc`, `deadletter`, `topologies`) through the containment-checked `Spawn_Coordinator::delete_directory_recursive()`, leaving the base dir itself to an `rmdir` that refuses a non-empty one.

**Four accessors resolve the runtime tree.** `Config::get_base_directory()` validates the configured `base_directory`; `get_logs_directory()`, `get_locks_directory()` and `get_offsets_directory()` return `{base}/logs`, `{base}/locks` and `{base}/offsets`. All four pass through the one `ensure_path()` gate — create at 0700 when absent, refuse a symlinked leaf or a `..` traversal, refuse a tree another uid owns — so an unusable base throws `RuntimeException` at the first read instead of writing somewhere unexpected. Each result is memoized for the process, and `Config::reset()` drops the memo with the parsed config.

**`Log_Discovery` answers what is actually IN that tree**, so a Partition added to a topology reaches every browsing surface with no registration step. `on_disk()` globs `GLOB_ONLYDIR` under `{base}/logs` and returns the sorted basenames verbatim — the flat layout carries the partition in the name, so `firehose.p0` is one entry and a `Log` file-sink's segment files stay out; `groups()` does the same across the three `GROUPS` roots (`logs`, `offsets`, `deadletter`), returning an empty list rather than a missing key for a root that does not exist, so a caller indexes all three without checking. Three readers share the one answer: the admin storage estimate counts `on_disk()`, `Raw_Logs_CI` lists `groups()`, and `SSE_Out` validates a subscription's `{group}/` prefix against `GROUPS`. Both entry points memoize per process, so a directory created after boot appears only once `reset()` runs — wired to `Config::RESET_ACTION` — and a scan FAILURE caches like any other result: `glob()` returns false on an I/O fault where a no-match returns `[]`, both branches store an empty list, and that list stands until the reset. A transient read fault on `{base}/logs` therefore pins the admin storage estimate at zero and empties the Raw Logs catalog for the rest of the PHP process, which a config reset or a new process fixes and a missing directory does not explain. `SSE_Out_Node`'s glob refresh takes the deliberate opposite side, skipping its removal pass on an I/O error so a transient failure cannot tear down open readers. Neither entry point is a pure read either: the first scan resolves the root through `Config::get_base_directory()` and inherits that accessor's `ensure_path()` side effect, so it CREATES `{base}` at mode 0700 when absent — a surprise for a caller reaching for an inventory rather than a write. An unconfigured `base_directory` throws rather than defaulting to `/tmp`, because a phantom tree reports "no logs" while the writer fills the real one.

A topology reaches the same tree through the `config` token namespace `Config::register_token_namespace()` installs at boot. Three names there derive off the base rather than off a config key — `<config:logs_dir>`, `<config:offsets_dir>` and `<config:deadletter_dir>`, so `{base}/deadletter` has a token and no accessor — while every other `<config:key>` reads the config file. `<config:vault>` refuses and logs, because that key holds the remote-server registry and its credentials and the Vault API is the only reader.

`Config::assert_within_base( $path )` is the companion the storage nodes ask before they write: `Partition_Node` confines its segment directory and `Consumer_Node` its source and offsetlog dirs, which is what keeps a `/command` graph from pointing a partition outside the tree where administrator file writes are otherwise disabled (`DISALLOW_FILE_MODS`, VIP-style installs). `File_Tail` is the deliberate exemption — following php's `error_log` or `wp-content/debug.log` is its whole job — so the confinement lands on its offsetlog instead. An empty path passes: it means unconfigured, not an escape.

**TLS posture is three `ui: false` keys, all defaulting to true.** `spawn_verify_ssl` decides whether the substrate's own internal loopback calls — the spawn POST and `Health_Probe_Client`'s cache fetch — verify the peer certificate and hostname; `Bootstrap` injects it into `Core::$verify_spawn_tls` rather than letting `Core` read it, because `Config` is a layer above `Core`. The other two cover the outbound direction: `vault_verify_ssl` sets the same verification on Vault spoke calls, and `vault_require_ssl` makes `HTTP_Out` drop a batch whose spoke url is not https at all. Lower one only for a self-signed internal certificate.

Sibling plugins (event-logger-nodes, pyrobase) adopt this same `Config_System\` namespace. Five of its files — `options-overlay`, `reset-gate`, `field-reset-assets`, `field` and `schema` — are loaded by consumers in hermetic test harnesses without the substrate, so they must stay free of any `Core::` or substrate-class call.

**Shared `Core::$memd` and cache policy.** The one process-wide `\Memcached` handle is built by the substrate itself (`Bootstrap::init_memcached`, reached lazily through diagnostic/runtime wiring) from the substrate's own `memcache_servers` config — not by an application plugin. Empty/invalid config leaves `Core::$memd` null rather than installing an unreachable fake connection. `Cache_Backend` then makes the policy explicit per caller: `local_first()` selects usable APCu then Memcached, while `shared_first()` selects Memcached then usable APCu. Command sessions, SSE slots, tables, batch counters, and stats use `shared_first()`: configured Memcached preserves shared scope, while APCu keeps a single host and one web cache domain functional when Memcached is absent.

Normal REST-spawned workers are long-running web requests, so they share that web APCu domain with the browser/hub authentication endpoints. APCu does not span another host or an independent PHP-FPM pool/cache domain; deployments that route related command-auth work across either boundary require Memcached. Command-session lookup misses, an unavailable backend, and failed single-use nonce claims remain fail closed. Other cache callers retain their documented fail-open, fail-closed, or fail-soft behavior.

**`get()` collapses three different facts into `false`** — a stored `false`, a confirmed miss, and a backend that failed — so a caller reading `false` as absence renders a broken memcached as an empty store. `read()` is what tells them apart, answering `array{status,value}` under the public `READ_HIT`, `READ_MISS` and `READ_ERROR` constants. Only the memcached arm can report an error, off `Memcached::getResultCode()`; the APCu arm cannot distinguish a failure from a miss and always answers hit or miss, so an APCu-only host loses the distinction entirely. Four callers branch on it, and between them they show the pattern: `Table_Node::lookup()` logs the error and falls through to its backing rather than caching absence, `SSE_Slot_Pool` fails CLOSED on `READ_ERROR`, `Health_Checks::cache_backend()` demands a `READ_HIT` carrying the exact value it just wrote, and `wp nodes memcache get` prints a distinct line for each.

**Counters are the one place the two backends natively disagree, and `Cache_Backend` forces them to agree.** `increment()` and `decrement()` return `int|false` and refuse a key that does not exist, so a counter must be SEEDED through `add()` or `set()` first — `Job_Intake::queue_many()` seeds both `batch_count_key()` and `batch_err_key()` before it writes a single member. The APCu arm's existence gate is what buys that: native `apcu_inc` and `apcu_dec` CREATE a missing key, so without it, decrementing an evicted batch counter would store a 0 that `Job_Worker_Node::settle_batch()` reads as a completed fan-in, firing `newspack_nodes/job_worker/batch_complete` on a batch that never finished. `decrement()` clamps at zero on both arms — memcached natively, the APCu arm by storing the clamped 0 back — so `false` means evicted or never seeded and 0 means genuinely settled.

**The batch pair is one round trip each.** `read_multi( $keys )` answers found-only values keyed by CACHE key, casting back the all-digit keys a PHP array hands over as ints, and carries no per-key status on purpose: `Memcached::getMulti()` reports one result code for the whole batch, so a per-key hit/miss/error would be a fiction. A batch that fails outright logs through `Core::print_less_often()` naming the backend and returns `[]`, which downstream reads as "nothing stored", so a caller that must tell a confirmed miss from a broken backend asks key by key through `read()`. `write_multi( $items, $ttl )` takes one TTL for the whole set, because both backends take it that way — group by lifetime and call once per group — and answers one bool, the APCu arm collapsing its failed-key list to match, so a caller needing to know WHICH key was refused re-sends that batch a key at a time. `Table_Node::lookup_multi()` and `store_multi()` are the substrate's own callers.

**Two operations carry a caveat worth reading before reaching for them.** `touch( $key, $ttl )` extends a key's expiry without rewriting its value, but only memcached has a native touch: the APCu arm fetches and re-stores, two operations, and a write landing between them is overwritten with the older value. It is safe only where the value is a lease its holder alone refreshes, which is exactly the shape of its one caller, `SSE_Slot_Pool::touch()`. `compare_and_swap( $key, $expected, $replacement )` atomically replaces one exact, non-expiring INTEGER with another and takes no TTL by design — it is for permanent, bounded identity pointers such as an SSE slot's owner pointer, whose slot count IS the host's stream cap — so a false return is a lost race and must never fall back to `set()`. Its memcached arm reads with `Memcached::GET_EXTENDED` and passes the opaque CAS token on as `string|int|float` un-narrowed, because extension releases declare that parameter differently and a 64-bit token cast to float loses its low digits; the APCu arm re-reads after `apcu_cas()`, so a true return there means the read-back saw the replacement.

## Substrate Lifecycle Events vs WordPress Hooks

Two distinct extensibility mechanisms, both first-class:

| Mechanism | Scope | Use |
|-----------|-------|-----|
| `register` / `notify` / `set_state` on Node | Per-node-instance. Events are declared in `node_schema()['registrations']` and seeded by the base constructor; listeners can only register for declared events. Late subscribers get the cached `set_state` payload immediately at registration time. Two listener-dispatch modes (closure, or Node name -> fill TM_INFO). | Substrate-internal lifecycle: Topic `READY`, Timer `FIRE`, Router `TIMER` (the hitchhike channel Timer subclasses register against). Per-instance, events as a contract surface. |
| WordPress hooks via `Hook` node | Global by name. Anyone can `add_action` / `apply_filters`; no pre-declaration. No payload cache. | Plugin extensibility points. Transformation filters, observation listeners, "let other plugins react to this." |

The full declared set: Router `FIRE` / `TIMER` / `NOT_AVAILABLE`, Timer `FIRE`, Fleet `FIRE` / `RELOAD`, and `READY` on Partition, Topic and Consumer (Tail and File_Tail included). Partition and Topic fire `READY` from `sink()`, since wiring the sink is what materializes the storage; a Consumer fires it from `poll_init()`, on its first poll inside the drain loop, because a reader is not usable until it has resolved its durable position. Those are the channels `register()` accepts; every other name throws, and that refusal is the contract surface.

**Declared events and cached state are not the same list.** `set_state( $event, $payload )` caches under any name and notifies whoever registered, so several nodes publish state on channels nobody can subscribe to: Partition `SEGMENT` / `CLEANUP`, Consumer `POLLING` / `SEGMENT` / `CHECKPOINT` / `OVERFLOW`, Lock `HELD` / `STOLEN` / `RELEASED`, SSE_In `CONNECTING` / `CONNECTED` / `RECONNECTING` / `DISCONNECTING` / `DISCONNECTED` / `ERROR`, and Job_Worker `CACHE_FLUSH`. Those surface through `dump_node` and, with `trace` on, as a `DEBUG: <event> <payload>` line. A channel meant for subscribers must be declared in `node_schema()['registrations']`.

The browser traces less, deliberately. JS `setState()` writes the `DEBUG:` line only for a SCALAR payload; a structured one is cached and notified but never traced, because `_output` publishes its transcript through a structured `setState()` and a trace line would land in the transcript it describes and publish itself again. A browser node publishing an object and showing no `DEBUG:` line under `trace` is working as designed.

**Multi-modal listener dispatch.** A registered listener identity is one of two things:

1. **Function or closure** — invoked directly with the payload. Returning **exactly `false`** removes the registration, which is the only self-heal a closure gets; every other return value, `null` and `0` included, keeps it.
2. **Node name** — fills a TM_INFO message into the named node with KEY=event and VALUE=payload. A name whose node is gone logs `WARNING: <listener> forgot to unregister from <event> on <emitter>` through `print_less_often` and drops the registration.

The `Hook` node is the WordPress-side bridge; see [Other Node Primitives](#other-node-primitives) for its two modes.
